# 7. Progressive Disclosure — Revealing Complexity Gradually

> Source: [DevIQ — Progressive Disclosure](https://deviq.com/principles/progressive-disclosure/).
> This note is the definitional anchor for a term used throughout the curriculum
> without being defined — see [3. Prompt & Context Engineering](../3.%20Prompt%20%26%20Context%20Engineering/README.md)
> for the context-window instance and [11. Harness Engineering](../11.%20Harness%20Engineering/README.md)
> for the harness mechanisms.

Progressive Disclosure is the principle of revealing complexity **gradually rather
than all at once** — information, features, or detail introduced incrementally, as
they become needed or as the audience is ready for them. It began as a 1995 UX
interaction pattern and turned out to describe something more general: whenever a
consumer has bounded working memory and a producer has unbounded detail, the
interface between them has to be layered. That consumer can be a user, a reader, a
player, a viewport, or a language model. The principle does not change; only the
budget does.

---

## 1. Why it works: bounded working memory

Human working memory holds a small number of items at once. Confront someone with
everything simultaneously and cognitive overload sets in — the information cannot be
processed, retained, or acted on, regardless of how well-organized it is. Progressive
Disclosure manages cognitive load by structuring information into layers so each can
be absorbed before the next arrives.

The mechanism generalizes because the constraint generalizes:

| Consumer | Bounded resource | What overflow looks like |
|---|---|---|
| Person reading | Working memory | Cognitive overload; nothing retained |
| Developer reading code | Working memory | Cannot form a mental model; "where do I even start" |
| Audience at a talk | Attention | Reading the slide instead of listening |
| Player learning a game | Learnable-rules budget | Quits in the tutorial |
| LLM agent | Context window | Degraded reasoning, lost-in-the-middle |
| Map viewport | Pixels | Illegible; every street labeled at world zoom |

> **Why it matters:** the principle is not a stylistic preference about how to be
> nice to readers. It is a response to a hard capacity limit. Once you see the limit,
> the layering follows.

It aligns with the [Principle of Least Astonishment](https://deviq.com/principles/principle-of-least-astonishment/):
a system that reveals complexity incrementally matches expectations more closely than
one that exposes everything upfront.

## 2. In software design

### 2.1 The C4 model

The [C4 model](https://c4model.com/introduction) — Simon Brown's four levels of
architectural abstraction — is Progressive Disclosure applied to documentation:

| Level | Shows | Audience |
|---|---|---|
| 1. **Context** | The system and its relationships to users and external systems | Business stakeholder |
| 2. **Container** | Major deployable components (web app, API, database) and how they communicate | Anyone technical |
| 3. **Component** | Internal components of a single container | Developer on that container |
| 4. **Code** | Classes, interfaces, relationships within a component | Developer in that component; optional |

No single diagram tries to show everything. C4's own framing is "maps of your code" —
you zoom the way you zoom Google Maps, and the analogy is exact rather than
decorative (see §7). The value is that each level has an *audience*, so "what should
this diagram show" has an answer other than "everything we know."

### 2.2 The scope hierarchy

Code has a natural hierarchy that supports the same drill-down:

| Scope | What it reveals |
|---|---|
| Application | User-facing behavior |
| Project / Module | Organizational boundaries |
| Class | Encapsulated data and behavior |
| Method | A specific behavior |
| Statement | An individual instruction |

Navigating an unfamiliar codebase means starting at the top and descending. Code that
breaks this — thousand-line classes, methods mixing several abstraction levels —
forces the reader to confront implementation detail before understanding intent. This
is why small, well-named units matter beyond aesthetics: the Single Responsibility
Principle and Separation of Concerns are what *preserve* the ability to read a system
at a chosen altitude. Mixing altitudes inside one unit collapses the hierarchy and
there is no layer left to stop at.

### 2.3 API and configuration design

A well-designed API presents a small surface for the common case with advanced options
available but not required. Configuration systems supply sensible defaults and allow
overrides rather than demanding every parameter explicitly.

> **Architectural takeaway:** *simple things should be simple; complex things should
> be possible.* Both halves are load-bearing. An API that only does simple things
> fails the expert; one that requires the full surface upfront fails everyone else.
> Progressive Disclosure is what lets a single API serve both without forking.

## 3. In UX and interface design

This is where the principle originated — Jakob Nielsen introduced it in 1995 as an
interaction design pattern for reducing user error in complex applications, by
deferring advanced or rarely-used features to a secondary screen. The seminal
formulation is earlier still: Kristina Hooper Woolsey, a founding member of the Apple
Human Interface Group, wrote in 1985 that in interface design one must "consider
carefully how one selectively informs a user about a particular system, providing
well-chosen bits and pieces that can constitute a general understanding of a system."

The canonical example is the macOS print dialog: a small subset of choices, with
**Show Details** revealing the rest. Common patterns:

- **Progressive form disclosure** — required fields first; optional and advanced
  fields on demand.
- **Expandable sections** — secondary content collapsed behind "show more."
- **Contextual help** — detailed explanation surfaced only when requested.

The pattern is not confined to screens. Theme park designers make only a short segment
of a queue visible from any vantage point; riders see discrete portions as they
advance, which makes the wait more bearable than seeing its full length at once.

## 4. In presentations

The characteristic failure is the wall-of-text slide: the speaker displays a dense
bullet list or complex diagram and then talks over an audience still trying to read
it. Attention is the bounded resource, and a full slide spends it all on reading.

The fix is to reveal incrementally — one point at a time, or one region of a diagram
at a time — so what is visible is what is being discussed. Walking an architecture
diagram follows the same shape as §2.1: overview first, then drill into subsections as
they become relevant.

---

## 5. In games

Well-designed games introduce mechanics, rules, and items gradually as the player
progresses. A first level typically presents only core movement. Power-ups, hazards,
and advanced mechanics arrive one at a time, each in an isolated context so it can be
learned without competing distractions.

> **Lesson:** games that teach by doing — revealing rules as they become relevant —
> are more accessible than games requiring a complete rulebook before play. This is
> the strongest argument against front-loaded documentation generally. A tutorial
> level is a well-ordered curriculum with an enforced pace; a rulebook is the same
> content with the ordering discarded.

## 6. In AI agent systems

LLM agents operate with a limited context window, which makes them the case where the
principle is most literally enforced — the budget is a number, and exceeding it is a
hard failure rather than a gradual degradation of comprehension.

Rather than loading every reference document upfront, a well-designed agent system
gives the agent enough to begin plus **pointers to detail it can retrieve when
needed**. Knowledge is structured as a hierarchy of summaries and supporting detail,
revealed on demand. The design requirement this creates: resources built for agent
use — MCP servers, skill libraries — must expose concise metadata and descriptions
good enough for the agent to decide *when* to load more. The description is not
documentation; it is a routing decision made under a token budget.

The mechanism, as implemented by Agent Skills:

| Tier | What loads | When |
|---|---|---|
| 1 | Name + one-line description from frontmatter | Always, at startup |
| 2 | Full `SKILL.md` body | When the description matches the task |
| 3 | `references/`, `scripts/`, templates | During execution, as needed |

Tier 1 is the whole design. It must be cheap enough to hold every available capability
simultaneously and informative enough to route correctly — which is why the frontmatter
description carries more engineering weight than the body it gates. The same
list-then-fetch tiering appears in MCP servers (`list_*` returning names, `get_*`
returning one full definition, then `query`), in schema exposure for large warehouses,
and in filesystem-shaped knowledge bases where filenames *are* the index.

> **Why it matters:** for humans, violating Progressive Disclosure produces a worse
> experience. For agents, it produces a worse *result* — and past a threshold, no
> result at all. This is the one domain where the principle is not advice.

## 7. In geospatial and high-resolution imaging

Tile pyramids are Progressive Disclosure implemented as a data structure. A world map
labeling every street would be unreadable, so map services render progressively more
detail as the user zooms:

- **Map tile systems** (Google Maps, OpenStreetMap) — detail increases with zoom
  level.
- **Image tile pyramids** — the [IIIF Image API](https://iiif.io/api/image/3.0/)
  describes image regions of consistent width and height across a series of
  resolutions, combined with `scaleFactors`, so a viewer fetches only the tiles needed
  for the current view. A very large image becomes viewable without ever downloading
  it. Formats like JPEG2000 and Pyramid TIFF pre-generate these levels into the file.
- **Level-of-detail (LOD) in 3D graphics** — distant objects use lower-polygon
  models; higher-detail models load as the viewer approaches.

The interesting property here is that the bounded resource is not cognition at all —
it is pixels and bandwidth. The principle survives the substitution intact, which is
decent evidence it is about the *shape* of the constraint rather than anything
specific to minds.

## 8. The common shape

Every instance above decomposes the same way:

| Element | C4 | UX | Agent skills | Tile pyramid |
|---|---|---|---|---|
| **Cheap index** | Context diagram | Default dialog | Frontmatter description | Lowest zoom level |
| **Trigger to descend** | Audience needs detail | "Show Details" | Description matches task | User zooms |
| **Expensive detail** | Component / Code diagram | Advanced options screen | `SKILL.md` body, `references/` | High-resolution tiles |
| **Bounded resource** | Working memory | Working memory | Context window | Pixels / bandwidth |

Designing for Progressive Disclosure is therefore three decisions, not one: what goes
in the always-loaded index, what signal triggers descent, and how many layers deep the
hierarchy goes. Most failures are a bad index rather than too many layers.

### Anti-patterns

| Anti-pattern | Where it shows up |
|---|---|
| **Everything upfront** | Wall-of-text slide; 40-field form; every reference doc preloaded into context |
| **Index too thin to route on** | A skill description that does not say when to use the skill; an unlabeled diagram |
| **Mixed abstraction levels** | A method mixing business logic and byte manipulation; a diagram with both services and class names — collapses the layer you wanted to stop at |
| **No path down** | Overview with no drill-down; a summary with no pointer to the source |
| **Layers that lie** | Summary that omits something load-bearing, so descending is mandatory and the index is pure overhead |

The last one is worth dwelling on. A layer is only useful if it can be *acted on*
without descending. An index that always requires a fetch has not disclosed
progressively; it has added a hop.
