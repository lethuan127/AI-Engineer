# 5.1 Git Worktrees

> Companion to [5. Git](./5.%20Git.md). Reread sections 1–3 of that note first — the working tree / index / HEAD model is the *only* way worktrees make sense.

A **worktree** is a second working directory backed by the same `.git` object database. Same commit graph, same refs, same configuration — but a different `HEAD`, a different index, and a different set of files checked out. One repository, N working directories, each on its own branch, all in sync with each other through the shared object store.

If branches are the cheap primitive that made feature-per-branch workflows possible in 2005, worktrees are the cheap primitive that makes **parallel-by-default** workflows possible in 2026 — for humans juggling reviews against in-flight work, and for AI coding agents that need isolated places to run experiments without stomping on your editor.

The feature has existed since Git 2.5 (2015) and most engineers have never used it. That ends here.

---

## 1. The Problem Worktrees Solve

Without worktrees, "I need to check out a different branch" is a destructive operation:

```text
   ┌──── one working directory ────┐
   │  HEAD ──► feature/auth        │
   │  files on disk = tree of      │
   │  feature/auth's commit        │
   └───────────────────────────────┘

   git checkout main

   ┌──── one working directory ────┐
   │  HEAD ──► main                │
   │  files on disk = tree of      │
   │  main's commit                │   ← editor reloads, build cache busted,
   │  + your uncommitted edits     │     `node_modules` may now be wrong,
   │  smeared on top               │     IDE reindexes, you lost flow
   └───────────────────────────────┘
```

The standard workarounds are all bad:

| Workaround | What hurts |
|---|---|
| `git stash`, switch, work, switch back, `git stash pop` | Stashes accumulate, conflict on pop, lose tool/IDE state, easy to forget |
| Clone the repo a second time | Doubles disk for objects, drifts out of sync, no shared refs, no shared hooks |
| Keep two clones manually synced | Same as above, plus you have to remember which clone is "yours" |
| "I'll just commit it as WIP and force-push later" | Pollutes history, blocks others, defeats CI |

Worktrees collapse all of this. One `.git`, N checkouts.

## 2. The Mental Model

A clone has exactly one of each:

```text
   <clone>/
   ├── .git/                      ← object DB + refs + config
   │   ├── objects/
   │   ├── refs/
   │   ├── HEAD                   ← which ref this checkout follows
   │   └── index                  ← staging area for this checkout
   └── <working tree files>       ← snapshot of HEAD's tree
```

A clone *with worktrees* hoists the per-checkout state out of `.git/` and into per-worktree subdirectories under `.git/worktrees/<name>/`:

```text
   <clone>/                                  ← the "main" worktree
   ├── .git/
   │   ├── objects/                          ← SHARED across all worktrees
   │   ├── refs/                             ← SHARED across all worktrees
   │   ├── HEAD                              ← main worktree's HEAD
   │   ├── index                             ← main worktree's index
   │   └── worktrees/
   │       ├── auth/
   │       │   ├── HEAD                      ← worktree 'auth's HEAD
   │       │   ├── index                     ← worktree 'auth's index
   │       │   └── gitdir                    ← path back to the .git file
   │       └── refactor/
   │           ├── HEAD
   │           ├── index
   │           └── gitdir
   └── <main working tree files>

   ../auth/                                  ← a linked worktree
   ├── .git                                  ← a *file* (not a dir) pointing
   │                                            into .git/worktrees/auth
   └── <auth branch working tree files>

   ../refactor/                              ← another linked worktree
   ├── .git
   └── <refactor branch working tree files>
```

> Architectural takeaway: a worktree is **(its own HEAD) + (its own index) + (its own checked-out files), all backed by a shared object DB**. That sharing is the whole point. A fetch in any worktree is visible to every other worktree instantly. Disk usage scales with checked-out file size, not with repository history.

Two invariants the design enforces:

1. **A branch can be checked out in at most one worktree at a time.** Try to check out `main` in two worktrees and Git refuses. This prevents you from making conflicting commits to the same branch from two directories. (Use `git worktree add --detach` or a separate branch if you genuinely need two checkouts of the same commit.)
2. **Refs and config are shared; reflogs and indexes are not.** Each worktree has its own `HEAD`-reflog, so `git reflog` is local to where you are. Branch reflogs (`logs/refs/heads/foo`) are shared.

## 3. The Command Surface

The entire feature is six subcommands of `git worktree`:

| Command | What it does |
|---|---|
| `git worktree add <path> <branch>` | Create a new worktree at `<path>` with `<branch>` checked out. Fails if branch is already checked out elsewhere. |
| `git worktree add <path> -b <new-branch> [<start-point>]` | Create a new branch *and* a worktree for it in one step. The 90% case. |
| `git worktree list [--porcelain]` | Show every worktree, its path, its HEAD, and its branch |
| `git worktree remove <path>` | Delete the worktree's directory and unregister it. Refuses if the worktree has uncommitted changes (use `--force`). |
| `git worktree prune` | Garbage-collect metadata for worktrees whose directory was deleted manually. Run after `rm -rf`'ing a worktree. |
| `git worktree move <path> <new-path>` | Rename/relocate a worktree. Rarely needed. |

### 3.1 The 90% workflow

```bash
# from your main checkout, on main
git worktree add ../myrepo-auth -b feature/auth
cd ../myrepo-auth
# work, commit, push as normal — `git push` knows the remote
# when done:
cd ../myrepo
git worktree remove ../myrepo-auth
git branch -d feature/auth   # or leave it if you'll keep iterating
```

### 3.2 Reviewing a PR without disturbing your work

```bash
git fetch origin pull/1234/head:pr-1234
git worktree add ../myrepo-review pr-1234
cd ../myrepo-review
# build, test, poke the running app — your main checkout is untouched
cd -
git worktree remove ../myrepo-review
git branch -D pr-1234
```

### 3.3 Hotfix while a long build is running

```bash
# your main checkout is building / running tests
git worktree add ../myrepo-hotfix -b hotfix/login-500 origin/main
cd ../myrepo-hotfix
# patch, commit, push, open PR — never touches the directory your build runs in
```

## 4. Directory Conventions

Worktree path placement is a small decision with large consequences for ergonomics. Two reasonable conventions:

| Layout | Example | Pros | Cons |
|---|---|---|---|
| **Sibling directories** | `~/code/myrepo/`, `~/code/myrepo-auth/` | Clean to `cd` between; editors treat each as its own project | Clutters the parent directory; tab-completion gets noisy |
| **`.worktrees/` subdirectory** | `~/code/myrepo/.worktrees/auth/` | Self-contained; one project = one folder; works well with multi-root editors | **Must be added to `.gitignore`** or Git will try to track the worktree itself |

The second convention is what the `using-git-worktrees` skill (shipped with this repo's superpowers plugin) standardizes on, and what most AI-harness tooling assumes by default. If you adopt it, the very first thing you do is:

```bash
echo '.worktrees/' >> .gitignore
git add .gitignore && git commit -m "chore: ignore .worktrees/"
```

> Lesson: a worktree directory inside your repo that is **not** gitignored will silently appear in `git status` from the main checkout as untracked files. Set the gitignore before creating the first worktree, not after.

## 5. Common Pitfalls

| Pitfall | What happens | Fix |
|---|---|---|
| Checking out the same branch in two worktrees | `fatal: '<branch>' is already used by worktree at '<path>'` | Use a different branch, or `--detach` |
| `rm -rf`'ing a worktree directory directly | `.git/worktrees/<name>/` stale metadata accumulates | `git worktree prune` |
| Hooks live in `.git/hooks/` and are shared | A `pre-commit` hook from one worktree affects all of them | Expected; this is usually what you want |
| Submodules in worktrees | Historically buggy; Git 2.25+ is much better but still edge-case-prone | If you live in submodule-heavy repos, test before relying |
| `node_modules` / `target/` / `.venv/` are per-worktree | Each worktree needs its own install/build | This is correct behavior — install scripts must re-run per worktree |
| Editor confused by `.git` being a file, not a directory | Old tools assume `.git` is a directory | Use a modern editor; this is a 2015-era bug at this point |

## 6. Worktrees as the Substrate for AI Coding Workflows

This is why the curriculum cares about worktrees specifically.

A modern AI coding harness (Claude Code, Cursor's background agents, Codex CLI, your own self-built harness from [7.2](../7.%20AI%20System%20Architecture/7.2.%20Self-Implemented%20Agent%20Harness%20%E2%80%94%20Components.md)) wants to do things like:

- Run a multi-step refactor that takes 20 minutes — without freezing your editor.
- Spawn N parallel attempts at the same task on N different branches and pick the best one (best-of-N).
- Hand a subagent a self-contained working directory it can `rm -rf` if its experiment goes sideways.
- Let you keep coding on `main` while a long-running agent investigation runs on `agent/triage-issue-123`.

All of these decompose to the same primitive: *"give me an isolated working tree on a fresh branch, backed by the same objects, that I can throw away when done."* That is `git worktree add -b` and nothing else.

Concretely, this is how the pieces fit together:

```text
   you (editor on main)             agent harness
   ─────────────────────            ─────────────
   ~/code/repo/  ◄──── shared ─────►  ~/code/repo/.worktrees/agent-task-1/
   on `main`         .git/objects     on `agent/task-1`
                     .git/refs
                     .git/config

                                      ~/code/repo/.worktrees/agent-task-2/
                                      on `agent/task-2`

                                      ~/code/repo/.worktrees/agent-task-3/
                                      on `agent/task-3`
```

Why this matters architecturally for an agent harness:

- **Blast radius is contained.** A subagent that runs `npm install`, edits 40 files, and runs your full test suite cannot affect your live edit session. If its branch turns out to be garbage, `git worktree remove` deletes it cleanly.
- **Parallelism is free.** Three subagents running in three worktrees do not contend for the working directory. They contend only for CPU, network, and (sometimes) ports.
- **Review is just `git diff`.** When the agent finishes, you review its branch the same way you review any other branch. No special "agent inbox" required.
- **Recovery is just `git branch`.** Even if the worktree directory is gone, the branch ref still exists in the shared object DB. You can always re-create the worktree.

> Why it matters: every harness primitive that promises "I'll run this in the background while you keep working" is either (a) using worktrees under the hood, or (b) accepting that it will fight your editor for the same directory. Once you see this, the design space of agent harnesses becomes much clearer.

The corresponding harness skill in this repo — `using-git-worktrees` — formalizes the directory selection, `.gitignore` verification, baseline-test-on-create, and cleanup-on-finish steps as a checklist. The skill exists *because* this is the kind of operation that is trivial once and a footgun if done ad-hoc fifty times.

## 7. When *Not* to Use a Worktree

Worktrees are not always the right tool:

- **Single-branch, single-task work.** If you only ever touch one branch at a time, `git switch` is fine. Worktrees are for parallelism.
- **Submodule-heavy monorepos on old Git.** Test first; upgrade Git if you hit edge cases.
- **CI runners.** CI almost always wants a fresh clone per job; worktrees add complexity without benefit there.
- **When disk is genuinely tight.** Worktrees share `.git/objects` but not checked-out files. A 5 GB working tree × 4 worktrees = 20 GB on disk.

For everything else — interactive development, code review, hotfixes, AI agent dispatch — worktrees are the right default.
