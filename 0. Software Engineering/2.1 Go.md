# 2.1 Go

> Companion to [2. Backend](./2.%20Backend.md). Go (often "Golang") is the language a large share of modern backend and AI-infrastructure systems are written in — Docker, Kubernetes, Temporal, most cloud-native tooling, and a growing number of LLM-serving and agent-orchestration services. This note is the architectural model an engineer needs to read, reason about, and write production Go — not a syntax tour.

Go is a small, opinionated language built at Google for one job: **let large teams build reliable network services that compile fast and run with predictable latency.** Every design choice — static binaries, a garbage collector tuned for low pause times, concurrency as a first-class primitive, a deliberately tiny feature set — serves that job. If you come from Python or Node, the mental shift is: Go trades expressiveness and dynamism for **simplicity, explicitness, and operational predictability**. You write more boilerplate; you get binaries you can drop on a server with no runtime, and a concurrency model that scales to hundreds of thousands of in-flight requests on one process.

The thesis of this note: Go's whole identity is **concurrency + explicitness + a single static binary**. Understand those three and the rest of the language is small enough to hold in your head.

## 1. Why Go Exists (and When to Reach for It)

| Property | What it buys you | The trade-off |
|---|---|---|
| **Compiles to one static binary** | No interpreter, no `node_modules`, no virtualenv on the server. `scratch` Docker images of a few MB. | Cross-compilation is easy, but you lose hot-reload dynamism. |
| **Goroutines + channels** | Cheap concurrency (KB stacks, M:N scheduling). One process serves huge fan-out. | You must reason about data races yourself; the compiler won't. |
| **Garbage collected, low-pause** | Memory safety without manual `free`; GC pauses typically sub-millisecond. | Less control than Rust/C++; not for hard-real-time. |
| **Tiny language spec** | A new hire reads the whole spec in an afternoon. Code looks the same across teams. | No generics until 1.18; still no enums, no `?`-style null safety, verbose error handling. |
| **Fast compile + built-in tooling** | `go build`, `go test`, `go fmt`, race detector, profiler all ship in the toolchain. | Opinionated to the point of rigid (`gofmt` is non-negotiable). |

> Why it matters: Go is the default for **network services, CLIs, and infrastructure** — anything where you ship a binary, care about tail latency, and want concurrency without a framework. It is a poor fit for data-science notebooks, heavy numeric work, or UI. For AI backends specifically, Go owns the **serving and orchestration layer** (gateways, routers, agent runtimes, queue workers) while Python still owns model training and the data-science ecosystem.

## 2. The Type System: Structs, Interfaces, and Implicit Satisfaction

Go is statically typed but structurally lighter than Java/C#. There are no classes. There are **structs** (data) and **interfaces** (behavior), and methods are functions with a receiver.

```go
type Money struct {           // a struct: just fields
    Amount   int64            // store money as integer cents, never float
    Currency string
}

func (m Money) Add(other Money) Money {   // method with a value receiver
    return Money{m.Amount + other.Amount, m.Currency}
}
```

The single most important type-system idea in Go is **implicit interface satisfaction**:

```go
type LLMProvider interface {
    Generate(ctx context.Context, req Request) (Response, error)
}

type OpenAIProvider struct{ /* ... */ }
func (p OpenAIProvider) Generate(ctx context.Context, req Request) (Response, error) { /* ... */ }
// OpenAIProvider now satisfies LLMProvider — with NO "implements" keyword.
```

A type satisfies an interface simply by having the right methods. You do not declare the relationship; the compiler checks it where the value is used.

> Architectural takeaway: Implicit interfaces are why Go is so good at **provider abstraction and dependency injection**. You define the small interface *at the consumer*, and any concrete type that fits drops in. Swapping OpenAI for Claude, or a real database for an in-memory fake in tests, is a matter of passing a different value that satisfies the same interface. Keep interfaces tiny — "the bigger the interface, the weaker the abstraction" (Go proverb). One- and two-method interfaces (`io.Reader`, `io.Writer`) are the ideal.

| Concept | Go form | Equivalent elsewhere |
|---|---|---|
| Data record | `struct` | class fields, dataclass |
| Behavior contract | `interface` | abstract class / protocol / trait |
| Method | `func (r Recv) Name()` | instance method |
| Polymorphism | interface value | virtual dispatch |
| Generics (1.18+) | `func Map[T, U any](...)` | templates / generics |
| Sum type / enum | *(none)* — use interfaces or `const` iota | enum, union |

## 3. Concurrency: Goroutines, Channels, `select`

This is Go's reason for being. The model is **CSP (Communicating Sequential Processes)**: *don't communicate by sharing memory; share memory by communicating.*

- A **goroutine** is a function running concurrently, started with `go f()`. It is not an OS thread — the Go runtime multiplexes many goroutines onto a few OS threads (M:N scheduling). Stacks start at ~2 KB and grow, so a single process can run **hundreds of thousands** of goroutines.
- A **channel** is a typed, thread-safe pipe. Sending (`ch <- v`) and receiving (`v := <-ch`) synchronize the two goroutines.

```go
func worker(jobs <-chan Job, results chan<- Result) {
    for j := range jobs {          // loops until jobs channel is closed
        results <- process(j)
    }
}

func fanOut(items []Job) []Result {
    jobs := make(chan Job, len(items))
    results := make(chan Result, len(items))
    for w := 0; w < 8; w++ {       // 8 workers — a worker pool
        go worker(jobs, results)
    }
    for _, it := range items { jobs <- it }
    close(jobs)                    // tells workers "no more work"
    out := make([]Result, 0, len(items))
    for range items { out = append(out, <-results) }
    return out
}
```

`select` lets a goroutine wait on multiple channel operations — the basis of timeouts, cancellation, and multiplexing:

```go
select {
case res := <-resultCh:
    return res, nil
case <-ctx.Done():               // context cancelled or deadline hit
    return Response{}, ctx.Err()
case <-time.After(30 * time.Second):
    return Response{}, errors.New("timeout")
}
```

> Why it matters: This is exactly how you make a flaky, slow LLM or network call safe. The worker-pool pattern bounds concurrency (don't launch 10,000 simultaneous provider calls); `select` with `ctx.Done()` bounds *time*. Unbounded goroutines and unbounded request lifetimes are the two most common ways Go services fall over in production.

**The catch: Go does not protect you from data races.** Two goroutines writing the same variable without synchronization is undefined behavior. Tools:

| Tool | Use |
|---|---|
| `sync.Mutex` / `sync.RWMutex` | Guard shared mutable state. |
| `sync.WaitGroup` | Wait for a set of goroutines to finish. |
| `errgroup.Group` | WaitGroup + first-error propagation + context cancel. |
| `sync.Once` | Run initialization exactly once (lazy singletons). |
| `go test -race` | The **race detector** — run your tests with it in CI, always. |

## 4. `context.Context`: Cancellation, Deadlines, Request Scope

`context.Context` is the spine of every Go service. It is the first parameter of almost every blocking function by convention (`func Do(ctx context.Context, ...)`).

```go
ctx, cancel := context.WithTimeout(parent, 30*time.Second)
defer cancel()                       // ALWAYS defer cancel to free resources
resp, err := provider.Generate(ctx, req)   // ctx flows down the whole call tree
```

A `Context` carries three things down a call tree: a **deadline/timeout**, a **cancellation signal** (`ctx.Done()` channel), and **request-scoped values** (auth identity, trace IDs — use sparingly).

> Architectural takeaway: Context is how a Go service bounds and cancels work. When an HTTP client disconnects, the server cancels the request context, which propagates to every goroutine and downstream call started from it — including the LLM call, the DB query, the cache lookup. Wiring `ctx` through every layer is non-negotiable in production Go; a function that ignores its context is a latency and resource leak waiting to happen.

## 5. Errors Are Values

Go has no exceptions for ordinary control flow. Functions that can fail return an `error` as their last value, and you check it explicitly.

```go
resp, err := provider.Generate(ctx, req)
if err != nil {
    return fmt.Errorf("generating loyalty offer: %w", err)  // %w WRAPS the error
}
```

- `errors.Is(err, ErrNotFound)` — check for a specific sentinel error through wrapping.
- `errors.As(err, &target)` — extract a specific error type.
- `panic`/`recover` exist but are reserved for **truly unrecoverable** situations (programmer bugs, not "the API returned 500"). Do not use them as exceptions.

| Idiom | Meaning |
|---|---|
| `if err != nil { return ..., err }` | The default — propagate up. |
| `fmt.Errorf("context: %w", err)` | Add context while preserving the chain. |
| `errors.Is` / `errors.As` | Inspect a wrapped error. |
| Sentinel: `var ErrQuota = errors.New("quota exceeded")` | A comparable, documented failure. |

> Lesson: The verbosity is the point. Every failure path is visible in the code, so reviewers see exactly what happens when the LLM provider rate-limits you. The discipline that makes this bearable: wrap errors with `%w` and a short "what I was doing" string at each layer, so the final log line reads like a stack of intentions.

## 6. Memory, Values, and Pointers

- Go passes everything **by value** (copies). To mutate or to avoid copying a large struct, pass a **pointer** (`*T`, taken with `&`).
- Value receiver (`func (m Money)`) vs pointer receiver (`func (p *Provider)`): use a pointer receiver when the method mutates the struct or the struct is large. Be consistent per type.
- The GC handles freeing. **Escape analysis** decides whether a value lives on the cheap stack or the GC-managed heap; you rarely control this directly but `go build -gcflags=-m` shows it.
- `slice` (a view over a backing array: pointer + len + cap) and `map` are the two workhorse types. A `nil` slice is safe to `append` to; a `nil` map panics on write — always `make` a map before writing.

> Why it matters: The most common Go memory bug is an unintended shared backing array between slices (a sub-slice still references the parent's memory, keeping it alive). The most common map bug is writing to a `nil` map. Neither is caught by the compiler.

## 7. Modules, Tooling, and Project Layout

Go's toolchain is batteries-included; there is no separate package manager, formatter, or test runner to choose.

| Command | Does |
|---|---|
| `go mod init <path>` | Start a module (creates `go.mod`). |
| `go get <pkg>@<ver>` | Add/upgrade a dependency (recorded in `go.mod` / `go.sum`). |
| `go build ./...` | Compile everything. |
| `go test ./... -race -cover` | Run tests with the race detector and coverage. |
| `go vet ./...` | Static checks for likely bugs. |
| `gofmt` / `goimports` | Canonical formatting — not optional, not configurable. |
| `go tool pprof` | CPU / memory / goroutine profiling. |

Conventions over configuration: package name = directory name; exported identifiers start **Uppercase**, unexported start lowercase (this *is* the access control — no `public`/`private` keywords); tests live in `*_test.go` beside the code; `cmd/<name>/main.go` holds entrypoints.

## 8. Standard Library: The Service Toolkit

Go's stdlib is unusually complete for backend work, which is why many Go services use few third-party deps:

- `net/http` — a production-grade HTTP client *and* server. You can write a real API with zero frameworks.
- `encoding/json` — marshal/unmarshal structs via field tags (`json:"amount"`). Central to parsing structured LLM output.
- `database/sql` — driver-agnostic SQL with connection pooling (pair with `pgx` for Postgres).
- `context`, `sync`, `time` — concurrency and timing primitives (sections 3–4).
- `log/slog` — structured logging (1.21+), the basis of observable services.
- `testing` — table-driven tests, benchmarks, and fuzzing, built in.

```go
// Table-driven test — the idiomatic Go test shape
func TestAdd(t *testing.T) {
    cases := []struct{ a, b, want int64 }{
        {1, 2, 3}, {0, 0, 0}, {-1, 1, 0},
    }
    for _, c := range cases {
        if got := Money{c.a, "USD"}.Add(Money{c.b, "USD"}).Amount; got != c.want {
            t.Errorf("Add(%d,%d) = %d, want %d", c.a, c.b, got, c.want)
        }
    }
}
```

## 9. Go for AI Backend Services

Go does not run models, but it is increasingly the language of the **layer in front of the models** — which is precisely the "Backend Engineer (AI Software)" job described across this curriculum's harness and architecture notes. Where Go fits in an AI system:

| AI-backend concern | Why Go fits | The Go primitive |
|---|---|---|
| **Provider abstraction** (swap OpenAI/Gemini/Claude) | Implicit interfaces make a `LLMProvider` swap trivial and testable. | interface (§2) |
| **Bounding slow/flaky model calls** | First-class deadlines and cancellation. | `context` + `select` (§3–4) |
| **High fan-out async work** (batch generation, enrichment) | Cheap goroutines + bounded worker pools. | goroutines + channels (§3) |
| **Non-deterministic output → consistent downstream** | Explicit errors + idempotent, validated writes; LLM proposes, a deterministic Go service validates and commits. | errors as values (§5) |
| **Observability** (latency, tokens, error rates) | Structured logging + the OpenTelemetry-Go SDK. | `log/slog`, OTel |
| **Workflow orchestration** of multi-step AI pipelines | Temporal's primary SDK is Go; durable execution with retries. | see [11. Harness Engineering](../11.%20Harness%20Engineering/) |

> Architectural takeaway: The reliability story for AI backends — "handle non-deterministic, slow, occasionally-failing model calls without breaking downstream consistency" — maps almost one-to-one onto Go's core features. Context bounds the time, worker pools bound the concurrency, interfaces isolate the provider, explicit errors make every failure path visible, and the deterministic service (not the LLM) owns the final write. Python expresses the same patterns with `async`/`await` and libraries; Go bakes them into the language and runtime.

## 10. The Sharp Edges (Know These Before Production)

- **`nil` map writes panic**; `nil` slice appends are fine. Initialize maps with `make`.
- **Loop-variable capture** in goroutines: before Go 1.22, `for _, v := range xs { go func(){ use(v) }() }` captured the *same* `v`. Fixed in 1.22, but know it for older code — pass `v` as an argument.
- **Data races are silent** — the compiler does not catch them. Run `-race` in CI.
- **Unbounded goroutines** leak memory and file descriptors; always have a way for a goroutine to exit (closed channel or cancelled context).
- **`defer` runs at function return, not block end** — in a long-lived loop, deferring a `Close()` per iteration piles them all up until the function returns.
- **Interface holding a nil pointer is not nil** — a classic gotcha when returning errors through an interface type.

> Lesson: Go's compiler is strict about *types* and lax about *concurrency*. The unused-import-is-an-error rigidity lulls you into trusting it, but the things that actually take down Go services — races, goroutine leaks, nil maps — are runtime concerns the compiler stays silent on. The race detector and disciplined context-plumbing are what close that gap.
