# 5. Git

Git is the version control system every other tool in your workflow assumes you already understand. Editors, CI, code review, deployment, AI coding agents — they all model the world as "a working tree on top of a commit graph on top of an object database". If that sentence does not mean anything specific to you, your tools will keep feeling magical and unpredictable. This note is the minimum architectural model an engineer needs to stop fighting Git and start using it as the substrate it is.

The goal is not to memorize commands. The goal is to understand the **three things Git actually models** — objects, refs, and the index — and how every command you run is just a different projection of those three things.

---

## 1. Git as a Content-Addressable Object Database

Underneath the porcelain (`git commit`, `git checkout`, `git pull`), Git is a tiny key-value store on disk under `.git/objects`. Four object types, addressed by the SHA-1 / SHA-256 hash of their content:

| Object | What it stores | Roughly equivalent to |
|---|---|---|
| **blob** | The bytes of a single file. No filename, no metadata. | A file's contents |
| **tree** | A list of `(mode, name, hash)` triples pointing at blobs or other trees. | A directory listing |
| **commit** | A pointer to one tree + parent commit hash(es) + author + message. | A snapshot + lineage |
| **tag** (annotated) | A signed/named pointer to one commit. | A release marker |

> Why it matters: Git does not store diffs. It stores **whole snapshots** of trees, deduplicated by content hash. Branches are not "lines of development" — they are movable labels pointing at one specific commit hash. Almost every "I broke something" story dissolves once you internalize this.

The implication: as long as the object exists in `.git/objects` (or in the reflog), nothing is truly lost. `git reset --hard`, `git rebase`, even `git branch -D` only move or delete **refs** — the underlying commits stick around until garbage collection runs (`git gc`, default ~90 days). This is why senior engineers treat history as recoverable and juniors treat it as dangerous.

## 2. Refs: Branches, Tags, HEAD

A **ref** is a file under `.git/refs/` (or packed in `.git/packed-refs`) that holds exactly one commit hash. That's it.

| Ref | Path | Meaning |
|---|---|---|
| Branch | `.git/refs/heads/main` | Movable pointer; advances on each new commit |
| Remote-tracking | `.git/refs/remotes/origin/main` | Local cache of where the remote's branch was at last `fetch` |
| Tag | `.git/refs/tags/v1.0` | Conventionally immutable pointer |
| `HEAD` | `.git/HEAD` | Pointer to the *current* ref (usually `ref: refs/heads/main`), or directly to a commit when detached |

> Architectural takeaway: "Switching branches" is not a deep operation. It rewrites `HEAD` to point at a different ref, then updates your working tree and index to match the tree of that ref's commit. Most of Git's apparent complexity is in **what happens to your in-flight, uncommitted changes** when you do this — which is what the index is for.

## 3. The Three Trees: Working Tree, Index, HEAD

Every Git command operates on some subset of these three:

```text
   working tree            index (staging)            HEAD (last commit)
   ──────────────          ──────────────             ──────────────────
   files on disk           "what will be in           tree of commit
   you can edit            the next commit"           HEAD points to
        │                        │                          │
        │   git add <file>       │                          │
        ├───────────────────────►│                          │
        │                        │   git commit             │
        │                        ├─────────────────────────►│
        │                        │                          │
        │◄───────────────────────┤   git restore <file>     │
        │      git checkout HEAD <file>   (working tree)    │
        │◄──────────────────────────────────────────────────┤
```

The **index** (also called the staging area, or `.git/index`) is Git's most under-explained primitive. It is a binary file that holds the tree of "what your next commit will look like". This is why `git status` shows two sections — *staged* (differs between HEAD and index) and *unstaged* (differs between index and working tree).

> Lesson: Once you can name which of the three trees a command moves data between, no Git command is mysterious anymore. `git restore --staged foo.py` moves `foo.py` from index back to match HEAD. `git restore foo.py` moves it from index to working tree. `git reset --hard HEAD` blasts both index and working tree back to HEAD.

## 4. The Daily Workflow Commands

These are the commands you run hundreds of times a week. Learn what tree(s) each one touches.

| Command | Reads | Writes | Notes |
|---|---|---|---|
| `git status` | working tree, index, HEAD | — | Always your first move when confused |
| `git diff` | working tree vs index | — | What you have *not* staged |
| `git diff --staged` | index vs HEAD | — | What you *will* commit |
| `git add <path>` | working tree | index | Use `-p` for hunk-level staging — the single biggest skill upgrade |
| `git restore <path>` | index | working tree | Discards working-tree edits |
| `git restore --staged <path>` | HEAD | index | Unstages without losing edits |
| `git commit` | index | new commit object, moves branch | Atomic snapshot; message is permanent |
| `git log --oneline --graph --all` | object DB | — | Visualize the commit graph; alias it |
| `git stash` | working tree + index | stash ref | Cheap escape hatch when you need to switch context |

## 5. Branching, Merging, Rebasing

Branching is cheap (it's a 41-byte file). The interesting decisions are how branches **come back together**.

| Strategy | What it produces | When to use |
|---|---|---|
| **Merge (no fast-forward)** | A merge commit with two parents; preserves the topology of the feature branch | Long-lived feature branches, shared/public history |
| **Fast-forward merge** | Branch pointer advances; no merge commit | Trivial integrations where the target branch hasn't moved |
| **Rebase** | Replays your commits on top of a new base; rewrites their hashes | Cleaning up your own private branch before pushing |
| **Squash merge** | One new commit on the target branch with the combined diff | PR-based workflows that want one commit per PR |

> Why it matters: rebase and merge are not religious choices — they answer different questions. Merge preserves *history*. Rebase produces a *story*. Most healthy teams use rebase locally to tidy a branch, then merge (often squash) into `main` for a clean linear-ish trunk.

The golden rule: **never rebase commits you have already pushed to a shared branch**. Rewriting public history forces every collaborator to re-anchor their work, and there is no good UX for that.

## 6. Remotes, Fetch, Pull, Push

A remote is just a named URL plus a set of remote-tracking refs.

| Command | What it actually does |
|---|---|
| `git fetch origin` | Downloads new objects from `origin`, updates `refs/remotes/origin/*`. **Does not touch your branches or working tree.** |
| `git pull` | `git fetch` + `git merge` (or `git rebase` if configured). Two operations in one command — which is exactly why it surprises people. |
| `git push origin feature` | Uploads objects, asks `origin` to fast-forward its `refs/heads/feature` to your local commit |
| `git push --force-with-lease` | Force-push, but refuse if the remote moved since your last fetch. **Always prefer this over `--force`.** |

> Architectural takeaway: `fetch` is read-only and safe. Run it constantly. `pull` is a convenience that conflates "see what changed" with "integrate it" — and is the source of most "why did Git make a weird merge commit?" stories. Many engineers eventually configure `pull.rebase = true` or `pull.ff = only` and never look back.

## 7. Recovery — Things You Thought You Lost

Three tools cover ~95% of "oh no" moments:

1. **`git reflog`** — Every time `HEAD` moves, Git logs the previous position. A deleted branch, a bad rebase, a `reset --hard` — all reachable via `HEAD@{N}` for at least 90 days. `git checkout HEAD@{2}` and you are back.
2. **`git fsck --lost-found`** — Surfaces dangling commits and blobs the object DB still has but no ref points to.
3. **`git stash list` / `git stash show -p`** — Stashes are often forgotten about; check before assuming work is gone.

> Lesson: if you have committed it (or even just staged it and then accidentally overwritten the file), Git almost certainly still has it. The recovery path is "find the right SHA via reflog/fsck, then create a branch pointing at it."

## 8. Bisect — Binary Search Through History

When a bug appears and you do not know which commit introduced it, `git bisect` automates a binary search over your history:

```bash
git bisect start
git bisect bad                  # current commit is broken
git bisect good v2.3.0          # known-good ancestor
# Git checks out the midpoint; you run your test and mark good/bad
git bisect bad   # or: git bisect good
# Git narrows the range; repeat
git bisect reset                # done — restores HEAD
```

For a 1,000-commit range, you converge in ~10 steps. With a scriptable test, `git bisect run ./my-test.sh` does it unattended — Git automatically marks commits good/bad based on the script's exit code and tells you the first bad commit at the end.

> Why it matters: bisect is the highest-leverage Git command most engineers never use. The first time it pinpoints a one-line regression buried 300 commits deep in 30 seconds, you stop debugging blindly forever.

## 9. Workflows Worth Knowing

| Workflow | Shape | Best for |
|---|---|---|
| **Trunk-based development** | One long-lived `main`, short-lived (<1 day) feature branches, feature flags for incomplete work | Teams shipping continuously to production |
| **GitHub Flow** | `main` + feature branches + PRs, deploy from `main` | Most product teams |
| **GitFlow** | `main` + `develop` + `feature/*` + `release/*` + `hotfix/*` | Teams shipping versioned releases (libraries, mobile apps) |
| **Forking workflow** | Contributors fork the repo, push to their fork, open PRs to upstream | Open source |

The right workflow is the simplest one that matches your release cadence. Trunk-based is the default for most modern web teams; GitFlow is overkill for anything that ships more than once a week.

## 10. Git for AI-Engineer Workflows

Two Git features become disproportionately important once you start working with AI coding agents:

- **Worktrees** — let an agent (or several agents in parallel) work in an isolated directory on a separate branch *of the same repo*, without disturbing your current checkout. This is the foundation for "run N implementations in parallel and pick the best one" and for [11.6. Slash Commands and Subagents](../11.%20Harness%20Engineering/11.6.%20Slash%20Commands%20and%20Subagents.md)-style parallel agent dispatch. Deep dive: [5.1 Git Worktrees](./5.1%20Git%20Worktrees.md).
- **Atomic, well-messaged commits** — the harness reads your `git log` and `git diff` as context. Sloppy commit messages and 800-line "WIP" commits actively degrade what the agent can reason about. Treat commit hygiene as prompt engineering.

> Why it matters: agents have no out-of-band memory of *why* a change was made. Your commit graph **is** the long-term context window for any future agent session on this repo.
