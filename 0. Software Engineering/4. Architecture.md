# System Design & Architecture

System design and software architecture are the practice of **deciding how the major pieces of a software system fit together** — services, data stores, APIs, queues, clients — and the rules that govern how they interact, evolve, and scale.

While every engineer makes design decisions at the function or module level, **architecture operates at a higher level of abstraction**: it defines the structure, boundaries, and quality attributes (scalability, reliability, security, maintainability, cost) of the system as a whole.

For an AI Engineer, architectural thinking is essential — production AI systems (RAG pipelines, agent workflows, model-serving infrastructure, evaluation systems) are inherently distributed and have unique constraints around latency, cost, statefulness, and reliability.

## Why It Matters

- **Avoids costly rewrites** — early architectural mistakes (wrong database, monolith vs. microservices, sync vs. async) compound and become expensive to undo.
- **Enables scale** — what works for 100 users often breaks at 1M; architecture defines how the system grows.
- **Aligns the team** — a shared architectural vision lets multiple engineers build in parallel without stepping on each other.
- **Manages trade-offs explicitly** — every decision has costs (e.g., consistency vs. availability, performance vs. simplicity).
- **Communicates intent** — diagrams and ADRs (Architecture Decision Records) document *why* a system looks the way it does, not just *what* it does.

## Roles and Responsibilities

A software/system architect (or senior engineer doing architecture work) is responsible for:

- **High-Level Design**: Defining system boundaries, components, services, and the contracts (APIs, events, schemas) between them.
- **Technology Selection**: Choosing languages, frameworks, databases, queues, and cloud services based on requirements and trade-offs — not hype.
- **Non-Functional Requirements**: Designing for scalability, performance, reliability, security, observability, and cost.
- **Standards & Patterns**: Establishing coding standards, design patterns, and reusable building blocks across teams.
- **Architecture Reviews**: Reviewing designs from other engineers, identifying risks, and ensuring alignment with the broader system.
- **Documentation**: Producing architecture diagrams (C4 model, sequence diagrams), ADRs, and runbooks.
- **Mentorship**: Coaching engineers on system thinking, trade-off analysis, and design skills.
- **Long-Term Roadmap**: Planning how the architecture should evolve over the next 6–24 months as the product and load grow.

## Core Concepts

### 1. Architectural Styles

- **Monolith** — single deployable unit; simple to build, harder to scale teams.
- **Modular Monolith** — monolith with well-defined internal modules; pragmatic for small/medium teams.
- **Microservices** — independently deployable services; flexible but operationally complex.
- **Serverless** — function-as-a-service; pay-per-use, auto-scaling, vendor lock-in trade-offs.
- **Event-Driven** — components communicate via events/messages; decoupled but harder to reason about.
- **Service-Oriented Architecture (SOA)** — predecessor to microservices, larger services with shared infrastructure.

### 2. Design Patterns (System-Level)

- **API Gateway** — single entry point for clients into a microservice system.
- **Backend-for-Frontend (BFF)** — tailored backends per client (web, mobile).
- **CQRS (Command-Query Responsibility Segregation)** — separate read and write models.
- **Event Sourcing** — store state changes as events, derive current state from them.
- **Saga Pattern** — manage distributed transactions across services.
- **Circuit Breaker, Retry, Bulkhead** — resilience patterns for distributed systems.
- **Strangler Fig** — gradually replace legacy systems by routing traffic to new components.

### 3. Data Architecture

- **Relational vs. NoSQL vs. Vector databases** — choose by access pattern, not popularity.
- **Caching strategies** — read-through, write-through, write-behind, cache-aside.
- **Sharding & Replication** — horizontal scaling and high availability.
- **CAP Theorem & PACELC** — trade-offs between consistency, availability, and partition tolerance.
- **Eventual Consistency** — when and how to use it.

### 4. Scalability & Performance

- **Vertical vs. Horizontal scaling**.
- **Load balancing** — round-robin, least-connections, consistent hashing.
- **Asynchronous processing** — queues (Kafka, SQS, RabbitMQ) for decoupling and throughput.
- **Rate limiting & backpressure** — protecting systems from overload.
- **CDNs & edge computing** — moving compute closer to users.

### 5. Reliability & Resilience

- **Redundancy & failover** — eliminating single points of failure.
- **Health checks, timeouts, retries with exponential backoff**.
- **Graceful degradation** — partial functionality when dependencies fail.
- **Disaster recovery** — RTO (Recovery Time Objective) and RPO (Recovery Point Objective).
- **Observability** — metrics, logs, traces (the three pillars).

### 6. Security Architecture

- **Authentication & Authorization** — OAuth2, OIDC, JWT, RBAC, ABAC.
- **Defense in depth** — layered security controls.
- **Secrets management** — vaults, rotation, least privilege.
- **Network security** — VPCs, private subnets, zero-trust models.

## Architecture for AI Systems

Architectural thinking matters even more for AI engineers. Common AI system architectures:

- **RAG (Retrieval-Augmented Generation)** — vector store + retriever + LLM + orchestration; trade-offs around chunking, embedding models, hybrid search, and context window.
- **Agent Systems** — LLM + tools + memory + planner; trade-offs around statefulness, tool execution sandboxing, cost control, and loop termination.
- **Model Serving** — batched vs. streaming, GPU autoscaling, model routing, fallback strategies, caching of embeddings/completions.
- **Evaluation Pipelines** — offline eval, online eval, A/B testing, human-in-the-loop feedback loops.
- **Data & Feedback Loops** — capturing user interactions, building training/eval datasets, closing the loop on model improvement.

Key AI-specific architectural concerns:

- **Latency budgets** — LLM calls are slow; design for streaming, parallel tool calls, and caching.
- **Cost control** — token usage, model selection per task, prompt caching, semantic caching.
- **Non-determinism** — LLMs are stochastic; design for evaluation, fallbacks, and observability.
- **Statefulness** — conversation history, agent memory, session management.
- **Safety & guardrails** — input validation, output moderation, prompt injection defenses.

## Tools & Practices

- **Diagramming**: [C4 Model](https://c4model.com/), [Mermaid](https://mermaid.js.org/), [Excalidraw](https://excalidraw.com/), draw.io.
- **ADRs (Architecture Decision Records)**: lightweight markdown docs capturing the *why* behind decisions. ([adr.github.io](https://adr.github.io/))
- **Design Docs / RFCs**: longer-form technical proposals reviewed before implementation.
- **System Design Interviews**: a useful framework for thinking about scale, even outside hiring contexts.

## Learning Path

1. **Fundamentals** — understand HTTP, DNS, TCP/IP, databases, caching, queues.
2. **Distributed Systems Basics** — CAP theorem, consensus, replication, partitioning.
3. **Patterns** — read [Designing Data-Intensive Applications](https://dataintensive.net/) by Martin Kleppmann (the canonical reference).
4. **Practice** — design real systems (URL shortener, chat app, RAG service) end-to-end.
5. **Read Production Architectures** — engineering blogs from Netflix, Uber, Stripe, Discord, OpenAI.
6. **Apply to AI** — design a RAG pipeline, an agent system, or a model-serving platform with explicit trade-offs.
