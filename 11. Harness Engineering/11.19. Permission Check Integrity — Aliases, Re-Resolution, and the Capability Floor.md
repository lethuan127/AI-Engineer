# 11.19. Permission Check Integrity — Aliases, Re-Resolution, and the Capability Floor

> Companion to [11.5. Hooks, Permissions, and Side Effects](./11.5.%20Hooks%2C%20Permissions%2C%20and%20Side%20Effects.md), which covers *what* a permission rule says. This note covers whether the rule is actually binding on the resource the tool touches. Related: [8.4. The Agent Containment Toolchain — Sandbox, Runtime, and Egress Proxy](../8.%20AI%20Safety%20%26%20Ethics/8.4.%20The%20Agent%20Containment%20Toolchain%20%E2%80%94%20Sandbox%2C%20Runtime%2C%20and%20Egress%20Proxy.md).

Almost every harness permission system is written the same way: a rule matches a **string** — a path glob, a command prefix, a domain — and the tool then acts on a **resource**. The string and the resource are not the same thing, and every gap between them is a bypass. A late-August 2026 run of Claude Code fixes shows three distinct ways the gap opens, and they generalize to any harness you build.

The thesis is narrow and portable: **a permission decision is only as good as the guarantee that the thing checked is the thing acted on.** Getting that guarantee needs three properties — alias-complete matching, re-resolution at use time, and a capability floor that does not depend on rules at all.

---

## 1. Three ways the check and the action diverge

| Failure class | What breaks | Concrete shape |
|---|---|---|
| **Alias** | One resource, many names. The rule matched one name; the tool reached the resource by another | A symlink inside the working directory pointing at `~/.ssh/id_rsa`; `Grep` reaching a denied file through a symlinked search path |
| **Re-resolution (TOCTOU)** | The name resolved to resource A at check time and resource B at open time | A symlink swapped between the permission check and the `open()` |
| **Parser divergence** | The matcher's grammar is not the executor's grammar. Both parse the same string, differently | A shell assignment the permission matcher reads as an inert variable and the shell evaluates as arithmetic (`OPTIND=1/0`) |

> Why it matters: none of these are model failures. The model asked for something reasonable; the harness approved the wrong thing. No amount of prompt engineering or model capability touches this class.

## 2. Alias-complete matching — allow is AND, deny is OR

When a resource is reachable by more than one name, the two rule kinds must resolve the alias set in **opposite directions**. Claude Code's documented behavior is the correct general design:

- **Allow rules apply only when *every* name matches.** A symlink inside an allowed directory pointing outside it does not inherit the allow — it falls back to prompting.
- **Deny rules apply when *any* name matches.** A symlink pointing at a denied file is itself denied.

```text
resource:  ~/.ssh/id_rsa
names:     ./project/key  (symlink)  ──►  ~/.ssh/id_rsa  (target)

allow Read(./project/**)   symlink ✓   target ✗   →  AND  →  not allowed
deny  Read(~/.ssh/**)      symlink ✗   target ✓   →  OR   →  DENIED
```

The asymmetry is the whole point. Allow is a claim about safety and must hold for the *worst* name in the set; deny is a claim about danger and must fire on the *best* one. A system that resolves both the same way is broken in one direction or the other — either it leaks (allow evaluated as OR) or it is unusable (deny evaluated as AND).

> Architectural takeaway: enumerate the alias set before evaluating any rule, then quantify allow universally and deny existentially over that set. This is not a symlink patch — it is the general rule for any resource with more than one address: case-insensitive filesystems, relative vs absolute paths, hardlinks, mount aliases, DNS CNAMEs, container bind mounts.

## 3. Derived operations inherit the deny set

The second alias trap is that permission rules are usually written for the *obvious* tool and silently skipped by its neighbors. `Read` has a deny rule; `Grep` and `Glob` also return file contents and paths, but they take a directory argument, so a naive implementation never evaluates the `Read` rules at all.

The fix that generalizes: **search and enumeration tools resolve their `path` argument and then apply the read-side deny rules to the resolved directory.** Same for a directory-change primitive — a `Cd` deny rule must check every spelling of the target, including each symlink hop it resolves through, so a rule written for one path also blocks a target that resolves to it.

| Tool | Naive check | Alias-complete check |
|---|---|---|
| `Read` | the path argument | symlink path **and** target |
| `Grep` / `Glob` | nothing (it's a directory, not a file) | read deny rules against the resolved search root |
| `Cd` | the literal argument | every hop on the resolution chain |
| `Bash` | the command string | the command string, parsed with the executor's grammar (§5) |

> Lesson: when you add a tool that reads, writes, or navigates, the question is not "does it need its own rules?" but "which existing rule namespace is it a member of?" A tool that returns file contents belongs to the read namespace no matter what its arguments look like.

## 4. Re-resolution — check and act on the same resolved target

Alias-complete matching still leaves a window. If the check resolves `./project/key` and the tool later opens `./project/key` by name, an attacker who can write inside the working directory can swap the link between the two events. The agent asked for one file and got another, with a valid approval attached.

The fix is stated as an invariant, not a mitigation:

```text
  resolve(path) ──► approved_target
                          │
                          │  (window: anything may change here)
                          ▼
  open(path) ──► actual_target
                          │
                          ▼
      assert actual_target == approved_target   else refuse
```

Claude Code now confirms, at open time, that the path still resolves to the location the permission check approved, and refuses otherwise. The portable version for your own harness: **carry the resolved identity forward from the check into the action, and compare.** Re-running the same string check twice does not close the window — it just moves it.

> Why it matters: this is the one failure class where the harness has already done everything right (correct rule, correct alias resolution, correct decision) and still acts on the wrong resource. It cannot be fixed in the policy layer, only in the plumbing between the policy layer and the syscall.

## 5. Parser divergence — the matcher must share the executor's grammar

The `Bash` surface has a different shape of the same bug. The permission matcher and the shell both read the command string, but they are two parsers, and the gap between them is exploitable. A shell variable assignment holding an arithmetic expression was auto-approved as inert while the shell evaluated it.

There is no clean general fix — command-line grammars are large and the matcher is always an approximation. What follows from that is an architectural constraint, not a patch:

> Architectural takeaway: string-matching a command line is a **heuristic**, not a boundary. Never let it be the only thing between an agent and the machine. Pattern rules over `Bash` are for reducing prompt fatigue on known-good commands; the actual boundary must be something that does not parse — a sandbox, a working-directory confinement, a stripped toolset.

That is exactly the argument for the layer in §6.

## 6. The capability floor — subtractive policy that no rule can undo

The complement to fine-grained rules is a mode that removes capability outright. Claude Code v2.1.248 added `--restricted` (or `CLAUDE_CODE_RESTRICTED=1`), aimed at the case where an evaluation harness drives the agent on a shared machine. It:

- removes the built-in tools that run commands or code, plus `WebFetch`, unless each is named individually in `--tools` — a `default` preset does **not** restore them;
- confines the built-in file tools to the declared working directories;
- loads only managed settings and `--settings`, ignoring the machine's user and project settings;
- refuses `bypassPermissions`;
- refuses to create cloud sessions.

The design property worth stealing is **subtractive and un-appealable**. Every additive mechanism in §2–§5 answers "is this specific action allowed?" and can be wrong. A capability floor answers "does this capability exist in this process?" and cannot be argued with by a rule file, a settings file the agent can write, or a cleverly-spelled path.

| Layer | Question it answers | Failure mode | Who can override |
|---|---|---|---|
| Allow/ask/deny rules | Is *this action* permitted? | Alias, TOCTOU, parser gaps | Settings precedence, `bypassPermissions` |
| Hooks | Does this action pass a *programmatic* check? | Hook runs with your privileges; can be slow or buggy | Whoever can edit the hook |
| **Capability floor** | Does the tool *exist* in this process? | None at this layer — the tool is absent | Nobody, at launch time |
| Sandbox / egress proxy | Can the process *reach* the resource at all? | Kernel/network policy bugs | Infrastructure owner |

Note the `--tools` detail: the floor is escaped only by naming each tool explicitly, never by a preset. That is deliberate and worth copying. Presets drift; a preset that silently regains a capability is how a floor stops being a floor.

## 7. What to check in your own harness

A short audit, in order of how often it finds something:

1. **Alias enumeration.** For each rule namespace, list every way a resource can be addressed. Confirm allow is quantified universally and deny existentially over that list.
2. **Namespace membership.** For every tool that returns file contents or paths, confirm it evaluates the read-side deny rules — including tools whose arguments are directories, not files.
3. **Resolved-identity carry-through.** Confirm the approved target is passed to the action, not re-derived from the same string.
4. **Matcher/executor grammar gap.** Assume it exists. Confirm something non-parsing sits behind it.
5. **Floor existence.** Confirm there is a launch mode where the dangerous tools are absent rather than denied, and that no settings file the agent can reach re-adds them.
6. **Settings provenance.** Confirm which settings sources the agent itself can write. A permission system the agent can edit is a suggestion. (Claude Code holds a repository-supplied `.claude/settings.local.json` — tracked in git, or reached through a symlinked `.claude` — until you trust the folder, for exactly this reason.)

> Lesson: items 1–4 are integrity work on a system you already have. Item 5 is the admission that 1–4 will eventually miss something. Ship both.
