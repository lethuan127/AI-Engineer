# 11.1. What Is a Harness

> Companion to [7.1. Claude Platform Managed Agent](../7.%20AI%20System%20Architecture/7.1.%20Claude%20Platform%20Managed%20Agent.md) and [7.2. Self-Implemented Agent Harness — Components](../7.%20AI%20System%20Architecture/7.2.%20Self-Implemented%20Agent%20Harness%20%E2%80%94%20Components.md). Those notes define the harness from the *builder's* side. This note defines it from the *consumer's* side and pins down the vocabulary used throughout section 11.

A **harness** is everything between you and the raw model. When you talk to `claude-3-7-sonnet` through `https://api.anthropic.com/v1/messages`, there is no harness. When you talk to it through Cursor, Claude Code, or your own agent loop — there is. The harness is what lets a stateless `(prompt) → (completion)` API behave like something that "uses" your computer.

---

## 1. Definition

A harness is the smallest set of components that turn a stateless LLM into an agent:

| Component | What it does |
|---|---|
| **Loop** | Calls the model, parses tool-use blocks, executes tools, feeds results back, repeats until done |
| **Tools** | Functions the model can call — file IO, shell, web, MCP servers, custom code |
| **Context manager** | Decides what enters the prompt window each turn: system prompt, history, attachments, tool results |
| **State** | Files on disk, conversation history, environment variables, secrets |
| **IO** | How the user talks to the agent (chat panel, terminal, IDE), and how the agent talks back (streaming) |

Strip any of these and you no longer have an agent — you have a chatbot, a script, or a prompt template. Add more (sandbox, observability, eval) and you have a *production* harness; see [7.2](../7.%20AI%20System%20Architecture/7.2.%20Self-Implemented%20Agent%20Harness%20%E2%80%94%20Components.md) for the full taxonomy.

## 2. Two perspectives on the same artifact

| | Builder perspective (section 7) | Consumer perspective (section 11) |
|---|---|---|
| Question | "How do I implement the loop, the sandbox, the event stream?" | "How do I make *this* loop behave correctly in *my* repo?" |
| Artifact | Code, infrastructure, APIs | Config files, instructions, hooks |
| Worry | Reliability, multi-tenancy, cost, scale | Drift, noise, secret leaks, papercut bugs |
| Lever | Add features to the runtime | Add rules to the runtime someone else shipped |

Almost every AI engineer lives on the right side of this table. Even at AI-native companies, only a small team owns the harness *as software*; the rest of engineering owns the harness *as configuration*. Section 11 is for the latter.

## 3. The vendor harness loop

For Cursor, Claude Code, Codex CLI, Copilot CLI — and any near-future entrant — the loop has the same shape:

```text
   ┌─────────────────────────────────────────────────────────┐
   │  1. Assemble context                                    │
   │     · system prompt   (vendor-controlled)               │
   │     · repo memory      (AGENTS.md, CLAUDE.md, .rules)   │
   │     · matched rules    (file-scoped .mdc)               │
   │     · matched skills   (description routing)            │
   │     · attachments      (selected files, terminals)      │
   │     · history          (compacted older turns)          │
   │     · user message     (this turn)                      │
   └────────────────────────────┬────────────────────────────┘
                                ▼
                        ┌───────────────┐
                        │  model call   │  ← streamed
                        └───────┬───────┘
                                ▼
                        ┌───────────────┐
                        │  parse blocks │  ← text + tool_use
                        └───────┬───────┘
                                ▼
                  ┌─────────────────────────┐
                  │  pre-tool hook (deny?)  │  ← user-controlled
                  └────────────┬────────────┘
                               ▼
                  ┌─────────────────────────┐
                  │  execute tool(s)        │
                  │  (built-in / MCP / sub) │
                  └────────────┬────────────┘
                               ▼
                  ┌─────────────────────────┐
                  │  post-tool hook         │  ← user-controlled
                  └────────────┬────────────┘
                               ▼
                  ┌─────────────────────────┐
                  │  feed tool_result back  │
                  └────────────┬────────────┘
                               ▼
                       (loop until stop)
```

Every consumer-side knob in section 11 plugs into one of these slots:

- Repo memory + rules + skills → assembled into the context (top of the loop).
- Hooks → executed before/after tool calls (middle of the loop).
- Slash commands → user-injected messages that re-enter the loop.
- Subagents → a recursive instance of the loop with isolated context.
- MCP servers → registered tools, callable in the "execute tool(s)" step.

If you can name which slot a configuration touches, you understand it. If you can't, you don't.

## 4. The two-prompt invariant

Every modern coding agent constructs its prompt from **two prompts stacked**:

1. **System prompt** — vendor-controlled, ~10–50K tokens. Defines tool schemas, formatting rules, the agent's identity. You cannot edit it.
2. **User-extension prompt** — repo memory + matched rules + skills + recently viewed files. ~1–20K tokens. You shape every byte.

> Architectural takeaway — harness engineering is, at the byte level, the discipline of writing the second prompt well. Every rule, every skill, every line in `AGENTS.md` becomes part of the prompt for every turn of every session.

This has two practical consequences:

- **Brevity is a feature.** A 5000-line `AGENTS.md` is a 5000-line tax on every model call. The harness reads it; the model also reads it; you pay tokens for it. (Prompt caching defrays repeat reads but not first reads. See [11.8](./11.8.%20Context%20Engineering%20in%20the%20Harness.md).)
- **Drift is the enemy.** If your `AGENTS.md` says "always use snake_case" and your `.cursor/rules/style.mdc` says "always use camelCase", the model gets contradictory instructions every turn. Section 11.11 covers drift detection.

## 5. What is *not* part of the harness

Useful to be precise about scope:

| Often confused with the harness | Actually a different thing |
|---|---|
| The model itself (Claude, GPT-5, Gemini) | Swappable behind the harness |
| The IDE chrome (panels, keyboard shortcuts) | UI, not behavior |
| Your codebase | Subject the harness operates on, not the harness |
| CI / pre-commit hooks | Run outside the agent loop; complementary, see [11.11](./11.11.%20Operational%20Concerns.md) |
| Per-user shell aliases / dotfiles | Personal environment; the harness is *repo*-scoped |
| LLM observability tools (Langfuse, Helicone, Braintrust) | Eval and tracing of the harness, not the harness itself |

Keeping the boundary clean matters because each of these has its own engineering discipline, and harness engineering does not subsume them.

## 6. Why the consumer side is its own discipline

You might object: "Isn't this just prompt engineering?" No. Prompt engineering optimizes a single prompt for a single model call. Harness engineering optimizes the *system* that produces prompts across thousands of model calls over the life of a project. The differences:

| Axis | Prompt engineering | Harness engineering |
|---|---|---|
| Time horizon | Per call | Per repo, per year |
| Author | The user writing this turn | The user *and* every future contributor |
| Artifact | A string | A versioned set of files in `.cursor/` and `.claude/` |
| Reuse | Cargo-cult templates | Skills, rules, slash commands |
| Failure mode | Bad output this turn | Bad output across the team forever |
| Test | Eyeball the response | Drift detection, eval, lint hooks |

> Lesson — prompt engineering is to harness engineering as a SQL query is to a database schema. Both matter; they are not the same skill.

## 7. Mental model — one-sentence summary

> A coding agent's harness is the vendor's loop + your repo's configuration; harness engineering is the discipline of making the second half of that sum carry its weight without bloating the first.
