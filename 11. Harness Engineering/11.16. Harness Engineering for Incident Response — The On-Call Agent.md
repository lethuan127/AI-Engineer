# 11.16. Harness Engineering for Incident Response — The On-Call Agent

> Domain transfer note, companion to [11.12](./11.12.%20Harness%20Engineering%20for%20Private%20Equity%20%26%20Venture%20Capital.md) and [11.13](./11.13.%20Harness%20Engineering%20for%20Stock%20Investment.md). Source: Anthropic's own CI/CD on-call agent, published 2026-08-18.

An on-call rotation is the harshest domain to point an agent at, and the most instructive. Unlike a coding agent, an incident-response agent is not invoked by a human at a keyboard — it is invoked by an *event*, at 10pm, with no one watching. It has to decide whether the event is worth waking someone for, investigate across half a dozen systems it does not control, and produce a written artifact a tired engineer will act on. Every section-11 primitive shows up, and two that coding harnesses can ignore become load-bearing: **the escalation boundary** and **the running lessons log**.

The thesis of this note: an on-call agent is not "an agent that fixes outages." It is a *triage and reporting* harness whose value is almost entirely in the first fifteen minutes, and whose write permissions should be far narrower than its read permissions.

---

## 1. The rotation as a "repository"

| Coding repo | On-call rotation |
|---|---|
| Files in `src/` | Services, clusters, pipelines, dashboards |
| Commits / PRs | Alerts firing, incidents opened, deploys, flag flips |
| `AGENTS.md` | `ONCALL.md` — escalation policy and routing rules |
| Tests | Alert rules and their thresholds |
| Linter rules | SITREP format; what a "root cause" claim must cite |
| Build pipeline | Detect → triage → resolve → verify → hand off |
| Production deploy | The mitigation itself (rollback, flag ramp, cordon, scale-up) |

The unit of work is **one incident at one stage**. The harness is what keeps the agent's behavior consistent across services, across weeks, and across whoever happens to be holding the pager.

## 2. The five stages, and who owns each

The Anthropic setup splits the loop into five stages. What matters architecturally is that the **alerting path stays deterministic while the escalation path is hybrid** — rules decide that something fired; the agent decides whether it matters.

| Stage | Agent's job | Human's job | Trust level |
|---|---|---|---|
| **Detection** | Read every alert; apply `ONCALL.md` criteria; page or defer. Propose new alert rules for young services from observed traffic | Own the threshold policy | 🟢 read-only |
| **Triage** | Fan out across observability sources; produce an evidence-grounded SITREP with a named hypothesis | Steer, inject competing hypotheses | 🟢 read-only |
| **Resolution** | Propose the mitigation; open a PR; ramp a canary behind a flag | Approve, merge, deploy | 🟡 gated writes |
| **Verification** | Re-query the same sources; confirm the metric returned to baseline | Confirm | 🟢 read-only |
| **Handoff** | Write the post-mortem to the lessons log; produce daily/weekly SITREPs | Read them | 🟡 writes to its own memory only |

> Architectural takeaway: the agent's *read* surface is enormous (metrics, logs, pager, repos, cluster, chat) and its *write* surface is almost nothing — a PR, a flag ramp behind a canary, and its own markdown journal. That asymmetry is the whole safety design. Compare [8.1. Agent Containment & Control](../8.%20AI%20Safety%20%26%20Ethics/8.1.%20Agent%20Containment%20%26%20Control%20%E2%80%94%20Capping%20the%20Blast%20Radius.md).

## 3. Slot-by-slot translation

### 3a. Repo memory ([11.2](./11.2.%20Repo%20Memory%20%E2%80%94%20AGENTS.md%20%26%20Friends.md)) — `ONCALL.md` as escalation policy

The root instruction file stops being "how we write code here" and becomes **an executable escalation policy**. Its distinguishing feature is that its rules are quantitative and falsifiable:

```text
If error_rate > 2% for > 5 minutes
AND now() is not inside a known deploy window
  -> page the on-call
ELSE
  -> append to lessons.md
```

That is a rule a human can audit, argue with, and version. Compare it with the prose most repo-memory files contain. Escalation policy is the one domain where the instruction file should read like configuration, not guidance.

### 3b. Rules ([11.3](./11.3.%20Rules%20and%20Project%20Instructions.md)) — matched by bug class, not file glob

A coding harness matches rules on path. An on-call harness matches on **signal shape**: which service, which alert family, which suspected bug class. The activation mechanism is identical; only the match key changes.

### 3c. Skills ([11.4](./11.4.%20Skills.md)) — one investigation procedure per bug class

This is the highest-leverage slot. Anthropic's setup keeps a separate reference markdown file per bug class, with the flagship being a ~600-line investigation skill for shadow-divergence bugs.

The origin of that skill is the part worth copying: it was produced by **troubleshooting one real incident turn-by-turn with the agent, then asking the agent to write down what just happened**. That is a materially better authoring loop than writing a runbook from memory, because the transcript captures the queries actually run and the dead ends actually hit.

> Lesson: don't author investigation skills. Author them *from transcripts*. The runbook you write at your desk describes the investigation you think you do; the transcript describes the one you actually did.

### 3d. Hooks and permissions ([11.5](./11.5.%20Hooks%2C%20Permissions%2C%20and%20Side%20Effects.md)) — the escalation boundary

Two gates carry all the risk:

1. **The page gate.** Deciding to wake a human is a side effect. Over-paging destroys trust in the agent within a week; under-paging is an outage. This gate belongs in deterministic rules with agent judgment layered on top, never the reverse.
2. **The mitigation gate.** Rollbacks, flag flips, cordoning nodes, scaling infrastructure. The published setup keeps the chat-resident agent **read-only** and puts progressive deployment in a *separate* agent running under a named engineer's permissions.

> Why it matters: splitting "the agent that investigates" from "the agent that changes production" is not bureaucracy. The investigating agent reads untrusted content — logs, third-party alerts, chat messages — and therefore must not hold high-privilege capabilities. This is the quarantine pattern from [8.4](../8.%20AI%20Safety%20%26%20Ethics/8.4.%20The%20Agent%20Containment%20Toolchain%20%E2%80%94%20Sandbox%2C%20Runtime%2C%20and%20Egress%20Proxy.md), applied to ops.

### 3e. Tools and MCP ([11.7](./11.7.%20Tools%20and%20MCP.md)) — the observability plane

Metrics (Grafana/Datadog), the log store, the pager, version control, the orchestrator, and the incident channels themselves — all wired as MCP connectors. Nothing exotic. The design decision is **breadth over depth**: an on-call agent with four of these six is worse than useless, because a hypothesis grounded in metrics alone is the same overconfident guess a human makes at 10pm.

The published lesson, recorded by the agent about its own operator: *query the data first, then theorize. Config tells you what could go wrong; metrics tell you what did.*

### 3f. Subagents ([11.6](./11.6.%20Slash%20Commands%20and%20Subagents.md)) — orchestrator plus per-source executors

The triage stage runs an orchestrator that spawns one executor per dependency or source of truth, then synthesizes their findings into a single SITREP. This is textbook fan-out-and-synthesize (see [Multi-Agent Orchestration in Production](../5.%20AI%20Agents%20%26%20Tool%20Use/Multi-Agent%20Orchestration%20in%20Production%20%E2%80%94%20Topologies%2C%20Token%20Economics%2C%20and%20Coordination%20Failure.md)), and the reason it fits incident response so well is latency, not quality: parallel leads compress MTTR, and each executor gets a clean context window so a red herring in the logs does not contaminate the metrics investigation.

Root-cause work is also where single-context agents suffer most from self-preferential bias — the agent grades its own first hypothesis generously. Structural separation is the fix.

### 3g. Context engineering ([11.8](./11.8.%20Context%20Engineering%20in%20the%20Harness.md)) — the channel *is* the context

An on-call agent lives in a chat channel, and the channel is its memory: alerts, human commentary, prior incidents, and its own past reports all accumulate in one place. Two consequences:

- **Adjacent channels are context inputs.** Subscribing the agent to deploy, config-change, and PR channels is how it learns that "a flag opened this morning" — the single most common root cause it will ever name.
- **The journal must be a file, not the channel.** Chat scrollback is not a queryable memory. Which brings us to the one genuinely new primitive.

## 4. The new primitive — the running lessons log

Coding harnesses have no equivalent of this. It is a single append-only markdown file (`lessons.md`) recording, per resolved incident: what happened, root cause, fix, and the gotcha worth remembering. Three properties make it work:

| Property | Why it matters |
|---|---|
| **Agent-authored** | The agent appends on its own after each incident. A log a human must remember to write is a log that stops after week three. |
| **Read first, always** | Every new investigation opens by reading it, so the first hypothesis is anchored on what has broken *recently* — the correct prior in any real system. |
| **Promotable** | When a pattern recurs enough, a human promotes it out of the log and into the investigation skill. |

That promotion step is the load-bearing one. The log is a **staging area for procedural knowledge**, not the knowledge store itself. Without promotion, the log grows monotonically until reading it costs more context than it saves; with promotion, the log stays short and the skills get sharper.

> Architectural takeaway: this is [11.15](./11.15.%20Self-Evolving%20Harnesses%20%E2%80%94%20Observability-Driven%20Automatic%20Evolution.md)'s evolution loop with a human in the promotion seat. Experience observability is the log; the falsifiable edit is the promotion; the reviewer is the on-call engineer. It is the cheapest version of self-evolution that actually holds up, precisely because the expensive judgment — "is this pattern general?" — stays human.

## 5. What the published numbers do and don't show

| Claim | What it measures | How to read it |
|---|---|---|
| First analysis published within ~15 min, median 14 min | Time to a written, evidence-grounded hypothesis | Real and useful. Compresses the "someone opens a laptop" gap, which dominates off-hours MTTR |
| Fastest cases name root cause in ~4 min | Best-case triage latency | Best case, not typical. Do not plan capacity on it |
| Claude authored the first SITREP in every recent incident that had one | Coverage of the reporting artifact | Note the qualifier — *incidents that had one*. This is partly a statement that the agent produces reports humans previously skipped |
| Engineers ship ~8x the code per quarter vs. 2021–2025 | Why agentic CI is needed at all | Company-specific, self-reported. The load-bearing point is directional: agentic coding raises CI event volume, so CI triage must scale too |

> Lesson: the honest framing is *time-to-first-written-hypothesis*, not MTTR. The agent is fast at the part humans are slowest at — starting.

## 6. What stays human

The published account is unusually candid about the limits, and the limits are the interesting part:

- **Report format required several iterations.** The agent can one-shot a status-report generator; what makes a report *readable* is team-specific taste. Human communication, not plumbing.
- **First hypotheses are often wrong.** The setup is explicitly multiplayer: either the agent or a human can steer the investigation and inject hypotheses mid-flight. An on-call agent designed as a one-shot oracle will be abandoned.
- **Every mitigation has a named human owner.** PR review, merge approval, and CI gates are unchanged. Throughput went up; the approval topology did not change.

## 7. When *not* to build this

- **No incident history.** The investigation skills and the lessons log are both distillations of past incidents. With fewer than a few dozen, you are writing fiction.
- **Fewer than ~2 incidents/week.** The harness costs hours to build and ongoing curation. Below that rate a runbook and a pager are cheaper.
- **Observability is not queryable by an agent.** If metrics live in a UI with no API, the agent cannot ground a hypothesis, and an ungrounded hypothesis is worse than silence.
- **Alert rules are untuned.** Point an agent at a noisy alert stream and you get a confident summary of noise. Tune the deterministic layer first.

## 8. One-sentence summary

> An on-call agent is a read-mostly triage harness whose escalation policy is quantitative configuration, whose investigation procedures are distilled from real incident transcripts, and whose memory is an agent-written lessons log that a human periodically promotes into skills.

The primitives are unchanged from [11.1](./11.1.%20What%20Is%20a%20Harness.md)–[11.11](./11.11.%20Operational%20Concerns.md). What incident response adds is a hard split between reading and acting, and a discipline for turning each outage into a durable artifact.
