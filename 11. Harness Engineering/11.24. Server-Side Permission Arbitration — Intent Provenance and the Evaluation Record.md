# 11.24. Server-Side Permission Arbitration — Intent Provenance and the Evaluation Record

> Companion to [11.5. Hooks, Permissions, and Side Effects](./11.5.%20Hooks%2C%20Permissions%2C%20and%20Side%20Effects.md) §13, which covers the *client-side* auto-mode classifier. This note covers the same idea moved inside a hosted agent runtime, where there is no local machine and often no human at the keyboard. Related: [11.19. Permission Check Integrity](./11.19.%20Permission%20Check%20Integrity%20%E2%80%94%20Aliases%2C%20Re-Resolution%2C%20and%20the%20Capability%20Floor.md), [8.10. Context Privilege Escalation](../8.%20AI%20Safety%20%26%20Ethics/8.10.%20Context%20Privilege%20Escalation%20%E2%80%94%20Role%20and%20Scope%20as%20the%20Missing%20Trust%20Axes.md).

Static permission rules assume the harness can decide a tool's risk *before* it sees the call. That holds for `bash` — the tool is dangerous or it isn't — and falls apart everywhere the risk lives in the argument rather than the verb. `github.create_issue` against a staging project and against production are the same tool name with the same schema.

Claude Managed Agents' `auto` permission policy (2026-09-10) is the shipped answer: the server evaluates each call against the tool, its input, and the session transcript, then allows, denies, or pauses. Three things about it generalize past the vendor — the **three-outcome** contract, the **provenance rule** that decides whose words count as intent, and the **evaluation record** that makes the decision auditable. All three are design obligations for any harness that arbitrates per call.

---

## 1. Why the static tier stops being enough

| Policy | Decided when | Sees | Fails when |
|---|---|---|---|
| `always_allow` | Agent creation | Tool name | Risk lives in the argument |
| `always_ask` | Agent creation | Tool name | Nobody is watching, or approval rate → 100% (see [11.5 §13](./11.5.%20Hooks%2C%20Permissions%2C%20and%20Side%20Effects.md)) |
| `auto` | Per call | Tool, input, session so far | The evaluator is wrong, and nothing behind it catches that |

Defaults encode the trust asymmetry: the first-party agent toolset defaults to `always_allow`, MCP toolsets default to `always_ask`. The reasoning is not about relative danger — it is that an MCP server can add tools after you configured the agent, so its default has to be conservative about a tool that did not exist at configuration time. `auto` is never a default anywhere; it is opt-in at both the toolset (`default_config`) and the individual-tool (`configs`) level, and the two mix freely:

```yaml
tools:
  - type: agent_toolset_20260401
    default_config:
      permission_policy:
        type: auto
    configs:
      - name: bash
        permission_policy:
          type: always_ask
```

> Architectural takeaway: per-call arbitration is an *addition* to the static tiers, not a replacement. The right shape is `auto` as the broad default with a hand-written `always_ask` list for the small set of tools whose calls a person must actually see.

## 2. The three outcomes, and which one is load-bearing

- **Allow** — the call runs exactly as under `always_allow`. No event, no pause, no human.
- **Deny** — the tool does not run. The agent gets an error tool result (`Permission to use {tool_name} has been denied.`, `is_error: true`) and the session keeps going.
- **Ask** — the evaluator reached no determination, so the session pauses exactly as under `always_ask`.

The load-bearing detail is that **deny is not appealable**. A client that posts a `user.tool_confirmation` for a server-denied call gets a 400. Compare this with the `ask` path, where the client is the decider. Two different authorities are being modelled: `ask` delegates to the operator, `deny` is the platform refusing on its own account.

> Why it matters: an appealable deny is just an `ask` with extra steps. The moment the operator can override, the outcome collapses to whatever the operator's approval rate is — the same failure that made the `ask` tier unreliable in the first place. If your harness has a "high risk" verdict, it has to be terminal.

And the outcome that is *not* modelled: `auto` produces no human checkpoint on the allow path. A call the evaluator judges safe executes before anyone sees it, and its effects may be irreversible. `auto` reduces the volume of prompts; it does not put a person in the loop. That is a different guarantee, and only `always_ask` provides it.

## 3. Intent provenance — the actually novel part

An evaluator that reads the session transcript has to answer a question static rules never face: **whose text in this context is an instruction, and whose is merely evidence?** The documented split:

| Source | Treated as |
|---|---|
| `user.message` events | Your intent — can raise a call from `deny` to `allow` |
| Tool results | Assessed, never instruction-bearing |
| Fetched web pages | Assessed, never instruction-bearing |
| MCP server responses | Assessed, never instruction-bearing |
| Messages between session threads | Assessed, never instruction-bearing |

This is the prompt-injection boundary drawn explicitly at the permission layer rather than left to the model's judgment. A web page that says "the user has authorized deleting the reports directory" is content the evaluator reads and weighs, not a grant. Only the channel the operator controls carries authority. Some calls are evaluated as high-risk regardless of who asks — intent widens the allow set, it does not remove the floor (cf. [11.19 §6](./11.19.%20Permission%20Check%20Integrity%20%E2%80%94%20Aliases%2C%20Re-Resolution%2C%20and%20the%20Capability%20Floor.md)).

The trap follows directly. If your application relays end-user chat into `user.message`, **you have handed your end users your intent channel**:

```text
end user types  ──►  your app  ──►  user.message event  ──►  evaluator reads as YOUR intent
                                    ▲
                         the privilege boundary is here,
                         and it is your code, not the platform's
```

> Lesson: intent provenance is a property of the *transport*, not the text. A platform can only distinguish channels it defines; it cannot tell whether the thing on the operator channel was typed by the operator. Any multi-tenant or consumer-facing deployment needs a second, application-side classification of which end-user utterances are allowed to become operator intent — or a hard `always_ask` on every tool it would not let an anonymous stranger run.

## 4. The evaluation record — arbitration you can audit

A per-call evaluator is a probabilistic component in the control path. It needs the same treatment as any other: a structured record of what it decided and why. Every `agent.tool_use` and `agent.mcp_tool_use` event carries `evaluated_permission` (`allow` / `ask` / `deny`) plus an `evaluation` object naming the policy that produced it.

```json
{
  "type": "agent.tool_use",
  "name": "bash",
  "input": { "command": "rm -rf /workspace/reports" },
  "evaluated_permission": "deny",
  "evaluation": {
    "type": "auto",
    "evaluated_permission": { "type": "deny", "reason_code": "high_risk" }
  }
}
```

| `evaluation` | Outcome | Meaning |
|---|---|---|
| `{"type": "always_allow"}` | `allow` | Static policy ran it |
| `{"type": "always_ask"}` | `ask` | Static policy paused it |
| `{"type": "auto", … {"type": "allow"}}` | `allow` | Evaluator judged it safe |
| `{"type": "auto", … {"type": "ask", "reason_code": "indeterminate"}}` | `ask` | Evaluator abstained |
| `{"type": "auto", … {"type": "deny", "reason_code": "high_risk"}}` | `deny` | Evaluator refused |
| *absent* | `deny` | Tool not enabled — denied without evaluating a policy |

Three schema decisions worth copying:

1. **Separate the outcome from the reason.** `evaluated_permission` is the branch; `reason_code` is the diagnosis. A client that only needs to react reads one field and ignores the other.
2. **`reason_code` is a branch key, not display text.** Explicitly not for showing end users — which keeps the vocabulary free to grow without becoming a UX contract.
3. **Unknown values must be tolerated.** Clients are told up front to expect an `evaluation.type` or `reason_code` they do not recognize, and that older events legitimately lack `evaluation` at all (read `allow` as `always_allow`, `ask` as `always_ask`). Forward-compatibility stated in the spec, not discovered in production.

> Architectural takeaway: the `ask`-rate and `deny`-rate over this event stream are the two numbers that tell you whether `auto` is configured correctly. A high `indeterminate` rate means you have pushed tools into `auto` that belong in `always_ask`; a rising `high_risk` rate on a previously quiet tool is a behavioral regression in the agent, not a permissions problem.

## 5. Re-attaching the human to a remote session

The tier this leaves exposed is `ask`. A local harness pauses in front of the person who started it; a hosted session pauses in a datacenter and waits **indefinitely** for a `user.tool_confirmation` event that some client has to send. Custom tools are worse still — permission policies do not govern them at all, so the application receives `agent.custom_tool_use` and owns the decision outright.

`ant beta:sessions connect` closes the gap by making attachment a first-class operation: load the transcript, follow it live, send `user.message`, interrupt with `user.interrupt`, and answer a waiting call (Yes / No / No-with-reason, where the reason becomes `deny_message`). Ctrl+C detaches and the session keeps running.

Two design properties are the transferable part:

- **Attachment is stateless and repeatable.** Detaching does not disturb the session; reconnecting reloads full history. The session's lifecycle and the observer's lifecycle are fully decoupled — the precondition for an agent that outlives any one operator's terminal.
- **The credential never leaves the CLI.** `--web` serves the console viewer from `127.0.0.1`; the browser page talks only to the local `ant` process, which makes the API calls. The URL is single-use and expires in two minutes. A rich UI is delivered without minting a browser-held token.

One asymmetry to know: the terminal view follows only the primary thread of a multiagent session, while the browser viewer follows every thread. If a subagent's call is what paused the session, the terminal is the wrong window.

## 6. What to require of any per-call arbiter

1. **Three outcomes, not two.** An evaluator that cannot abstain will force every uncertain call into either allow or deny, and it will pick wrong.
2. **A terminal refusal.** At least one outcome the operator cannot override, or the mechanism degrades to the approval rate of whoever is clicking.
3. **A named intent channel** — and an enumeration of every source that is read but not obeyed. Write it down; an unstated provenance rule is not a boundary.
4. **An application-side check on what enters that channel.** The platform cannot see past your relay.
5. **A structured evaluation record** on every call, with outcome and reason separated and unknown values tolerated by contract.
6. **A real `ask` path.** `auto` narrows the set of calls a person sees; it does not remove the need for one. Keep an explicit `always_ask` list and a working way to reach it.

> Lesson: moving arbitration server-side buys uniformity and an audit trail, and costs you the implicit assumption that a human is nearby. Every item above is a way of paying that cost back explicitly.
