# 11.21. Agent Fleet Economics — Agent-Workdays and the Intervention Ceiling

> Source: OpenAI's *Research acceleration: The view inside OpenAI*, 2026-09-06. Companion to [11.14. Tuning the Harness, Not the Model](./11.14.%20Tuning%20the%20Harness%2C%20Not%20the%20Model%20%E2%80%94%20The%20Harness%20as%20an%20Optimization%20Surface.md) and [11.20. Harness Benchmarking](./11.20.%20Harness%20Benchmarking%20%E2%80%94%20Controlled%20Cross-Harness%20Evaluation.md). 11.14 argues the harness is worth tuning; 11.20 measures harnesses against each other on one task set. This note is about the layer above both: what it costs to run a *fleet* of agents next to a team of humans, and which number tells you whether it is working.

Most published agent numbers are benchmark scores. This one is an operations report. OpenAI disclosed how its own research org used coding agents through 2026, and three of the figures are directly useful when you size, budget, or instrument a harness of your own.

The number that should change your design is not the spend. It is that **over half of the *successful* 4–8 hour agent tasks needed at least one human intervention.** Autonomy did not arrive; interruptibility did. A harness built on the assumption that a long task runs unattended is being designed against the observed failure distribution.

---

## 1. Three numbers

| Metric | Value (mid-August 2026) | What it measures |
|---|---|---|
| Agent-workdays per human workday | 3.1 | Agent runtime supplied per unit of human labor, against an 8-hour day |
| Median inference spend per researcher | > $600 / day at API prices | The per-seat cost of that supply |
| 90th-percentile inference spend | > $7,000 / day | The spread — heavy users run an order of magnitude above the median |
| Intervention rate on successful 4–8h tasks | > 50% needed one or more | How often a long run that *worked* still required a human |

The spend curve is the shape worth remembering: near zero through February 2026, roughly $50/day by April, a plateau at $150–165 through June and July, then a steep climb to about $600 by late August. That is not gradual adoption. It is a step change concentrated in a few weeks.

> **Why it matters:** if your capacity plan assumes agent spend grows linearly with headcount, you will be wrong twice — once on the level, once on the variance. The p50-to-p90 gap of roughly 10x means a flat per-seat quota either starves your best users or overprovisions everyone else.

## 2. Agent-workdays is a supply metric, not an output metric

"3.1 agent-workdays per human workday" is a compute-consumption ratio expressed in time units. It says how much agent runtime the org bought, not how much research got done. OpenAI says this itself: runtime does not map directly to progress.

This distinction is the whole reason to be careful with the number. Agent-workdays behaves like *machine-hours* in a factory — a useful denominator, a terrible KPI. Optimize it directly and you get agents that run longer, not agents that finish more.

| Metric class | Example | Safe to target? |
|---|---|---|
| Supply | Agent-workdays, tokens burned, sessions started | No — trivially inflatable |
| Cost | Spend per seat, cost per completed task | Only as a constraint |
| Throughput | Experiments per active experimenter | Yes, with a quality gate |
| Quality ceiling | Intervention rate, rework rate | Yes — this is the one to move |

The throughput metric OpenAI actually reports movement on is **experiments per active experimenter**, at an all-time high in August 2026 against a baseline that starts January 2025. That is a per-person productivity measure with a real denominator, which is why it is the more honest of the two headline claims.

> **Architectural takeaway:** instrument agent-workdays because it is your bill. Report throughput and intervention rate because they are your outcome. Never put the first one on a dashboard without the other two beside it.

## 3. The intervention ceiling

The most transferable finding is the least flattering one. On tasks whose human equivalent takes four to eight hours, more than half of the runs that *succeeded* still involved at least one human intervention. Failures are not counted in that figure — this is the success path.

Read as a design constraint, that means:

- **Long-horizon autonomy is not the shipping mode.** The working pattern is a long run with human checkpoints, not fire-and-forget.
- **The interrupt path is a first-class surface.** Steering mid-run, resuming after a correction, and re-grounding an agent that drifted are core harness features, not conveniences. See [Breaking the Lockstep Turn](../5.%20AI%20Agents%20%26%20Tool%20Use/Breaking%20the%20Lockstep%20Turn%20%E2%80%94%20Async%20Tool%20Calls%2C%20Mid-Turn%20Steering%2C%20and%20Configuration%20Updates.md).
- **Intervention rate is the metric that tells you the harness improved.** If your agents run longer at constant intervention rate, you bought more compute. If intervention rate drops at constant task length, the harness got better.
- **A run that cannot be interrupted cheaply is a run that must be restarted expensively.** Durable per-attempt state — a scoreboard file rather than a growing transcript — is what makes a mid-run correction cost one iteration instead of the whole session. That is the same pattern argued for in [6.4. The Automated Alignment Researcher](../6.%20Evaluation%20%26%20Observability/6.4.%20The%20Automated%20Alignment%20Researcher%20%E2%80%94%20A%20Hill-Climbing%20Harness%20and%20Its%20Gates.md).

> **Lesson:** measure intervention rate bucketed by task length. A single aggregate hides the fact that the rate climbs with horizon, which is exactly the curve you are trying to flatten.

## 4. What the fleet is actually pointed at

The work agents absorb is concentrated, not general. Reported use is coding, research-infrastructure troubleshooting, technical support, monitoring, and experiment execution. High-level planning is explicitly a small share of output.

That distribution matches the harness primitives that pay off:

| Work type | Harness primitive that carries it |
|---|---|
| Coding and refactors | Repo memory, rules, tool scope ([11.2](./11.2.%20Repo%20Memory%20%E2%80%94%20AGENTS.md%20%26%20Friends.md), [11.3](./11.3.%20Rules%20and%20Project%20Instructions.md)) |
| Infra troubleshooting | Hooks, deterministic gates, on-call patterns ([11.16](./11.16.%20Harness%20Engineering%20for%20Incident%20Response%20%E2%80%94%20The%20On-Call%20Agent.md)) |
| Experiment execution | Skills as packaged procedures ([11.4](./11.4.%20Skills.md)) |
| Monitoring | Event-triggered agents, not chat sessions |
| High-level planning | Nothing yet — this stays human |

The scoping language in the disclosure is careful and worth borrowing: the claimed milestone is a system that carries out **well-defined tasks under human direction**, including tasks whose human equivalent takes a few days. People still set priorities, judge which results to pursue, and decide whether to scale, pause, or deploy. That is a much narrower claim than "automated researcher," and the narrowness is the credible part.

## 5. What this evidence does not support

The disclosure is self-reported by a party with an interest in the conclusion, published alongside a recursive-self-improvement framing. Treat it accordingly:

- **No counterfactual.** There is no control arm. Experiments-per-experimenter rising in the same period as a major internal model rollout does not isolate the agent's contribution.
- **Cost is quoted at API prices, not at OpenAI's marginal cost.** The $600 figure is a valuation of internal consumption, not a bill anyone paid.
- **The spend jump is unexplained in the source.** The most plausible reading — early internal access to a stronger model in late July — is inference by outside readers, not a stated cause.
- **Nothing here transfers to a different task distribution.** ML research infrastructure is unusually well suited to agents: fast feedback, deterministic verification, high tolerance for throwaway work. A domain with slow or ambiguous verification will not see this curve.

> **Why it matters:** the useful export is the *metric set*, not the values. Copy agent-workdays, per-seat spend, throughput-per-person, and intervention-rate-by-horizon into your own instrumentation. Do not copy 3.1 into a business case.

## 6. What to instrument

A minimal fleet-economics dashboard, in the order you should add the rows:

```text
per-seat spend (p50, p90)        ← the bill; alert on p90 drift, not p50
intervention rate by horizon     ← the ceiling; the number a harness change must move
throughput per active user       ← the outcome; needs a quality gate beside it
cost per completed task          ← ties 11.20's cost-per-pass to production
agent-workdays supplied          ← the denominator; never a target
```

The first four are collectable from any harness that emits per-session cost and a human-turn count. The intervention row is the one most teams do not have, because it needs a definition: an intervention is any human turn inside an agent run that is not the initial prompt or the final acceptance. Define it once, log it, and it becomes the single number that tells you whether harness work is compounding.
