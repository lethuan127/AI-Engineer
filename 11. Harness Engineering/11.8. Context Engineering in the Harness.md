# 11.8. Context Engineering in the Harness

> Companion to [3. Prompt & Context Engineering](../3.%20Prompt%20%26%20Context%20Engineering/README.md) (which covers context engineering as a *modeling* topic) and [7.1. Claude Platform Managed Agent §4.4](../7.%20AI%20System%20Architecture/7.1.%20Claude%20Platform%20Managed%20Agent.md). This note covers what the *harness* does to the context window, what knobs you have over it, and how to keep token cost from quietly tripling on you. For the same regions read as a *privilege* surface rather than a cost surface, see [8.10. Context Privilege Escalation](../8.%20AI%20Safety%20%26%20Ethics/8.10.%20Context%20Privilege%20Escalation%20—%20Role%20and%20Scope%20as%20the%20Missing%20Trust%20Axes.md).

The context window is the agent's working memory. The vendor harness manages it for you — *partially*. The parts it manages well are invisible. The parts it doesn't, you pay for. This note maps the boundary.

---

## 1. The four context regions

Every turn, the harness assembles a prompt out of four regions, each with different costs and lifecycles:

| Region | Source | Cached? | Cost behavior |
|---|---|---|---|
| **System prompt** | Vendor + tool schemas | Yes (long prefix) | Paid once at session start; cached thereafter |
| **Repo memory + rules + skills** | Your `AGENTS.md`, `.cursor/rules/`, `.claude/skills/` | Yes (after first turn) | Paid on first cache miss; cheap re-reads |
| **Session history** | Prior turns of this conversation | Yes (sliding) | Paid as conversation grows; compaction kicks in |
| **Per-turn additions** | User message, attachments, tool results | No | Paid every turn |

> Architectural takeaway — the per-turn region is the one that bites. If you reduce one number in your harness budget, reduce *attachments and tool results per turn*.

## 2. Prompt caching — what the vendor does for you

Both Anthropic (Claude) and OpenAI (GPT) expose **prompt caching**: cache the prefix of a prompt server-side, charge a fraction of the per-token cost for re-reads.

The shape:

```text
Token 1                                                Token N
  │ ─────── cached prefix (cheap re-read) ─────── │ ── tail (full price) ──
  │                                               │
  System + tool schemas + AGENTS.md + rules + …   │ User message + tool result
```

Practical consequences:

- **A stable harness pays off.** If `AGENTS.md` doesn't change between turns, the cache hits. If you edit it every turn, you cache-bust on every turn.
- **Order matters.** Stable content (system, memory, rules) goes first; volatile content (this turn's message) goes last. Both vendors do this automatically; don't fight it.
- **Cache TTL is short.** Minutes, not hours. A 30-minute coffee break invalidates the cache.

> Lesson — every byte of repo memory and rules is *cheap on re-read, expensive on cache miss*. Optimize for steady-state, not first-turn.

### 2.1. The append-never-mutate invariant

The three bullets above are the *user's* view of caching. From inside a harness the rule is
sharper: **cache hits require the old prompt to be an exact prefix of the new prompt.** Every
turn appends; nothing already sent is ever edited. OpenAI's writeup of the Codex agent loop
makes the consequence explicit — when the sandbox mode, approval policy, or working directory
changes mid-conversation, Codex does *not* rewrite the original `<permissions instructions>`
or `<environment_context>` message. It appends a **new** message in the same format and lets
the model take the later one as authoritative. Mutating the earlier item would be cleaner to
read and would invalidate the entire prefix.

Under that invariant, the cache-miss triggers are enumerable, and most of them are things a
harness does to itself:

| Trigger | Why it busts the prefix | Harness mitigation |
|---|---|---|
| Tool list changes mid-conversation | `tools` is part of the cached prefix | Freeze the tool set per session — or, on models that support it, declare the full set up front and use `tool_addition` / `tool_removal` blocks so `tools` never changes (see [11.7 §](./11.7.%20Tools%20and%20MCP.md)) |
| Tool list *reordered* | Prefix compares byte-wise, not set-wise | Enumerate tools in a deterministic order |
| MCP `notifications/tools/list_changed` honored mid-run | Server-driven tool churn rewrites `tools` | Defer the refresh to the next turn boundary, or ignore it |
| Model switch | Model-specific system instructions sit in the prefix | Treat `/model` as a session boundary, not a toggle |
| Sandbox / approval / cwd change | Lives in an early `developer`/`user` item | Append a new item; never edit the old one |

> Architectural takeaway: a harness that assembles context as an *append-only log* gets linear
> sampling cost from prompt caching. A harness that rebuilds its prompt each turn — even
> producing byte-identical output in the common case — pays quadratic cost the moment any
> early item legitimately changes. The invariant is worth enforcing in the type system, not
> the code review.

Codex also declines the obvious shortcut here. The Responses API offers `previous_response_id`
so a client can send only the new message and let the server hold history; Codex does not use
it, keeping every request fully stateless so that Zero Data Retention deployments behave
identically. That is the same tradeoff MCP made in `2026-07-28` — statelessness bought at the
cost of resending the transcript, paid for by caching. See
[5. AI Agents & Tool Use — MCP Goes Stateless](../5.%20AI%20Agents%20%26%20Tool%20Use/MCP%20Goes%20Stateless%20—%20The%202026-07-28%20Release%20Candidate.md).

## 3. Compaction — what happens when history grows

Past some threshold (~100K tokens for Claude, ~128K for GPT-4o-class), the harness can't fit the whole conversation. Two strategies, both used:

| Strategy | What it does | When it happens |
|---|---|---|
| **Compaction** | Summarize older turns into a shorter recap that replaces them in context | Automatic, near the window cap; user can trigger with `/compact` |
| **Truncation** | Drop the oldest turns outright (kept on server for replay) | Last resort; vendor-specific |

Compaction is lossy. The summary preserves *what* the conversation did but loses *exactly what was said*. For most coding tasks this is fine. For tasks that depend on a specific prior tool output, it can be a quiet bug source.

### 3.1. Text-summary compaction vs. server-side compaction

The "summarize older turns" model above describes the first generation: the harness asks the
model to write a recap, then substitutes that prose for the transcript. It is transparent —
you can read the summary — and it is lossy in exactly the way prose is lossy.

There is now a second mechanism that is not a summary at all. OpenAI's Responses API exposes
compaction as a first-class operation, either automatically via
`context_management=[{"type": "compaction", "compact_threshold": N}]` on the create call, or
explicitly via a standalone `/responses/compact` endpoint. What comes back is not a paragraph.
It is a new context window containing retained items plus a **compaction item carrying an
`encrypted_content` blob** that the docs describe as opaque and "not intended to be
human-interpretable," and that "carries forward key prior state and reasoning using fewer
tokens." The window generally contains more than the compaction item alone; retained messages
and reasoning items come back too.

| Axis | Text-summary compaction | Server-side compaction |
|---|---|---|
| Artifact | Model-written prose recap | Retained items + opaque `encrypted_content` item |
| Inspectable | Yes — you can read and audit it | No — deliberately not human-readable |
| Preserves reasoning | Only what the summary happens to mention | Stated to carry prior state *and* reasoning |
| Who owns the policy | The harness | The provider, at a threshold you set |
| Portability | Works against any model | Bound to that provider's format |

Two operational rules follow, and they cut against normal instincts. **Do not prune the
compacted window** — the returned list is the canonical next context, so it is passed through
as-is rather than filtered. And when chaining by `previous_response_id`, do not prune at all;
manual pruning is only valid in the stateless input-array mode, where items *before* the most
recent compaction item may be dropped.

> Why it matters: this moves compaction from a harness concern to a protocol concern. The
> upside is real — an opaque blob can retain latent reasoning that prose cannot. The cost is
> that you can no longer read what your agent believes about its own history, and the blob
> only means something to the provider that minted it. A harness that wants to stay
> portable, or that needs an auditable record of what survived a compaction boundary, still
> has to keep its own summary alongside. The docs, notably, state nothing about what
> compaction loses.

For the theory of *what* compaction can and cannot preserve, see
[Context Compaction Theory](../3.%20Prompt%20%26%20Context%20Engineering/Context%20Compaction%20Theory%20—%20Selection%2C%20Generation%2C%20and%20the%20Budget%20Lower%20Bound.md).
For the attack surface an opaque, client-carried reasoning blob opens, see
[8.3. Client-Carried Reasoning State](../8.%20AI%20Safety%20%26%20Ethics/8.3.%20Client-Carried%20Reasoning%20State%20—%20The%20Encrypted%20Chain-of-Thought%20Attack%20Surface.md).

Practical disciplines:

- **Compact deliberately.** When you start a new sub-task, run `/compact` (or its equivalent) before — clean slate, fresh budget.
- **Spill important context to disk.** If a decision was made based on a 50-page log, write the decision to a file before compaction loses the log.
- **Watch for compaction during long sessions.** Both Cursor and Claude Code log when it happens; pay attention.

## 4. Filesystem-as-memory

The defining pattern of modern agent harnesses: **the filesystem is the agent's external memory**.

Instead of stuffing everything into context:

```text
[bad]
Tool returns 200 KB of grep output.
   ──► entire output enters next turn's context.
   ──► next tool result also enters.
   ──► context budget burns; quality drops.
```

The harness instead spills:

```text
[good]
Tool returns 200 KB of grep output.
   ──► harness writes to /tmp/tool_outputs/xxx.txt.
   ──► model receives: "Output too large; saved to /tmp/.../xxx.txt. Preview: …".
   ──► model can `Read` the file selectively if needed.
```

The model can also *write* to disk on its own initiative — scratch notes, intermediate results, plans. The discipline:

> Treat the agent's filesystem as its working memory. Anything that would have been a 5 KB note in context becomes a 5 KB file. Context is for *what the model needs right now*.

For session-scoped scratch space, look for `/tmp/`, `/workspace/scratch/`, or a vendor-specific path. Many harnesses have a convention (Claude Code: workspace cwd; Managed Agents: `/mnt/session/`).

## 5. Attachments — the per-turn surprise

When the user (or the IDE) attaches a file, that file's content enters the per-turn region. **Every byte costs.** And the harness has limited say in deduplication: if the same file is attached twice in a session, it's paid for twice.

Common attachment sources in Cursor / Claude Code:

| Source | Behavior | Cost |
|---|---|---|
| Currently focused file | Auto-attached every turn | Recurring (until cached as part of history) |
| Recently viewed files | Some attached; some metadata-only | Variable |
| `@`-mentioned files | Full content, this turn | One-time |
| Image / PDF attachments | Multimodal tokens; expensive | Significant |
| Open terminals | Stdout snippets | Small to large |

Disciplines:

- **Close files you don't need.** "Open" usually means "attached".
- **Avoid `@`-mentioning files the agent will obviously `Read`.** Let the agent fetch.
- **Trim large attachments.** A 10K-line CSV pasted into chat is rarely necessary; a `Read` of the first 200 lines is.

## 6. Recently-viewed and IDE state

The IDE pushes a stream of "free" context into every turn: which files are open, where the cursor is, which files you viewed in the last few minutes. This is genuinely useful for the agent — but it's *not free*.

Look at any Cursor system reminder block in a session: there's a `<open_and_recently_viewed_files>` payload. It's small (kilobytes) but it lives in the per-turn region. If you can use one of these to point the agent at the right place, it saves a `Read` call. If you ignore it, it's silent cost.

## 7. The skill description tax

From [11.4. Skills](./11.4.%20Skills.md): **every skill's description (~30 words) is loaded every turn**.

If you have:

| Skills count | Description tax per turn |
|---|---|
| 5 | ~150 tokens |
| 20 | ~600 tokens |
| 100 | ~3000 tokens |
| 500 | ~15000 tokens (real number for some plugin-heavy installs) |

Audit periodically. A skill that hasn't fired in 90 days is paying rent.

## 8. The MCP description tax

Same problem, different surface. Every MCP tool's description loads every turn. A 20-tool MCP with verbose descriptions can cost 2000+ tokens per turn.

Mitigations:

- **Audit installed MCPs.** Disable the ones you don't actually use this week.
- **Prefer narrow MCPs over Swiss Army knife ones.** A `linear-issues` server with 5 focused tools beats a `linear-everything` server with 30.
- **For some MCPs (search, databases), the harness exposes a "tool search" tool** that lazily reveals tools by description. This is an explicit trade: latency on first call vs. tokens every turn.

## 9. Steering vs. interrupt — context shaping mid-flight

The third lever, beyond what's in context and how it's compacted: **adding to it during the run**.

| Mechanism | Effect |
|---|---|
| **Steering** | Send a follow-up user message while the loop is mid-run. Appended to history; the next model call sees it. |
| **Interrupt** | Cancel the current model call entirely; reset to user-message-ready state with the partial output. |

Both are user-facing actions. They are also context engineering:

- A steering message at the right moment can save a 50-turn detour ("stop, you're refactoring the wrong file").
- An interrupt clears in-flight tool outputs that haven't fed back into context yet — a context window saver in long runs.

> Lesson — long agent runs are a context-engineering exercise. The user is part of the loop, not just a passenger.

## 10. The harness's compaction policy is *not* your strategy

A common mistake: assuming the harness will paper over an unbounded session. It will compact. It will not magically preserve everything you cared about.

A strategy that survives compaction:

1. **Plan sessions around natural boundaries.** Finish a sub-task; compact; start the next.
2. **Externalize decisions.** Write important decisions to a file (an ADR, a `NOTES.md`) — files survive compaction, context summaries do not.
3. **Use subagents for big-context sub-tasks.** A subagent's context is separate; the parent doesn't pay for it. See [11.6](./11.6.%20Slash%20Commands%20and%20Subagents.md).
4. **Watch for the cliff.** When you notice the model becoming forgetful, you're already past the point where you should have compacted.

## 11. Anti-patterns

| Smell | Why it's bad | Fix |
|---|---|---|
| **Editing `AGENTS.md` every session** | Cache-busts the longest cached region | Update on a cadence, not per-turn |
| **Pasting the entire schema in chat every time** | Per-turn cost recurs | Save to a file once; reference it |
| **Long-running session for many unrelated tasks** | History bloats; compaction loses fidelity | One session per task; new session for new task |
| **Plugin spree** | Skill + MCP descriptions tax every turn | Audit; disable unused |
| **Attaching the same file repeatedly** | Per-turn cost recurs | Trust the cache; or save to scratch |
| **Verbose tool outputs** | Spill threshold gets exceeded; model sees previews only | Make custom tools concise |

## 12. Mental model

> Context is a budget. The vendor gives you a window; your harness configuration decides how much you have *left* for the actual work. Repo memory, skills, MCP descriptions, and attachments all draw from the same well. Every kilobyte of "just in case" instructions you leave in costs you in every turn forever.

The discipline is the same as any engineering budget: measure, prune, monitor, repeat.
