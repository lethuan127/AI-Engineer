# 11.10. Reference Implementation Tour

> Companion to [11.1](./11.1.%20What%20Is%20a%20Harness.md) through [11.9](./11.9.%20Vendor%20Diff%20Matrix.md). Those notes describe the primitives in the abstract. This note walks through the harness actually configured in *this* repository — every file in `AGENTS.md`, `.cursor/`, and `.claude/` — and explains why each one exists.

If you opened this repository in Cursor or Claude Code today, this is what you'd inherit. Read it as a worked example: small, opinionated, sized for a curriculum repo, and deliberately *not* over-engineered.

## 2. The data flow

A typical "write a new note" interaction touches most of the inventory:

```text
User: "/new-note 5 'Programmatic Tool Calling'"

                                Cursor                              Claude Code
                                  │                                     │
1. Parse slash command   .cursor/commands/new-note.md       .claude/commands/new-note.md
                                  │                                     │
2. Inject AGENTS.md      ────────────────── shared root file ──────────────────
                                  │                                     │
3. Match Always rules    .cursor/rules/markdown-style.mdc   (Claude has no
                         .cursor/rules/no-emoji.mdc          equivalent rules
                                  │                          mechanism; uses
4. Agent-Requested       .cursor/rules/naming-convention.mdc memory + skills)
                                  │                                     │
5. Invoke canonical procedure
                         .claude/skills/add-curriculum-note/SKILL.md   (same)
                                  │                                     │
6. Read style reference  7.1. Claude Platform Managed Agent.md (same)
                                  │                                     │
7. Scaffold the file     Built-in Write tool                Built-in Write
                                  │                                     │
8. Hook fires            .cursor/hooks.json → check-references.sh       .claude/settings.json
                                                                        → check-references.sh
                                                                        (wrapper) → same script
                                  │                                     │
9. Update README         Built-in Edit tool                 Built-in Edit
```

Every primitive in section 11 has a slot. No primitive is duplicated. Skills are the single source of truth; rules and commands link in.

## 3. AGENTS.md — the constitution

[`AGENTS.md`](../AGENTS.md). Seven sections, ~140 lines.

Sections and their purpose:

| Section | Purpose |
|---|---|
| 1. What This Repository Is | One paragraph, never re-derived |
| 2. House Style for Notes | Heading levels, voice, forbidden vocabulary |
| 3. File Naming | The `X.Y. Title Case.md` convention |
| 4. Working Agreement | Allowed / confirm / forbidden — permission-shaped |
| 5. References Section Format | The format every note ends with |
| 6. Linked Tooling | Pointers to the rest of the harness |
| 7. Mental Model | One paragraph closing |

Decisions encoded:

- **AGENTS.md, not CLAUDE.md.** Both Cursor (2026+) and Claude Code (via `@`-import) read it; one source of truth.
- **Constitution shape, not playbook.** Procedures live in skills; rationale in commit history.
- **References section is required.** Concrete, enforceable. The hook backs it up.

## 4. `.cursor/rules/` — the statutes

Four rule files, each ~80 lines:

| File | Mode | Why it exists |
|---|---|---|
| `markdown-style.mdc` | Always, scoped to `*.md` | Voice rules are repo-wide but only relevant for markdown |
| `references-section.mdc` | Auto-Attached on `[0-9]*/[0-9]*.md` | Numbered notes only; stubs are exempt |
| `naming-convention.mdc` | Agent-Requested | Only fires when the agent is *creating* a file |
| `no-emoji.mdc` | Always | Tiny; cheap on every turn |

Why not roll these into `AGENTS.md`? Two reasons:

1. **Auto-Attached rules** don't load when editing files outside the curriculum tree (e.g., `.cursor/rules/foo.mdc` itself, which is markdown but not a numbered note). Folding into memory would cost tokens needlessly.
2. **Agent-Requested rules** (`naming-convention`) only fire on intent — adding to memory would mean every turn pays for naming rules even when the user is just editing.

Each rule ends with a link to the canonical skill where applicable (`references-section.mdc` → `normalize-references/SKILL.md`). That's the single-source-of-truth pattern in action.

## 5. `.cursor/commands/` and `.claude/commands/` — explicit entry points

Two commands, mirrored across both surfaces:

| Command | What it does | Delegates to |
|---|---|---|
| `/new-note <track> <title>` | Scaffold a new numbered note | `add-curriculum-note` skill |
| `/check-refs [path] [--fix]` | Audit / repair References section | `normalize-references` skill |

The command files are deliberately thin (~50 lines each):

- Parse arguments.
- Find/disambiguate target.
- Defer to the skill for the actual work.
- Report at the end.

This separation lets us keep the commands stable while iterating on the skills.

## 6. `.cursor/mcp.json` — one server, pinned

[`/.cursor/mcp.json`](../.cursor/mcp.json):

```json
{
  "mcpServers": {
    "context7": {
      "command": "npx",
      "args": ["-y", "@upstash/context7-mcp@latest"]
    }
  }
}
```

Why pin context7 at repo level when most users have it global already?

> Reproducibility. A new contributor cloning the repo gets the doc-lookup MCP automatically. No setup instructions to follow.

Why not more MCPs? This is a notes repo. We don't need DB introspection, ticket integration, or browser automation. Following the rule from [11.7. Tools and MCP §6](./11.7.%20Tools%20and%20MCP.md), every MCP earns its description tax. Context7 earns it; nothing else does here.

## 7. `.cursor/hooks/` + `.claude/hooks/` — one script, two wires

Cursor and Claude Code have converged on the same hook protocol: a JSON payload arrives on **stdin** with a `file_path` field (Cursor at the top level; Claude Code nested under `tool_input`). One shared script accepts either shape, and each vendor config is a single-line wire to it.

| File | Role |
|---|---|
| `.cursor/hooks/check-references.sh` | The shared logic. Reads stdin JSON, looks for `.file_path` or `.tool_input.file_path`, falls back to `$1` for manual smoke-tests. |
| `.claude/hooks/check-references.sh` | One-line wrapper that just `exec`s the shared script so Claude Code's config can stay vendor-folder-local. |
| `.cursor/hooks.json` | Wires `afterFileEdit` (filtered by `matcher: "Write"`) to the shared script, with `failClosed: false`. |
| `.claude/settings.json` (`hooks` block) | Wires `PostToolUse` on `Edit\|Write` to the wrapper. |

Properties:

- **Advisory, never blocking.** Exit code is always 0.
- **Single one-line message.** `[hook] <file>: <issue>`.
- **Tolerates missing tools** (`jq`, `rg`). Hooks should fail soft.
- **Skips files it doesn't care about** (non-numbered, stubs, top-level README files).
- **Smoke-testable from the command line** — passing a path as `$1` bypasses stdin entirely.

The script is the smallest possible thing that demonstrates the primitive. Production hooks add: timing, telemetry, finer matchers, multiple checks. We don't.

## 8. `.claude/settings.json` — permissions + hook registration

[`/.claude/settings.json`](../.claude/settings.json). Three blocks:

```json
{
  "permissions": {
    "allow": ["Read(*)", "Glob(*)", "Grep(*)", "Bash(git status:*)", "Bash(git diff:*)", "Bash(git log:*)", "Bash(ls:*)", "Bash(rg:*)"],
    "ask":   ["Bash(git add:*)", "Bash(git commit:*)", "Bash(git push:*)", "Bash(git reset:*)", "Bash(rm:*)", "Bash(mv:*)"]
  },
  "hooks":  { "PostToolUse": [...] },
  "env":    { "AI_ENGINEER_REPO_HARNESS": "1" }
}
```

The permission stance:

- **Read-only operations are pre-approved.** Reading files, searching, looking at git status — all auto-allowed. No friction.
- **Mutations require confirmation.** `git add`, `commit`, `push`, `reset`, `rm`, `mv` — the agent must ask. Even if the model is wrong about wanting to do it, the user catches it.
- **Nothing is denied outright.** This is a personal repo. A team repo would deny `rm -rf /`, `curl * | bash`, and similar.

The env var is a sentinel — a quick way for a hook to detect it's running under the configured harness.

## 9. `.claude/agents/` — narrow children

Two subagents, ~80 lines each:

| Agent | Purpose | Tools | Returns |
|---|---|---|---|
| `curriculum-author` | Write/refactor notes in this repo's voice | Read, Glob, Grep, Edit, Write, WebFetch, WebSearch | A finished file + README diff |
| `reference-validator` | Audit References sections | Read, Glob, Grep, WebFetch (no Edit, no Write) | A report table only |

The capability-narrowing pattern is on display: `reference-validator` cannot edit. Even if its model decides to "fix" something, the tool isn't there.

Both link to the canonical skill for the procedural detail (`add-curriculum-note/SKILL.md`, `normalize-references/SKILL.md`). The agent file is *system prompt + tool whitelist*; the workflow lives in the skill.

## 10. `.claude/skills/` — the canonical procedures

| Skill | Owns | Referenced by |
|---|---|---|
| `add-curriculum-note/SKILL.md` | New-note scaffolding workflow | Both `/new-note` commands, the `curriculum-author` subagent |
| `normalize-references/SKILL.md` | References format + validation | Both `/check-refs` commands, the `reference-validator` subagent, the `references-section.mdc` rule |

The single-source-of-truth pattern from [11.4. Skills §7](./11.4.%20Skills.md): every other file in the harness that touches these topics *links* to the skill rather than restating the workflow. When the format changes, exactly one file changes.

Each SKILL.md is ~150 lines: frontmatter, when-to-use / when-not-to-use, inputs, numbered workflow, hard rules, verification.

## 11. What this implementation deliberately doesn't have

| Missing | Why |
|---|---|
| Per-folder `AGENTS.md` | No need — repo is small and uniform |
| `.cursorrules` | Deprecated; `AGENTS.md` covers it |
| Tens of skills | One skill per *recurring intent*; we have two |
| Custom MCP server | Nothing private to expose |
| Linter / formatter on save | The advisory hook does the only check we need |
| Blocking hooks | None earned the risk |
| CI integration | This repo doesn't have CI yet; would live separately |
| Telemetry / tracing | Personal repo; would matter at team scale |

A team repo would have most of those. A personal curriculum repo doesn't need them, and adding them would bloat without payoff.

## 12. What you'd change for a different repo

If you were applying this same pattern to a *code* repo (say, a Next.js + Postgres app), most of the structure transfers; only the content changes:

| Slot | Notes repo (this one) | Code repo (hypothetical) |
|---|---|---|
| `AGENTS.md` | Curriculum style, naming | Tech-stack conventions, deploy gates |
| `.cursor/rules/` | `markdown-style.mdc`, `references-section.mdc` | `typescript-style.mdc`, `react-server-components.mdc`, `db-migrations.mdc` |
| `.cursor/commands/` | `/new-note`, `/check-refs` | `/new-migration`, `/scaffold-route`, `/audit-deps` |
| Subagents | `curriculum-author`, `reference-validator` | `migration-author`, `security-auditor`, `test-writer` |
| Skills | `add-curriculum-note`, `normalize-references` | `add-api-route`, `update-deps`, `write-tests-for-changed-files` |
| MCPs | `context7` | `context7`, `postgres`, `linear`, `github` |
| Hooks | Advisory: References-section check | Advisory: lint on save. Blocking: deny direct push to `main`. |
| Permissions | Loose (`Read(*)`) | Tight (`deny: ["Read(.env)", "Bash(rm -rf:*)"]`) |

The *shape* is identical. The *content* reflects what the repo cares about.

## 13. Mental model — one-sentence summary

> A configured harness for a small repo is a 1500-line code review of your own conventions: enforce them automatically so future-you and future-contributors don't have to remember them.

The rest of this section (especially [11.11. Operational Concerns](./11.11.%20Operational%20Concerns.md)) covers what changes when "future-you" becomes "a team of fifteen".
