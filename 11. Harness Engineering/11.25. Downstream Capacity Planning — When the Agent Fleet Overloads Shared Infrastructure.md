# 11.25. Downstream Capacity Planning — When the Agent Fleet Overloads Shared Infrastructure

> Source: Anthropic's *Agentic coding is straining CI. Here's how we scaled test impact analysis at Anthropic*, 2026-09-14. Companion to [11.21. Agent Fleet Economics](./11.21.%20Agent%20Fleet%20Economics%20%E2%80%94%20Agent-Workdays%20and%20the%20Intervention%20Ceiling.md) and [11.17. The AI-Native SDLC](./11.17.%20The%20AI-Native%20SDLC%20%E2%80%94%20The%20Committed%20Artifact%20Chain.md). 11.21 measures what the fleet costs you in inference. 11.17 describes the artifact chain the fleet produces. This note is about the third bill: the *shared services downstream of the fleet* that were sized for humans and are now being driven by machines.

Harness engineering usually stops at the agent's boundary — rules, skills, hooks, tools, context. This note argues the boundary is drawn too tight. An agent fleet does not just consume inference; it emits work into every system the team already runs: CI, the merge queue, artifact storage, the code host, the observability pipeline. Those systems were provisioned against human request rates. Anthropic's CI job volume rose **25x in six months** against roughly flat headcount, and the service that decides which tests to run failed three times in a row while the team applied patches that each bought less time than the last. The transferable content is not the fix — it is the *rate at which half-measures decay* once the producer upstream is a machine.

---

## 1. The load shape a fleet emits

Three compounding multipliers, none of which is headcount:

| Multiplier | Mechanism | Effect on downstream load |
|---|---|---|
| Code volume | Claude authors >80% of merged code; per-engineer merge volume up ~8x vs 2024 | More changes per person per day |
| PR granularity | Agents prefer small, focused PRs over large human-shaped ones | More PRs per unit of change |
| Duty cycle | Agents push overnight and on weekends | Raises the *floor*, does not flatten the peak |

Multiply them and you get an exponential on job count while the org chart stays linear. Anthropic's tests also grew 10x over the window, so the cross-product — changes × tests — is what the test-selection service actually had to absorb.

The duty-cycle point deserves emphasis because it is counterintuitive. Agents running overnight do not smooth the curve; humans still drive and approve a large share of PRs during business hours, so the daily peak stays, and a new non-zero baseline appears underneath it. Capacity plans built on "agents will fill the troughs" are planning for a load shape that does not occur.

> Why it matters: none of these three multipliers appears in a headcount-based capacity model. A team that plans CI capacity off "engineers × commits per engineer" will be wrong by an order of magnitude within two quarters.

## 2. The anatomy of a service that falls over

The service in question is a **test impact analysis** (or test selection) service: given a change, decide which subset of tests must run. It had two deterministic halves that must stay in sync.

```text
   CI runs ──────► listener ──────► per-test result history ──────► selector ──────► test subset for PR
                   (writes)                 (state)                  (reads)
```

The v0 design kept a running history per test in process memory, which forced a **single writer**, which forbade horizontal sharding. That single architectural choice is the whole story. Everything that follows is a consequence of it.

The failure mode is not an outage. It is **listener lag** — the writer falls behind the PR queue and the selector starts deciding from stale history. Twenty minutes of lag translated into tens of thousands of unapplied test updates, which degrades in three distinct directions:

| Stale-history condition | Downstream symptom | Who pays |
|---|---|---|
| A bad change merged | A test starts failing for everyone | Every subsequent PR author investigates the same red |
| A dependency starts flaking | Flaky reds block the merge queue | The queue, globally |
| A test was fixed or added | It does not get selected yet | A regression ships unnoticed |

> Architectural takeaway: a stale *selector* is worse than a slow one. A service that degrades into silently-wrong test selection has no alarm of its own — the symptom surfaces as other people's broken builds, which is the most expensive possible place to discover it.

## 3. The collapsing half-life of a patch

The reported sequence, with how long each bought:

| Patch | Technique | Time bought |
|---|---|---|
| 1 | Vertical scaling — double the cores | 70 days |
| 2 | Shard the listener per package (one writer per package, not per service) | 29 days |
| 3 | Daily restarts to dodge a memory ceiling | < 1 day |
| — | Redesign: journal in an in-memory store, stateless workers, separate rollup consumer | Stable since |

The techniques are ordinary. The *decay curve* is the finding: 70 → 29 → <1 days, against a workload growing exponentially. Each intervention bought roughly a third of what its predecessor did, which is exactly what you get when a linear capacity increase meets an exponential load.

The redesign took **three weeks for one engineer** — work that the author estimates would have been closer to a quarter a year earlier. Combine the two facts and the cost-benefit inverts:

> Lesson: when patches decay geometrically and rewrites get cheaper, the expected value of "one more quick fix" goes negative much earlier than engineering instinct expects. The instinct was calibrated on a world where a rewrite cost a quarter and a patch bought a year.

Patch 3 is also the one to study, because the team looked for a quick win and found there wasn't one: four bugs, a swapped memory allocator that did nothing, and a refusal to memory-profile a loaded singleton. The absence of a cheap fix was itself the signal that the architecture, not the implementation, was the problem.

## 4. The redesign, stated as a rule

The fix is the standard one — take the state out of the process:

- Any listener worker accepts any result, appends it to a **journal** in an in-memory store, and returns. It holds nothing. It is stateless, therefore horizontally scalable.
- A small separate consumer rolls the journal up into per-test history every few seconds.
- The selector reads the rolled-up history.

This costs more to run and is easier to scale and profile than a singleton. That trade — more expensive, more operable — is the one to take when the producer upstream is a fleet.

The generalizable rules, in the order they bite:

1. **Keep state out of the process from the start.** State in process memory is what forbids sharding, and the prohibition only becomes visible under load you did not plan for.
2. **Never run a critical shared service as a single instance** unless you can measure it and canary changes to it.
3. **Size v0 for 10–20x perceived scale**, budget permitting. Over-engineering has not disappeared, but the bar has moved; assume 25x within two quarters.
4. **Instrument for conservation, not just for health.** The specific check recommended is that *jobs in equals jobs out* — a count-conservation invariant, which is what makes lag observable before it becomes staleness.

## 5. Test selection is a harness surface

The easy reading of this story is that it is a CI infrastructure post. The harness-relevant claim is stronger and is stated in one line of the source: **humans are good at recognizing which test failures don't apply to them; agents are not.** Give an agent a precise, valid set of tests and it self-verifies and iterates; give it a noisy set and it burns turns chasing failures it did not cause.

That makes test selection a *context-quality* problem wearing infrastructure clothes:

| Harness concern | Ordinary framing | Framing under this note |
|---|---|---|
| Feedback signal | "Run the tests" | Select the *valid* tests, or the agent optimizes against noise |
| Context cost | Tokens in the prompt | Irrelevant red output the agent must read and dismiss |
| Turn count | A model property | Inflated by every false failure — see [11.20](./11.20.%20Harness%20Benchmarking%20%E2%80%94%20Controlled%20Cross-Harness%20Evaluation.md) on turn count as the cost driver |
| Intervention rate | Harness quality metric ([11.21](./11.21.%20Agent%20Fleet%20Economics%20%E2%80%94%20Agent-Workdays%20and%20the%20Intervention%20Ceiling.md)) | A human is dragged in to say "that red isn't yours" |

So a stale selector does not merely waste CI minutes. It degrades the verification loop the agent depends on, and it shows up in your harness metrics as higher turn counts and more interventions, with no harness change to explain it. This is the case for treating **any deterministic service the agent reads from as part of the harness**, subject to the same eval and drift discipline as rules and skills ([11.11](./11.11.%20Operational%20Concerns.md)).

## 6. The monitoring pattern worth stealing

One operational detail is a small, reusable design. Rather than a dashboard nobody watched, the author kept a **long-running agent session dedicated to one service**, wired so that listener lag past 50,000 jobs pinged him and *resumed the existing conversation*. The value was continuity: months of prior attempts, rejected options, and context did not have to be re-supplied at each page.

This is the on-call agent pattern of [11.16](./11.16.%20Harness%20Engineering%20for%20Incident%20Response%20%E2%80%94%20The%20On-Call%20Agent.md) narrowed to a single service, and it is cheaper than it looks:

- **Threshold-triggered, not poll-triggered.** A deterministic metric crossing a line is the trigger; the agent is the responder. Same split as 11.16.
- **One session per service, not per incident.** The accumulated history *is* the artifact. A fresh session each page would re-litigate the same options monthly.
- **The agent argued for the overhaul repeatedly and was overruled.** Worth sitting with: the recommendation was right and the humans discounted it three times. A monitoring agent's value is partly that it does not get tired of making an unpopular argument — which only pays if someone eventually reads the argument rather than the alert.

## 7. What to be skeptical about

- **One organization, one service, self-reported.** The 25x figure comes from a company with unusually deep agent adoption (>80% of merged code authored by Claude). A team at 20% adoption should expect the shape, not the magnitude.
- **"Assume 25x in two quarters" is advice, not a measurement.** It is a planning heuristic derived from one trajectory. The defensible version is weaker and still useful: *measure your own downstream job growth rate monthly and extrapolate exponentially, not linearly.*
- **Over-engineering has not become free.** "Design for 10–20x" is qualified with *as long as your budget allows*. The distributed redesign is explicitly more expensive to run. The claim is that the cost of premature scale fell relative to the cost of emergency re-architecture — not that headroom is costless.
- **Not every downstream service is CI.** The mechanism generalizes — a fleet drives artifact registries, code hosts, log pipelines, and the merge queue the same way. Anthropic's own footnote on GitHub is the external evidence: roughly one billion commits across all of 2025, versus 275 million per week by mid-2026. But the specific fix (journal plus stateless workers) is a fix for *this* class of write-heavy stateful singleton, not a template.
- **The listener/selector split is not universal.** Many teams still run every test on every change. That is the thing this architecture replaces, and the source concedes it works "up to a point" — the point being where CI gates get long, expensive, and untrusted. Do not adopt test impact analysis to solve a scale problem you do not yet have; adopt it when agents start ignoring your CI signal.

## 8. Checklist

Before the next quarter's capacity plan, for each shared service downstream of your agents:

```text
[ ] Is its load driven by agent output rather than headcount?   → re-forecast exponentially
[ ] Does any component hold state in process memory?            → that is the sharding blocker
[ ] Does it run as a single instance?                           → canary path, or redesign
[ ] Is there a conservation invariant instrumented (in == out)? → this is your lag alarm
[ ] Does an agent read its output as ground truth?              → it is a harness surface; eval it
[ ] What did your last three patches buy, in days?              → if the series is shrinking, stop patching
```

The last line is the cheapest diagnostic in this note. Time-bought per patch is a number most teams already have in their incident records and almost none of them plot.
