# 11.12. Harness Engineering for Private Equity & Venture Capital

> Domain transfer note. [11.1](./11.1.%20What%20Is%20a%20Harness.md) through [11.11](./11.11.%20Operational%20Concerns.md) develop harness engineering for **coding agents** in a code repository. This note re-applies the same primitives — repo memory, rules, skills, hooks, permissions, tools, MCP, subagents, context engineering — to **deal-intelligence agents** in a PE/VC firm. The thesis: the discipline is unchanged; only the content of each slot changes.

A PE/VC firm running an agent over its deal pipeline is structurally the same problem as a developer running Claude Code over a monorepo. Both have a long-lived corpus (codebase / deal room), a stream of incoming work (PRs / new opportunities), domain conventions that the model must respect (style guide / underwriting policy), and side effects that must be gated (rm / send-to-IC). The configuration surfaces are the same; the costs, identities, and audit requirements are different. This note maps the translation, and ends with the one harness primitive — **identity propagation** — that coding harnesses don't need but enterprise harnesses must invent.

---

## 1. The PE/VC pipeline as a "repository"

A coding harness operates on a directory of files. A PE/VC harness operates on a directory of **deals**. The surface area is similar:

| Coding repo | PE/VC pipeline |
|---|---|
| Files in `src/` | Deals in the pipeline (CRM rows, Kanban cards, deal-room folders) |
| Commits / PRs | New opportunities, CIM uploads, IC memos, term-sheet revisions |
| `README.md` | Fund thesis / investment mandate |
| Tests | Underwriting checklist, return thresholds, concentration limits |
| Linter rules | House style for memos, citation format, redaction rules |
| Build pipeline | Stage-gates: screen → diligence → IC → close |
| Production deploy | Wire transfer / closing docs / cap-table update |

The unit of work is **a deal at a stage**. The agent's job, at any given moment, is to advance one deal one stage with one artifact (an opportunity summary, a diligence question list, a draft IC memo, a portfolio update). The harness is what keeps that work consistent across analysts, funds, vintages, and years.

## 2. Three real agent roles in a PE/VC firm

Not one giant agent. Three (or four) **narrow S2 roles** ([11.1 §3](./11.1.%20What%20Is%20a%20Harness.md)) wired into the firm's workflow:

| Role (S2) | Triggered when | Output | Tool surface |
|---|---|---|---|
| **Sourcing scout** | New inbound email / referral / pitch deck arrives | One-paragraph "is this in mandate?" verdict + structured fields (stage, sector, geo, check size) | Inbox MCP, CRM write, fund-mandate doc, web search |
| **Diligence analyst** | Deal advances past initial screen | Diligence question list; first-pass financial summary; market-map draft | Deal-room read, financial-data MCP (Pitchbook/Crunchbase/internal warehouse), portfolio-comp lookup, web search |
| **IC memo drafter** | Diligence complete, deal heading to IC | Draft memo in firm template; risk flags; comp table | All of the above + memo-template skill + redline tool |
| **Portfolio monitor** | Quarterly / on-event | Variance vs. plan; covenant check (for credit); KPI dashboard; flagging | Portfolio-co data warehouse, board-meeting notes MCP, financial-statements MCP |

The same Anthropic Claude (or GPT-5, or Gemini) sits inside all four. **What differentiates them is the harness configuration** — system prompt, tool subset, context inputs, permissions, hooks. That is the section-11 thesis applied to PE/VC verbatim.

## 3. Slot-by-slot translation

Walking the section-11 primitives, with the PE/VC analogue and the *load-bearing* design decision:

### 3a. Repo memory ([11.2](./11.2.%20Repo%20Memory%20%E2%80%94%20AGENTS.md%20%26%20Friends.md)) — the fund constitution

Coding: `AGENTS.md` at repo root, read every turn.

PE/VC: **`FUND.md`** (or whatever your firm calls it). Loaded into every turn for every role. Contents:

- **Mandate.** Sector, stage, geo, check size, ownership target. The "in-scope / out-of-scope" line.
- **Underwriting hurdle.** Minimum target return; deal-killer criteria; ESG exclusions.
- **House style for memos.** Section order; what counts as a "comparable"; citation format; redaction policy.
- **Pipeline taxonomy.** What "screen / DD / IC / closed" actually mean at this firm.
- **Names and conventions.** Sponsor names; portfolio-co codenames; standard abbreviations.

> Lesson — the fund's `FUND.md` is what stops the agent from drafting an IC memo for a Series A SaaS deal in the format your firm uses for late-stage healthcare buyouts. It carries thesis context, not policy enforcement; that's hooks.

### 3b. Rules ([11.3](./11.3.%20Rules%20and%20Project%20Instructions.md)) — conditional context

Coding: `.mdc` files matched by file glob.

PE/VC: rules matched by **deal attribute** rather than path. The match key changes; the activation pattern is identical.

| Match key | Example rule |
|---|---|
| Sector | "When deal is in healthcare, always include HIPAA/regulatory column in the risk table" |
| Stage | "When deal is pre-seed, do not insist on 3-year financial projections" |
| Geo | "When deal HQ is EU, flag GDPR; when LATAM, flag FX hedging in IC memo" |
| Deal size | "When check size > $50M, require a written commitment-committee sign-off path" |
| Source | "When deal is from sponsor X, the memo must include relationship history" |

The agent reads `description` frontmatter for each rule, decides which apply to the current deal, pulls them in. Same activation primitive as Cursor's `description`-routed rules — the index changes from filesystem glob to a structured deal tag.

### 3c. Skills ([11.4](./11.4.%20Skills.md)) — packaged procedures

This is the slot that earns its keep fastest in PE/VC. Most analyst work is a sequence of steps repeated across hundreds of deals: pull the comps, build the waterfall, redline the term sheet against last quarter's. Each one is a SKILL.md:

| Skill | When triggered | Workflow |
|---|---|---|
| `draft-ic-memo` | "Write an IC memo for deal X" | (1) verify deal stage = DD complete (2) pull diligence artifacts (3) build comp table from skill `find-comps` (4) instantiate firm memo template (5) draft each section in order (6) emit redactable PDF |
| `find-comps` | Need comparable companies | Filter by sector/stage/geo; rank by metric similarity; return top 8 with citations |
| `screen-deal` | New inbound | Match against `FUND.md` mandate; score 0–5; route to sourcing analyst or auto-reject template |
| `redline-term-sheet` | Term sheet received | Diff against firm-standard; highlight off-market terms; cite precedents from past deals |
| `quarterly-portfolio-update` | Quarterly trigger / portfolio review | Pull KPIs; build variance table; flag covenant breaches; draft commentary |

The repo's own MCPs for CACO/CO3 already point in this direction — `deal-analyst-rules`, `source-tier-prioritization`, `board-write-protection` are exactly this style of packaged procedure, distributed as plugin skills.

> Architectural takeaway — the **memo is the unit of output**, the **skill is the unit of reuse**. Build the skills once; the memo regenerates correctly across hundreds of deals because every analyst hits the same `draft-ic-memo` skill from the same `FUND.md`.

### 3d. Hooks and permissions ([11.5](./11.5.%20Hooks%2C%20Permissions%2C%20and%20Side%20Effects.md)) — where the risk actually lives

Coding: block `rm -rf`, deny edits to `.env`.

PE/VC: the threat surface is **outbound communication and database mutations**, not destructive shell. The hook taxonomy:

| Hook point | Pattern | Example |
|---|---|---|
| **Pre-tool: send email** | Block any outbound email to a sponsor / counterparty until human approves | Drafts go to a review queue, not the wire |
| **Pre-tool: write to CRM** | Require human confirmation on stage transitions past `screen` | Auto-write notes; ask before moving to IC |
| **Pre-tool: query MNPI** | Restrict by user identity + deal access list | Junior analyst can't query a deal they aren't staffed on |
| **Post-tool: financial figures** | Run a "source-tier" check (audited > management-prepared > model output) and annotate every quoted figure | Implemented as a skill in this repo's `chicago-atlantic-toolkit` plugin |
| **Post-tool: PII / NDA** | Redact counterparty names from outputs that will leave the firm's network | Compliance |
| **Post-tool: citation lint** | Every claim must have a deal-room file ID + page reference; flag uncited claims | Audit |
| **Stop: audit log** | Every agent session flushes (prompt, tools called, outputs, user) to an immutable log | Mandatory for regulated funds |

The permission tiers from section 11.5 §4 translate directly:

| Coding tier | PE/VC tier | Example |
|---|---|---|
| `allow` | `allow` | Read deal-room files; query internal warehouse |
| `ask` | `draft-and-review` | Update CRM stage; send email to internal team |
| `deny` | `deny` | Wire transfer; cap-table mutation; sending memo to LPs |

> The pattern: **reads and drafts allow; sends and writes draft-and-review; financial mutations deny outright.** The agent never has the firm's chequebook. It can compose the cheque; a human signs it.

### 3e. Tools and MCP ([11.7](./11.7.%20Tools%20and%20MCP.md)) — the firm's data plumbing

Coding tools are universal (Read/Write/Bash/Grep). PE/VC tools are domain-specific and almost always live behind MCP servers, because the data sources are databases and SaaS APIs, not the local filesystem.

A realistic MCP loadout for a PE/VC harness:

| MCP server | Surface |
|---|---|
| **Deal-room MCP** | Read CIMs, financials, contracts, board decks; resource per deal |
| **CRM MCP** (Salesforce / Affinity / DealCloud) | Read deal records; write notes; transition stages |
| **Financial-data MCP** (Pitchbook / Crunchbase / Capital IQ / FactSet) | Comparables, valuations, transaction history |
| **Warehouse MCP** (Snowflake / Databricks) | Internal portfolio KPIs, historical deal performance |
| **Compliance MCP** | Restricted-list check; conflict-of-interest check |
| **Document MCP** (NetDocuments / iManage) | Legal docs; precedent search |
| **Calendar / Email MCP** | Schedule diligence calls; draft (not send) outbound |
| **Context7 / web search** | Live news, market data, regulatory updates |

> Rule of thumb (from [11.7 §6](./11.7.%20Tools%20and%20MCP.md)): every MCP earns its description-tax tokens. Six MCPs is healthy. Twenty is a context-window disaster — and a confused agent that can't decide whether to query Capital IQ or Pitchbook.

### 3f. Subagents ([11.6](./11.6.%20Slash%20Commands%20and%20Subagents.md)) — narrow children

Three patterns appear over and over:

| Subagent | Why it's a subagent, not a tool |
|---|---|
| `comp-finder` | Long retrieval task with its own scratchpad; isolate from the parent context to avoid bloat |
| `risk-flagger` (read-only) | Restrict toolset — it should not be able to write anywhere, only annotate |
| `memo-section-drafter` | Parallel: dispatch one per memo section; aggregate at the end |
| `compliance-reviewer` | Independent verdict; must not see the parent's draft until it has formed an opinion |

The repo's `reference-validator` subagent is the coding analogue of `compliance-reviewer` — read-only by design, narrow charter, returns a verdict.

### 3g. Context engineering ([11.8](./11.8.%20Context%20Engineering%20in%20the%20Harness.md)) — the deal-room problem

Coding repos have the "5K-file repo, 200K-token window" problem; the solution is retrieval and attachment.

PE/VC has the **deal-room problem**: 300-page CIM, 50-tab data-room spreadsheet, dozens of past memos for comparables. You will *never* fit the full deal room in context. Three patterns ([7.2 §7](../7.%20AI%20System%20Architecture/7.2.%20Self-Implemented%20Agent%20Harness%20%E2%80%94%20Components.md) is the upstream view):

1. **Filesystem-as-memory.** The deal room *is* the working directory. The agent reads files on demand via the deal-room MCP. The harness pins only file *paths* into context, not contents. Same pattern as Claude Code's `Read` tool over a large repo.
2. **Aggressive compaction.** Diligence sessions span weeks. Use `compact_20260112`-style summarization at session boundaries: "Here is what we concluded about this deal so far; the underlying transcripts are in `<dealroom>/sessions/2026-Q2/`."
3. **Per-deal scratchpad.** A `deal-notes.md` lives in the deal room. The agent appends findings as it reads. The next session loads the scratchpad as repo memory. This is the section 7.2 "filesystem as memory" pattern with a domain skin.

### 3h. Slash commands ([11.6](./11.6.%20Slash%20Commands%20and%20Subagents.md)) — analyst workflow shortcuts

| Command | Effect |
|---|---|
| `/screen <deal>` | Runs the `screen-deal` skill end-to-end |
| `/memo <deal>` | Runs `draft-ic-memo`; opens result in firm's memo editor |
| `/comps <deal>` | Runs `find-comps`; emits a markdown table |
| `/diligence-questions <deal> <sector>` | Generates a tailored DD list from a sector playbook skill |
| `/portfolio-review <quarter>` | Triggers the portfolio-monitor agent across all active investments |

These are analyst-facing buttons; each delegates to a skill. Same single-source-of-truth pattern as [11.4 §7](./11.4.%20Skills.md): the skill is canonical; the command is the UI entry.

## 4. The one new primitive — identity propagation

Coding harnesses have effectively one identity (you). Enterprise harnesses have many. Every tool call must propagate **whose authority it is being executed under**.

```text
analyst (Alice, deal access: [CACO-074, CO3-031])
   │
   ▼
┌──── harness ──────────────────────────────────────────────────┐
│  fund.md  ·  rules matched on deal tags  ·  skills            │
│                                                               │
│              ┌──── agent ────┐                                │
│              │  Claude       │                                │
│              └───────┬───────┘                                │
│                      │ tool_use(name="deal_read",             │
│                      │          deal_id="CACO-099") ⚠         │
│         ┌────────────▼────────────┐                           │
│         │ pre-tool: ACL check     │── deny ─▶ "Alice does     │
│         │  (Alice ∉ CACO-099)     │           not have        │
│         └────────────┬────────────┘           access"         │
│                                                               │
│                      │ approved                               │
│         ┌────────────▼────────────┐                           │
│         │ tool exec               │── audit log               │
│         │  (acting as: Alice)     │   (actor=Alice,           │
│         └────────────┬────────────┘    deal=CACO-074, …)      │
│                                                               │
└──────────────────────┼────────────────────────────────────────┘
                       ▼
                   Deal Room API
```

Three rules:

1. **The model never sees the identity token.** It sees only the analyst's *name and role* (in repo memory) and emits tool calls. The harness attaches the actual auth credentials.
2. **ACL enforcement is at the tool layer, never the model.** Telling the model "you cannot read CACO-099" in the prompt is not security; it's a suggestion. The pre-tool hook is the security.
3. **Every tool execution is logged with the actor.** Without this you cannot prove which analyst's agent did what — and you will be asked to prove it (compliance, LP audit, regulator).

This is the single biggest divergence from a coding harness, and the reason a PE/VC harness is a months-long project, not an afternoon.

## 5. Operational concerns — what changes vs. [11.11](./11.11.%20Operational%20Concerns.md)

Every operational concern from section 11.11 has a PE/VC analogue, with a higher stakes:

| Concern | Coding | PE/VC |
|---|---|---|
| **Drift** | `AGENTS.md` and `*.mdc` disagree → agent confused | `FUND.md` and updated investment policy disagree → agent writes memos against last year's mandate |
| **Eval** | Sample 50 PRs, did the agent produce reasonable diffs? | Sample 50 past deals: did the agent recommend the same screen verdict / red-flag the same risks as the human? Score on *agreement with the historical IC outcome*, not on prose quality. |
| **Versioning** | Skills are git-managed | Skills are git-managed *and* tagged to the fund vintage. Vintage I uses a different memo template than Vintage III. |
| **Observability** | Logfile, occasional trace | Per-deal trace; per-analyst trace; quarterly compliance review |
| **Governance** | One developer maintains the harness | Compliance + Investment Ops + IT + at least one Partner; quarterly review cycle |
| **Audit retention** | None | Regulator-mandated (SEC Rule 204-2 requires ≥ 5 years for U.S. RIAs, first 2 readily accessible; AIFMD imposes parallel obligations for EU funds). Treat the agent's tool-call log as an investment-advisory record from day one. |

The harness is no longer a developer-productivity tool; it is **a regulated workflow system**. Treat it as such from day one.

## 6. When *not* to build a harness for this

The temptation in PE/VC is to wrap every analyst task in an agent. Don't. The harness sniff test from [11.1 §4](./11.1.%20What%20Is%20a%20Harness.md):

| Situation | Verdict |
|---|---|
| One-shot summarization of a CIM | Just an API call. No harness. |
| Quarterly portfolio update across 40 companies | Workflow (fixed graph), not an agent. Build with cron + LLM steps, not Claude Code. |
| "Find me deals like X from our pipeline" — single retrieval | Search tool with LLM reranking. Not an agent. |
| Open-ended diligence assistant that reads the data room, asks follow-up questions, drafts the memo | **Agent harness.** This is what section 11 covers. |
| Every analyst's email needs an LLM-drafted reply | Copilot UI, not autonomous agent. Thin harness. |

The mistake to avoid: building a fully autonomous deal-sourcing agent when what the firm actually needs is a deterministic workflow that pings a human at each stage. **An autonomous agent is the right answer only when the action space is genuinely open.** Most PE/VC tasks are not.

## 7. A 90-day adoption arc

If a firm decides to apply harness engineering end-to-end:

| Phase | Weeks | What ships |
|---|---|---|
| **Phase 0 — Single skill, no agent** | 1–2 | One `SKILL.md` (e.g. `find-comps`) invoked manually via Claude Code or a thin wrapper. Pure win, zero infra. |
| **Phase 1 — Fund memory** | 3–4 | `FUND.md` checked into the firm's docs repo; loaded by every analyst's Claude session. Drift starts being measurable. |
| **Phase 2 — Deal-room MCP** | 5–8 | First production MCP, against the deal-room store. Read-only. Now the agent has corpus access. |
| **Phase 3 — Permissions and audit** | 9–10 | Identity propagation, pre-tool hooks, immutable audit log. Compliance now signs off. |
| **Phase 4 — First scoped role** | 11–12 | The `sourcing-scout` role ships to one analyst; eval on historical deals; iterate. |
| **Phase 5 — Second role and review** | 13+ | `diligence-analyst`; quarterly governance cycle established. |

The order matters: **memory → MCP → permissions → role → eval**. Skipping permissions until the end is the most common failure mode and the most expensive to retrofit.

## 8. One-sentence summary

> A PE/VC harness is the same primitives as a coding harness — repo memory, rules, skills, hooks, MCP, subagents — bolted to a different corpus (deals, not files), defending different side effects (sends and writes, not destructive shell), and required to prove what it did (audit) in a way coding harnesses never are.

The discipline transfers. The work of transferring it is mostly in **identity, audit, and the deal-room MCP**. Everything else is section 11 with the labels swapped.
