# 11.11. Operational Concerns

> Companion to [11.10. Reference Implementation Tour](./11.10.%20Reference%20Implementation%20Tour.md). That note is what one person ships for one repo. This note is what changes when fifteen people contribute to that harness over two years.

Harness engineering as a personal practice is tidy. As a team practice it has all the failure modes of any shared config: drift, dead code, version skew, untested changes, mystery behavior. None of these are unique to AI; they just hit faster because the harness is doing more for you, more silently.

---

## 1. The five failure modes

Catalog of what actually breaks in a multi-developer harness:

| Failure | Symptom | Source |
|---|---|---|
| **Drift** | `AGENTS.md` says one thing, a rule says another. Agent picks inconsistently. | Two PRs edited adjacent surfaces; nobody noticed the conflict. |
| **Dead rules / skills** | Files in `.cursor/rules/` that haven't been loaded in months. | Codebase changed (framework swapped, folder renamed); nobody updated the rule. |
| **Vendor churn** | Hooks worked last quarter; new vendor version changed the payload shape. | Vendor surfaces evolve; configs lag. |
| **Behavioral regression** | "The agent used to know our naming convention, now it doesn't." | Someone trimmed `AGENTS.md` aggressively. |
| **Permissive permissions** | Agent did something destructive that shouldn't have been allowed. | `allow:` list was too broad; nobody reviewed. |

Each has a different fix; treating them as one problem is the mistake.

## 2. Versioning the harness

Treat the harness as **shipping configuration**, the same way you'd treat database migrations or CI YAML.

Concrete practices:

| Practice | Why |
|---|---|
| **Check everything in.** `AGENTS.md`, `.cursor/`, `.claude/` (except secrets). | A teammate's edit is reviewable, mergeable, revertable. |
| **PR review for harness changes.** Same approval bar as code. | Catches drift and contradictions before merge. |
| **Changelog entry for material changes.** "Harness: tightened deny list to block `Bash(curl * | bash:*)`." | Future archeology. |
| **Pin MCP versions.** `@upstash/context7-mcp@1.4.2`, not `@latest`. | Avoids the silent dependency-bump. |
| **Tag the harness with the repo.** When you release v2.0 of your app, the harness is at that tag too. | Reproduces a session against the harness as it was. |

> Architectural takeaway — the harness is code. The fact that it's markdown and JSON doesn't change that.

## 3. Drift detection

The most common drift: rules and memory contradict each other. Detect it.

Concrete checks (run in CI or a pre-commit hook):

1. **Frontmatter sanity.** Every `.mdc` rule has either `globs` or `description` (Auto-Attached or Agent-Requested), or `alwaysApply: true`. Reject ambiguous rules.
2. **No orphan globs.** For each rule's `globs`, confirm at least one file in the repo matches. A glob that matches nothing is dead config.
3. **No conflicting style claims.** A simple grep for known opposites: "use tabs" vs "use spaces", "snake_case" vs "camelCase", etc. Brittle but catches embarrassments.
4. **AGENTS.md size budget.** Fail PRs that grow `AGENTS.md` past N lines (e.g., 200). Force pushback to a rule or skill.
5. **Cross-link validity.** Every `(./path)` link in the harness resolves to a real file.
6. **MCP server existence.** For each entry in `mcp.json`, confirm the command resolves (e.g., `npx --no <pkg>` succeeds).

A 40-line shell script catches 80 % of drift. Better than nothing; do this first.

## 4. Eval — the long form

For a personal repo, eyeballing agent behavior is enough. For a team, "vibes" don't scale.

The minimum eval layer:

| Layer | What it tests |
|---|---|
| **Smoke tasks** | A small set of canonical prompts (e.g. "add a new note about X to section Y"). After every harness change, run them; compare outputs. |
| **Rule firing** | Inspect the loaded rules per-session in a sample run. Confirm the rule you expected to fire actually fired. |
| **Cost tracking** | Tokens per turn, turns per task. Alert on regressions. |
| **Subagent dispatch correctness** | When the parent should dispatch the validator, it does; when it shouldn't, it doesn't. |

You don't need a sophisticated eval framework on day one. A `tasks/` folder with prompt files and a wrapper script that runs them through `claude` or `cursor-agent` CLI is enough to start. See section 6 of this repo's [`6. Evaluation & Observability`](../6.%20Evaluation%20%26%20Observability/README.md) for deeper methodology.

> Lesson — the moment you start "improving" the harness without eval, you're flying blind. Even a minimal test suite catches the regressions you'd otherwise hear about a week later.

## 5. Observability

For an interactive agent in a single IDE, the IDE's own logs are usually enough. For:

- **Headless agent runs** (CI, scheduled jobs, automation).
- **Multi-user platforms** (you run agents on behalf of users).
- **Long-running tasks** (background work that should be inspectable).

…you need real observability. Hook in via [11.5 §10](./11.5.%20Hooks%2C%20Permissions%2C%20and%20Side%20Effects.md):

| Signal | Source | Useful for |
|---|---|---|
| **Per-turn tokens** | Vendor API / CLI output | Cost tracking, drift alarms |
| **Tool invocations** | PreToolUse hooks | Detecting unexpected tool patterns |
| **Hook duration** | Wall-clock around hook execution | Catching slow hooks |
| **Subagent count + cost** | Task tool tracing | Parallelism overhead |
| **Compaction events** | Vendor logs / `/cost` output | "Why did the agent forget?" debugging |

Wire to whatever you already have (Datadog, Honeycomb, OpenTelemetry, plain logs). The point isn't the backend; it's that you can answer "what did the agent do during session X" weeks later.

## 6. Multi-developer governance

When more than one person edits the harness, you need shared norms.

A useful charter (adapt to your team):

1. **Ownership.** One person owns `AGENTS.md`. Two people minimum review changes to it. The Bus Factor on `AGENTS.md` is not 1.
2. **Categories.** Decide where things go (memory vs. rule vs. skill vs. command) once. Document the decision tree in `AGENTS.md`. Enforce in review.
3. **Renames are migrations.** Moving a skill or renaming a slash command breaks anyone whose muscle memory uses the old name. Treat with the care of a database migration: deprecation period, alias, then remove.
4. **Personal vs. shared.** Encourage user-scoped overrides (`~/.claude/`, `~/.cursor/`) for individual preferences. Reserve repo-scoped config for what *everyone* on the team should have.
5. **Onboarding doc.** New contributors get a one-page guide that points at `AGENTS.md`, `11. Harness Engineering/README.md`, and the team's smoke-test process.

## 7. The drift-on-vendor-update problem

Cursor ships a new version. Claude Code changes its hook payload. Your hooks break, silently or loudly.

Mitigations:

| Tactic | What it buys |
|---|---|
| **Pin vendor versions where possible.** Cursor and Claude Code both let you stay on a specific minor in enterprise contexts. | Stability, at a velocity cost. |
| **Smoke tests run on vendor update.** When CI detects a new `cursor` or `claude` version, re-run the smoke task suite. | Detect breakage at update-time, not mid-task. |
| **Wrap vendor-specific I/O in adapters.** Like this repo's `.claude/hooks/check-references.sh` wrapping a shared `.cursor/hooks/check-references.sh`. | Localize churn to small adapter files. |
| **Subscribe to vendor changelogs.** Cursor blog, Anthropic engineering blog, Codex changelog. | Anticipate breaking changes. |
| **Vendor diff matrix as a living doc.** Like [11.9](./11.9.%20Vendor%20Diff%20Matrix.md). Date it. Re-validate periodically. | Institutional memory. |

> Lesson — every coupling to vendor specifics is a future maintenance task. Push couplings to the edges of your harness (one or two adapter files) so the core stays stable.

## 8. CI / pre-commit integration

The harness shapes interactive agent behavior. CI is the *non-interactive* sibling: runs in the background, catches what the interactive agent let slip.

Concrete checks worth in CI for the harness itself:

| Check | Tool |
|---|---|
| `AGENTS.md` exists and is non-empty | `test -s AGENTS.md` |
| All `.mdc` rules have valid frontmatter | A small Python / shell script |
| Hook scripts are executable | `find … -name '*.sh' -not -executable` returns nothing |
| Hook scripts pass `shellcheck` | `shellcheck .cursor/hooks/*.sh .claude/hooks/*.sh` |
| MCP `*.json` is valid JSON | `jq empty .cursor/mcp.json` |
| Cross-references inside the harness resolve | Custom |
| Smoke tasks complete successfully | Custom (call agent CLI) |

For a notes repo, pre-commit suffices. For an app, GitHub Actions or equivalent runs the same checks on every PR.

## 9. Secret governance

[11.5 §6](./11.5.%20Hooks%2C%20Permissions%2C%20and%20Side%20Effects.md) covered secret hygiene. The operational angle:

- **A `gitleaks` or `trufflehog` scan on the harness itself.** Same as code. A leaked API key in `.cursor/mcp.json` is just as compromised as one in `src/`.
- **Periodic permission review.** Quarterly: walk through `permissions.allow`. Anything that "doesn't need that anymore"?
- **Bind keys to an identity, not to a workspace.** Claude Platform added **personal keys** and **service account keys** on 2026-08-27: each acts as a specific user or service account, carries that account's permissions, and **stops working when the account is removed from the org**. Legacy workspace keys have no such lifecycle — they outlive the person who made them. For a fleet, a service account key per agent is the difference between "revoke one key" and "rotate everything and hope." This is the same key-identity gap the [MCP roadmap](../5.%20AI%20Agents%20%26%20Tool%20Use/The%20Post-Stateless%20MCP%20Roadmap%20%E2%80%94%20Agent%20Identity%2C%20Progressive%20Discovery%2C%20and%20One%20Transport.md) names at the protocol layer, being closed one vendor at a time.
- **Deny list as positive control.** A deny list is testable: try to do the thing; assert the harness blocks it.

## 10. Killing a harness primitive

Eventually you'll want to remove something. A rule that's no longer needed, a skill that nobody uses, an MCP that's been replaced by a built-in.

The discipline:

1. **Find its references.** `grep -r <name> .` across the harness.
2. **Update references first.** Move callers to the replacement or to nothing.
3. **Soft-remove.** Mark deprecated in the file (`description: "[DEPRECATED] …"`) for one release cycle.
4. **Hard-remove.** Delete the file.
5. **Announce.** Changelog entry; team channel.

The same loop as removing a public API.

## 11. Maturity ladder

A rough progression of harness maturity:

| Stage | Marker | Investment |
|---|---|---|
| **0. No harness** | No `AGENTS.md`. Agent guesses. | Free; pays in papercuts. |
| **1. Constitution only** | `AGENTS.md` exists. Agent has voice and conventions. | A few hours. |
| **2. Configured surfaces** | Rules, skills, commands, hooks all in use. | Days. |
| **3. Versioned & reviewed** | Harness changes go through PR review. Drift checks in CI. | Weeks. |
| **4. Evaluated** | Smoke tests on every harness change. Cost tracking. | Months (with team buy-in). |
| **5. Observable** | Production-grade tracing of agent runs. Audit logs. | Sustained investment; often paired with platform work. |

Most personal repos sit at stage 2. Most healthy team repos at stage 3–4. Anyone offering an agent as a product needs stage 5.

## 12. Where the harness executes — managed vs. self-hosted

Everything above assumes the harness runs somewhere you don't have to think about — a laptop, or the vendor's managed compute. That assumption is now a choice. As of 2026-08-06, Claude Code offers **self-hosted environments** (public beta, Team and Enterprise plans): sessions started from web, mobile, desktop, the CLI, or a scheduled routine execute on infrastructure the organization provisions — a fleet of "runners" — instead of Anthropic's hosted sandboxes.

| | Managed (default) | Self-hosted |
|---|---|---|
| **Repo checkout, build artifacts, secrets** | On Anthropic's hosted sandbox | Stay on your infrastructure |
| **Prompts, model responses, tool results, transcripts** | Sent to Anthropic for inference | Still sent to Anthropic for inference — this doesn't change |
| **Network reachability** | Only what the sandbox can reach | Internal services, databases, private registries, on the org's own network |
| **Customization** | Fixed image | Pre-install compilers, SDKs, internal CLIs into the runner image |
| **Who owns it** | Anthropic | A platform or dev-productivity team — provisioning, image builds, updates, runner capacity |

Two runner modes: **fixed** (a standing pool of runners) or **on-demand** (an orchestrator launches a runner per session, tears it down after). Sessions from any surface route to the same environment, and each checkout is isolated so concurrent developers don't collide.

> Lesson — self-hosting moves *where code executes*, not *where inference happens*. Transcripts and tool payloads still leave the network for the model call. If the actual requirement is "nothing about this codebase reaches a third party," self-hosted environments don't satisfy it on their own; they only satisfy "artifacts and secrets never leave our network." Read the data-flow diagram before promising compliance based on the feature name.

## 13. Vendor-managed audit trails — the Compliance API

§5 above treats observability as something *you* wire up. The vendor-managed alternative: Claude Platform's **Compliance API** (GA since 2026-03-30, gated behind account-team enablement) gives admins programmatic access to org-wide audit logs — admin/system actions (workspace changes, API key creation) and resource activity (file operations, skill modifications) — without building a tracing pipeline.

As of 2026-08-11, coverage extended to session transcripts for **Cowork** (Claude, Claude Desktop, Claude Mobile) and **Claude Code** (CLI, Claude Desktop), in beta for Claude Enterprise. Notably absent from that beta: Claude Code on web, Claude Code via the Claude Platform, and sessions run on Bedrock or Vertex AI — check the coverage table before relying on it for a specific surface. The API excludes inference activity itself (no prompt/completion content); it's audit metadata and session transcripts, not a replacement for the per-turn token/tool tracing in §5.

As of **2026-08-26** the session endpoints came out of beta for Cowork and Claude Code, and the *local* session endpoints (sessions on users' own machines) extended in beta to **Claude Science** (`product_surface: claude_science`) and **Claude for Microsoft 365** in Excel, PowerPoint, Word, and Outlook (`office_agents*`). Same Compliance Access Key, same `read:compliance_user_data` scope. The same release moved the **Admin API** into the `ant` CLI and every first-party SDK under `client.beta.organization` — org info, members, invites, workspaces, API keys, rate limits, service accounts, workload identity federation, and CMEK. Usage/cost reports and the Claude Enterprise user-management endpoints stay curl-only.

> Why it matters: the audit surface is now shaped like the *product surface*, not like the API. Every place a person can start an agent — CLI, desktop, a Word document — is a separate `product_surface` you either enrolled or did not. Enumerate them against your org's actual usage rather than assuming "we turned on the Compliance API" means full coverage.

> Architectural takeaway — a vendor-managed compliance API and your own hook-based tracing aren't substitutes for each other. The Compliance API answers "who did what, when, across the org" for eDiscovery and SIEM ingestion. Your own §5 instrumentation answers "why did this specific session behave this way." Stage-5 maturity (§11) increasingly means both, not one or the other.

## 14. Mental model — one-sentence summary

> Operational harness engineering is treating your `AGENTS.md`, rules, hooks, and MCP config as exactly the kind of artifact you'd never deploy without review, testing, and versioning — because that's what they are.

The seductive part of harness engineering is the configuration surface. The boring part — and the part that separates a "neat config" from a *durable* one — is everything in this note.
