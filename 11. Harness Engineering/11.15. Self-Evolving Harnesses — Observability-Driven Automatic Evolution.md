# 11.15. Self-Evolving Harnesses — Observability-Driven Automatic Evolution

> Companion to [11.14. Tuning the Harness, Not the Model](./11.14.%20Tuning%20the%20Harness%2C%20Not%20the%20Model%20%E2%80%94%20The%20Harness%20as%20an%20Optimization%20Surface.md).
> 11.14 argues the harness is an optimization surface and shows a *human* running
> the tune-screen-repeat loop. This note is the automated cousin: a closed loop
> where an agent edits the harness, predicts the effect, and keeps or reverts the
> change based on measured outcomes — the base model frozen throughout. Evidence
> is the *Agentic Harness Engineering* (AHE) work from Fudan/Peking University and
> Qiji Zhifeng.

11.14 established the thesis: most agent failures are scaffolding failures, and
tuning the harness is ~10x cheaper than upgrading the model. The natural next
question is whether the tuning loop itself can be automated. AHE answers yes,
but the interesting part is *what it takes to make automation safe*. You cannot
just hand an agent write-access to its own prompts and tools and tell it to
"improve." Without structure, the loop degrades into unfalsifiable prose edits
and silent regressions. AHE's contribution is the three kinds of **observability**
that turn harness self-editing from a wish into a measurable, reversible process.

---

## 1. Why naive self-improvement fails

The obvious design — let the agent read its failures and rewrite its own system
prompt — has three failure modes that compound:

| Failure mode | What goes wrong |
|---|---|
| **Opaque action space** | The agent doesn't know what it's allowed to change or how to change it reversibly. Prompt, tool, and control-flow edits blur into one text blob. |
| **Evidence overflow** | Real trajectories are millions of tokens. Dumped raw into context, they drown the signal; summarized too aggressively, they lose the root cause. |
| **Unfalsifiable edits** | "I improved the prompt" is a claim with no test. Regressions land silently because no one wrote down what the edit was *supposed* to do. |

> **Why it matters:** each of these is the automated version of a discipline a
> careful human already applies — version control, log triage, a hypothesis per
> change. AHE's design is essentially "make those three disciplines machine-legible."

---

## 2. The three observability pillars

AHE decomposes the problem into three observability layers, each attacking one
failure mode above.

### 2.1 Component observability — an explicit, reversible action space

The harness is exposed as **seven editable component types**, each mounted as a
file at a fixed location:

1. System prompt — behavioral rules and task framing
2. Tool description — the interface the model sees
3. Tool implementation — the executable backend
4. Middleware — execution guards and recovery hooks
5. Skill — reusable action sequences
6. Sub-agent configuration — auxiliary agent setup
7. Long-term memory — lessons persisted across tasks

Because every component is a file, every edit is a git-level diff and every
rollback is a git-level revert. The action space is explicit (the agent knows
exactly what it can touch) and reversible (nothing is a one-way door).

> **Architectural takeaway:** file-as-component is the same move as
> file-system-as-memory in [11.8](./11.8.%20Context%20Engineering%20in%20the%20Harness.md).
> Making the harness a set of files is what makes automated editing tractable —
> the diff *is* the audit log.

### 2.2 Experience observability — distilling trajectories into layered evidence

Raw trajectories are too large to reason over. AHE runs them through an "Agent
Debugger" that treats each trajectory as a navigable file environment and
produces a **progressive-disclosure hierarchy**:

```text
benchmark overview        ← aggregate failure patterns across all tasks
    └── per-task report    ← root cause, grounded in pass/fail status
            └── raw trace  ← full trajectory, for verification / drill-down
```

The evolving agent reads the top layer, drills into the reports that matter, and
only opens raw traces to verify a hypothesis. This is the same **compaction +
retrieval** pattern from context engineering, applied to the harness's own logs
instead of to task documents.

### 2.3 Decision observability — the falsifiable-edit contract

This is the load-bearing idea. Every edit ships with a **self-declared
prediction**: which failing tasks it should fix, and which passing tasks it
might put at risk. That prediction is written into a change manifest *before*
the next evaluation round.

After the next round, the loop compares predicted deltas against observed
task-level deltas. An edit whose prediction fails to hold is reverted at file
granularity.

> **Lesson:** this converts each edit from *post-hoc justification* ("I changed
> the prompt because it seemed better") into a *falsifiable contract* ("this edit
> fixes tasks 12, 40, 71 and risks 8"). An edit that doesn't do what it claimed
> is garbage-collected automatically — the loop cannot accumulate confident-but-wrong
> changes, which is exactly how naive self-improvement rots.

---

## 3. The evolution loop

The loop runs a fixed sequence each iteration, over a frozen base model:

```text
rollout        run the current harness over the eval set, capture trajectories
   ↓
clean          normalize / isolate trajectories into per-task file environments
   ↓
attribute      score the PREVIOUS manifest's predictions; revert edits that missed
   ↓
distill        build the layered evidence corpus (§2.2)
   ↓
edit           Evolve Agent adds / modifies / removes components + writes predictions
   ↓
commit         version the edits and the new manifest; loop
```

The key structural choice: **attribution happens before the next edit**, so the
loop always cleans up the prior round's mistakes before compounding new ones.
The harness that survives is the intersection of edits that repeatedly kept
their contracts.

---

## 4. What the evidence shows

On Terminal-Bench 2, over ten iterations with a fixed model, AHE lifted pass@1
from a **69.7% seed to 77.0%**, beating a human-designed CLI harness (71.9%) and
two prior self-evolving methods (ACE 68.9%, Training-Free GRPO 72.3%). Gains
concentrated on the harder tail.

Two results matter more than the headline number:

| Result | Number | Why it's the interesting one |
|---|---|---|
| **Frozen-harness transfer** | 75.6% on SWE-bench-verified with **32% fewer tokens** than a baseline, *no re-evolution* | The evolved harness encodes general engineering structure, not benchmark overfit. |
| **Cross-model transfer** | +2.3 to +10.1 pp when the frozen harness is dropped onto other model families | A harness evolved on model A improves model B. Bigger lift on models further from saturation. |

Component ablations are the practitioner's takeaway:

- **Long-term memory** carried the most standalone value (+5.6 pp), then **tools**
  (+3.3 pp), then **middleware** (+2.2 pp).
- **System prompt edits alone regressed** (−2.3 pp).

> **Architectural takeaway:** structural components (memory, tools, middleware)
> transfer; prose strategy (system-prompt wording) does not, and optimizing it in
> isolation can hurt. This is a direct rebuke to the instinct that "self-improvement"
> means an agent rewriting its own instructions. The durable wins are in the
> *mechanism* layer, not the prose layer.

---

## 5. When this is worth it — and when it isn't

Self-evolving harnesses are not free. Each iteration is a full rollout over an
eval set plus a distillation and edit pass — expensive, and only as good as the
eval that grounds it.

| Use it when | Skip it when |
|---|---|
| You have a **capability-resolved eval** (per [11.14 §2](./11.14.%20Tuning%20the%20Harness%2C%20Not%20the%20Model%20%E2%80%94%20The%20Harness%20as%20an%20Optimization%20Surface.md)) that scores tasks individually — the loop needs task-level deltas to attribute edits. | You only have an aggregate score. Without task-level grounding, predictions can't be falsified and the loop rots. |
| The harness surface is **large and structured** — many tools, middleware, skills — so there's real search space. | The harness is a single prompt. Human tuning (11.14) is faster and cheaper. |
| You'll run the agent over **many tasks over time**, so amortizing evolution cost makes sense. | One-off or low-volume agents. |

> **Lesson:** the eval is the ceiling. A self-evolving harness cannot discover
> quality your eval can't measure — it will happily optimize toward whatever the
> eval rewards, including its blind spots. The prerequisite for automation is the
> same per-capability eval that made *manual* tuning work in 11.14; automation
> raises the stakes on getting that eval right.

## 6. The generalization critique, and AHE's answer to it

Two follow-on papers, both 2026, sharpen the picture above.

**The critique.** *Rethinking the Evaluation of Harness Evolution for Agents*
(submitted 2026-07-14) points at a methodology flaw common to AHE-style work:
searching for a harness configuration and reporting final performance *on the
same public benchmark* conflates two different things — a better harness, and
extra search iterations the comparison never controlled for. Under matched
search/inference budgets and held-out tasks, the authors found that "automatic
harness evolution does not consistently outperform simple test-time scaling
methods and exhibits limited generalization." In other words: some of the
published gains may be the same benchmark rewarding its own search process,
not the harness structurally improving.

**The answer.** *HarnessCompass* (submitted 2026-08-03) is a direct response —
it targets exactly the overfitting failure mode the critique names. It adds
three things on top of AHE's loop: (1) **global constraints** that restrict
edits to task-agnostic changes, so the search can't quietly specialize to the
eval set; (2) **proactive feedback** — the agent reports on its own harness
usage, not just trajectory-derived signal; (3) **component-wise optimization**
that tunes harness pieces separately before unifying them, reducing cross-edit
interference. On SWE-bench Verified it lifted pass@1 from 54% to 66% in five
iterations, and the paper reports it generalizes to held-out tasks and other
model families more reliably than the prior AHE method.

| Claim | Who tests it |
|---|---|
| "Evolved harnesses transfer to held-out tasks and other models" | AHE's own frozen-harness and cross-model transfer results (§4) — self-reported |
| "That transfer claim needs a fair baseline to mean anything" | The July 2026 critique — an independent check on the whole method family |
| "Here's a version built specifically to survive that check" | HarnessCompass — built after and in response to the critique |

> **Architectural takeaway:** the critique doesn't invalidate self-evolving
> harnesses — it raises the evidentiary bar for believing a "generalizes"
> claim. Before trusting an evolved harness in production, ask whether it was
> validated against a held-out task set and a matched-budget baseline, not
> just against its own before/after on the tasks it was evolved on. That is
> the same discipline as [11.14 §2](./11.14.%20Tuning%20the%20Harness%2C%20Not%20the%20Model%20%E2%80%94%20The%20Harness%20as%20an%20Optimization%20Surface.md)'s
> capability-resolved eval, applied one level up: to the *evaluation of the
> evolution process itself*.

## 7. What a shipped version looks like — Warp's two-skill loop

Everything above is research. Warp — an agentic development environment — runs a
stripped-down version of the same loop in production, described in an Anthropic
case study on 2026-08-26. It is worth studying because of what it *drops*.

The architecture is two skills with human feedback in between:

- **Base skill** — the domain knowledge and instructions the working agent runs
  on. Warp's PR review agent loads this plus the diff to produce its review.
- **Improver skill** — a scheduled observer, not a per-task one. It pulls recent
  tasks that carried human feedback, summarizes them into structured signals,
  and proposes edits to the base skill file.

Feedback enters at the junction. A thumbs-down is nearly useless; a specific
correction — "your suggested rename conflicts with our naming convention" — is
what makes an edit derivable. Warp's stated point is that agents are very good
at editing file-based skills, so the improver's output is a normal diff that
goes through normal code review before it merges.

| | AHE (§3) | Warp |
|---|---|---|
| Reward signal | pass/fail over a scored eval set | human corrections on real tasks |
| Cadence | every iteration, full rollout | scheduled batch over accumulated feedback |
| Edit surface | seven component types (§2.1) | the base skill file |
| Gate on an edit | attribution against a prediction the loop wrote (§2.3) | a domain expert's code review |
| Revert path | automatic revert when the prediction misses | git |

Three design choices carry the weight:

1. **Failures are grouped by root cause, not patched individually.** Warp
   categorizes by failure mode — wrong tool selection, hallucinated file path —
   because one prompt edit can clear fifty failures when the grouping is right.
   This is AHE's *distill* step done by hand.
2. **The improver is out of band.** Because it runs on a schedule rather than
   per-task, a bad edit cannot take effect mid-task, and the batch carries enough
   evidence to tell a pattern from one annoyed reviewer.
3. **The gate is a human, not an eval.** §5 says the eval is the ceiling. Warp
   swaps the eval for a domain expert — much cheaper to stand up, and it does not
   rot as the eval's blind spots drift. The cost is that it does not scale, and it
   only catches regressions the reviewer thinks to look for.

Note the apparent contradiction with §4: Warp's loop edits the *prose* layer,
the one AHE's ablation showed regressed on its own (−2.3 pp). The difference is
the signal. AHE's prose edits were derived from trajectories by another agent;
Warp's are derived from a domain expert saying exactly what was wrong, and a
human refuses the bad ones before they land. Prose edits do transfer — when the
gradient comes from someone who knows the domain.

> **Architectural takeaway:** the load-bearing substrate here is that skills are
> *files under version control*. Three of the disciplines AHE had to build from
> scratch — an explicit action space, reversible edits, a durable record of what
> changed and why — Warp gets from git for free. If your harness lives as prose
> in a database or a vendor console, you have to build all three yourself before
> any self-improvement loop is safe. This is the same trade
> [11.16](./11.16.%20Harness%20Engineering%20for%20Incident%20Response%20%E2%80%94%20The%20On-Call%20Agent.md)
> makes: the cheapest self-evolving harness that holds up is one where the
> expensive judgment stays human and the mechanism stays a diff.
