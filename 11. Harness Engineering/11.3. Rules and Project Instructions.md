# 11.3. Rules and Project Instructions

> Companion to [11.2. Repo Memory — AGENTS.md & Friends](./11.2.%20Repo%20Memory%20%E2%80%94%20AGENTS.md%20%26%20Friends.md). Repo memory is unconditional and always-loaded. Rules are conditional — they load only when their trigger matches. The whole point is to *not pay context tokens* for instructions that don't apply this turn.

If `AGENTS.md` is the constitution of your harness, **rules** are the statutes — narrower, more specific, scoped to a file pattern or an explicit invocation. The most useful and most misused primitive in modern coding agents.

---

## 1. The four activation modes

Every rules system in current coding agents (Cursor, Claude Code project memory, Continue, OpenCode) reduces to four modes:

| Mode | Trigger | Always loaded? | Use for |
|---|---|---|---|
| **Always** | None — every turn | Yes | Tiny, universal rules. Style guide, vocabulary bans. |
| **Auto-Attached** | File-pattern match (`globs`) | Only when matched | "When editing TypeScript, prefer …" |
| **Agent-Requested** | Agent decides based on `description` | Only when agent pulls | Multi-step procedures that need triggering by intent |
| **Manual** | Explicit `@rule-name` mention | Only on demand | Rare/expert workflows; templates |

Cursor encodes this in `.cursor/rules/*.mdc` frontmatter:

```yaml
---
description: <required for Agent-Requested>
globs: ["**/*.ts", "**/*.tsx"]      # required for Auto-Attached
alwaysApply: true                   # required for Always
---
```

Combinations:

| Activation | `alwaysApply` | `globs` | `description` |
|---|---|---|---|
| Always | `true` | optional (scopes Always) | optional |
| Auto-Attached | `false` | required | optional |
| Agent-Requested | `false` | absent | required |
| Manual | `false` | absent | absent |

Claude Code project memory is simpler — it's all "Always" — but compensates with per-folder memory ([11.2](./11.2.%20Repo%20Memory%20%E2%80%94%20AGENTS.md%20%26%20Friends.md#7-per-folder-memory)) for the Auto-Attached equivalent, and skills ([11.4](./11.4.%20Skills.md)) for the Agent-Requested equivalent.

## 2. The scoping discipline

The single most important question when writing a rule:

> **Does this rule apply when the agent is editing every file in the repo?**

- **Yes → it's not a rule, it's memory.** Move to `AGENTS.md`.
- **No → it's a rule.** Specify `globs` (Auto-Attached) or `description` (Agent-Requested).

Most rule sprawl comes from treating rules as "things I forgot to put in `AGENTS.md`". They shouldn't be. A rule is *narrower than memory by construction*.

> Architectural takeaway — rules are conditional context injection. If every rule fires every turn, you've reinvented `AGENTS.md` with more files.

## 3. What rules are good for

The canonical use cases:

| Use case | Mode | Example |
|---|---|---|
| Per-language style | Auto-Attached, `globs: ["**/*.py"]` | "Use type hints; prefer `pathlib.Path` over `os.path`" |
| Per-framework conventions | Auto-Attached, `globs: ["app/**/*.tsx"]` | "Server components by default; mark `'use client'` only when needed" |
| Per-directory contract | Auto-Attached, `globs: ["src/db/**"]` | "Migrations are append-only; never edit a shipped migration" |
| Codebase-specific workflow | Agent-Requested, with `description` | "When the user asks to add a new API endpoint, follow these steps…" |
| Style hard rule | Always (small) | "No emoji decoration"; "no double-blank lines" |
| Template scaffold | Manual | `@new-rfc` to pull a Request-for-Comments template |

What rules are **not** good for:

- Long prose explaining *why* something matters. Rules are short and prescriptive; rationale lives in commit messages, ADRs, or `AGENTS.md`.
- Information the agent could derive from the codebase by reading one file. If you can say "look at `src/foo.ts` for the pattern", do — don't restate.
- Anything secret. Rules are checked into git.

## 4. Anatomy of a good rule

This repo's [`.cursor/rules/references-section.mdc`](../.cursor/rules/references-section.mdc) as a worked example:

```markdown
---
description: Enforce the trailing References section on numbered curriculum notes.
globs: ["[0-9]*/[0-9]*.md", "[0-9]*/*[0-9].*.md"]
alwaysApply: false
---

# References Section — Required Format

(One short paragraph stating the scope.)

## Format
(Canonical example. Show, don't tell.)

## Validation
(Bullet list of checks. No prose.)

## Source-of-truth pointer
(Link to the SKILL.md that owns the deeper logic.)
```

Five hallmarks of a good rule:

1. **Scoped frontmatter.** `globs` or `description`, never both.
2. **One responsibility.** One file = one concern. Don't bundle "style + naming + references" into one mega-rule.
3. **Show, don't tell.** A canonical example beats five sentences of explanation.
4. **Defers to a skill** when the workflow has more than three steps. Rules state *what*, skills state *how*.
5. **Length budget.** A rule that's longer than ~80 lines is probably a skill in disguise.

## 5. The skill / rule boundary

This trips up most teams. Both rules and skills inject conditional context. The rule of thumb:

| Question | Rule | Skill |
|---|---|---|
| Trigger is a file-pattern match | yes | — |
| Trigger is an intent ("create a new note") | — | yes |
| Content is < 80 lines and prescriptive | yes | — |
| Content is a multi-step procedure with branching | — | yes |
| Agent needs to *do* vs *avoid* something | avoid | do |
| Shared logic across rules and skills | references skill | owns it |

The single-source-of-truth pattern: if a rule and a skill cover the same domain, the rule states the contract (one paragraph + canonical example) and the skill owns the procedure. The rule ends with: `Detailed workflow: see [.claude/skills/<name>/SKILL.md](...)`.

## 6. Anti-patterns

Catalog of bad rules seen in the wild:

| Smell | Why it's bad | Fix |
|---|---|---|
| **The wall.** 500-line rule with everything in it. | Always-loaded → context bloat. Hard to maintain. | Split by concern. |
| **The restatement.** Rule duplicates `AGENTS.md`. | Drift inevitable. | Move all of it to memory or all of it to the rule. |
| **The vague description.** `description: "Coding rules"`. | Agent-Requested never fires because router can't match. | Be specific: "When writing or refactoring TypeScript React components". |
| **The dead glob.** `globs: ["**/*.foo"]` for a pattern no file matches. | Silent — rule never loads. | Audit globs. Add a check. |
| **The contradiction.** Rule says "use tabs", memory says "use spaces". | Agent picks one inconsistently. | Pick one source of truth; reference from the other. |
| **The narrative.** "We had a problem in 2024 where…" | Cost tokens, not behavior. | Rationale belongs in commit messages and ADRs, not rules. |
| **The secrets leak.** `API_KEY=sk-…` in a rule for the agent to "use when calling …". | Checked into git. Public. | Use env vars and `.env`; rule says "read from env". |

## 7. Auditing rules

Rules drift the same way prompts drift. Adopt a periodic audit:

1. **List active rules.** `ls .cursor/rules/`.
2. **For each, ask:**
   - Does it still apply? (Maybe the framework was removed.)
   - Does its glob actually match files in the repo today?
   - Does it contradict any other rule or `AGENTS.md`?
   - Is it < 80 lines?
3. **Delete aggressively.** A stale rule is worse than no rule.

[11.11. Operational Concerns](./11.11.%20Operational%20Concerns.md) goes deeper on drift detection across the whole harness.

## 8. Cursor-specific mechanics

Cursor's `.mdc` rule files have a few specific behaviors worth knowing:

- **`alwaysApply: true` + `globs: [...]`** is a scoped Always rule — always loaded for files matching the glob. Useful for hard repo-wide rules that only apply to certain extensions (`*.md`).
- **`description`** routes the rule to the agent's "rule selector" — set it concretely. "When creating a new …" beats "Coding rules".
- **MDC link syntax** uses `[label](mdc:relative/path)` for in-Cursor navigation. Plain markdown links also work; `mdc:` enables IDE-aware previews.
- **Nested rule files** (`packages/foo/.cursor/rules/*.mdc`) apply only when the agent is working in that subtree. Good for monorepos.

## 9. Claude Code-specific mechanics

Claude Code doesn't have `.mdc` rules per se. The equivalents:

- **Per-folder `CLAUDE.md`** (or `AGENTS.md`) for directory-scoped instructions.
- **`@`-imports** in memory files to pull in shared content: `@.claude/rules/style.md`.
- **Skills** (`.claude/skills/<name>/SKILL.md`) for the Agent-Requested mode.
- **`/memory` command** to edit memory interactively.

The skill router is more discoverable than a `.mdc` rule list, but you lose precise glob-based triggering. Most teams supplement Claude Code with `AGENTS.md` per folder where Cursor would use `.cursor/rules/`.

## 10. Sizing the rules folder

A healthy `.cursor/rules/` directory tends to look like:

| Repo type | Typical count | Typical sizes |
|---|---|---|
| Small repo (one language) | 2–5 rules | 20–80 lines each |
| Mid-size monorepo | 8–20 rules | nested per package |
| Large platform repo | 30+ rules | strict scoping, periodic audit mandatory |

If you have 50 always-applied rules, you have an `AGENTS.md` problem. If you have 200 file-scoped rules, you may have a real codebase — audit, deduplicate, and accept the cost.
