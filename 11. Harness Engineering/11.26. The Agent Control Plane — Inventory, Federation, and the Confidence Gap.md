# 11.26. The Agent Control Plane — Inventory, Federation, and the Confidence Gap

> Deepens [11.11. Operational Concerns](./11.11.%20Operational%20Concerns.md), which asks what changes when more than one person owns a harness. This note asks what changes when nobody owns the *list*.

Every primitive in notes 11.1 through 11.25 is **per-agent**. Repo memory, rules, skills, hooks, permissions, tool architecture, lockfiles — each one presumes you are holding a specific agent and shaping it. None of them answers the question an organization actually gets asked first: *what is running, who owns it, and who can turn it off.*

That question is the **agent control plane** — a fleet-level registry and policy layer sitting above every agent, regardless of which framework built it or whose runtime executes it. Forrester began tracking it as a distinct category in Q2 2026; WSO2 shipped an Apache-2.0 reference implementation to GA on 2026-09-15. The category is worth understanding not because the products are mature — they are not — but because it exposes a governance boundary that harness engineering, as practiced, does not cover, and because the survey data around it contains one finding that generalizes well beyond agents.

---

## 1. Why the harness does not scale to the estate

A harness is a configuration surface you apply to an agent you are already holding. It has no opinion about agents you are not holding. Three properties of agent deployment break that assumption faster than they broke it for services:

| Property | Service-era analogue | Why agents are worse |
|---|---|---|
| Creation cost | A service needs a repo, a pipeline, an on-call rotation | An agent is a prompt, a model endpoint, and a tool list — a competent non-engineer can ship one in an afternoon |
| Framework spread | Mostly one language per team | LangChain, CrewAI, Strands, Microsoft Agent Framework, and hand-rolled loops coexist in the same org by month three |
| Behavioral stability | Same input, same output | Nondeterministic by construction — there is no stable "who" to know |

Gartner's projection — from fewer than 15 agents per Fortune 500 enterprise in 2025 to over 150,000 by 2028 — is a marketing number in the sense that nobody can verify it, but the *shape* is the point. Agent count grows like script count, not like service count, while the governance model most orgs apply to it was built for service count.

> Architectural takeaway: the harness is the unit of *behavior* control. The control plane is the unit of *existence* control. Confusing them produces an org with beautifully tuned `AGENTS.md` files and no idea how many agents it runs.

## 2. The five planes a control plane has to unify

The recurring capability list across shipped implementations resolves to five concerns, each of which most enterprises already own a tool for — bought separately, for a different job:

| Concern | Question it answers | Pre-existing tool it displaces | Why the old tool is insufficient |
|---|---|---|---|
| Registry / inventory | What exists? | CMDB, service catalog, spreadsheet | No discovery path for a thing created outside a pipeline |
| Identity | Who is acting, on whose behalf? | IAM (human and service accounts) | An agent is neither; delegation and token exchange have no home |
| Policy / guardrails | What may it access, and what may it emit? | API gateway, DLP | Enforces at the request edge, not at the MCP or tool-call boundary |
| Observability / eval | What did it do, and how well? | APM, LLM tracing | Tracks model-level latency and cost, not trajectory-level correctness |
| Lifecycle / runtime | Which version, in which stage, and how do I stop it? | CI/CD, Kubernetes | Promotion criteria assume determinism |

The strong version of the argument is not "you need a new tool." It is that these five are **coupled through the agent's identity**, and splitting them across five products means no single system can answer "agent X did Y on behalf of Z under policy P at version V" — which is the only form in which an audit question is ever actually asked. Note 8.7 develops the identity half of this; note 8.5 develops the authorization half. The control plane is the claim that they, plus inventory and lifecycle, have to sit in one system of record.

## 3. Framework-agnosticism is the load-bearing constraint

The design decision that determines whether a control plane survives contact with a real org is where it attaches. Two options:

```text
  (a) Framework-coupled                (b) Standard-seam
  ┌──────────────────────┐             ┌──────────────────────┐
  │ Control plane        │             │ Control plane        │
  └──────┬───────────────┘             └──────┬───────────────┘
         │ framework SDK hooks                │ OTel spans
         │ (per-framework adapter)            │ MCP call boundary
         ▼                                    │ OAuth2 token exchange
  ┌──────────────┐                            ▼
  │ LangGraph    │  ← each new framework   ┌──────────────────┐
  └──────────────┘    needs an adapter     │ any framework    │
                                           │ that emits OTel  │
                                           └──────────────────┘
```

Option (a) is faster to build and dies the first time a team adopts a framework the vendor has not written an adapter for. Option (b) constrains you to instrumentation every framework already emits — which today means OpenTelemetry for traces, MCP for the tool-call boundary, and OAuth2 for delegation. That is a thin seam, and it is thin on purpose.

> Why it matters: the whole point of a governance layer is that it outlives the thing it governs. If adopting a new agent framework requires rebuilding the policy layer underneath it, the policy layer is not governance — it is part of the framework, and it will be skipped by the first team in a hurry.

This is the same argument [11.7](./11.7.%20Tools%20and%20MCP.md) makes for MCP at the tool boundary, applied one level up. It is also why the control-plane category and the MCP specification are converging: MCP is the only place where a tool call from *any* framework is legible to an outside observer.

## 4. The confidence gap, measured

Harness surveyed 700 enterprises already running agents in production or live pilot (Sapio Research, July 2026), asking confidence and then control, domain by domain. The confidence answers all landed between 74% and 77%. The controls did not:

| Domain | Confident | Has the control | Gap |
|---|---|---|---|
| Testing — "our evals would catch a production-impacting failure" | 74% | 19% have a gate that blocks every bad release | 55 pts |
| Rollback — "we could disable a misbehaving agent in under 15 minutes" | 76% | 33% have an instant kill switch | 43 pts |
| Inventory — "we have a complete inventory and no shadow AI" | 77% | 44% run active discovery tooling | 33 pts |
| Security — "our agents are secure end to end" | 75% | 23% have a dedicated agent security layer | no correlation |
| Cost — "we have a complete picture of cost per agent" | 74% | 60% overran budget anyway | not a gap |

Security is the interesting negative result: the confident group experienced agent-related security incidents at 88%, against 87% for the full sample. Confidence carried no signal at all. In the other domains a gap at least tells you which control to add; here it tells you that self-assessment is not measuring the thing.

The authors' explanation is the right one, and it is the part that generalizes: **confidence tracks whether a control exists, not whether it is sufficient for the failure mode in question.** A dashboard, a partial gate, a tool in pilot, a rollback script someone wrote once — from inside the org each of these feels like coverage. Graded against a specific failure, most are pointed at the wrong target.

> Lesson: "do you have a control for X" is a question that cannot distinguish a gate from a gesture. The diagnostic question is *when did it last fire*. A gate that has never blocked a release is either perfect or not a gate.

## 5. The inventory asymmetry

Inventory deserves separate treatment because it is the only one of the five domains where the control is **binary**. Testing admits degrees — you can have four eval methods and no blocking gate, and that is genuinely better than nothing. Discovery does not: either a system is scanning for unregistered agents, or it is not.

Put the two inventory numbers together and 41% of the entire sample are asserting an absence — "we have no shadow AI" — with nothing in place that could detect a presence. If a shadow agent appeared in one of those organizations tomorrow, neither the inventory nor the confidence would change. That is not a tooling gap; it is a belief with no mechanism under it.

The epistemics here are worth stating plainly because they recur everywhere in agent operations:

- **Asserting presence needs only an example.** "We run agents" is verified by pointing at one.
- **Asserting absence needs a detector.** "We run no unregistered agents" is verified by a scan that could have found one and did not.

Every claim of the second kind in an agent estate — no shadow agents, no unapproved MCP servers, no agent reaching production without review — requires a running detector, and most orgs have substituted a process document for one. A process is an intention. The finding in [8.8. The Skill Supply Chain](../8.%20AI%20Safety%20%26%20Ethics/8.8.%20The%20Skill%20Supply%20Chain%20%E2%80%94%20Install-Time%20Scanning%20and%20Why%20It%20Collapses.md) is the same shape: a check that runs once, at a moment nobody revisits, is indistinguishable from no check.

## 6. Yesterday's rollout tooling, applied to nondeterministic releases

The third measured finding is that blast-radius techniques did not make the crossing. Canary deployments: 26%. Blue/green: 25%. Meanwhile 42% manage agent changes with the same tooling as code, with workarounds, and 9% require a full code redeploy to edit a prompt.

This is backwards in a specific and correctable way. Progressive delivery was invented because a deterministic release can still be wrong in a way testing missed. An agent release is wrong *differently on every run*. The technique is more load-bearing here than it was for services, and it is adopted at a quarter of the rate.

The promotion gate shows the same thing: 42% of organizations promoting agent changes to production have no fixed standard — 31% do ad hoc review where criteria shift by reviewer, 11% have no process. Combined with the tooling numbers, roughly 70% are releasing agents with tooling built for humans, or with no consistent standard for when a change is safe, or both. 58% report *more* production incidents per 100 changes since deploying agents; only 25% report fewer.

> Architectural takeaway: the incident rate is not evidence that agents are a net negative. It is evidence that the version of the lifecycle most orgs have deployed — partial evals, workaround config, an inconsistent gate — is the wrong lifecycle, and the fixes are all techniques the industry already knows.

## 7. Where federation stops being control

The capability most control planes lead with is **federated management**: one inventory covering agents on any framework, any runtime, cloud or on-prem, including agents the platform does not host. It is the right ambition and it hides an asymmetry that matters operationally.

| Agent location | What the control plane can do | What it cannot do |
|---|---|---|
| Hosted on the control plane's runtime | Observe, evaluate, version, suspend, sandbox | — |
| External, instrumented (emits OTel to the plane) | Observe, evaluate, alert | Suspend, sandbox, force a version |
| External, uninstrumented | Nothing until discovery finds it | Everything |

For external agents, the plane is an **observer with an advisory channel**, not an enforcement point. The kill switch that makes the inventory worth having only works on the agents you already run. That is the same read/act split [11.16](./11.16.%20Harness%20Engineering%20for%20Incident%20Response%20%E2%80%94%20The%20On-Call%20Agent.md) draws for the on-call agent, and the same containment boundary [8.1](../8.%20AI%20Safety%20%26%20Ethics/8.1.%20Agent%20Containment%20%26%20Control%20%E2%80%94%20Capping%20the%20Blast%20Radius.md) draws — enforcement lives where execution lives, and no amount of registry coverage moves it.

Two consequences for anyone designing this:

- **Discovery and enforcement are separate programs with separate timelines.** Shipping discovery gets you the inventory and an accurate picture of how bad the sprawl is. It does not get you the ability to do anything about it. Budget and sequence them separately, and do not let a discovery win be reported as a governance win.
- **The control plane is itself a high-value target and a single point of failure.** It holds every agent identity, every delegation policy, and a suspend button for the estate. Everything in [11.5](./11.5.%20Hooks%2C%20Permissions%2C%20and%20Side%20Effects.md) and [8.1](../8.%20AI%20Safety%20%26%20Ethics/8.1.%20Agent%20Containment%20%26%20Control%20%E2%80%94%20Capping%20the%20Blast%20Radius.md) about blast radius applies to it with the multiplier of the fleet it governs.

## 8. What to build first

If you are standing this up rather than buying it, the survey data implies a sequence, because it identifies which controls are both missing and binary:

1. **A detector.** Active discovery across model endpoints, MCP servers, and agent processes. Without it every subsequent claim is an intention. This is the single highest-value artifact and it is mostly egress and telemetry analysis, not new infrastructure.
2. **A system of record with an owner field.** Today the leading answer is a centralized inventory tool at 30%; 8% still track agent ownership in a repository README. An agent with no named owner cannot be triaged, deprecated, or billed.
3. **A kill switch that is instant and has been tested.** 76% believe they can stop an agent in 15 minutes; 33% have the mechanism. A redeploy is not a kill switch.
4. **One written promotion standard, applied identically by every reviewer.** Automated is better; a manual checklist applied consistently beats ad hoc review by a wide margin and costs nothing.
5. **Progressive rollout for agent changes**, treated as more necessary than it was for services, not less.

Identity, guardrails, and continuous evaluation come after, and are where a bought platform earns its keep — they are genuinely hard to build and genuinely commoditizable. The first four are neither, which is why the gap is embarrassing rather than difficult.

> Why it matters: 76% of surveyed organizations expect to buy agent lifecycle tooling within six months. Money spent against a felt picture of what is missing buys less than money spent against a verified one — and verifying the picture requires exactly the detector that 56% of them do not run.

## 9. Open questions

- **Does the control plane converge with the AI gateway, or stay separate?** A gateway already sits on LLM and MCP traffic and is the natural enforcement point. The argument for separation is lifecycle and identity; the argument for merger is that two policy engines on the same traffic is how policy bypasses happen.
- **What is the inventory's unit?** A long-running deployed agent is obviously an entry. A subagent dispatched for ninety seconds inside a session is obviously not. Everything between — a scheduled agent, a skill that spawns a loop, an agent embedded in someone's IDE — has no settled answer, and the answer determines whether "150,000 agents" is a real number or a counting artifact.
- **Who owns it?** Platform engineering, security, and the AI function all have a claim, and the tooling reflects the confusion: 30% inventory tool, 13% internal developer portal, 10% GRC system. This is the CMDB ownership fight again, and it went badly the first time.
