# 11.23. Cost-Performance Hillclimbing — Searching the Model, Effort, and Prompt Space

> Companion to [11.14. Tuning the Harness, Not the Model](./11.14.%20Tuning%20the%20Harness%2C%20Not%20the%20Model%20%E2%80%94%20The%20Harness%20as%20an%20Optimization%20Surface.md),
> which argues the harness is an optimization surface, and to
> [11.20. Harness Benchmarking](./11.20.%20Harness%20Benchmarking%20%E2%80%94%20Controlled%20Cross-Harness%20Evaluation.md),
> which supplies the controlled measurement. This note is about the *search procedure* that runs
> on top of them. Cache mechanics live in
> [Prompt Caching](../3.%20Prompt%20%26%20Context%20Engineering/prompt-caching.md);
> fleet-level spend lives in [11.21. Agent Fleet Economics](./11.21.%20Agent%20Fleet%20Economics%20%E2%80%94%20Agent-Workdays%20and%20the%20Intervention%20Ceiling.md).
> Evidence is drawn from Anthropic's September 2026 cost-optimization writeup; the method is vendor-neutral.

Cost and quality are usually treated as a dial: spend less, accept worse. For a configured agent that
framing is wrong often enough to be a trap. Three of the levers that move cost — prompt-cache hit
rate, accumulated prompt instructions, and effort level — also move accuracy, and on a
mis-tuned configuration they move it in the *same* direction. The configuration
`{model, effort, prompt}` is therefore a **search space with a joint objective**, not a tradeoff curve
to slide along. This note is about treating it that way: what the three levers are, why they couple,
and what it means that the search itself is now an agent job with a train/test split.

---

## 1. Three levers, one objective

| Lever | What it controls | Failure when mis-set | Cost direction | Quality direction |
|---|---|---|---|---|
| **Cache hit rate** | How much of the prefix is re-read instead of re-prefilled | A volatile byte early in the prompt; a fork whose prefix isn't byte-identical; a blocking tool call outliving the TTL | Large — cache reads dominate a tool-heavy loop | Neutral |
| **Instructions** | What the prompt tells the model to do beyond the task | Anti-patterns written for a weaker model that a frontier model now obeys literally | Up (extra tool calls, duplicated reasoning) | Down (contradictions, colliding scaffolds) |
| **Effort** | How many tokens the model spends per response, thinking and tool calls alike | Set high where the task isn't thinking-bound; set low where evidence is still findable | Roughly linear in effort | Non-monotonic |

Only the first is purely a cost lever. The other two are the reason the tradeoff framing breaks: an
instruction anti-pattern and a miscalibrated effort level each cost money *and* accuracy, so removing
them is a strict improvement with no dial to slide.

> **Why it matters:** if you believe cost and quality trade off, you stop looking as soon as you find
> a cheaper-but-worse configuration. If you believe they are jointly searchable, you keep looking —
> and on a config that has never been swept, the first few steps are usually free wins.

---

## 2. The migration anti-patterns

A prompt accumulates instructions that patch the weaknesses of whatever model it was written
against. When the model is replaced, those patches do not decay quietly — a stronger
instruction-follower obeys them *more* literally. Six recurring shapes:

| Anti-pattern | Example | What a frontier model does with it |
|---|---|---|
| **Verification ritual** | "double-check your work", "verify twice before responding" | Duplicates the tool call it already made |
| **Emphasis booster** | "be maximally thorough", "CRITICAL: YOU MUST ALWAYS…" | Verbosity and a fan-out of unneeded searches |
| **Mandatory procedure / scratchpad** | "think step by step in a scratchpad", a fixed six-step process | Stacks on top of native reasoning; can write a tool call *inside* the reasoning and never execute it |
| **Stale few-shot examples** | Demonstrations tuned to an older model's failure modes | Teaches long reasoning chains on requests that don't need them |
| **Contradictory rules** | "always refund within policy" vs. "never refund without escalation" | Follows both literally: stalls and asks the user to confirm |
| **Dated configuration** | A manual thinking budget from a previous generation | The platform rejects the request outright |

In a controlled migration (one anti-pattern planted at a time, six prompts, Opus 4.8 → Opus 5), an
audit that removed them cut cost **14.6%** and raised accuracy **5.3%** on average. Note where the
accuracy came from: a retired thinking setting that made every routing request 400, contradictory
refund rules that withheld four owed refunds, and a manual scratchpad that swallowed three tool calls.
None of those are quality-versus-cost tradeoffs. They are bugs that a model upgrade *exposed*.

> **Architectural takeaway:** a model upgrade is not a one-line change to a model ID. The prompt is
> versioned against the model it was written for, and the migration step is an audit of the prompt,
> the skills, and the tool descriptions — not just the string in the request.

---

## 3. Effort as a curve, not a setting

Effort is a behavioral signal telling the model how hard to work; it applies to every output token,
thinking and tool calls alike. Its cost–performance relationship is model- and task-specific, and the
*shape* of the curve is the diagnostic:

| Curve shape across a low→max sweep | What it means | What to do |
|---|---|---|
| Steep and still rising | Task is thinking-bound; there is evidence left to find | Buy more effort |
| Steep then flattening at the top | Diminishing returns; the last step is inside run-to-run noise | Stop one level below max |
| Flat throughout | Task is not thinking-bound at all | Run at low; spend the budget elsewhere |

Two measured examples make the spread concrete. On a hard coding benchmark, Fable 5 goes 11.5% → 30.9%
from low to max effort — about 2.7× the score for about 3.5× the cost, a curve worth climbing. On
Humanity's Last Exam without tools, Fable 5.1 goes ~53% → ~61%, but the final step to `max` buys about
half a point for 46% more cost: inside the noise, so you are paying for nothing measurable.

Miscalibration hurts in both directions. Too high and the model deliberates past the point where
evidence exists, adding latency and sometimes degrading the answer. Too low and it stops early: fewer
tool calls, answering from the first search result rather than the third, skipping the check it would
otherwise have run. The low-effort failure is the more dangerous one, because the answer *looks*
finished.

> **Lesson:** a stronger model at low effort is frequently cheaper than a weaker model at high effort.
> On one coding benchmark Fable 5.1 at low effort matched Fable 5 at high effort for a third of the cost —
> partly because it does less work per task, partly because its cache reads are priced 4× lower. "Downgrade
> the model to save money" is the wrong default move; *upgrade the model and drop the effort* is the one
> to test first.

## 4. Why the levers couple

The three levers are not independent, and the coupling is almost entirely through the cache prefix:

```text
tools ──┐
system ─┼──► cached prefix ──► conversation (grows) ──► new turn
effort ─┘        ▲
                 └── model ID, effort, and any prompt-affecting parameter are *part of* this prefix
```

Consequences that fall out of that diagram:

- **Changing model or effort mid-conversation breaks the cache**, because both render ahead of the
  content. On models that support per-message effort, an effort-only system message changes the level
  without touching the earlier prefix; on the rest, pick a level at session start and hold it.
- **A fork inherits the parent's cache only if its prefix is byte-identical** — same model, same effort,
  same tools. Subagents that differ in any of the three pay a full write, which is the hidden cost in
  a fan-out topology.
- **Compaction is the cheap moment to re-tune.** It already rewrites most of the cache, so a model or
  effort switch there costs nothing extra. Schedule configuration changes at cache-breaking boundaries.
- **A synchronous tool call that outlives the TTL turns the next turn into a write**, at 1.25× input
  price (2× on a 1-hour cache) instead of a cheap read. Long blocking sub-calls are a caching decision,
  not just a latency one.

> **Why it matters:** this is why a per-lever sweep gives the wrong answer. Effort changes cost through
> tokens *and* through cache invalidation; model changes cost through price *and* through cache read
> rates. The levers must be swept jointly or not at all.

## 5. The search procedure

What makes this tractable now is that the search is itself an agent task. The shape that works:

1. **Profile where the tokens go.** From organization usage/cost reporting if you have admin access,
   from the per-response usage object if the application logs it, otherwise by reading the
   request-building code and estimating. You cannot rank savings you have not measured.
2. **Fix the free wins first.** Cache breakpoint placement, trimming what each request carries, an
   anti-pattern audit, bounding output length, batching unattended work. None of these need an eval.
3. **Sweep model × effort against an eval.** This is where a held-out split matters: the search reads
   failing *train* examples to propose prompt changes, and the final configuration is scored on test
   cases the search never saw.
4. **Let the search read its own failures.** The interesting behavior is step 3 recovering quality after
   a downgrade: stepping from Opus 5 to Sonnet 5 dropped accuracy 98.9% → 88.9%, and reading the failing
   tickets produced routing rules and a refund-cap cross-reference that restored 98.9% at the cheaper
   price. Held-out result: 90.5% versus the original 78.6%, at roughly a fifth the cost.

Measured outcomes across four public benchmarks, starting from one baseline model, show what each lever
actually contributed:

| Benchmark | Cost reduction | Where it came from |
|---|---|---|
| LegalBench | ~58% | Shared-prefix caching, low effort, batch processing — thinking tokens 102,779 → 8,284 with pass rate inside noise |
| tau2-bench retail | ~73% | Prompt caching with explicit breakpoint placement alone; pass rate flat |
| OfficeQA Pro | ~52% | Batch processing plus document caching |
| SWE-bench Verified | ~55% | Caching was already correct; savings came from medium effort and bounding output — median steps 29 → 17 |

The SWE-bench row is the instructive one. Its default config already cached correctly, so the cache
lever was exhausted and the win came from output discipline. A search that only knew one lever would
have found nothing.

> **Architectural takeaway:** the deliverable of this exercise is not a cheaper number. It is a
> *reproducible configuration search* attached to an eval, which is the only thing that survives the
> next model release. Every frontier model ships and invalidates the previous answer.

---

## 6. What this asks of the harness

To run this search at all, the harness has to expose things most homegrown loops do not:

- **Cache-miss attribution.** Not "the hit rate dropped" but "the system prompt diverged and 41,850
  tokens of prefix were lost". Anthropic's cache-diagnostics beta does this by fingerprinting each
  request and comparing against the previous response ID; a self-built loop needs the equivalent, even
  if it is just a diff of the rendered bytes of consecutive requests.
- **Per-request usage logging.** Cache read, cache write, input, output, and thinking tokens, per call,
  attributable to a task. Without it, step 1 degrades to reading code and guessing.
- **A configuration surface that is data, not code.** Model, effort, TTL, breakpoint placement, and
  output bounds must be settable without a deploy, or the search cannot iterate.
- **An eval with a train/test split.** A search that scores on everything it optimized against will
  overfit to the eval, and you will not find out until production.

The first three are instrumentation; the fourth is the discipline. Together they are the precondition
for treating cost as an engineering variable rather than an invoice.
