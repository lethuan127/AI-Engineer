# 11.18. Tool Architecture — The Interface as a Behavioral Knob

> Companion to [11.7. Tools and MCP](./11.7.%20Tools%20and%20MCP.md) (the taxonomy of the action surface) and [11.14. Tuning the Harness, Not the Model](./11.14.%20Tuning%20the%20Harness%2C%20Not%20the%20Model%20%E2%80%94%20The%20Harness%20as%20an%20Optimization%20Surface.md) (the harness as an optimization surface). This note supplies the controlled measurement that 11.14 argues for, on the one surface most teams treat as a checklist.

Almost all published work on agent tooling asks *what can the agent do* — add a browser, add a database, add a deploy tool. Two August 2026 papers ask a different question: holding capability fixed, how much does the **organization and exposure** of those capabilities change agent behavior? The answer is: enough that tool architecture belongs in your eval budget, not your setup script.

The finding that should reorder your priorities is that the tool most teams reach for first — a scratchpad the agent can write its reasoning into — measured as approximately inert, while the choice between "bash" and "structured file operations" moved run-to-run consistency by nearly 5×.

---

## 1. The dimension being isolated

Xu et al. name the variable **tool architecture**: how capabilities are organized and exposed to the model, as distinct from which capabilities exist. Their setup holds the underlying information and actions roughly constant across six architectures and varies only the interface, on repository-level issue fixing, across three actors and 11,700 trajectories.

That design is what makes the results readable. A benchmark showing "agent with tool X beats agent without tool X" tells you nothing about interface design, because capability and exposure are confounded. Here they are not.

```text
capability   ── what actions exist at all          ← the usual axis
architecture ── how those actions are named,       ← the axis measured here
                grouped, parameterized, and
                surfaced to the model
```

## 2. What the experiment found

Against a baseline where the agent has only a `bash` tool:

| Architecture | Reported effect vs bash-only baseline |
|---|---|
| Structured low-level interfaces | Up to **4.7×** better consistency across repeated attempts |
| Natural-language search | Repository exploration broadens; **>11%** more access to relevant files |
| Python CodeAct-style interface | Comparable task performance with **41.6% fewer steps** and **56.3% lower token usage** |
| Lightweight cognitive scaffolding (e.g. a tool to record intermediate reasoning) | Limited effect on actor behavior |

Three of those four rows are wins on *different* axes, which is the practically useful part.

## 3. Three separable wins, not one ranking

The temptation is to read the table as a leaderboard and adopt the winner. It isn't one. Each architecture buys a different property:

| You care about | Reach for | Because |
|---|---|---|
| **Reproducibility** — the same issue, the same fix, twice | Structured low-level ops instead of raw shell | Free-form shell has a combinatorially larger action space per step, so two runs diverge early and never reconverge |
| **Recall** — the agent finds the file that actually matters | Natural-language search alongside exact-match tools | `grep` requires the agent to already know the token; semantic search does not |
| **Cost and latency** — fewer round trips | CodeAct-style programmatic calling | One generated program can express a dozen tool calls; the loop pays for one turn instead of twelve |

> Architectural takeaway: these are not competing choices. Consistency, recall, and step count are three different failure modes, and the interface that fixes one does not fix the others. A production toolset that optimizes only for token cost will be cheap and unreliable.

The CodeAct row is independently corroborated: the same shape shows up in Microsoft Agent Framework's CodeAct provider and in Anthropic's code-execution-with-MCP work — see [Code Execution as the Tool-Calling Substrate](../5.%20AI%20Agents%20%26%20Tool%20Use/Code%20Execution%20as%20the%20Tool-Calling%20Substrate%20—%20Programmatic%20Tool%20Calling.md). When three independent efforts report roughly half the steps and half the tokens for the same task class, that is a substrate change, not a benchmark artifact.

## 4. The null result is the expensive one

The finding worth internalizing is the one that reports *no* effect: lightweight text-based cognitive-scaffolding tools — the "think" tool, the scratchpad, the notes file the agent writes intermediate reasoning into — had limited effect on actor behavior.

This is uncomfortable, because those tools are cheap to add, feel principled, and are the first thing most harness guides recommend. They also produce visible output, which makes them feel like they are working.

> Lesson: **a tool that changes what the transcript looks like is not the same as a tool that changes what the agent does.** Scaffolding tools generate legible artifacts, which is why they survive scrutiny without evidence. If your harness includes one, the burden is on you to show a behavioral delta, not a prettier trace.

Two caveats before you delete yours. The result is for *lightweight, text-based* scaffolding on repository issue-fixing with capable actors — it is not a claim about structured planning artifacts that later steps are required to consume (the `plan.md` pattern in [11.17](./11.17.%20The%20AI-Native%20SDLC%20%E2%80%94%20The%20Committed%20Artifact%20Chain.md) is a different mechanism, because something downstream reads it). And a tool that does not change behavior may still be worth keeping for human observability, provided you are honest that observability is the reason.

## 5. The other half — diagnosing why the wrong tool got picked

Tool architecture determines the space of choices. A separate question is why the agent picks wrong inside that space, and standard evals answer it badly: they report *that* the model chose the wrong tool, rarely *why*.

Anand and Chattaraj propose **canary tools** — diagnostic probe tools deliberately planted in an agent's MCP tool set, each engineered to trigger one specific selection weakness. A single "wrong tool" outcome becomes a profile across six failure types.

| Canary type | The weakness it probes |
|---|---|
| **Semantic decoy** | A plausible-sounding name that is not the right action |
| **Parameter trap** | Right tool, argument schema that invites misuse |
| **Capability mirage** | A tool that appears to do more than it does |
| **Prerequisite blindness** | Calling a tool whose precondition has not been established |
| **Temporal decoy** | Right action, wrong point in the sequence |
| **Granularity trap** | Choosing a coarse or fine tool where the other was correct |

The evaluation covers eight models across three capability tiers, 120 tasks, three canary-density conditions and three seeds (8,640 runs), plus a 2,880-run subtlety ablation, graded by a provider-independent judge and corroborated by a second (Cohen's κ = 0.75).

## 6. Three results that should change procurement

**Susceptibility is not a proxy for tier.** Per-task canary susceptibility rate (CSR) ranges about **36×** across the eight models — lowest for Claude Opus 4.8, highest for Llama 3.1 8B. But capability tier alone does not predict it: the most susceptible *hosted* model is mid-tier, and within a single provider the cheaper model can be the safer one.

> Why it matters: if you are routing steps by model (see [Model Routing in the Agent Loop](../5.%20AI%20Agents%20%26%20Tool%20Use/Model%20Routing%20in%20the%20Agent%20Loop%20—%20Per-Step%20Model%20Selection.md)), "bigger model for the risky step" is not a sound heuristic. Tool-selection reliability has to be measured per model on *your* tool set, not inferred from a price tier.

**The failure modes stratify.** Capability mirages are what most reliably trap frontier models; the other five types are largely inert against strong models but fire against small open-weight ones. So the taxonomy discriminates by capability rather than being uniformly weak — and it tells you which failure to design against depends on which model you deploy.

**The probes measure reasoning, not pattern-matching.** Softening each canary's give-away phrasing left frontier CSR essentially unchanged. That rules out the obvious objection that canaries just detect models that skim tool descriptions for keywords.

And the load-bearing correlation: susceptibility predicts task failure (Spearman ρ = −0.34), while the least susceptible models are not significantly degraded by canary pressure. The diagnostic is measuring something that costs you outcomes.

## 7. What to actually do

1. **Treat the toolset as a tuned artifact, not a config file.** It has measurable effects on consistency, recall, and cost. That makes it eligible for the tune–screen–repeat–regress loop in [11.14](./11.14.%20Tuning%20the%20Harness%2C%20Not%20the%20Model%20%E2%80%94%20The%20Harness%20as%20an%20Optimization%20Surface.md), and for the same regression discipline.
2. **Name the axis you are optimizing before you change the interface.** Consistency, recall, and step count pull toward different architectures.
3. **Demand a behavioral delta from scaffolding tools.** If the only evidence is that the transcript reads better, the tool is documentation.
4. **Plant canaries in your own tool set.** Six adversarial probe tools alongside your real ones, run against each model you might route to, gives you a per-model susceptibility profile that no vendor benchmark will.
5. **Prune before you tune.** Selection errors scale with the number of plausible-looking wrong answers on offer; see [tool call — filtering strategy](../5.%20AI%20Agents%20%26%20Tool%20Use/tool%20call%20-%20filtering%20strategy.md).

> Architectural takeaway: the two papers describe the same surface from opposite ends. One says the interface changes behavior even when capability is fixed; the other gives you an instrument for finding out *how* it misleads a specific model. Together they move tool design out of the category of setup and into the category of things you measure, version, and regress — which is the whole thesis of this section applied to the one primitive teams still treat as inert.
