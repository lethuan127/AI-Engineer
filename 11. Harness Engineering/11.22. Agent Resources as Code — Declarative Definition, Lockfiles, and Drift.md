# 11.22. Agent Resources as Code — Declarative Definition, Lockfiles, and Drift

> Deepens [11.11. Operational Concerns](./11.11.%20Operational%20Concerns.md) §2 (versioning) and §3 (drift detection), which argue that a harness owned by more than one person needs a declared state and a way to detect divergence from it. This note is the first vendor implementation of exactly that for *server-side* agent resources.
>
> Companion to [7.1. Claude Platform Managed Agent](../7.%20AI%20System%20Architecture/7.1.%20Claude%20Platform%20Managed%20Agent.md), which describes the resources being declared.

Local harness configuration has always been files in a repository. `AGENTS.md`, `.cursor/rules/*.mdc`, `.claude/skills/*/SKILL.md` — every primitive in [11.2](./11.2.%20Repo%20Memory%20%E2%80%94%20AGENTS.md%20%26%20Friends.md) through [11.7](./11.7.%20Tools%20and%20MCP.md) is read off disk at session start, so it is reviewed, versioned, and diffed for free. **Hosted** agent resources — the agent definition, its sandbox environment, its memory store, its scheduled deployment — have not been. They were created by clicking in a console or by an imperative SDK call, which means the running configuration lived in a vendor's database and the repository had no opinion about it.

Anthropic's `ant apply` (CLI 1.30.0, 2026-09-03) closes that gap with a plan/approve/lockfile workflow that will look immediately familiar to anyone who has run `terraform apply`. The pattern is not the interesting part. The interesting part is the three places where a *state-machine-with-side-effects* — an agent with a memory store and a cron schedule — forced different answers than infrastructure-as-code gives for a load balancer.

---

## 1. What becomes a file

Five resource kinds move into the repository. Each file is the request body you would have POSTed to that kind's create endpoint:

| Kind | Format | Conventional path | Where the prose goes |
|---|---|---|---|
| Agent | Markdown / YAML / JSON | `agents/` | The `system` prompt |
| Environment | Markdown / YAML / JSON | `environments/` | The `description` |
| Memory store | Markdown / YAML / JSON | `memory_stores/` | The `description` |
| Deployment | Markdown / YAML / JSON | `deployments/` | The message that starts each session |
| Skill | Directory with `SKILL.md` | `skills/` | The skill body (uploaded as one bundle) |

The Markdown-with-frontmatter shape is the load-bearing choice. Frontmatter holds the structured configuration; the body fills the kind's single free-text field. That means an agent definition is *the same artifact shape as a `SKILL.md`* — frontmatter routing metadata over a prose payload — and a reviewer reads the system prompt as prose in a diff rather than as an escaped JSON string. Everything in [11.4 §4](./11.4.%20Skills.md) about writing a reviewable `SKILL.md` transfers directly to writing an agent.

Kind is inferred, in order: an explicit top-level `type` field, then the containing directory name, then a filename prefix (`environment_staging.md`). Files matching none — READMEs, CI config — are skipped unless named explicitly on the command line.

> Why it matters: an agent's system prompt is the highest-leverage, least-reviewed string in most AI systems. Moving it into a Markdown file under the repository's normal review gate is worth more than the deployment automation wrapped around it.

## 2. Paths as references, resolved in dependency order

Wherever the API expects another resource's ID, you write the **relative path** to that resource's file. A deployment names its agent as `../agents/reviewer.md`; a coordinator agent lists `./reviewer.md` in its multiagent roster; an agent lists `../skills/pr-summary` under `skills`. The tool topologically sorts, creates in dependency order, and substitutes the real IDs.

```yaml
# deployments/nightly.md — frontmatter
name: Nightly review
agent: ../agents/reviewer.md          # sent as {type: agent, id, version}
environment_id: ../environments/cloud.yaml
resources:
  - path: ../memory_stores/review-notes.yaml
    access: read_write
schedule:
  type: cron
  expression: "0 3 * * *"
  timezone: America/Los_Angeles
```

Two details that matter more than they look:

- **References are pinned to the version applied in the same run.** Editing `reviewer.md` bumps everything that points at it, atomically within the run. Without this, a coordinator agent would keep dispatching to a stale subagent version — the exact drift class [11.11 §3](./11.11.%20Operational%20Concerns.md) warns about, but invisible because it lives in a vendor's database.
- **A path also works inside an object**, as in the `resources` entry above, where sibling keys like `access` survive the substitution. So the reference is a *field-level* substitution, not a whole-document preprocessing pass.

Anything that is not a managed path is sent as written — a literal `agent_...` ID for a resource these files do not own, or a first-party reference like `{type: anthropic, skill_id: xlsx}`. A skill reference may also be a GitHub tree URL, downloaded and **pinned to the resolved commit** until you run with `--upgrade`. That is a genuine supply-chain control: a shared skills repository is an executable dependency, and pinning it by commit is the same discipline you would apply to any other vendored code.

## 3. The lockfile is an identity table, not a state dump

`claude-lock.json` is small and does exactly one job — map file path to remote identity — plus one guard:

```json
{
  "version": 1,
  "origin": {
    "base_url": "https://api.anthropic.com",
    "organization_id": "1b0c2a4d-6c1f-4f0e-9a57-2e8d1c3b4a5f",
    "workspace_id": "wrkspc_01JwQvzr7rXLA5AGx3HKfFUJ"
  },
  "resources": {
    "./agents/summarizer.md": {
      "kind": "agent",
      "id": "agent_011CYm1BLqPXpQRk5khsSXrs",
      "version": "1",
      "hash": "d23251c8d99b3613a64f3f8d87f5fad4",
      "remote_hash": "1b771bee5bdbf600a5ad972fdac32d94"
    }
  }
}
```

The **two hashes** are the design. `hash` fingerprints what was last sent; `remote_hash` fingerprints what the API returned. Comparing the file against `hash` detects a local edit. Comparing the live resource against `remote_hash` detects an edit made outside these files — someone changing the system prompt in the Console. One hash would conflate the two; two hashes distinguish "you changed it" from "someone else changed it," which is what makes §4 possible.

The `origin` block pins organization and workspace, and the tool **refuses credentials that resolve anywhere else**. This is the guard against the worst plausible accident in agents-as-code: applying a staging lockfile with production credentials and silently retargeting live scheduled deployments. Keep one lockfile per organization/workspace pair and select it with `--lock-file`.

Commit it. It is also where you read an agent's ID to start a session, so it doubles as the repository's service-discovery table.

## 4. Drift is a refusal, not a merge

If a resource was edited, archived, or deleted outside the files, the plan ends with `This plan cannot be applied:` and a reason, and the command exits with `refusing to apply`. `--force` overwrites.

That is the right default and worth stating as a rule. Infrastructure tooling has historically defaulted to *reconciling* drift — plan the difference, apply it, overwrite the human. For agent resources the blast radius is asymmetric: someone editing an agent in the Console at 2 a.m. is usually mitigating an incident, and silently reverting that mitigation on the next CI run turns a fix into a regression with no signal. Refusing forces the operator to reconcile the console edit back into the file.

> Architectural takeaway: for any resource a human can hot-patch under pressure, drift detection should **stop the pipeline**, not resolve it. Reconcile-by-default is safe only where nobody edits out of band.

## 5. The three unsafe edges

Declarative tools are judged by their deletion and adoption semantics, and this is where the rough edges are:

| Edge | Behavior | Consequence |
|---|---|---|
| **Delete a file** | Resource stays, with a warning; `--prune` archives it (deletes it, for a skill) | Safe default; but a repo without `--prune` in CI accumulates orphans indefinitely |
| **Rename a file** | Declares a *new* resource; the old one persists until pruned | A rename is a create-plus-orphan. There is no `moved` block, so renaming an agent under a live deployment briefly doubles it |
| **Adopt an existing resource** | Not possible. Applying a file describing an existing agent **creates a second one** | Anything built in the Console is stranded unless exported via **Export as code**, which ships its own lockfile |

The rename gap is the one to plan around: pick resource filenames as carefully as you would pick a database table name, because in this model the path *is* the primary key. The adoption gap means the decision to manage resources as code is effectively made once, at the start — retrofitting a Console-built fleet means exporting it, not describing it.

Field clearing has its own asymmetry: deleting a field from a file clears it on the resource **if the API allows that field to be cleared**; a field you never set, or one the API cannot clear, keeps its current value. So the file is not a complete specification of remote state. It is a set of assertions over it.

## 6. The CI shape

Without a terminal the tool prints the plan and stops, demanding `--yes` or `--dry-run`. The documented pipeline:

```bash
# On pull requests — informational; exits 0 even when the plan is blocked
ant apply --dry-run .

# On the default branch after merge — name the directory, not a bare invocation
ant apply --yes .
```

Four operational rules come with it, each of which is a bug you would otherwise ship:

1. **Name the project directory.** A bare `ant apply --yes` reconciles only files the lockfile already tracks, so a newly added agent is silently skipped.
2. **Commit the updated lockfile even when the apply failed partway** — a partial apply still created resources, and losing that record orphans them.
3. **Run one apply at a time.** Nothing locks the lockfile. There is no state locking, which is the single biggest capability gap versus mature IaC.
4. **Authenticate with [Workload Identity Federation](https://platform.claude.com/docs/en/manage-claude/workload-identity-federation), not a stored key.** A long-lived key in CI that can rewrite every agent and scheduled deployment in a workspace is a poor trade against a short-lived OIDC-derived token.

The dry-run-exits-0 choice is deliberate but sharp-edged: a blocked plan will not fail your PR check. If you want drift to block a merge, you have to parse the output yourself.

## 7. Where this sits against general-purpose IaC

| | `ant apply` | Terraform / Pulumi | `kubectl apply` |
|---|---|---|---|
| State | Path→ID lockfile, dual-hash | Full state file / backend | Live cluster is the state |
| Drift | **Refuses**, `--force` to override | Plans a reversion by default | Server-side merge by field owner |
| Deletion | Orphan by default, `--prune` opt-in | Destroy by default from plan | Prune opt-in, `--prune` |
| Adoption of existing | **Not supported** | `import` | Native (apply is upsert) |
| Rename | Create + orphan | `moved` block preserves identity | Name *is* identity; same problem |
| Concurrency | **No locking** | State locking (DynamoDB, etc.) | Optimistic concurrency via `resourceVersion` |

The honest read: this is a v1 with the ergonomics of a mature tool and the safety properties of an early one. It is well ahead of clicking in a console, and it is not yet something to run unattended against production from three branches at once. Use it where you would use a first-generation deployment script — with serialized CI, a pinned workspace, and a human reading the plan.

## 8. What actually changes for the harness engineer

The primitive worth internalizing is not the CLI. It is that **the boundary between "harness config" and "deployed infrastructure" has stopped existing**. Before this, section 11's primitives (files, reviewed, versioned) and section 7's primitives (sessions, environments, deployments — created imperatively, living in a vendor database) were governed by different disciplines. Now an agent, its sandbox, its memory store, and its cron schedule are all Markdown in the same pull request as the `SKILL.md` it loads and the `AGENTS.md` it reads.

That collapses three of the five failure modes in [11.11 §1](./11.11.%20Operational%20Concerns.md) — undocumented config, per-developer divergence, and untracked change — into one already-solved problem: code review. It also means the review checklist for a pull request now has to cover a system prompt, a network policy, and a cron expression, which most teams' review culture is not yet calibrated for.

> Lesson: the moment agent configuration becomes reviewable, the quality of your agents becomes a function of your code-review standards. That is a better place for it to live than a console, and a worse place than most teams currently realize.
