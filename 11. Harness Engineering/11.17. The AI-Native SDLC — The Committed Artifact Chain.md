# 11.17. The AI-Native SDLC — The Committed Artifact Chain

> Source: Anthropic Applied AI, "The AI-native SDLC playbook", published 2026-08-21. Companion to [11.4. Skills](./11.4.%20Skills.md), [11.5. Hooks, Permissions, and Side Effects](./11.5.%20Hooks%2C%20Permissions%2C%20and%20Side%20Effects.md), [11.6. Slash Commands and Subagents](./11.6.%20Slash%20Commands%20and%20Subagents.md), and [11.16. Harness Engineering for Incident Response](./11.16.%20Harness%20Engineering%20for%20Incident%20Response%20%E2%80%94%20The%20On-Call%20Agent.md).

Notes 11.1–11.11 treat the harness as something you configure for one repository. This note is what happens when you configure it for the whole *lifecycle*: plan, design, build, test, deploy, maintain. The interesting claim is not that agents write code faster — that is assumed. It is that the **handoff medium changes**. A traditional SDLC hands work between stages as tickets, documents, and sign-offs, all of which assume a human on both ends. An AI-native SDLC hands work between stages as a **file committed to version control** that a human and an agent can both read and act on, and the chain of those commits *is* the audit trail.

The second claim is the one that matters for anyone in a regulated org: the control objectives do not change. Design review, separation of duties, change approval, evidence retention all survive. What changes is the **enforcement mechanism** — from a person reading a diff to a hook, a skill, an eval, or a branch-protection rule. Getting the mapping between control and mechanism right is the whole discipline.

---

## 1. Why the shape of the lifecycle changes

The traditional six-stage SDLC was optimized for an era when writing code was the most expensive step. Collapse build from weeks to hours and three things break at once:

- **The bottleneck moves left and right of build.** Planning and review/deploy still run at human speed, so they become the critical path.
- **Controls stop matching reality.** Line-by-line human review made sense when a person wrote the line. It does not survive agents writing most of the diff.
- **Governance cost rises relative to build cost.** Exceptions still route through a weekly or monthly committee while the change they gate took an afternoon.

> Why it matters: the failure mode is not "agents produce bad code." It is a **review queue**. A security team sized for human output either becomes the new bottleneck or waves changes through under-reviewed. Neither is acceptable in a regulated environment, and neither is fixed by a better model.

## 2. The committed artifact chain

Each stage ends by writing an artifact to version control; the next stage begins by reading it. Markdown dominates the early stages because a product owner and an agent can act on the same file; from build onward the artifact is code and its records.

| Stage | Artifact | Written by | Triggers |
|---|---|---|---|
| Plan | `intent.md` | Originator, with an agent, reviewed by the product owner | Acceptance fires the design pass |
| Design | `spec.md` | Agent, constrained by policy skills; human approves | Approval fires plan mode |
| Build | `plan.md`, then the diff and its tests | Agent in plan mode; engineer interrogates the plan | Merged PR fires the pipeline |
| Test | Eval results, CI evidence | CI, non-interactively | Pass/fail gates the merge |
| Deploy | PR with review findings | Review agent; code owner approves | Merge fires deployment |
| Maintain | Incident record → the next `intent.md` | Agent invoked by a deterministic detector | Breached control band restarts the loop |

Two properties make this more than a naming convention:

1. **Machine-actionable handoff.** The next stage's prompt is "read the committed artifact," not "attend the handover meeting." Stage transitions become jobs.
2. **Audit trail for free.** Author, timestamp, revision history, and the accept/reject decision are all recorded as ordinary VCS events. Nobody writes a compliance narrative afterwards.

> Architectural takeaway: the artifact chain is the same primitive as [11.2's repo memory](./11.2.%20Repo%20Memory%20%E2%80%94%20AGENTS.md%20%26%20Friends.md) applied along the time axis instead of the file-tree axis. Repo memory answers "what does this codebase expect of you"; the artifact chain answers "what did the previous stage decide, and why."

## 3. Which primitive enforces which control

This is the load-bearing table of the whole note. Harness primitives are not interchangeable — they differ in whether a session can ignore them.

| Mechanism | Strength | Fails how | Use for |
|---|---|---|---|
| `CLAUDE.md` | Advisory, always in context | Silently, when stale or too long | Conventions, commands, "things the agent gets wrong twice" |
| Skill | Advisory, conditionally loaded | Silently, when the description doesn't trigger | Institutional knowledge that must be applied *consistently* |
| Hook (allow/block) | Deterministic, in-session | Loudly — the action is refused | Policies that must always hold |
| Hook (ask) | Deterministic, blocks on a human | Slowly — a person is back on the critical path | Named approval gates only |
| Managed settings | Deterministic, un-switchable by the engineer | Loudly, org-wide | Non-negotiables: credential denial, sandbox, marketplace provenance |
| Branch protection | Deterministic, outside the agent | Loudly, at merge | Separation of duties |

> Architectural takeaway: a skill makes a violation *rare*; a hook makes it *close to impossible*. Any policy described as mandatory and implemented only as a skill is mis-tiered. The corollary is the honest version of the advisory tier: measure a skill by whether PR review findings citing that policy trend to zero. If they don't, the skill isn't triggering or its text has drifted from the policy it claims to encode.

## 4. Where hooks go — build guardrails versus approval gates

The same primitive plays two different roles depending on where it fires, and conflating them is the most expensive mistake in the playbook.

| | Build-phase hook | Deploy-phase gate |
|---|---|---|
| Verdict | Allow or block, no human | Ask — pauses for a named approver |
| Latency budget | Milliseconds; scoped to the changed file | Human-scale; expected to wait |
| Examples | Block edits to generated/frozen paths, run the formatter, keep credentials out of the diff | Block a production migration without a change ticket |
| Ownership | Team, in `.claude/settings.json`, checked into git | Platform/IT admin, in managed settings the engineer cannot disable |

> Lesson: an approval prompt during the build puts a person on the critical path of *every* parallel session at once. If you are running three worktrees, a build-phase `ask` hook triples the interruptions and destroys the reason you were running three worktrees. Approval belongs at the gate, where one decision covers one change.

A block should explain itself. A hook that exits non-zero and prints nothing teaches the agent to retry variations; a hook that surfaces the reason and the route to approval turns a refusal into a redirect.

## 5. Test — three verification loops, not one

The playbook separates three things that are often collapsed into "the agent runs tests":

| Loop | When it runs | Context | Purpose |
|---|---|---|---|
| Feedback loop | Continuously during the task, as many times as needed | The working session | Let the agent verify its own work — `make test`, a build, a screenshot diff |
| Verifier subagent | Once, at the end | A fresh context window | A verdict not coloured by the assumptions that produced the code |
| Continuous evals | On config change and on a schedule, in CI | Non-interactive | Regression-test the *harness*, not the code |

The verifier subagent's contract is worth quoting in shape: *run the app, check the behaviour, report only — do not fix anything.* Separating the diagnosis from the repair is the same read/act split that [11.16](./11.16.%20Harness%20Engineering%20for%20Incident%20Response%20%E2%80%94%20The%20On-Call%20Agent.md) applies to incident response.

Two rules do real work here:

- **For a bug fix, commit the failing test first**, then ask the agent to make it pass without editing the test.
- **Protect the loop itself.** An agent fixing code must not be able to weaken the check on that code — a hook that blocks test-file edits during a fix, or a review pass that rejects any diff touching a test.

> Why it matters: this is the falsifiability requirement from [11.15](./11.15.%20Self-Evolving%20Harnesses%20%E2%80%94%20Observability-Driven%20Automatic%20Evolution.md) restated operationally. A self-verifying agent whose verification it can edit is not self-verifying; it is self-certifying.

### Configuration is code, so it gets a regression suite

The sharpest idea in the Test stage is that `CLAUDE.md`, skills, and hooks steer the agent and therefore *deserve the regression testing that code gets*. The suite is 20–50 real tasks drawn from recent work, each written as a prompt plus checks (tests pass, lint clean, behaviour unchanged, policy followed), run non-interactively on a schedule and on any change under `.claude/`:

```yaml
on:
  pull_request:
    paths: ["CLAUDE.md", ".claude/**"]
  schedule:
    - cron: "0 2 * * *"
```

Each production incident earns a permanent eval, written by the owning team. And the suite is live, not frozen: as models improve, cases that once discriminated stop discriminating, so replacement cases have to come from ongoing monitoring.

## 6. Deploy — the production gate

The governing principle: **the agent may act up to the production gate and cannot pass it.**

- The review agent gives findings, not approvals. Branch protection still requires a code owner, so **separation of duties survives because the agent that wrote the code has no way to approve it.**
- A repo-root `REVIEW.md` divides review into passes — bugs and logic; security; compliance against `spec.md` and `plan.md` — and defines Important versus Nit, with a hard cap on nit volume. Uncapped nits are how a review agent gets ignored.
- Findings feed back into `CLAUDE.md` on the *second* occurrence of the same class, which is the same promotion rule as the lessons log in 11.16.
- Pipeline autonomy is a ladder, not a switch: read-only judgment steps (triage a failed build, draft a changelog) → write steps that can only produce a PR → sandboxed execution with short-lived scoped tokens → deploy/status/rollback exposed as MCP tools scoped per environment → autonomy tiered by environment.

> Architectural takeaway: exposing deployment as scoped MCP tools rather than a shell script with credentials converts the agent's production powers into an allowlist. That is the [11.7](./11.7.%20Tools%20and%20MCP.md) tool-boundary argument with the stakes raised — the tool surface *is* the permission model, and a shell is a tool surface with no permission model.

And the unglamorous one: **rollback should be the most rehearsed path in the pipeline**, because the Maintain stage calls it automatically.

## 7. Maintain — control bands close the loop

Stage 6 runs with no human in the invocation path, which forces a specific architecture: **detection stays deterministic; the model is only invoked after a threshold is crossed; what it may do is set by which threshold.**

| Band | Response |
|---|---|
| 1σ | Log only |
| 2σ | Invoke the agent read-only to diagnose |
| 3σ | Agent may act, but only by opening a PR into the review gate or triggering a pre-approved runbook |

The detector is a version-controlled, unit-tested script computing mean and standard deviation over a rolling window, with Western Electric-style rules so slow drift is caught as well as spikes. Tiers live in a `bands.yaml` next to it. The agent's output is an `intent.md` in Stage 1 format, which is what makes the lifecycle a loop rather than a line. Dismissals at triage tune the bands.

> Why it matters: putting a model in the *detection* path would make alerting non-deterministic and unauditable. Putting it in the *diagnosis* path, gated by a deterministic threshold and a permission tier, keeps the alerting story unchanged while collapsing incident-to-diagnosis time. This is the escalation boundary from 11.16 expressed numerically instead of in prose.

The same machinery works on process metrics, not just production ones — PR cycle time drifting past 3σ produces a report for engineering leadership by exactly the same path.

## 8. The legacy source-of-truth problem

Jira, ServiceNow, Figma, and change boards are hard to displace precisely because auditors already accept them. The rule is not "move everything into git." It is: **for every artifact, name exactly one system as source of truth.**

| Configuration | How it works | Cost |
|---|---|---|
| Repo as source of truth | Artifacts live in git; legacy records link to commits | Cleanest, but needs auditor buy-in |
| Legacy system as source of truth | Agent reads the record at session start and writes back through an MCP connector in the same session | Connector reliability becomes a lifecycle dependency |
| Linkage only | Artifacts note the record ID; legacy records hold the commit SHA | Two sources of truth, accepted knowingly — a reasonable starting point |

The failure mode is the unnamed fourth option: two systems both treated as authoritative, drifting, with no one able to say which timestamp counts.

## 9. Measuring it — leading and lagging pairs

Every play in the playbook carries one leading and one lagging indicator, which is a discipline worth stealing wholesale.

| Play | Leading | Lagging |
|---|---|---|
| `intent.md` | Time from first conversation to committed intent | Share of intents accepted into design |
| Plan mode | Share of changes merging on the first implementation pass | Rework cycles; whether the merged diff still matches `plan.md` |
| `CLAUDE.md` | How often the agent repeats a mistake it should have caught | Time to first merged PR for a new team member |
| Skills | Time from policy approval to skill merge | Review findings citing that policy (should trend to zero) |
| Feedback loop | First-pass CI success rate on agent-written changes | Review time per PR; change failure rate |
| Parallel sessions | Concurrent sessions per engineer while review quality holds | Changes merged per engineer per week, read alongside rework rate |
| Control bands | Time from band breach to a triaged `intent.md` | Share of findings that become merged fixes; repeat incidents |

> Lesson: the pairing exists to stop a leading indicator from becoming the goal. "Concurrent sessions per engineer" optimized alone produces an engineer rubber-stamping four worktrees. Read against rework rate, it produces the actual ceiling — **the practical limit on parallel sessions is how many streams one person can review properly**, not how many the machine can run.

## 10. What to be skeptical about

- **Review capacity is still the binding constraint.** The playbook moves review from lines to artifacts and adds an agent reviewer, but a human code owner still approves every merge. That is a deliberate control, and it means throughput scales with reviewer attention, not with session count.
- **Advisory controls are load-bearing in the early stages.** Design (Stage 2) depends on brand, security, compliance, and UX policies encoded as skills — all advisory. A spec that quietly skips a policy because a skill did not trigger produces a downstream diff that looks compliant and is not.
- **The shape is vendor-specific even where the idea is not.** `CLAUDE.md`, `.claude/skills/`, plan mode, managed settings, and worktree parallelism are one vendor's spelling. The transferable primitives are: committed handoff artifacts, an advisory/deterministic control split, config as a tested asset, and deterministic detection with tiered model response. Map those onto whatever harness you run — see [11.9](./11.9.%20Vendor%20Diff%20Matrix.md).
- **Every deny trades against capability.** The regulated managed-settings example (denying `WebFetch`, `curl`, `wget`, `.env` reads, unsandboxed commands, unknown marketplaces, and pinning a minimum client version) is presented as a starting point to tailor, not a template to copy. A deny list tuned by copy-paste produces prompt fatigue, which is the [8.1 §10](../8.%20AI%20Safety%20%26%20Ethics/8.1.%20Agent%20Containment%20%26%20Control%20%E2%80%94%20Capping%20the%20Blast%20Radius.md) failure mode wearing a compliance badge.
