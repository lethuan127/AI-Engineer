# 11.6. Slash Commands and Subagents

> Companion to [11.4. Skills](./11.4.%20Skills.md). Skills are *agent-routed* procedures — the agent decides when to invoke them. Slash commands are *user-routed* — the user types `/name`. Subagents are *parent-dispatched* — the current agent calls a child agent. All three move work between contexts; the difference is who pulls the trigger.

A configured harness has three call-sites where work crosses a context boundary: the user types something, the model decides something, the agent loop spawns a child. Slash commands and subagents are the explicit, named entry points for the first and third. Skills cover the middle.

---

## 1. Slash commands — definition

A **slash command** is a user-invokable prompt stored as a markdown file with frontmatter. The user types `/name <args>`, the harness inlines the file body (substituting argument placeholders) as if the user had typed it, and the loop continues.

The shape, mirrored across vendors:

```markdown
---
description: Scaffold a new numbered curriculum note in a track folder.
argument-hint: <track-folder-or-number> <title>
---

# /new-note

(Body: instructions that read like a prompt to the agent. May reference
$ARGUMENTS for the raw argument string, or interpolate specific args.)
```

The body is **a prompt the user is sending**, not a function the agent is calling. That distinction matters: slash commands are syntactic sugar for "I keep typing this", not a new control-flow primitive.

## 2. Slash commands vs. skills

The most common confusion. Both store reusable procedures as markdown.

| Axis | Slash command | Skill |
|---|---|---|
| Trigger | User explicitly types `/name` | Agent routes by intent |
| Discovery | User must know it exists | Description-routed, automatic |
| Argument handling | Positional, structured (`$1`, `$ARGUMENTS`) | Loose, derived from prompt |
| Location | `.cursor/commands/`, `.claude/commands/` | `.claude/skills/`, others |
| Use case | "Give me a button" | "Whenever the user wants X" |
| Composes with | Can invoke skills | Cannot invoke commands (they're user-facing) |

The practical pattern: commands are thin, skills are thick. The command does argument parsing and disambiguation; it delegates the *how* to a skill.

```text
User types /new-note 5 "Programmatic Tool Calling"
        │
        ▼
.cursor/commands/new-note.md   ← parses args, picks track folder
        │
        ▼
.claude/skills/add-curriculum-note/SKILL.md   ← scaffolds the file
```

> Architectural takeaway — the command is *what the user invokes*. The skill is *what the harness reuses*. Don't put the workflow in the command and then duplicate it in a skill — pick one canonical place and link.

## 3. Slash command anatomy

Standard sections (see this repo's [`.cursor/commands/new-note.md`](../.cursor/commands/new-note.md)):

1. **Frontmatter** — `description` (one sentence), `argument-hint` (display string).
2. **Title** — `# /<name>`.
3. **Usage** — explicit example invocations.
4. **Steps** — what the agent should do, numbered, prescriptive.
5. **Constraints** — what the agent must NOT do.
6. **Optional**: output expectations, fallback behavior, links to the skill it delegates to.

Length budget: 30–120 lines. A command that wants to grow past that is hiding a skill.

## 4. Subagents — definition

A **subagent** is a child agent loop dispatched by the parent. It has:

- Its own **system prompt** (often domain-narrow: "you are a reference validator").
- Its own **tool subset** (often restricted: read-only, no write).
- Its own **context window** (does not inherit the parent's history).
- Its own **return value** (a single final message to the parent).

In Claude Code, subagents live in `.claude/agents/<name>.md`:

```markdown
---
name: reference-validator
description: Use to audit the `## References` section of one or more curriculum notes…
tools: Read, Glob, Grep, WebFetch
model: inherit
---

# Reference Validator

(Body: system prompt for the child agent.)
```

In Cursor, the equivalent is the `Task` tool dispatched with a `subagent_type`. The set of subagent types is user-global (configured in `~/.cursor/` or via plugins); per-repo subagent files are not yet a first-class feature in Cursor at time of writing — see [11.9. Vendor Diff Matrix](./11.9.%20Vendor%20Diff%20Matrix.md).

## 5. When to dispatch a subagent

Three concrete reasons:

| Reason | Example |
|---|---|
| **Context isolation** | A long exploration that would bloat the parent's context — dispatch a child to do the search, parent receives a summary |
| **Capability narrowing** | A task that should run with a restricted toolset — read-only validator that cannot accidentally edit |
| **Parallelism** | Multiple independent tasks — dispatch N children, await all, synthesize |

Anti-reasons (don't dispatch a subagent for these):

- **Token saving on the parent's prompt.** A subagent has its own setup cost; the savings are usually a wash.
- **"Different persona".** A different `description` is enough; a separate process is overkill.
- **Tool that the parent doesn't have.** Add the tool, don't fork.

## 6. The context-isolation pattern

The most useful subagent pattern is **exploration → summary**:

```text
Parent agent:                  Subagent (explore):
  User: "Refactor the auth     ┌─────────────────────────┐
   module to use JWT."         │ Read 15 files, run     │
                               │ grep across 200 more.   │
  ──── dispatch ─────────►     │ Build a mental model.   │
                               │ Return: 1-page summary  │
                               └─────────────────────────┘
  ◄─── 1-page summary ──── ─

  (Parent's context now has the summary, not the 15 files.
   Parent uses its full window to design and write the refactor.)
```

Why it matters:

> **Subagents trade wall-clock for context window.** You pay a model call (or several) up front; you get back a clean, compact context for the parent's hard work.

This is the same idea as RAG, but for the agent's own working set. Useful any time the parent would otherwise read and discard a lot of files.

## 7. The capability-narrowing pattern

Pair a subagent with a restricted `tools:` list. The child *cannot* edit, regardless of what the model decides:

```yaml
---
name: reference-validator
tools: Read, Glob, Grep, WebFetch   # no Edit, no Write, no Bash
---
```

This is a *belt* on top of the *braces* of permissions ([11.5](./11.5.%20Hooks%2C%20Permissions%2C%20and%20Side%20Effects.md)). Even if the model emits a `tool_use` for `Edit`, the subagent's tool registry doesn't include it — the call fails cleanly.

> Lesson — use subagents for *capabilities*, not just *prompts*. A "validator that cannot edit" is structurally safer than a system prompt that says "do not edit".

## 8. The parallelism pattern

When the parent agent has several **independent** tasks, dispatch in parallel:

```text
Parent: "Audit references in tracks 4, 5, and 7."
  │
  ├──► subagent(reference-validator, "track 4")
  ├──► subagent(reference-validator, "track 5")
  └──► subagent(reference-validator, "track 7")
       │
       ▼
  (await all)
       │
       ▼
  Synthesize three reports into one summary.
```

Caveats:

- **Independence is mandatory.** If task B depends on task A's findings, parallelism is a hazard, not a win.
- **N is bounded.** Most harnesses cap concurrent subagents at 5–10. Beyond that, latency stops improving.
- **Cost is N×.** N subagents = N system-prompt reads = N billed model calls. Watch the budget.

## 9. Subagent design checklist

When writing a subagent file (`.claude/agents/<name>.md`), verify:

1. `description` starts with "Use to …" and lists concrete triggers.
2. `tools` list is the minimum required (deny-by-default).
3. System prompt body declares the single output format the child must return.
4. "Hard rules" section repeats the most-important invariants.
5. "Anti-patterns" section calls out the obvious mistakes the child could make.
6. Returns a *report*, not a *commit*. Mutations happen in the parent, where they are reviewable.

The last bullet is contested. Some teams let subagents commit code directly (e.g., the `code-implementer` pattern). For safety, the higher-leverage path is **parent commits, subagents recommend** — the parent has more context for final decisions.

## 10. Slash command + subagent composition

The killer combo: a slash command that dispatches a subagent.

```markdown
---
description: Audit references on all numbered notes in the repo.
---

# /audit-refs

Dispatch the `reference-validator` subagent with scope `**/*.md`.
Synthesize its report.
```

Properties:

- **User-discoverable.** They type `/audit-refs`.
- **Context-isolated.** The audit runs in a child, doesn't bloat the parent.
- **Tool-restricted.** The subagent cannot edit files.
- **Composable.** Other commands can invoke other subagents.

This is harness engineering at its most rewarding: a complex workflow reduced to a single user keystroke, with each layer doing one job.

## 11. Anti-patterns

| Smell | Why it's bad | Fix |
|---|---|---|
| **Slash command IS the procedure.** 400 lines of step-by-step in `new-note.md`. | Cannot reuse from a subagent or a skill. | Move the procedure to a skill; command delegates. |
| **Subagent with full tool list.** `tools` omitted, child has everything. | Removes the safety benefit of subagents. | Specify the minimum tool set. |
| **Subagent that calls itself.** Infinite recursion if `description` matches. | Stack blow / budget burn. | Forbid in the system prompt; add a max-depth guard if available. |
| **Slash command with no arg validation.** `/new-note 99 "X"` creates `99.1. X.md` in nowhere. | User confusion; broken files. | Verify the track folder exists in step 1. |
| **Two commands doing the same thing.** `/new-note` and `/scaffold-note`. | Discovery confusion. | Pick one; alias the other. |
| **Subagent that doesn't return a summary.** Just dumps tool outputs. | Defeats the context-saving purpose. | Require a 1-paragraph summary as the last message. |

## 12. Sizing recommendations

Healthy harnesses tend to have:

| Repo size | Slash commands | Subagents |
|---|---|---|
| Personal repo | 2–5 | 0–2 |
| Team repo | 5–15 | 3–8 |
| Platform repo | 15+ (categorized) | 10+, with namespacing |

If you have 50 commands, you have a discovery problem; group them by prefix (`/db-…`, `/auth-…`) and document the groups in `AGENTS.md`. If you have 20 subagents, audit for ones that should be merged into a single, parameterized agent.
