# 11.6. Slash Commands and Subagents

> Companion to [11.4. Skills](./11.4.%20Skills.md). Skills are *agent-routed* procedures — the agent decides when to invoke them. Slash commands are *user-routed* — the user types `/name`. Subagents are *parent-dispatched* — the current agent calls a child agent. All three move work between contexts; the difference is who pulls the trigger.

A configured harness has four call-sites where work crosses a context boundary: the user types something, the model decides something, the agent loop spawns a child, and — most recently — a peer session sends a message. Slash commands and subagents are the explicit, named entry points for the first and third. Skills cover the second. Cross-session messaging ([§12](#12-coordination-beyond-parentchild--resuming-messaging-sessions)) covers the fourth.

---

## 1. Slash commands — definition

A **slash command** is a user-invokable prompt stored as a markdown file with frontmatter. The user types `/name <args>`, the harness inlines the file body (substituting argument placeholders) as if the user had typed it, and the loop continues.

The shape, mirrored across vendors:

```markdown
---
description: Scaffold a new numbered curriculum note in a track folder.
argument-hint: <track-folder-or-number> <title>
---

# /new-note

(Body: instructions that read like a prompt to the agent. May reference
$ARGUMENTS for the raw argument string, or interpolate specific args.)
```

The body is **a prompt the user is sending**, not a function the agent is calling. That distinction matters: slash commands are syntactic sugar for "I keep typing this", not a new control-flow primitive.

## 2. Slash commands vs. skills

The most common confusion. Both store reusable procedures as markdown.

| Axis | Slash command | Skill |
|---|---|---|
| Trigger | User explicitly types `/name` | Agent routes by intent |
| Discovery | User must know it exists | Description-routed, automatic |
| Argument handling | Positional, structured (`$1`, `$ARGUMENTS`) | Loose, derived from prompt |
| Location | `.cursor/commands/`, `.claude/commands/` | `.claude/skills/`, others |
| Use case | "Give me a button" | "Whenever the user wants X" |
| Composes with | Can invoke skills | Cannot invoke commands (they're user-facing) |

The practical pattern: commands are thin, skills are thick. The command does argument parsing and disambiguation; it delegates the *how* to a skill.

```text
User types /new-note 5 "Programmatic Tool Calling"
        │
        ▼
.cursor/commands/new-note.md   ← parses args, picks track folder
        │
        ▼
.claude/skills/add-curriculum-note/SKILL.md   ← scaffolds the file
```

> Architectural takeaway — the command is *what the user invokes*. The skill is *what the harness reuses*. Don't put the workflow in the command and then duplicate it in a skill — pick one canonical place and link.

## 3. Slash command anatomy

Standard sections (see this repo's [`.cursor/commands/new-note.md`](../.cursor/commands/new-note.md)):

1. **Frontmatter** — `description` (one sentence), `argument-hint` (display string).
2. **Title** — `# /<name>`.
3. **Usage** — explicit example invocations.
4. **Steps** — what the agent should do, numbered, prescriptive.
5. **Constraints** — what the agent must NOT do.
6. **Optional**: output expectations, fallback behavior, links to the skill it delegates to.

Length budget: 30–120 lines. A command that wants to grow past that is hiding a skill.

## 4. Subagents — definition

A **subagent** is a child agent loop dispatched by the parent. It has:

- Its own **system prompt** (often domain-narrow: "you are a reference validator").
- Its own **tool subset** (often restricted: read-only, no write).
- Its own **context window** — historically the defining property, but no longer unconditional. See [§5](#5-context-inheritance--clean-slate-vs-fork).
- Its own **return value** (a single final message to the parent).

In Claude Code, subagents live in `.claude/agents/<name>.md`:

```markdown
---
name: reference-validator
description: Use to audit the `## References` section of one or more curriculum notes…
tools: Read, Glob, Grep, WebFetch
model: inherit
---

# Reference Validator

(Body: system prompt for the child agent.)
```

In Cursor, the equivalent is the `Task` tool dispatched with a `subagent_type`. The set of subagent types is user-global (configured in `~/.cursor/` or via plugins); per-repo subagent files are not yet a first-class feature in Cursor at time of writing — see [11.9. Vendor Diff Matrix](./11.9.%20Vendor%20Diff%20Matrix.md).

## 5. Context inheritance — clean slate vs. fork

For most of the subagent's short history, the defining property was **input isolation**: the child begins with an empty window and learns only what the parent's delegation message tells it. That is no longer the default. Since Claude Code 2.1.232 (13 August 2026), **fork mode is on by default in interactive sessions**, and a forked subagent inherits the parent conversation wholesale.

The two are distinct primitives sharing one name:

| Axis | Clean-slate subagent | Fork |
|---|---|---|
| Input context | Fresh window plus a delegation message the parent composes | Full conversation history as of the spawn |
| System prompt | The definition file's body | Byte-identical to the parent's |
| Tools | The definition's `tools` list, then two harness filters | The parent's exact tool pool; both filters skipped |
| Model | The definition's `model` field | Same as the parent |
| Prompt cache | Its own | Shared with the parent |
| Recursion | May spawn children, to three levels deep | Cannot spawn further forks |

What forking does *not* change: the child's tool calls stay out of the parent's transcript, and only its final message returns.

> **Output isolation is preserved; input isolation is the thing forking trades away.** The parent's window still stays clean. What you give up is the guarantee that the child reasons only from a brief you wrote deliberately.

The prompt-cache row is the load-bearing one. Because a fork's system prompt and tool definitions are identical to the parent's, its first request reuses the parent's cached prefix. A cold subagent pays for its own prefix from scratch. So the cost comparison is not "one call versus two" — it is *briefing cost* versus *cache reuse*.

> Architectural takeaway — choose on briefing cost. If writing a delegation prompt good enough for a cold child would cost more tokens than the child's actual task, fork. If the parent's accumulated history is *noise* for the task — a fresh pair of eyes on a file, a validator that should not know what the parent already concluded — pay the briefing cost and stay cold.

### What a clean-slate child actually loads

"Empty window" overstates it. A non-fork subagent starts with its own system prompt, the delegation message, the full `CLAUDE.md` hierarchy, a git-status snapshot taken at the parent session's start, the body of any skill named in its `skills` field, and — when it holds the messaging tool and at least one sibling is named — a roster of the agents it may address. The built-in `Explore` and `Plan` agents are the exceptions — they skip `CLAUDE.md` and git status to keep research cheap, and there is no setting to change that.

This matters when debugging a subagent that "ignored the project rules": it did load them. The likelier fault is that the delegation message contradicted them.

### Controlling fork mode

| Session kind | Default | Override |
|---|---|---|
| Interactive | Fork mode on | `CLAUDE_CODE_FORK_SUBAGENT=0` |
| Non-interactive (`-p`) | Fork mode off | `CLAUDE_CODE_FORK_SUBAGENT=1` |
| Agent SDK | Fork mode off | `CLAUDE_CODE_FORK_SUBAGENT=1` |

Two consequences are easy to miss. First, where fork mode is on, *every* spawned subagent runs in the background and the model cannot request the foreground — the flag changes scheduling, not just context. Second, to keep background dispatch but forbid forking specifically, deny the subagent type with an `Agent(fork)` permission rule rather than turning the mode off.

The user-facing entry point is `/subtask <task>`, which starts a fork regardless of mode. A fork may also be spawned with `isolation: "worktree"` so its edits land in a throwaway git worktree instead of the live checkout — the natural pairing when you fork several times to try competing approaches from one starting point.

## 6. When to dispatch a subagent

Three concrete reasons:

| Reason | Example |
|---|---|
| **Context isolation** | A long exploration that would bloat the parent's context — dispatch a child to do the search, parent receives a summary |
| **Capability narrowing** | A task that should run with a restricted toolset — read-only validator that cannot accidentally edit |
| **Parallelism** | Multiple independent tasks — dispatch N children, await all, synthesize |

Anti-reasons (don't dispatch a subagent for these):

- **Token saving on the parent's prompt.** A cold subagent has its own setup cost; the savings are usually a wash. A fork changes this arithmetic — it reuses the parent's cached prefix — but a fork also does not isolate the input, so it is not a substitute for a validator.
- **"Different persona".** A different `description` is enough; a separate process is overkill.
- **Tool that the parent doesn't have.** Add the tool, don't spawn a child.

## 7. The context-isolation pattern

The most useful subagent pattern is **exploration → summary**:

```text
Parent agent:                  Subagent (explore):
  User: "Refactor the auth     ┌─────────────────────────┐
   module to use JWT."         │ Read 15 files, run     │
                               │ grep across 200 more.   │
  ──── dispatch ─────────►     │ Build a mental model.   │
                               │ Return: 1-page summary  │
                               └─────────────────────────┘
  ◄─── 1-page summary ──── ─

  (Parent's context now has the summary, not the 15 files.
   Parent uses its full window to design and write the refactor.)
```

Why it matters:

> **Subagents trade wall-clock for context window.** You pay a model call (or several) up front; you get back a clean, compact context for the parent's hard work.

This is the same idea as RAG, but for the agent's own working set. Useful any time the parent would otherwise read and discard a lot of files.

Note that this pattern requires a *cold* child. Forking here would defeat the purpose: the fork already carries the parent's history, so it saves the parent nothing on input — only on the transcript of the exploration itself.

## 8. The capability-narrowing pattern

Pair a subagent with a restricted `tools:` list. The child *cannot* edit, regardless of what the model decides:

```yaml
---
name: reference-validator
tools: Read, Glob, Grep, WebFetch   # no Edit, no Write, no Bash
---
```

This is a *belt* on top of the *braces* of permissions ([11.5](./11.5.%20Hooks%2C%20Permissions%2C%20and%20Side%20Effects.md)). Even if the model emits a `tool_use` for `Edit`, the subagent's tool registry doesn't include it — the call fails cleanly.

> Lesson — use subagents for *capabilities*, not just *prompts*. A "validator that cannot edit" is structurally safer than a system prompt that says "do not edit".

The corollary in a fork-by-default world: **a fork is not a capability boundary.** Forks skip the tool filters and receive the parent's exact tool pool, so a restricted-tool child must be a named subagent with a `tools` list. If the safety property you want is "cannot write", forking silently removes it.

## 9. The parallelism pattern

When the parent agent has several **independent** tasks, dispatch in parallel:

```text
Parent: "Audit references in tracks 4, 5, and 7."
  │
  ├──► subagent(reference-validator, "track 4")
  ├──► subagent(reference-validator, "track 5")
  └──► subagent(reference-validator, "track 7")
       │
       ▼
  (await all)
       │
       ▼
  Synthesize three reports into one summary.
```

Caveats:

- **Independence is mandatory.** If task B depends on task A's findings, parallelism is a hazard, not a win.
- **N is bounded.** Claude Code's default ceiling is 20 concurrent subagents per session (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` to change it); beyond a handful, latency usually stops improving anyway.
- **Cost is N×, unless the prefix is shared.** N cold subagents = N system-prompt reads = N billed prefixes. Fanning out N forks from one parent instead reuses the cached prefix. Harnesses have started staggering same-prefix siblings so the first writes the cache entry and the rest read it, rather than N racing children all paying full price.

> Architectural takeaway — parallel fan-out is a *cache* problem before it is a concurrency problem. The dominant cost of a wide fan-out is usually N duplicated prefixes, not N model calls.

## 10. Subagent design checklist

When writing a subagent file (`.claude/agents/<name>.md`), verify:

1. `description` starts with "Use to …" and lists concrete triggers.
2. `tools` list is the minimum required (deny-by-default).
3. System prompt body declares the single output format the child must return.
4. "Hard rules" section repeats the most-important invariants.
5. "Anti-patterns" section calls out the obvious mistakes the child could make.
6. Returns a *report*, not a *commit*. Mutations happen in the parent, where they are reviewable.

The last bullet is contested. Some teams let subagents commit code directly (e.g., the `code-implementer` pattern). For safety, the higher-leverage path is **parent commits, subagents recommend** — the parent has more context for final decisions.

## 11. Slash command + subagent composition

The killer combo: a slash command that dispatches a subagent.

```markdown
---
description: Audit references on all numbered notes in the repo.
---

# /audit-refs

Dispatch the `reference-validator` subagent with scope `**/*.md`.
Synthesize its report.
```

Properties:

- **User-discoverable.** They type `/audit-refs`.
- **Context-isolated.** The audit runs in a child, doesn't bloat the parent.
- **Tool-restricted.** The subagent cannot edit files.
- **Composable.** Other commands can invoke other subagents.

This is harness engineering at its most rewarding: a complex workflow reduced to a single user keystroke, with each layer doing one job.

## 12. Coordination beyond parent–child — resuming, messaging, sessions

Parent-dispatch describes a tree: work flows down, one summary flows back, and the child is dead on return. Two additions have widened that into a graph.

**Resuming a finished child.** A completed subagent that receives a message auto-resumes in the background — no second `Agent` call, no re-briefing, its context intact. This turns the subagent from a function call into an addressable, long-lived correspondent. The obvious hazard is name collision: if a re-spawned agent has taken a name, a message addressed to that name would reach the wrong agent. Harnesses now bind the check to the conversation and refuse the send rather than misdeliver, reporting which agent the name currently reaches. Address by ID when you mean a specific instance.

**Messaging a peer session.** Since Claude Code 2.1.224, and with `@`-mention targeting added in 2.1.232, independent sessions on the same machine can address each other by name via `ListAgents` and `SendMessage`. This is a genuinely different topology — the peers have no parent in common, no shared transcript, and no shared permission state.

| Channel | Direction | Carries | Lifetime |
|---|---|---|---|
| Subagent dispatch | Parent → child | Delegation prompt | One task |
| Fork | Parent → child | Entire conversation | One task |
| Subagent resume | Parent → finished child | Plain text | Reopens the child's context |
| Cross-session message | Peer → peer | Plain text only | Independent sessions |

The design constraint that makes peer messaging tractable is that **the channel is deliberately thin**. Only text crosses. Never conversation history, never files, never permissions. An inbound message cannot approve a pending permission prompt, cannot alter permission settings or `CLAUDE.md`, and a slash command inside the text arrives as inert characters rather than executing. Receiving sessions choose `accept`, `hold`, or `refuse`; when nothing is configured, the default derives from the two sessions' permission modes, and a session that bypasses prompts holds messages from one that does not. Loops are rate-limited and identical repeats within a short window are dropped, so two agents cannot talk each other into an infinite exchange.

> Architectural takeaway — peer messaging is a *notification* channel, not a *context-transfer* channel. If two sessions need the same context, resume one session or fork it; do not attempt to reconstruct state by narrating it across the wire. The thinness is the safety property, not a limitation to engineer around.

The practical use is coordinating parallel worktrees: one session lands a schema migration and tells the session working the API that rebasing is now safe. That is a message worth sending. "Here is everything I learned in the last hour" is not.

## 13. Anti-patterns

| Smell | Why it's bad | Fix |
|---|---|---|
| **Slash command IS the procedure.** 400 lines of step-by-step in `new-note.md`. | Cannot reuse from a subagent or a skill. | Move the procedure to a skill; command delegates. |
| **Subagent with full tool list.** `tools` omitted, child has everything. | Removes the safety benefit of subagents. | Specify the minimum tool set. |
| **Subagent that calls itself.** Infinite recursion if `description` matches. | Stack blow / budget burn. | Forbid in the system prompt; add a max-depth guard if available. |
| **Slash command with no arg validation.** `/new-note 99 "X"` creates `99.1. X.md` in nowhere. | User confusion; broken files. | Verify the track folder exists in step 1. |
| **Two commands doing the same thing.** `/new-note` and `/scaffold-note`. | Discovery confusion. | Pick one; alias the other. |
| **Subagent that doesn't return a summary.** Just dumps tool outputs. | Defeats the context-saving purpose. | Require a 1-paragraph summary as the last message. |
| **Forking a child that was supposed to be restricted.** The "read-only validator" is spawned as a fork. | Forks skip the tool filters and inherit the parent's full pool — the restriction silently vanishes. | Spawn restricted children by name with an explicit `tools` list; never by fork. |
| **Narrating context across a peer message.** Session A sends session B a 2,000-word recap. | The channel is plain text with no cache sharing; you pay full price on both ends and B still lacks the artifacts. | Send the decision, not the reasoning. Point at a file or a commit. |

## 14. Sizing recommendations

Healthy harnesses tend to have:

| Repo size | Slash commands | Subagents |
|---|---|---|
| Personal repo | 2–5 | 0–2 |
| Team repo | 5–15 | 3–8 |
| Platform repo | 15+ (categorized) | 10+, with namespacing |

If you have 50 commands, you have a discovery problem; group them by prefix (`/db-…`, `/auth-…`) and document the groups in `AGENTS.md`. If you have 20 subagents, audit for ones that should be merged into a single, parameterized agent.

## 15. Cache TTL follows lifetime, not importance

Prompt caching is priced on two axes — what you pay to write a cache entry, and how long the entry survives before the next read misses. A longer TTL costs more per write. The natural instinct is to spend that on whatever seems most important, which is usually the main conversation. That instinct happens to be right, but for a reason worth stating explicitly: **the parent and its children have opposite lifetimes.**

The main conversation is long-lived and returns to the same stable prefix — system prompt, `AGENTS.md`, tool definitions — across gaps of minutes while the user reads, thinks, or steps away. A subagent from §6 is the opposite: it is spawned, runs a bounded tool loop, returns a summary, and is gone. It never comes back to its own prefix after an idle gap, because there is no idle gap.

Claude Code 2.1.243 exposes this as two independent settings, `promptCacheTtl` and `subagentPromptCacheTtl`, so API-key and cloud-provider users can hold a one-hour cache on the main conversation while subagents stay at five minutes.

> Architectural takeaway: cache TTL is a bet on idle time, not on value. Pay the long-TTL premium exactly where a human's think-time sits between two turns; anywhere the loop runs to completion without stopping, the short TTL is not a compromise, it is the correct setting. The §9 parallelism pattern makes this concrete — twenty concurrent children each writing a one-hour cache entry they will never read twice is pure write premium.

This also composes badly if you get it backwards. A fork (§5) inherits the parent's prefix, so a long parent TTL is what makes forking cheap; a clean-slate child builds its own prefix from nothing, so its TTL only ever pays for reads *within* that child's own short run.
