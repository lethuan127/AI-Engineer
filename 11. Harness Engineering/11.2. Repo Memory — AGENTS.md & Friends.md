# 11.2. Repo Memory — AGENTS.md & Friends

> Companion to [11.3. Rules and Project Instructions](./11.3.%20Rules%20and%20Project%20Instructions.md). Repo memory is the *unconditional* instruction layer — always in context, regardless of what file you're editing. Rules are the *conditional* layer. Get the boundary right and both stay small.

The first byte of user-controlled prompt that every coding agent reads is the **repo memory file** at the project root. It is the agent's `~/.bashrc` for your codebase: tone, conventions, hard constraints, allowed and forbidden actions. Get it right and most other configuration becomes redundant.

---

## 1. The files

There are three filenames in circulation. Their semantics are converging but not identical.

| File | Origin | Read by today | Stance |
|---|---|---|---|
| `AGENTS.md` | OpenAI Codex CLI (Apr 2025), endorsed by Cursor, Aider, Sourcegraph, others | Cursor, Codex CLI, Aider, Sourcegraph Cody, OpenCode, **Claude Code (with import)** | **Recommended default.** Open convention, multi-vendor. |
| `CLAUDE.md` | Anthropic Claude Code (Feb 2025) | Claude Code (native), tools that mimic CC | Claude-only. Becoming legacy as Claude Code learns to read `AGENTS.md`. |
| `.cursorrules` | Cursor (legacy) | Cursor (deprecated path) | Use only for backward compatibility. New repos: skip. |

Practical rule for 2026:

> **Write one `AGENTS.md`** and, if you support Claude Code, optionally a one-line `CLAUDE.md` that imports it (`@AGENTS.md`). Don't maintain three.

Both Cursor and Claude Code in current versions read `AGENTS.md`; Claude Code additionally reads `CLAUDE.md` and supports an `@`-import directive that lets you point it at `AGENTS.md`.

## 2. What belongs in repo memory

The four buckets:

| Bucket | Example | Why here |
|---|---|---|
| **Repo identity** | "This is a curriculum repo of markdown architectural notes." | One sentence the agent should never need to re-derive |
| **House style** | Heading levels, naming convention, voice, forbidden vocabulary | Applied to every edit; cheaper as memory than as a rule |
| **Working agreement** | What's allowed without asking, what requires confirmation, what is forbidden | Permission-shaped, but applies repo-wide |
| **Cross-references** | "See `7.1` as the style reference", "skills live in `.claude/skills/`" | Pointers the agent uses to bootstrap into other context |

Each is **always-relevant**. If a topic only applies when editing a *particular* file or class, it belongs in a rule ([11.3](./11.3.%20Rules%20and%20Project%20Instructions.md)) or a skill ([11.4](./11.4.%20Skills.md)) — not in repo memory.

## 3. What does *not* belong

Common bloat to keep out:

- **Step-by-step workflows.** Those are skills. Repo memory is a *constitution*, not a *playbook*.
- **Tool documentation.** The vendor already supplies tool schemas in the system prompt; restating them wastes tokens.
- **Anything model-specific.** "Use Claude 4 for X" leaks into a repo that someone may open in a different agent next week.
- **Secrets, API keys, environment values.** Those go in env files; memory is checked in.
- **Long lists of "do this, don't do that"** that read like an issue tracker. If you have 30 of them, you have a rules problem, not a memory problem.

> Lesson — when memory grows beyond ~200 lines, it has stopped being a constitution and become an unread README. Split.

## 4. Precedence and conflicts

When multiple memory-like instructions exist, the precedence in agent prompt assembly is roughly:

```
1. Vendor system prompt           (highest, you cannot edit)
2. Repo memory                    (AGENTS.md / CLAUDE.md at root)
3. Per-folder memory              (CLAUDE.md / AGENTS.md in subfolders, Claude Code)
4. Matched rules                  (file-scoped .mdc, project memory imports)
5. Matched skills                 (description-routed)
6. User message                   (this turn's prompt)
```

A few traps:

- **Per-folder memory overrides root.** Useful for monorepos (`packages/foo/AGENTS.md` for Python conventions, `packages/bar/AGENTS.md` for TypeScript). Dangerous when you forget.
- **Rules can contradict memory.** If `AGENTS.md` says "use snake_case" and `.cursor/rules/style.mdc` says "use camelCase", the rule typically wins because it's matched closer to the cursor. Audit for this. See [11.11. Operational Concerns](./11.11.%20Operational%20Concerns.md).
- **The user message always wins.** A user saying "ignore the style guide, just give me the code" overrides everything below it. This is correct behavior but worth knowing.

## 5. Anatomy of a good `AGENTS.md`

Borrowing the structure from this repo's [`AGENTS.md`](../AGENTS.md):

```markdown
# AGENTS.md — <Project Name>

## 1. What this repository is
   (One paragraph. What does the codebase *do*?)

## 2. House style
   (Numbered list of style rules. Tables where comparison helps.)

## 3. File naming / project layout
   (Conventions any new file must follow.)

## 4. Working agreement
   (Allowed without asking / confirm with user first / forbidden — three groups.)

## 5. Required structures
   (E.g., every note ends with a References section.)

## 6. Linked tooling
   (Pointers: rules live in .cursor/rules, skills in .claude/skills, etc.)

## 7. Mental model
   (One paragraph: voice, audience, success criteria.)
```

Seven sections, each scoped. The whole file fits on one screen of an IDE. No section grows unbounded; if it wants to, that's a sign it belongs in a rule or a skill.

## 6. The single-source-of-truth pattern

When you have parallel files (`AGENTS.md` for Cursor/Codex/Aider, `CLAUDE.md` for Claude Code), pick one as canonical and have the other import it.

**Claude Code import syntax:**

```markdown
# CLAUDE.md

@AGENTS.md
```

The `@<path>` directive inlines the target. Now your single source of truth is `AGENTS.md`; `CLAUDE.md` is a one-line stub.

**Cursor:** reads `AGENTS.md` natively in current versions; no import needed.

**Codex CLI / Aider / Sourcegraph Cody:** read `AGENTS.md` natively.

Anti-pattern: maintaining `AGENTS.md` and `CLAUDE.md` as parallel-but-slightly-divergent files. After three commits, they drift. After thirty, one is stale and you don't know which.

## 7. Per-folder memory

Both Claude Code and Cursor support per-folder memory files for monorepos. The pattern:

```
my-monorepo/
├── AGENTS.md                         (repo-wide constitution)
├── packages/
│   ├── api/
│   │   └── AGENTS.md                 (Python, FastAPI conventions)
│   └── web/
│       └── AGENTS.md                 (TypeScript, Next.js conventions)
```

When the agent is working in `packages/web/`, both the root `AGENTS.md` and `packages/web/AGENTS.md` are in context. The per-folder file should be **additive and specific** — don't restate the root.

> Why it matters — the alternative is a 1000-line root `AGENTS.md` with "if you're in the web package, do X; if API, do Y" sections that the agent has to filter through every turn. Per-folder memory is conditional loading at the directory level.

## 8. Versioning and review

Repo memory is shipping code. Treat it as such:

- Check it into git from the first commit.
- Review changes in PRs like any other production file.
- Add a test (or at least a hook) that flags accidental deletions — losing `AGENTS.md` is a silent regression.
- When changing it, ask: "would I want this for every future contributor for the next year?" If not, push it down to a rule or skill.

> Architectural takeaway — repo memory is the *constitution* of your agent harness. Few articles, all load-bearing, rarely amended. If you find yourself amending it weekly, your discipline has slipped.

## 9. Decision tree — memory vs. rule vs. skill

Use this when you're not sure where a new instruction belongs:

```text
Does it apply to *every* edit in the repo?
├── Yes → AGENTS.md.
└── No → Does it apply to a specific file pattern?
        ├── Yes → .cursor/rules/<name>.mdc with `globs:`.
        └── No → Is it a multi-step procedure invoked by intent?
                ├── Yes → .claude/skills/<name>/SKILL.md.
                └── No → It probably doesn't need a config file at all.
                          (User can include it in the prompt that turn.)
```
