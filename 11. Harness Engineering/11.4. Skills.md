# 11.4. Skills

> Companion to [11.3. Rules and Project Instructions](./11.3.%20Rules%20and%20Project%20Instructions.md). Rules are conditional context; skills are conditional **procedures**. The unit of reuse for "when the user wants X, here is how to do X" — versioned, packaged, addressable.

A skill is a SKILL.md file (plus optional supporting files) that the agent **discovers by description and invokes when intent matches**. It's the closest thing the harness has to a callable function: small, named, side-effect-clear, reusable.

---

## 1. The Anthropic Agent Skills standard

Anthropic published "Agent Skills" in late 2025 as a portable format. The shape:

```
skills/<name>/
├── SKILL.md           ← required, the procedure
├── reference.md       ← optional, deeper material loaded on demand
├── examples/          ← optional, worked examples
└── scripts/           ← optional, helper scripts
```

`SKILL.md` is the entry point. It has frontmatter and a body:

```markdown
---
name: add-curriculum-note
description: Use when creating a new numbered curriculum note (X.Y. Title.md) anywhere in the AI-Engineer repo. Encodes filename convention, structural skeleton, voice…
---

# Add Curriculum Note

(Body: when to use, when NOT to use, workflow steps, hard rules.)
```

The frontmatter has two load-bearing fields:

| Field | Purpose |
|---|---|
| `name` | Stable identifier. Filesystem path is `<name>/SKILL.md`. |
| `description` | The **router**. The agent reads only this field at load time and uses it to decide whether to pull the full SKILL.md into context. |

That second point is the architectural crux of the standard.

## 2. Description as router

Here is what makes skills different from rules.

Rules with `globs` activate by **file pattern**. Skills with `description` activate by **intent**. The agent reads the descriptions of all available skills up front, decides which one(s) apply to the user's current request, and pulls the bodies in.

This means:

> **The `description` is the most important sentence in the skill.** It is the only thing the agent sees most of the time.

Hallmarks of a good description:

| Trait | Example |
|---|---|
| Starts with "Use when …" | `Use when creating a new numbered curriculum note (X.Y. Title.md)` |
| Names concrete triggers | `User asks: "add a note", "write a new note", or runs /new-note` |
| Distinguishes from sibling skills | `Encodes filename convention, structural skeleton, voice` |
| One sentence, no fluff | ~30 words; nothing about "comprehensive helper" |

Bad descriptions:

- `A skill for adding notes` — vague, no trigger.
- `Adds a new note to the curriculum. This skill is comprehensive…` — marketing, not routing.
- `Use this skill when needed.` — useless.

> Architectural takeaway — every skill description is competing for the agent's attention against every other skill in scope. If your description doesn't carry its weight, your skill silently never fires.

## 3. Lifecycle — how a skill enters context

```text
┌────────────────────────────────────────┐
│ 1. Harness scans skill paths           │
│    .claude/skills/, ~/.claude/skills/, │
│    plugin caches, .cursor/skills/      │
└────────────────┬───────────────────────┘
                 ▼
┌────────────────────────────────────────┐
│ 2. Parses frontmatter only             │
│    Loads (name, description) into a    │
│    "skill registry" appended to system │
│    prompt every turn                   │
└────────────────┬───────────────────────┘
                 ▼
┌────────────────────────────────────────┐
│ 3. Model receives user turn            │
│    Sees skill registry; emits a        │
│    "load skill" decision (implicit)    │
└────────────────┬───────────────────────┘
                 ▼
┌────────────────────────────────────────┐
│ 4. Harness reads full SKILL.md         │
│    Inserts body into context           │
│    Subsequent turns have full skill    │
└────────────────────────────────────────┘
```

Practical consequence: **descriptions are always loaded, bodies are conditional.** If you have 30 skills with 50-word descriptions, that's 1500 tokens every turn just for the registry. A few-dozen skills is fine; hundreds is a real cost.

## 4. SKILL.md anatomy

Standard sections (see this repo's [`.claude/skills/add-curriculum-note/SKILL.md`](../.claude/skills/add-curriculum-note/SKILL.md)):

1. **Frontmatter** — `name`, `description`. That's it.
2. **Title** — `# Skill Name`.
3. **When to use / When NOT to use** — explicit boundaries. Saves the model from over- or under-firing.
4. **Inputs** — what the skill expects: arguments, currently focused file, env.
5. **Workflow** — numbered steps. Each step is one tool call's worth of action.
6. **Hard rules** — forbidden actions, invariants. Repeat key constraints here even if `AGENTS.md` has them.
7. **Verifying** — optional. How to confirm the skill executed correctly (lint, test, hook).

Length budget: 100–300 lines. Beyond ~300, the skill is doing too much; split it.

## 5. When to write a skill vs. a slash command

These overlap. Both inject a procedure into context. The difference:

| Axis | Skill | Slash command |
|---|---|---|
| Trigger | Intent (agent decides) | User explicitly types `/name` |
| Composes with | Other skills, rules, memory | Other commands, skills |
| Argument handling | Loose — pulled from prompt | Structured — `$ARGUMENTS` placeholder |
| Discovery | Description-based, automatic | User has to know it exists |
| Use case | "Whenever the user asks to do X" | "Give me a button for X" |

Many primitives are best as **both**: the slash command is the explicit UI entry point, and the skill is the source of truth that the command delegates to. This repo does that: `/new-note` (`.cursor/commands/new-note.md`) delegates to the `add-curriculum-note` skill.

## 6. Skill, rule, and command — pick one

When you have an instruction that could be any of the three, decide with this table:

| Need | Use |
|---|---|
| "Whenever the user does X intent" | Skill |
| "Whenever the agent edits a file matching pattern" | Rule (Auto-Attached) |
| "Whenever the user types `/X`" | Slash command (delegates to skill) |
| "Always, for every turn" | Repo memory (`AGENTS.md`) |
| "When the user calls out `@X`" | Manual rule, or rare |

Mixing primitives without a clear discipline produces drift. A consistent pattern: **memory for constitution → rules for file-scoped contracts → skills for procedures → commands for explicit invocation**.

## 7. The single-source-of-truth pattern

When the same procedure is referenced by a rule, a command, and a subagent, pick **the skill** as canonical and have the others link to it:

```text
.cursor/rules/references-section.mdc
   "Detailed workflow: see .claude/skills/normalize-references/SKILL.md"

.cursor/commands/check-refs.md
   "Read .claude/skills/normalize-references/SKILL.md and follow it."

.claude/commands/check-refs.md
   "Read .claude/skills/normalize-references/SKILL.md and follow it."

.claude/agents/reference-validator.md
   "Use the format rules in .claude/skills/normalize-references/SKILL.md as
    the canonical reference for what 'valid' looks like."
```

Now there is one place to update when the format changes. Rules and commands stay short and stable.

> Lesson — skills are the function library of a harness. Everything else is a thin wrapper.

## 8. Skill storage and discovery

| Location | Scope | Read by |
|---|---|---|
| `.cursor/skills/<name>/SKILL.md` | This repo only | Cursor (native since 2.4, Nov 2025) |
| `.claude/skills/<name>/SKILL.md` | This repo only | Claude Code |
| `~/.cursor/skills/<name>/SKILL.md` | User-global | Cursor |
| `~/.claude/skills/<name>/SKILL.md` | User-global | Claude Code |
| `~/.cursor/plugins/cache/.../skills/<name>/SKILL.md` | Plugin-provided | Cursor (auto-installed by plugin) |
| `~/.claude/plugins/cache/.../skills/<name>/SKILL.md` | Plugin-provided | Claude Code |

Because Agent Skills is now a [published open standard](https://agentskills.io/home), the directory layout (`<name>/SKILL.md` with `name` + `description` frontmatter) is identical across vendors. For repo-scoped skills, the canonical move is to put them under the vendor folder you ship with — `.claude/skills/` if Claude Code is the primary surface, `.cursor/skills/` if Cursor is — and document the path so contributors looking from the other tool know where to find them. Cursor 2.4 also includes a built-in `/migrate-to-skills` skill that converts existing dynamic rules and slash-commands into skills.

## 9. Anti-patterns

| Smell | Why it's bad | Fix |
|---|---|---|
| **Description ends with "and more"** | Vague routing → skill underfires | List concrete triggers |
| **SKILL.md > 500 lines** | Costs tokens on every invocation | Split or move detail to `reference.md` |
| **Skill duplicates a rule** | Drift | Pick one as canonical; the other links |
| **Skill has no "When NOT to use"** | Over-fires | Add an exclusion section |
| **Skill embeds API keys / paths to local-only tools** | Breaks for other contributors | Reference env vars; document setup |
| **Skill calls a tool that doesn't exist in the harness** | Silent failure | Validate against the agent's tool surface |
| **Skill name doesn't match folder** | Broken discovery | `name` frontmatter must equal folder name |

## 10. Skill governance

For a team-shared harness:

- **Treat skills as code.** Review in PRs. Add a `lint` step that validates frontmatter.
- **Version with the repo.** Skill behavior changes are part of the changelog.
- **Eval before shipping.** A skill that changes the agent's behavior on common requests should have a smoke test ([11.11](./11.11.%20Operational%20Concerns.md)).
- **Retire skills aggressively.** A skill that hasn't been invoked in 90 days is probably stale; delete or rewrite.

> Architectural takeaway — skills are the part of the harness most likely to *become a library*. Build them with the same care you'd give to a shared SDK.
