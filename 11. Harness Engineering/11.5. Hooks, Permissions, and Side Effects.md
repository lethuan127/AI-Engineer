# 11.5. Hooks, Permissions, and Side Effects

> Companion to [11.4. Skills](./11.4.%20Skills.md). Rules and skills shape what the agent *says*. Hooks and permissions shape what the agent *does* — what it's allowed to touch, what runs after it acts, and what gets blocked before it leaves a mess.

This is the dangerous chapter. Hooks are the one primitive in a coding harness that runs arbitrary code on your machine in response to model output. Done well, they are a quiet safety net. Done badly, they are loud, slow, and the reason your agent session is unrecoverable.

---

## 1. What a hook is

A hook is a **user-supplied script invoked by the harness at a specific point in the agent loop**. Both Cursor and Claude Code expose hook points; the names differ, the semantics are similar.

The event surface in current versions:

| Event class | When it fires | Typical use |
|---|---|---|
| **Pre-model** (`UserPromptSubmit`) | Just before the model is called | Inject extra context; redact secrets from the prompt |
| **Pre-tool** (`PreToolUse`, `beforeShellExecution`) | After model emits `tool_use`, before the tool runs | **Block** dangerous calls; rewrite arguments |
| **Post-tool** (`PostToolUse`) | After the tool result is computed, before it goes back to the model | Lint, transform, summarize, redact |
| **File-level** (`afterFileEdit`, `beforeFileEdit`) | When a file is about to be / has been written | Format, lint, run a quick check |
| **Stop / SubagentStop** | When the agent loop terminates | Cleanup, notification, audit-log dump |
| **Notification / Status** | Idle, waiting, error states | Desktop notification, telemetry |

Each fires synchronously by default — the agent loop **waits** for the hook to return. That is what makes them powerful (`block` a tool call) and what makes them dangerous (a slow hook stalls every turn).

## 2. The blocking vs. advisory split

Two flavors of hook, with very different implications:

| Flavor | Behavior | Failure mode |
|---|---|---|
| **Advisory** | Hook output is appended to the agent context as a note. Loop continues. | Noise; cost of tokens. |
| **Blocking** | Non-zero exit (or specific output) cancels the action. Tool call never happens; edit is rolled back. | Catastrophic — agent loop gets stuck or thrashes. |

> Architectural takeaway — default every hook to advisory unless you have a clear, defended reason to block. Blocking hooks should feel like *production safety equipment*, not lint.

Concretely:

- **Blocking is right for:** preventing `rm -rf /`, blocking writes to `.env`, forbidding pushes to `main`.
- **Advisory is right for:** lint warnings, format reminders, "no References section yet" nudges, telemetry pings.

This repo's reference-section hook ([`.cursor/hooks.json`](../.cursor/hooks.json)) is advisory: it warns but never blocks. A missing References section is a bug, not a security incident.

## 3. Lifecycle of a hook event

```text
   model emits tool_use
           │
           ▼
  ┌─────────────────────────┐
  │ PreToolUse hooks fire   │ ─── any blocks?
  │ (sequential, sync)      │       │
  └────────┬────────────────┘       └─ Yes → abort, surface block reason
           │ all advisory or pass    │
           ▼
   tool executes (bash / fs / MCP)
           │
           ▼
  ┌─────────────────────────┐
  │ PostToolUse hooks fire  │
  │ (sequential, sync)      │
  └────────┬────────────────┘
           │
           ▼
   result → model
```

Three properties to internalize:

1. **Hooks are sequential.** If hook A takes 3 s and hook B takes 4 s, the tool call costs 7 s of wall-clock before any result comes back.
2. **Hooks see arguments and outputs.** A PreToolUse hook can read the proposed shell command. A PostToolUse hook can read the file just written. This is the leverage; it is also the risk surface.
3. **Hooks run with your user's privileges.** They are not sandboxed. A misbehaving hook can do anything your shell can do.

The tool call is not the only hookable transition. As of Claude Code v2.1.251 the same block/confirm/annotate contract extends to **model switching** (`PreModelSwitch`, `PostModelSwitch`), and `SessionStart` resume hooks now receive session staleness and the estimated re-cache cost.

> Why it matters: this generalizes the hook surface from "the agent is about to act on the world" to "the agent is about to change its own execution parameters." A model switch mid-session is a cost event, a capability event, and a cache event all at once — and until it was hookable, it was the one state change a harness could not gate. If you are building your own loop, the lesson is to enumerate *every* transition that changes cost, capability, or context validity, not just tool dispatch. See [Model Routing in the Agent Loop — Per-Step Model Selection](../5.%20AI%20Agents%20%26%20Tool%20Use/Model%20Routing%20in%20the%20Agent%20Loop%20%E2%80%94%20Per-Step%20Model%20Selection.md).

## 4. Permissions — the second mechanism

Permissions are the **allowlist / denylist** governing what tools the agent can call without confirmation. Both vendors expose this as JSON.

Claude Code (`.claude/settings.json`):

```json
{
  "permissions": {
    "allow": [
      "Read(*)",
      "Bash(git status:*)",
      "Bash(git diff:*)"
    ],
    "ask": [
      "Bash(git push:*)",
      "Bash(rm:*)"
    ],
    "deny": [
      "Bash(rm -rf /:*)",
      "Bash(curl * | bash:*)"
    ]
  }
}
```

Cursor (`.cursor/settings.json`, similar shape; UI-driven in the IDE).

Three tiers:

| Tier | Behavior |
|---|---|
| **allow** | Tool runs without confirmation |
| **ask** | Tool prompts user before each call |
| **deny** | Tool is blocked at the harness level, regardless of model output |

> Lesson — permissions are the cheap, declarative safety net. Hooks are the expensive, programmatic one. Use permissions first; reach for a hook only when a pattern can't be expressed in the allowlist.

A rule is only binding if the string it matched names the resource the tool actually touches. Symlink aliases, re-resolution between check and open, and the gap between the permission matcher's grammar and the shell's are three separate ways that stops being true — see [11.19. Permission Check Integrity](./11.19.%20Permission%20Check%20Integrity%20%E2%80%94%20Aliases%2C%20Re-Resolution%2C%20and%20the%20Capability%20Floor.md).

## 5. Hook vs. permission — pick one

| If the rule is … | Use |
|---|---|
| Static pattern (`rm -rf:*`, `git push:*`) | Permission |
| Depends on file path being inside / outside a folder | Permission with glob |
| Depends on file content (e.g., "any file containing `API_KEY=`") | Hook |
| Depends on a quick external check (`gitleaks` scan) | Hook |
| Requires rewriting the command before it runs | Hook |
| Requires running a linter on the output | Hook |
| Requires user judgment per call | `ask` permission |

The default reach should be **permission first, hook only when permission can't express it**.

## 6. Secret hygiene

The single biggest threat surface in a configured harness is **secrets leaking through tool calls**. Three layers:

1. **`.gitignore` your secrets.** `.env`, `*.pem`, `credentials.json`. Not optional.
2. **Deny tool access to them.** Permissions list: `deny: ["Read(.env)", "Read(**/*.pem)"]`.
3. **Pre-model hook to scrub the prompt.** If a user pastes a secret in chat, redact before it reaches the model. (Cursor and Claude Code do some of this server-side; not a substitute for client-side.)

For agent-injected commands:

4. **Deny by default for outbound network.** Permissions: `ask` on `curl`, `wget`, `Bash(http:*)`.
5. **Audit hook on the bash tool.** A PostToolUse hook that grep's tool output for known secret patterns and warns if found.

> Architectural takeaway — assume the agent will at some point try to read a `.env`, paste it into a curl command, and post it to a paste site. Build the harness so each step in that sequence has an independent gate.

## 7. Anti-patterns

Catalog of bad hook patterns:

| Smell | Why it's bad | Fix |
|---|---|---|
| **Slow blocking hook.** `npm test` on every save. | Stalls every edit. | Advisory; or background; or only on `git commit`. |
| **Network call in a hook.** `curl https://lint.example.com` before tool run. | Hook flakes when the service is down. | Move to local-only; if network needed, advisory. |
| **Hook writes back into the agent context.** Verbose output. | Token bloat. | Summarize; cap output length. |
| **Hook does its own model call.** Calling another LLM from a hook. | Recursive cost; loop hazards. | Hooks are deterministic; LLMs in the loop go in subagents. |
| **Hook silently fails.** `set -e` missing; bad exit codes ignored. | Harness thinks all is well. | Always `set -u`, log failures, exit advisory `0` only when intentional. |
| **Hook depends on developer-local tools.** `mdfmt` not installed on CI. | Breaks the harness for others. | Check for tool presence; degrade gracefully. |
| **Hook reads the entire file every time.** | I/O cost on every save. | Read only what you need; cache. |
| **Hook gated by a glob over the Bash command string.** `if: "Bash(cat *)"` to trigger a secret scan. | Shell syntax is not a glob-shaped language. Claude Code 2.1.243 fixed `if` conditions like `Bash(cat *)` firing on unrelated commands that contained `$()` or backtick substitution followed by more arguments — the same parsing gap that produces false positives produces silent false negatives. | Gate on the tool name, then parse the command inside the hook body where you have a real shell and can fail closed. |

> Why it matters: the last row generalizes past hooks. Any mechanism that decides *whether a command is dangerous* by pattern-matching the command string — hook `if` conditions, permission allow rules, an MCP gateway's regex filter — inherits shell quoting, substitution, and argument-reordering as an attack surface. Treat command-string matching as routing, never as a boundary. The boundary lives in §4's `deny` tier and in the containment planes of [8.4](../8.%20AI%20Safety%20&%20Ethics/8.4.%20The%20Agent%20Containment%20Toolchain%20—%20Sandbox,%20Runtime,%20and%20Egress%20Proxy.md).

## 8. Pattern — the advisory check

This repo's `check-references.sh` is the canonical example. Read it as the template:

```text
[hook] 7.3. Foo.md: missing '## References' section (see AGENTS.md §5).
```

Properties:

- **Exits 0 always.** Never blocks.
- **Prefixed `[hook]`** so the agent and the user can grep it out of transcripts.
- **One-line message.** Action ("missing"), location ("§5"), and that's it.
- **Skips files it doesn't care about.** Returns 0 early for non-markdown, stubs, etc.
- **Tolerates missing dependencies.** No required tools beyond `bash` and `grep`.

This is what hooks should look like 90 % of the time.

## 9. Pattern — the block-on-pattern guard

For the 10 % where blocking is correct:

```bash
#!/usr/bin/env bash
# block-secret-paste.sh — Pre-tool guard. Blocks Edit/Write that contains a
# known secret pattern.
set -u
file_content=$(cat)  # JSON payload from harness
if echo "$file_content" | jq -r '.tool_input.content' | rg -q 'AKIA[0-9A-Z]{16}'; then
  echo '{"decision":"block","reason":"AWS access key detected in proposed write"}'
  exit 0
fi
exit 0
```

Properties:

- **Outputs structured JSON.** Decision + reason.
- **One regex.** Fast, single-purpose.
- **No side effects.** Pure check.
- **Reason is actionable.** The model can recover; the user can audit.

## 10. Telemetry — observability for the agent loop

Hooks are the natural place to wire telemetry:

- `PreToolUse` → emit a span start with tool name and arguments.
- `PostToolUse` → emit span end with duration and result size.
- `Stop` → flush the session's spans to your tracing backend.

For a personal repo this is overkill. For a team or production deployment it's mandatory; see [11.11. Operational Concerns](./11.11.%20Operational%20Concerns.md).

## 11. Hook portability between Cursor and Claude Code

| Concern | Cursor | Claude Code |
|---|---|---|
| Hook config location | `.cursor/hooks.json` | `.claude/settings.json` (under `hooks`) |
| Hook trigger names | `beforeShellExecution`, `afterFileEdit`, `preToolUse`, … | `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, … |
| Payload to hook | JSON on stdin (`file_path`, `edits`, `tool_input`, …) | JSON on stdin (`tool_name`, `tool_input.file_path`, …) |
| Filtering | `matcher` field (tool type for `afterFileEdit`, command regex for `beforeShellExecution`, etc.) | `matcher` field (tool name regex) |
| Output mechanism | Stdout (advisory) / `{"permission":"deny"}` JSON or `failClosed: true` on failure (block) | JSON on stdout (`{"decision": "block", "reason": ...}`) or non-zero exit |
| Cross-OS notes | Hook scripts use bash on macOS/Linux; PowerShell on Windows | Same |

The two protocols converge: both vendors now pipe a JSON payload on stdin, both use a `matcher` field to filter by tool, and both pass `file_path` for file-edit events. Cursor explicitly documents loading Claude-Code-format hooks. The cheapest portability strategy is therefore a **single shared script** that reads stdin JSON and accepts either shape (`.file_path` or `.tool_input.file_path`). This repo's [`.cursor/hooks/check-references.sh`](../.cursor/hooks/check-references.sh) does exactly that and is wired from both [`.cursor/hooks.json`](../.cursor/hooks.json) and [`.claude/settings.json`](../.claude/settings.json) via a thin wrapper.

## 12. The platform-layer analog — inference hooks

Everything above is a *local* hook: it runs on the developer's machine, scoped to one harness session, with the user's own privileges. In August 2026 Anthropic shipped the same interception idea one layer up — **inference hooks**, a Claude Enterprise beta that routes every governed prompt through an organization-controlled server for an allow/deny verdict *before* inference runs, uniformly across chat, Claude Code, and Claude Cowork (tool-call/response checking is announced but not yet live). It trades the local hook's flexibility (block, rewrite, run arbitrary logic) for org-wide, un-bypassable coverage and a binary verdict. See [8.1. Agent Containment & Control §8](../8.%20AI%20Safety%20&%20Ethics/8.1.%20Agent%20Containment%20&%20Control%20—%20Capping%20the%20Blast%20Radius.md#8-a-fourth-checkpoint--inference-hooks-move-the-boundary-onto-the-vendors-network) for the full comparison table.

## 13. Auto mode — a classifier absorbing the "ask" tier

The three-tier permission model in §4 (allow/ask/deny) assumes a human is a reliable backstop for "ask." Anthropic's own data says otherwise: users approve 97% of Claude Code permission prompts, and a controlled study with 1,053 paid testers found human reviewers catch a swapped-in dangerous command only 13.6% of the time. Starting 2026-08-14, Claude Code's `auto mode` — a per-tool-call classifier that blocks actions it judges irreversible, destructive, or out-of-bounds and otherwise proceeds without a prompt — becomes the **default** on Pro, Max, and Team plans, effectively replacing most `ask`-tier friction with a probabilistic filter that outperformed the humans it replaces in Anthropic's testing (89% catch rate vs. 13.6%). `allow`/`deny` rules still fire first and are unaffected; only overly broad allow rules that grant arbitrary code execution (e.g. `Bash(python:*)`) are set aside while auto mode is active, since they would otherwise let a call skip the classifier entirely. If auto mode hits three consecutive blocks, or twenty in a session, Claude Code falls back to manual approval.

> Lesson — the "ask" tier in a permission model is only as good as the human behind it. When that human's approval rate approaches 100%, "ask" has quietly become "allow." A classifier narrowly tuned to a specific risk category can be a better default than a prompt nobody reads anymore. See [8.1 §10](../8.%20AI%20Safety%20&%20Ethics/8.1.%20Agent%20Containment%20&%20Control%20—%20Capping%20the%20Blast%20Radius.md) for the full safety data, including the prompt-injection resistance numbers.

The same idea shipped server-side in September 2026 as the Managed Agents `auto` permission policy, where the classifier lives in a hosted runtime rather than on a laptop and gains a third outcome, a non-appealable deny, and a documented rule for which context counts as operator intent. See [11.24. Server-Side Permission Arbitration](./11.24.%20Server-Side%20Permission%20Arbitration%20%E2%80%94%20Intent%20Provenance%20and%20the%20Evaluation%20Record.md).

## 14. A third layer — the MCP-portal gateway

§12 named one platform-layer analog to the local hook: Anthropic's inference hooks, which move the checkpoint onto the model vendor's own network. Cloudflare's **WriteGuard** (private beta, 2026-08-05) is a second, differently-scoped analog worth distinguishing from both:

| | Local hook (§1–§11) | Inference hook (§12) | MCP-portal gateway (WriteGuard) |
|---|---|---|---|
| Runs where | Developer's machine, one harness session | Model vendor's network, before inference | MCP-server portal / gateway, in front of the tool call |
| Scoped to | One repo, one user | One org's traffic to one model vendor | One org's traffic to *every* MCP server it exposes, regardless of which harness or model called it |
| Sees | Tool arguments and outputs | The prompt, pre-inference | The tool call and its result, post-model-decision, pre-execution |
| Bypassable by | Switching harness or editing config | Nothing — org-mandated | Switching to a different MCP server not behind the portal |

The distinguishing property: a local hook and an inference hook both assume you control (or your org controls) the harness or the model endpoint. WriteGuard assumes neither — it sits at the **MCP transport boundary**, so it covers an agent built on any harness calling through the portal, not just ones your team wrote hooks for.

WriteGuard's policy model is a four-tier risk classification per tool, finer-grained than the three-tier allow/ask/deny in §4:

| Risk tier | Example | Default handling |
|---|---|---|
| **Read only** | Search, view | Pass through unchanged |
| **Minimal impact** | Add a reaction, mark notification read | Pass through, logged |
| **Contained write** | Post a comment, open a merge request, update a field | Allowed, attributed, audited |
| **Critical** | Production deploy, bulk delete, merge to main | Blocked before the tool handler runs |

For every write it allows, WriteGuard injects agent + session attribution and emits a scrubbed audit event (server, tool, risk tier, outcome, user, client, duration — secret-shaped values omitted) to a centralized log, independent of what any individual MCP server does with the call.

> Lesson — as agents get more of their tool surface from shared, org-run MCP servers rather than locally-configured ones, the natural place for a write-side policy checkpoint moves with the tools: not the developer's `settings.json`, not the model vendor's inference path, but the gateway the MCP traffic already passes through. Pick the checkpoint that's actually in the request's path, not the one that's easiest to configure.
