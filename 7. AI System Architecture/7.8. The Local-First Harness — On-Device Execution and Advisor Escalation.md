# 7.8. The Local-First Harness — On-Device Execution and Advisor Escalation

> **Source:** Perplexity Research's
> [A Local-First Agent for Private and Cost-Effective Knowledge Work](https://www.perplexity.ai/hub/blog/a-local-first-agent-for-private-and-cost-effective-knowledge-work)
> (**2026-08-25**), the Portable Computer
> [launch](https://www.perplexity.ai/hub/blog/introducing-portable-computer-for-local-first-ai)
> and [Windows release](https://www.perplexity.ai/hub/blog/portable-computer-for-windows-is-here)
> (**2026-09-14**).
> The fourth position on the axis drawn by
> [7.1. Claude Platform Managed Agent](./7.1.%20Claude%20Platform%20Managed%20Agent.md),
> [7.2. Self-Implemented Agent Harness — Components](./7.2.%20Self-Implemented%20Agent%20Harness%20%E2%80%94%20Components.md),
> [7.4. The Open Harness](./7.4.%20The%20Open%20Harness%20%E2%80%94%20Embedding%20an%20Agent%20Runtime%20Instead%20of%20Building%20One.md),
> and [7.7. The Agents API as a Managed Harness](./7.7.%20The%20Agents%20API%20as%20a%20Managed%20Harness%20%E2%80%94%20Sessions%2C%20Executors%2C%20and%20the%20Split%20Lifecycle.md).

`7.7` described an **executor inversion**: the harness runs in OpenAI's datacenter and dials out to a sandbox on your infrastructure. This note covers the exact opposite bet. Loop, planner, tool router, sandbox, scheduler, and a 27B model all run on the user's GPU; the network is used for one thing only, and it is not execution.

Two claims make this worth reading even if you never install it. First, the published cross-harness numbers are the cleanest public evidence that **the harness is a larger performance lever than the model weights** — the same base model spans 8.6 points across three harnesses, while post-training the model inside the winning harness buys 2.8. Second, escalation here is an **advice channel, not a delegation channel**: the frontier model returns text and never touches a tool, which is a materially different trust boundary from every routing scheme in [Model Routing in the Agent Loop](../5.%20AI%20Agents%20&%20Tool%20Use/Model%20Routing%20in%20the%20Agent%20Loop%20—%20Per-Step%20Model%20Selection.md).

---

## 1. Where the loop runs, relative to the data

The build/buy axis in `7.1`/`7.2`/`7.4` asks *who wrote the loop*. That is the wrong axis for this system. The axis that matters is *where the loop sits relative to the bytes it reads*.

| Topology | Loop runs | Tool execution | Model inference | Data crosses the network |
|---|---|---|---|---|
| Managed runtime (`7.1`) | Vendor | Vendor sandbox | Vendor | Everything |
| Hosted loop (`7.6`) | Vendor, per-request | Mixed hosted/client | Vendor | Everything in context |
| Managed harness (`7.7`) | Vendor, durable session | **Your** sandbox | Vendor | Everything in context |
| Open harness (`7.4`) | Your process | Your sandbox | Vendor | Everything in context |
| **Local-first (this note)** | **Your device** | **Your device** | **Your device** | **Only approved escalations** |

The open harness of `7.4` already moved the loop onto your machine. It did not move the *model*, which means every file the agent reads still becomes tokens in someone else's datacenter. Local-first closes that last gap, and closing it is the entire product thesis — the worked example is a finance user pointing the agent at two years of brokerage summaries and tax returns with, in Perplexity's phrasing, no document ever reaching a chatbot.

> Why it matters: for regulated work the binding constraint is rarely the loop's location. It is whether the *content* leaves. `7.7` ends on US-only residency and no zero-data-retention, and notes that self-hosting the sandbox does not fix it, because the harness holds the state. Local-first is the only topology on this table where that sentence does not apply.

## 2. The harness is deterministic code; the model only proposes

The clearest architectural statement in the source is also the most conventional, which is the point:

> *"The orchestrator is deterministic harness code, not an LLM: it maintains the loop, assembles context, and enforces policy. The local model proposes the next action; the orchestrator executes approved tool calls in the sandbox and returns their results to the model."*

This matters more when the model is small. A 27B model is a worse planner and a worse long-horizon controller than a frontier model; the design response is to shrink the surface it is asked to control. Concretely:

- **Minimal system prompt, small core toolset.** Everything else is a **skill loaded and unloaded across the trajectory** — research, data science, visualization, document creation, software engineering. Same mechanism as [11.4. Skills](../11.%20Harness%20Engineering/11.4.%20Skills.md), but here it is load-bearing rather than ergonomic, because the effective context is the scarce resource (§4).
- **Connectors are CLI tools, not MCP servers.** Gmail, GitHub, Outlook, and Google Calendar were converted into compact command-line tools because MCP tool definitions *"consume a substantial share of the context."*
- **Self-verification is hybrid-triggered** — the model can request it, or harness hooks watching trajectory health can force it. A heuristic supervisor compensating for a weaker policy model.

> Architectural takeaway: the deterministic-orchestrator split is not a small-model concession — it is the correct default at every scale, and small models merely make the cost of violating it visible sooner. If your loop's control flow is itself an LLM decision, you have no place to put a policy check.

The MCP demotion deserves a flag, because it cuts against [11.7. Tools and MCP](../11.%20Harness%20Engineering/11.7.%20Tools%20and%20MCP.md) and the whole protocol argument in [The Agent Protocol Stack](../5.%20AI%20Agents%20&%20Tool%20Use/The%20Agent%20Protocol%20Stack%20—%20MCP%2C%20A2A%2C%20AGENTS.md.md). Under a 100K effective window, MCP's discovery ergonomics stop being free and start competing with the user's actual documents. The shipping product then re-adds MCP for third-party desktop apps — so the position is not "MCP is wrong," it is **MCP for the long tail, hand-written CLI tools for the hot path.** That is a context-budget decision wearing a protocol decision's clothes, and it is the same trade [7.6](./7.6.%20The%20Responses%20API%20as%20a%20Hosted%20Agent%20Loop.md) describes as progressive disclosure, resolved by deletion instead of deferral.

## 3. The harness outweighs the model

Perplexity ran the same base model (Qwen 3.8 27B, medium reasoning, on DGX Spark) inside three harnesses — its own Computer, plus the off-the-shelf Pi and Hermes agents. This is the controlled experiment [11.20. Harness Benchmarking](../11.%20Harness%20Engineering/11.20.%20Harness%20Benchmarking%20%E2%80%94%20Controlled%20Cross-Harness%20Evaluation.md) argues for, published with numbers.

**Local Knowledge Work Bench** — 53 held-out tasks, 3 trials each:

| Harness + model | Score | Tokens / task | Wall time / task |
|---|---|---|---|
| Computer + PPLX 27B (post-trained) | 85.4% | 678k | ~250 s |
| Computer + Qwen 3.8 27B | 82.6% | 520k | 218 s |
| Pi + Qwen 3.8 27B | 77.6% | 681k | **176 s** |
| Hermes + Qwen 3.8 27B | 74.0% | 634k | 292 s |

Read the middle three rows as one experiment with one variable. Holding the weights fixed, **the harness moves the score 8.6 points**. Then holding the harness fixed and post-training the model inside it moves the score **2.8 points** — and costs 30% more tokens and ~15% more wall time to do it.

The gap widens on tasks with more tool surface. On **BrowseComp** (1,266 tasks) Computer scores 66.7% against Pi's 50.2% and Hermes' 43.9%, at *51% less wall time and 70% fewer tokens than Pi*. On **ParseBench-100** the spread is not a spread but a cliff: 65.1% / 34.6% / 13.9%, with Pi burning 829k tokens per task against Computer's 20.1k — a 41× difference on the same model. Caveat the BrowseComp comparison: Computer uses Perplexity's own search backend while Pi and Hermes use Brave, so search quality is confounded with harness quality there. ParseBench and the internal bench are not confounded that way.

> Lesson: this is the empirical case for [11.14. Tuning the Harness, Not the Model](../11.%20Harness%20Engineering/11.14.%20Tuning%20the%20Harness%2C%20Not%20the%20Model%20%E2%80%94%20The%20Harness%20as%20an%20Optimization%20Surface.md). A 41× token ratio on identical weights is not a tuning difference; it is a difference in what the harness *lets the model see*. Before you fine-tune anything, find out what your harness is spending context on.

The post-training itself is worth noting for [RL Environments for LLM Agents](../5.%20AI%20Agents%20&%20Tool%20Use/RL%20Environments%20for%20LLM%20Agents%20%E2%80%94%20Where%20Agents%20Are%20Actually%20Trained.md): two stages — rejection fine-tuning on verifier-scored rollouts, then RL — run **inside the production harness**, on synthetic environments (a Docker container plus a verifier) whose task distribution is derived from real usage. The model is not fine-tuned for a benchmark; it is fine-tuned for a harness. That coupling is the reason the 2.8-point gain does not transfer.

## 4. Effective context, not advertised context

The single most reusable number in the source:

> Qwen 3.8 27B advertises a **260K** token window, but *"we found empirically that they begin to struggle beyond **100K** tokens."*

A 2.6× gap between the spec sheet and the working limit. Every design decision in §2 — skill loading and unloading, CLI tools instead of MCP definitions, compaction of stale context on long trajectories — is downstream of that one measurement. See [11.8. Context Engineering in the Harness](../11.%20Harness%20Engineering/11.8.%20Context%20Engineering%20in%20the%20Harness.md); the practical instruction is to measure your own model's degradation curve on your own task distribution and budget against *that*, not against the number in the model card.

## 5. Escalation: advice in, no authority out

When the local model hits something it cannot do — planning, ambiguity, repeated failure, final verification — it can consult a frontier **advisor**. The shape of that call is the most transferable idea in the system.

```text
local model ──(requests advice)──► harness orchestrator
                                     │  selects relevant context
                                     │  runs PII classifier
                                     │  shows user what would leave
                                     ▼
                              [user approves]
                                     │
                                     ▼
                            frontier advisor (cloud)
                                     │
                                returns TEXT only
                                     ▼
                              local model continues
                     (advisor never touches files, tools, or the user)
```

Three properties, in order of how often they are gotten wrong elsewhere:

1. **The model requests; the harness decides and executes.** *"The local model decides when to request advice, while the harness orchestrator retains tool authority and controls what context is sent."* The escalation request is a suggestion, not a syscall.
2. **The advisor has no tool authority and no channel to the user.** It returns guidance text. Compare the usual escalation pattern, where the bigger model inherits the full toolset — and with it the full blast radius. Here the trust boundary of [8.4. The Agent Containment Toolchain](../8.%20AI%20Safety%20&%20Ethics/8.4.%20The%20Agent%20Containment%20Toolchain%20%E2%80%94%20Sandbox%2C%20Runtime%2C%20and%20Egress%20Proxy.md) is enforced by the advisor's *interface shape*, not by a policy the advisor could be talked out of.
3. **Egress is a harness component.** Context selection, a PII classifier, and a preview of exactly what would leave, all in the orchestrator, all before the request. The privacy boundary is code on the egress path, not a paragraph in a system prompt.

The cost curve, on Terminal Bench 2.1 (89 tasks), all inside the Computer harness:

| Configuration | Score | API cost / rollout |
|---|---|---|
| Qwen 3.8 27B, fully local | 59.6% | ~$0 |
| Qwen 3.8 27B + Claude Opus 5 advisor | 73.0% | $0.415 |
| Claude Opus 5 alone | 82.4% | $0.65 |

Escalation recovers roughly three-fifths of the gap to the frontier at about two-thirds of the frontier's cost. Stated plainly: **advisor escalation is a worse deal than it looks.** Saving 36% of spend to give up 9.4 points is a trade you make for the privacy property, not for the economics. The economic argument for local-first lives elsewhere — in the 678k tokens per task that cost nothing because they never hit a meter, which is what makes repo-scale migrations and batch document work practical at all.

> Architectural takeaway: separate the two justifications. *Privacy* argues for running the loop locally. *Cost* argues for running the high-volume, low-difficulty steps locally — the heterogeneous-architecture claim in [Small Language Models for Agents](../5.%20AI%20Agents%20&%20Tool%20Use/Small%20Language%20Models%20for%20Agents%20%E2%80%94%20The%20Heterogeneous%20Architecture.md). They point the same way here, but they are not the same argument and they fail independently.

## 6. The sandbox fails closed

Code and tool execution run in an OS-level sandbox on the user's device that restricts processes, filesystem paths, and network access by policy. One behaviour is worth stealing outright:

> *"If the sandbox is unavailable, the harness disables itself before any tool calls rather than degrading to unsandboxed execution."*

The contrast Perplexity draws is with Pi and Hermes, which run commands directly with the user's permissions. That is the real local-agent failure mode — not a weak sandbox, but *no* sandbox and no notice. Fail-closed on containment loss belongs in the component checklist of `7.2` alongside the loop and the tool router.

Two honest gaps in the public record. The product pages name a *"proprietary SPACE sandbox"* with no mechanism described — no namespaces, seccomp, VM, or egress-rule detail — so any claim about isolation strength is unsupported by the sources. And the product copy enumerates a **durable task queue** among the on-device components while the research post describes only orchestrator ↔ model ↔ sandbox with compaction. Treat the durability story as unverified; [7.3. Durable Execution for Agents](./7.3.%20Durable%20Execution%20for%20Agents%20%E2%80%94%20Surviving%20Crashes%20Mid-Loop.md) is still your problem to reason about, especially for the scheduled recurring tasks the product advertises.

## 7. What it costs to take this bet

| Constraint | Detail |
|---|---|
| Hardware floor | NVIDIA DGX Spark (GB10, 128 GB unified memory), or an RTX / RTX PRO GPU with **≥ 24 GB VRAM**. NVIDIA-only. |
| Platforms | Linux (Aug 2026), Windows (Sep 14, 2026). macOS not announced. |
| Model choice | One local model at a time. PPLX 27B broadly; Qwen 3.8 27B on DGX Spark only; Nemotron 3.5 Lightning (30B) announced. |
| Capability gap | Local model trails the frontier on every published head-to-head; escalation narrows, does not close. |
| Shared weakness | Document *layout* parsing is bad everywhere — Computer scores 16.2%, the best of the three. |
| Latency | Not automatically better. Pi beats Computer on the internal bench (176 s vs 218 s per task) despite scoring 5 points lower. |

> Lesson: local-first is not the cheap option or the fast option. It is the option where the data does not move, bought with a hardware floor, a capability gap, and a harness you must co-design with the model that runs in it. Those are the terms; the useful question is whether your workload's sensitivity is worth them.
