# 7.3. Durable Execution for Agents — Surviving Crashes Mid-Loop

> **Updated 2026-06-14.** An agent loop is a *long-running, stateful* program
> running on *unreliable* infrastructure. It calls flaky external APIs, waits
> minutes or hours, and may pause for a human to approve. The default — hold the
> whole loop in the memory of one process — means a crash, a timeout, or a deploy
> wipes the run and you start from step zero, re-burning every token. **Durable
> execution** is the architecture that fixes this: persist progress after every
> step, and resume from the last good checkpoint instead of the beginning. In
> 2026 this idea crossed from niche infra into the default way serious agents are
> built — AWS, Cloudflare, and Vercel all shipped durable-workflow products, and
> Temporal (the category's reference implementation) raised a large round on the
> strength of AI-native traffic. This note explains the mechanism, the
> *replay-safety contract* that LLM non-determinism makes tricky, and where it
> fits. It is the reliability counterpart to
> [7.2. Self-Implemented Agent Harness — Components](./7.2.%20Self-Implemented%20Agent%20Harness%20%E2%80%94%20Components.md)
> (the "Sessions & State" and recovery components) and pairs with
> [11.11. Operational Concerns](../11.%20Harness%20Engineering/11.11.%20Operational%20Concerns.md).

---

## 1. Why the agent loop needs it

A chatbot turn is one request/response — if it fails, the user retries. An agent
is a *process*: plan → call tool → observe → call model → repeat, often for
minutes, sometimes across human approvals. Three things make that fragile by
default:

- **Compounding unreliability.** Reliability multiplies across steps. Five steps
  at 99% each is only ~95% end-to-end; ten steps drop to ~90%. The longer the
  loop, the more certain a transient failure becomes — and a transient failure
  on step 8 throws away steps 1–7.
- **Token re-burn on retry.** Naively retrying a failed run re-runs every prior
  LLM call. The expensive inference you already paid for is repeated, and any
  side effect those steps performed (a write, an email, a payment) may fire
  *twice*.
- **Unbounded waits are impossible.** Human-in-the-loop approval, or "wait for
  the vendor's webhook," can take hours or days. You cannot hold a live process —
  or a serverless function with a timeout — open that long.

> **Why it matters:** the failure mode that kills production agents is rarely
> "the model gave a bad answer." It is "the run died on step 8 of 12 and there
> was no way to resume." Model quality is an *application* problem; surviving a
> crash mid-loop is an *infrastructure* problem, and it needs an infrastructure
> answer.

---

## 2. The core abstraction

Durable execution platforms all share one move: **code that automatically
persists its state at defined checkpoints and can resume from those checkpoints
after any failure.** Each logical operation becomes a discrete **step** whose
result is journaled to a persistent store. On crash, restart, or redeploy, the
runtime reconstructs where the loop was and continues — it does *not* re-run
completed work.

```text
   step 1 ──✓──► [persist result]
   step 2 ──✓──► [persist result]
   step 3 ──✓──► [persist result]
   step 4 ──✗  ☠  CRASH / TIMEOUT / DEPLOY
   ───────────────────────────────────────
   on resume:  replay 1·2·3 from store (no re-execution)
               re-attempt step 4 live
```

The payoff is **exactly-once semantics** for the work that matters: each step's
effect happens once even though the surrounding loop may be (re)started many
times. The framing that matters architecturally — from Temporal's founder — is
that durable execution is an **infrastructure primitive, not an application
framework**: it gives a reliability guarantee underneath any loop without
dictating how the agent itself is written.

---

## 3. Two mechanisms: journal-replay vs. checkpoint-snapshot

There are two implementations of "persist and resume," and the difference shapes
how you write agent code.

| | **Journal-based replay** (Temporal-style) | **Database checkpointing** (LangGraph-style) |
|---|---|---|
| What's stored | An event log of every completed step + its result | A snapshot of graph/agent state per node |
| How resume works | Re-execute the workflow function; **replay** the log to skip done steps, returning their recorded results | Load the latest state snapshot and continue from that node |
| Code constraint | Workflow code must be **deterministic** (see §4) | Looser; state is data, not replayed code |
| Strength | Precise resume to the exact failed step; rich timers/signals | Simple mental model; state is directly inspectable |
| Typical stores | Internal event history service | `MemorySaver` (dev), SQLite / Postgres (prod) |
| Watch out for | Workflow-history bloat with large LLM payloads | Snapshot granularity = your resume granularity |

LangGraph exposes the trade-off directly as **durability modes**: `exit`
(persist only when the graph finishes — cheapest, least safe), `async` (persist
in the background while the next step runs), and `sync` (persist *before* the
next step starts — safest, slowest). Choosing a mode is choosing how much work
you are willing to lose on a crash.

> **Architectural takeaway:** journal-replay buys you the finest-grained resume
> and the best long-wait primitives, at the cost of a strict determinism
> contract on your code. Checkpoint-snapshot is easier to reason about and to
> debug, but you only resume as finely as you chose to snapshot. Neither is
> "memory" — see §7.

## 4. The replay-safety contract — where LLMs make it hard

Journal-replay only works if re-running the workflow function produces the *same
sequence of steps* it did the first time — otherwise the recorded log no longer
lines up with the code. That **determinism requirement** collides head-on with
how agents work: **LLM outputs are non-deterministic** (the same prompt can
return different text), and that text often decides the *next* step.

The resolution is a discipline, not magic:

- **Wrap every non-deterministic or side-effecting operation as a recorded
  step.** The LLM call, each tool call, each external API hit is a step. Its
  result is journaled the first time and **memoized** on replay — the model is
  *not* re-invoked, the cached completion is returned. This is what stops token
  re-burn and prevents a write from firing twice.
- **Ban raw non-determinism in workflow code.** No `Date.now()`, no
  `random()`, no direct network calls *in the orchestration body* — time and
  randomness must be injected through recorded steps, or replay diverges.
- **Idempotency keys on side effects.** Each external mutation carries a stable
  key so an at-least-once retry of the *step itself* (distinct from replay of the
  *loop*) doesn't double-charge or double-send.

```text
  result = await step("call-llm", () => model.invoke(prompt))   # recorded once, memoized on replay
  await step("charge-card", () => pay(amount), {idempotencyKey}) # safe to retry
  # NOT: if (Date.now() % 2) ...   ← divergent on replay, forbidden
```

> **Why it matters:** the non-determinism of LLMs is exactly what makes agents
> useful *and* what breaks naive durability. The fix is to treat every model call
> and every side effect as a transaction boundary: do it once, write down the
> result, and on replay read the result instead of redoing the act. Get this
> contract wrong and you get the worst bug class in the space — *silent
> divergence on resume*.

## 5. What it buys you

Once steps are durable, four capabilities fall out — and each maps to a real
failure the harness would otherwise have to hand-roll:

| Capability | What it gives the agent |
|---|---|
| **Crash recovery** | Resume at the exact failed step after a process death, restart, or deploy — no lost work, no token re-burn. |
| **Step-level retries** | A rate-limited or timed-out tool call retries with backoff *in isolation*; one flaky step doesn't fail the whole run. |
| **Suspend / resume** | `sleep` for days or `wait-for-event` (approval, webhook) while persisting full state and **consuming no compute** during the wait — this is what makes human-in-the-loop and long-running agents possible. |
| **Time-travel / replay debugging** | The journal *is* an execution history: inspect what the agent saw at each step, or fork from a past checkpoint to test a different branch. |

The suspend/resume primitive is the one teams underestimate. "Pause for a human
to approve, then continue exactly where you were, three days later" is trivial
with durable execution and a nightmare without it.

## 6. The 2026 landscape

Durable execution moved from a specialist concern to a default building block:

- **Temporal** is the reference implementation — workflow-as-code with
  journal-replay, signals, and timers — and reports the bulk of recent growth
  coming from AI-native workloads (it raised a large round in early 2026 on that
  basis). Known caveat: large LLM payloads can bloat workflow history, so keep
  big blobs out of the journal and pass references instead.
- **Hyperscalers shipped it.** AWS added durable / long-running Lambda workflows
  (runs measured in **up to a year**), Cloudflare took **Workflows** to GA, and
  Vercel launched a **Workflow DevKit** — durability is now a platform feature,
  not a library you bolt on.
- **Agent frameworks made checkpointing first-class.** LangGraph ships
  checkpointers as standard (`MemorySaver` for dev, SQLite/Postgres for prod)
  with the three durability modes above; Inngest, DBOS, and Dagster cover the
  same ground with step-based or function-based models.

> **Lesson:** when AWS, Cloudflare, and Vercel all ship the same primitive in the
> same window, the architectural question has flipped. It is no longer "do I need
> durable execution for my agent?" — it is "which durability model fits my loop,
> and what am I willing to lose between checkpoints?"

## 7. Where it fits — and where it is *not* the answer

**Reach for durable execution when:**

- The loop is **long, multi-step, or spans waits** — anything with human
  approval, external webhooks, or runs longer than a request timeout.
- Steps have **side effects** (writes, payments, emails) where double-execution
  is harmful — you want exactly-once.
- Each LLM call is **expensive enough** that re-burning tokens on retry hurts.

**Don't bother (or it's overkill) when:**

- The agent is a **single short turn** with no side effects — a crash just means
  the user retries; durability is pure overhead.
- The work is **trivially idempotent and cheap** to redo from scratch.

**And keep two boundaries straight:**

- **Durable execution is not memory.** It recovers the *state of one run* — where
  the loop was, what each step returned. It is *not* the agent learning across
  runs. Cross-run knowledge is
  [Agent Memory Architectures](../5.%20AI%20Agents%20%26%20Tool%20Use/Agent%20Memory%20Architectures%20—%20Tiered%2C%20Vector%2C%20Temporal-Graph.md)
  and
  [Agentic Context Engineering](../5.%20AI%20Agents%20%26%20Tool%20Use/Agentic%20Context%20Engineering%20—%20Evolving%20Playbooks%20for%20Self-Improving%20Agents.md).
  A run can be perfectly durable and still learn nothing.
- **Durability is not context management.** Persisting steps to disk is separate
  from deciding what goes *into the model's window* —
  [11.8. Context Engineering in the Harness](../11.%20Harness%20Engineering/11.8.%20Context%20Engineering%20in%20the%20Harness.md)
  owns the latter.

> **Architectural takeaway:** durable execution answers exactly one question —
> *"if the process dies, where do we resume?"* — and answers it well. Treat it as
> the reliability substrate the agent loop runs **on top of**, peer to (not a
> replacement for) memory, context management, and tool design.
