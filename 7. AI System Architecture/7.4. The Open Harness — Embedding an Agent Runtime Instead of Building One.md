# 7.4. The Open Harness — Embedding an Agent Runtime Instead of Building One

> **Source:** OpenAI's [Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform)
> post, dated **2026-08-19**, and the
> [app-server protocol docs](https://learn.chatgpt.com/docs/app-server).
> Third option on the axis defined by
> [7.1. Claude Platform Managed Agent](./7.1.%20Claude%20Platform%20Managed%20Agent.md)
> (buy the runtime) and
> [7.2. Self-Implemented Agent Harness — Components](./7.2.%20Self-Implemented%20Agent%20Harness%20%E2%80%94%20Components.md)
> (build it). For the consumer-side view of the same primitives see
> [11.1. What Is a Harness](../11.%20Harness%20Engineering/11.1.%20What%20Is%20a%20Harness.md).

Until August 2026 the harness question had two answers: rent a vendor's runtime and accept its boundaries, or write the loop yourself and own every component in 7.2's checklist. A shipping coding agent's harness — loop, sandbox, approval flow, session state, streaming — was either someone's product or your problem.

OpenAI has now published the harness behind Codex as Apache-2.0 code you link against. The thesis of this note is narrow: **an open harness moves the loop and the sandbox from "component you own" to "dependency you version," and the interesting engineering is no longer writing the loop but deciding where the seam between your product and the harness sits.**

---

## 1. The third option on the build/buy axis

The three options are not three products. They differ in *which components you keep*.

| Component (7.2 taxonomy) | 7.1 Managed runtime | 7.2 Self-built loop | Open harness (this note) |
|---|---|---|---|
| Agent loop | vendor | you | dependency |
| Tool execution | vendor's toolset | you | dependency, but your tools |
| Sandbox | vendor, opaque | you | dependency, configurable policy |
| Approval / permission gate | vendor's policy | you | dependency, your decisions |
| Session state | vendor, server-side | you | dependency, local process |
| Model choice | vendor's models | any | coupled to the vendor's models |
| Product context, business rules | your prompts | yours | yours |
| Multi-tenancy, durability, billing | vendor | you | **still you** |
| Upgrade path | vendor ships, you adapt | you choose | you pin a version |

The last two rows are the ones people miss. An open harness gives you a *single-tenant local runtime*, not a service. Everything in [7.3. Durable Execution for Agents](./7.3.%20Durable%20Execution%20for%20Agents%20%E2%80%94%20Surviving%20Crashes%20Mid-Loop.md) — checkpointing, resume after crash, unbounded waits for human approval — remains on your side of the line, as does anything about serving many customers from one deployment.

> Why it matters: the pitch is "you no longer have to build the harness." The accurate version is "you no longer have to build the *loop and the sandbox*." Those are two of about ten components in 7.2. They happen to be the two that are tedious, subtle, and worthless as differentiation — which is exactly why importing them is a good trade.

## 2. Three entry points, three granularities

The release is not one artifact. It is three, and picking the wrong one is the first mistake available.

| Entry point | Shape | You get | Use when |
|---|---|---|---|
| `codex exec` | CLI, non-interactive | Run a bounded workflow, get structured output back | CI jobs, cron, one-off background tasks. No UI, no live control. |
| Codex SDK | Library | Start, resume, and stream tasks programmatically | Application code that drives an agent but renders nothing agent-specific. |
| app-server | Local process + JSON-RPC protocol | Open conversations, streamed events, interruption, tool exposure, approval requests | You are building a *product surface* — an IDE panel, a review UI, an internal console. |

The ladder is granularity of control, and the cost is the amount of lifecycle you must now handle yourself. `codex exec` has no notion of an approval prompt because it never pauses for one. app-server has approvals precisely because something is on the other end that can answer.

> Architectural takeaway — choose the lowest rung that renders your product. If nothing in your UI shows agent progress, the SDK is enough; adopting the protocol buys you events you will discard.

## 3. What the app-server protocol actually standardizes

This is the part worth reading even if you never adopt it, because it is a working answer to a design question every harness builder faces: *what is the wire format between an agent runtime and a client that has to show progress and ask a human things?*

**Transport.** JSON-RPC 2.0, bidirectional. stdio with newline-delimited JSON is the default; WebSocket (experimental) and WebSocket-over-Unix-socket are the alternatives. WebSocket clients present `Authorization: Bearer <token>` during the handshake, and the server enforces auth *before* the JSON-RPC `initialize` — auth is a transport concern, not a protocol message.

**Handshake.** `initialize` (with client metadata) → `initialized` notification. The server rejects every other request until that completes. A two-step handshake instead of one exists so capability negotiation has somewhere to live.

**The state hierarchy** is three levels deep, and the naming is the useful part:

```text
thread          a conversation; thread/start, thread/resume
  └── turn      one user request; turn/start, turn/interrupt
        └── item   one unit of work inside the turn
                   (a command execution, a file change, a message)
```

Progress arrives as notifications — `turn/started`, `item/started`, `item/completed` — so a client renders by appending items, not by diffing state. Interruption is `turn/interrupt`, and the turn then *completes* with `status: "interrupted"` rather than vanishing. That is the correct choice: a cancelled turn is a fact about the conversation, not an absence.

**Approvals are server-to-client requests.** The runtime sends `item/commandExecution/requestApproval` or `item/fileChange/requestApproval`; the client answers `accept`, `acceptForSession`, `decline`, or `cancel`; the server confirms with `serverRequest/resolved` before the item completes.

Two things follow. First, `acceptForSession` is a protocol-level primitive, not a client-side convenience — the "don't ask me again for this thread" policy lives in the runtime where it can actually be enforced. Second, the direction of the call means the *runtime* blocks on a human, so the client cannot forget to gate anything; there is no path where a command runs because a UI failed to render a dialog. Compare [11.5. Hooks, Permissions, and Side Effects](../11.%20Harness%20Engineering/11.5.%20Hooks%2C%20Permissions%2C%20and%20Side%20Effects.md), where the same gate is a consumer-configured surface rather than a wire message.

**Tools cross the boundary as MCP.** `mcpServer/tool/call` invokes a tool on a thread; `mcpServer/oauth/login` handles server auth; `mcpServer/elicitation/request` lets a tool server ask the client for structured input. Tools can be injected dynamically at `thread/start` or `thread/resume`.

> Why it matters: this pins MCP as the *application's* tool boundary, not just the vendor's integration format. Your business actions enter the harness as an MCP service you own. See [The Agent Protocol Stack](../5.%20AI%20Agents%20%26%20Tool%20Use/The%20Agent%20Protocol%20Stack%20%E2%80%94%20MCP%2C%20A2A%2C%20AGENTS.md.md) for where that sits in the layer cake.

## 4. The seam the design forces

The documented split is short enough to quote as a rule:

- **Your application owns** product context, business rules, and tools.
- **The harness owns** the agent loop and sandboxed execution.

Read that as a constraint, not a suggestion. Every piece of domain knowledge you want the agent to have must arrive as prompt content, as an MCP tool, or as an approval policy. There is no fourth channel — no hook into the loop's tool-selection step, no place to rewrite context between turns.

This is a real loss of control relative to 7.2, and it is also the reason the thing is adoptable. A harness with an extension point at every step is a framework, and frameworks at this layer age badly.

> Lesson: an open harness is worth adopting exactly when your differentiation is in the tools and the domain, and not in the loop. If your product's value *is* a custom loop — speculative execution, per-step model routing, a bespoke planner — you are back to 7.2, and you should stop reading the vendor's post as an option.

## 5. What to check before you depend on it

Five questions, in the order they will bite:

1. **Model coupling.** The code is Apache-2.0; the models it drives are not. Confirm you are willing to have your agent loop and your model vendor be the same procurement decision. This is the single largest difference from 7.2.
2. **Sandbox policy fit.** The runtime enforces *its* sandbox model. If your containment requirements are the hardware-boundary kind argued for in [8.4. The Agent Containment Toolchain](../8.%20AI%20Safety%20%26%20Ethics/8.4.%20The%20Agent%20Containment%20Toolchain%20%E2%80%94%20Sandbox%2C%20Runtime%2C%20and%20Egress%20Proxy.md), the harness's policy is a layer inside your boundary, not a replacement for it.
3. **Protocol churn.** app-server ships with an experimental transport and no long deprecation guarantee of the sort MCP now has. Pin a version, and budget for the client work each bump costs.
4. **Local-process assumption.** "Connect to a local Codex process" means one process per conversation on a machine you operate. Multi-tenant serving, queueing, and crash recovery are yours — see 7.3 §2.
5. **Observability.** The event stream is a good trajectory log, but it is the runtime's view of itself. Anything you need for the monitoring in [6.2. Production Trajectory Monitoring](../6.%20Evaluation%20%26%20Observability/6.2.%20Production%20Trajectory%20Monitoring%20%E2%80%94%20Sampling%2C%20Staging%2C%20and%20the%20Long-Context%20Cliff.md) has to be captured at the seam, because you cannot instrument inside the loop.

## 6. Decision guide

| Situation | Take |
|---|---|
| Agent behavior is the product; tools are domain-specific; model vendor already chosen | Open harness, app-server rung |
| Batch or CI automation, no UI, structured result | Open harness, `codex exec` rung |
| Need server-side sessions, managed sandbox, no infra of your own | 7.1 managed runtime |
| Must stay model-portable, or the loop itself is differentiated | 7.2, build it |
| Long-running, resumable, human-in-the-loop across hours | Open harness *plus* 7.3 durable execution around it |

> Architectural takeaway — the build/buy question was never really about the loop. It is about which of 7.2's components you are willing to let someone else version. An open harness is the first option that lets you answer that per-component instead of all-or-nothing.
