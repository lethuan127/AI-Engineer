# 7.5. Transactional Agents — A Reference Architecture for Agents That Move Money

> **Source:** Anthropic's [anatomy of effective commerce agents](https://claude.com/blog/the-anatomy-of-effective-commerce-agents)
> engineering guide and the [claude-for-commerce-agents](https://claude.com/blog/claude-for-commerce-agents)
> announcement, both dated **2026-09-02**, plus the Apache-2.0
> [anthropics/commerce-agents](https://github.com/anthropics/commerce-agents) reference implementation.
> Fills the gap between [7.2. Self-Implemented Agent Harness — Components](./7.2.%20Self-Implemented%20Agent%20Harness%20%E2%80%94%20Components.md)
> (what the parts are) and a shipped product (how the parts are wired for a flow that
> takes a customer's money). Companion to
> [5. Tool-Call Reliability](../5.%20AI%20Agents%20%26%20Tool%20Use/Tool-Call%20Reliability%20%E2%80%94%20Idempotency,%20Postcondition%20Verification,%20and%20Replay-Safe%20Authorization.md)
> and [8.5. The Tool-Authorization Plane](../8.%20AI%20Safety%20%26%20Ethics/8.5.%20The%20Tool-Authorization%20Plane%20%E2%80%94%20Write%20Scope,%20Attribution,%20and%20Audit.md).

Most published agent architecture is about *read* work — research, code, analysis. A transactional agent is different in one respect that changes every layer: a wrong token is a wrong price, a wrong SKU, or a refund that should not exist. The blast radius is a database row in someone's order system, not a bad paragraph.

The thesis of this note is that the commerce blueprint is not a commerce pattern. It is **the general shape of any agent whose output is a write against a system of record** — booking, ticketing, provisioning, claims, scheduling. Two of its mechanisms — *staged writes* and *ID provenance* — are the load-bearing ones, and both live in the harness, not the prompt.

---

## 1. The counter-intuitive shape: one agent, not a swarm

The reference architecture is **one model in one standard agent loop**, with skills for specialized flows and tools that call existing backends. Not an orchestrator over subagents.

That contradicts the direction of travel in
[Multi-Agent Orchestration in Production](../5.%20AI%20Agents%20%26%20Tool%20Use/Multi-Agent%20Orchestration%20in%20Production%20%E2%80%94%20Topologies,%20Token%20Economics,%20and%20Coordination%20Failure.md),
and the reason it does is worth naming precisely. A subagent handoff is **state-lossy**: the parent must serialize what the child needs to know, and anything not serialized is gone. For research that is usually fine — a subagent returns a finding. For a cart, the state *is* the product. "Swap the medium for the large, keep the rest, and re-apply the promo" only works if the turn that handles it can see the whole conversation.

| Property | Read-heavy agent (research, code) | Transactional agent (cart, booking) |
|---|---|---|
| What a subagent returns | A finding, self-contained | A partial mutation of shared state |
| Cost of a lossy handoff | Slightly worse answer | Wrong order, wrong price |
| Parallelism payoff | High — independent branches | Low — steps are causally ordered |
| Correct default | Orchestrator + subagents | Single loop + skills |

> Architectural takeaway: pick the topology from the *shape of the state*, not from the perceived complexity of the task. Independent, self-contained subproblems justify subagents. A single evolving object that every step mutates does not — there, "modularity" means skills and tools inside one context, not processes outside it.

### When a subagent does earn its place

"No subagents" is too blunt. The blueprint names two shapes that survive, and the distinction between them is **who owns the conversation**:

| Shape | Conversation owner | When it fits |
|---|---|---|
| **Delegation** (subagent-as-tool) | Orchestrator | A narrow, self-contained task that wants its own context window and returns one compact answer. Deep research is canonical: search, read, run code, hit dead ends — all inside the child, one summary out. |
| **Hand-off** | The domain agent, talking to the user directly | The domain already runs a purpose-built agent with its own compliance surface (pharmacy, financial services). It takes over the task until done. |
| **Bouncing** (anti-pattern) | Orchestrator, but the domain agent is called in and out mid-turn | Never. This is delegation applied to stateful work; it degrades on every exchange. |

> Lesson: delegation is safe exactly when the child's output is a *value*, not a *mutation*. The moment a child needs to write to the shared object, you want a skill, or a full hand-off — not a round trip.

One more consideration the blueprint flags: the placement rules below are tuned to the current generation. Longer contexts and more tools per model release loosen them, so re-measure rather than treating the thresholds as settled.

### Where the modularity goes instead

| Layer | Holds | Admission rule |
|---|---|---|
| System prompt | Search semantics, cart rules, presentation rules | Relevant to **>33% of traffic** |
| Skills | Domain flows, loaded on demand | Everything below that bar |
| Tools | Calls into existing backends | Never reimplement backend logic in the agent |

Two refinements to that table:

- **Safety, legal, brand, and critical user facts go in the prompt regardless of frequency.** An allergy is not a one-in-three fact; it is a fact that must never fail to load.
- **If a skill is predictable from a signal you already have** — the page the session started from, the dashboard the operator opened — inject it from the harness before the first model call. Loading a skill costs a model turn; a signal you already possess should not.

The "never reimplement backend logic" rule has a useful tell. When you find yourself writing domain logic *inside* a tool — an availability check that fans out to catalog, inventory, and fulfillment, then applies substitution rules in the tool's own code — you have discovered a missing backend endpoint, not a tool requirement. The tool boundary is where the backend's logic ends and the model's judgment begins: `search_products` returns results **already ranked**; the model decides which serve the goal and how to present them.

Tool *results* are context, so return the fields the model reasons with and drop the rest (image URLs on every search row are the usual offender). On failure, return an instruction rather than a code — `"Include a product ID when querying availability"` beats a generic 403.

The >33% rule is the useful part. It is a concrete answer to the question [11.8. Context Engineering in the Harness](../11.%20Harness%20Engineering/11.8.%20Context%20Engineering%20in%20the%20Harness.md) keeps circling: *what earns permanent context residency?* Anything rarer than one turn in three pays for itself as a skill that loads when needed.

## 2. Staged writes — the agent never commits

No financial operation is executed by the model. Every write — order, price change, refund, promotion — produces a **staged change with a server-issued ID** that then goes through the organization's existing approval workflow.

```text
model turn ──► tool: propose_price_change(sku, new_price)
                     │
                     ▼
              backend stages change  ──► change_id: chg_8f21  (status: pending)
                     │
                     ▼
              existing human approval workflow ──► commit | reject
```

This is a stronger claim than "human in the loop." The approval does not live in the harness as a permission prompt — [8.1 §10](../8.%20AI%20Safety%20%26%20Ethics/8.1.%20Agent%20Containment%20%26%20Control%20%E2%80%94%20Capping%20the%20Blast%20Radius.md) has the numbers on what happens to those (97% approval rate, 13.6% catch rate on a planted dangerous command). It lives in the system that already owned the decision before the agent existed, with the same reviewers and the same audit trail.

> Why it matters: staging converts "did the agent do the right thing?" into "is this diff correct?" The second question has an existing owner, an existing UI, and an existing rollback story. The first does not.

## 3. ID provenance — the harness refuses IDs it did not issue

The single most transferable mechanism in the blueprint. The harness keeps a **per-session record of every ID the server returned**. Only those IDs are accepted for a write or a render. A SKU, order ID, or promo code that the model produced from its own weights — or that a user typed — is refused *before* it reaches the backend.

```text
tool result  ──► server returns {sku: "AC-4471", order: "ord_92b"}
                 harness records both in session provenance set
                 ...
model emits  ──► add_to_cart(sku="AC-4470")     ── not in set ──► refused
model emits  ──► add_to_cart(sku="AC-4471")     ── in set     ──► executes
```

This is the difference between *asking* the model not to hallucinate an identifier and *making it structurally unable to act on one*. It also closes the user-supplied variant: a customer pasting a stale or guessed order ID cannot steer the agent into another account's record, because that ID was never handed out in this session.

Pair it with **fenced third-party content**. Reviews, merchant listings, and policy text are sanitized and wrapped in fixed fence markers before entering context, and the system prompt says: report on fenced content, never act on it. Provenance is the enforcement; fencing is the framing. Injection that survives the fence still cannot produce a usable ID.

> Architectural takeaway: for any agent that writes, the identifier space is a capability. Treat "which IDs may this session touch" as an access-control question answered by the harness, not a correctness question answered by the model.

The blueprint adds a third, mundane guard: **per-session write serialization**. Parallel tool calls are allowed for reads, but writes are serialized so two concurrent calls cannot jointly exceed a quantity cap or transaction limit. Every check-then-act limit in a backend has this race; parallel tool use is what makes an agent hit it.

## 4. Presentation as typed tool calls

UI — carousels, comparison tables, itineraries, seat maps — is emitted as **typed tool calls**, not as custom markup inside the text response.

| Approach | Conversation history stays queryable | Renderer coupling | Eval-able |
|---|---|---|---|
| Custom markup in text | No — must re-parse prose | Tight, string-shaped | Awkward |
| Typed presentation tool call | Yes — structured, native to the API | Schema boundary | Directly |

The payoff is not rendering. It is that "what did the agent show the customer?" becomes a structured field in the transcript, so a compliance question or a regression test can read it. Markup in a text block is a parsing problem forever.

Two consequences worth designing around:

- **The presentation call is the agent's record of what is on screen.** When the customer says "the third one down on the left," the layout is sitting in the arguments of the last presentation call. That only works if **the arguments mirror the rendered structure** — ordered rows and carousels, not a flat list the client rearranges. Referential grounding is free if the schema matches the DOM and impossible if it does not.
- **Validation and streaming granularity trade off.** Each top-level tool argument buffers server-side for schema validation, so sub-components arrive in steps even with streaming on. Setting `eager_input_streaming: true` on the tool definition buys token-level streaming at the cost of the server-side guarantee — worth it on a consumer surface, but wrap the call in a retry, because the guarantee is what you just gave up.

## 5. Memory: extract asynchronously, read in three layers

Two design choices here go against the common pattern.

**Storage is a typed database, not a markdown profile.** Facts are keyed by type and by user/operator, and carry a category, a value, and the originating session. Type validation happens at the write path.

Key by **person, not by account**. Operator logins on a business account are routinely shared, so a per-account profile mixes several people's preferences and — worse — lets reads cross a permission boundary. A store manager's agent should not recall a fact a district manager stated.

**Extraction is asynchronous.** A separate process reads the conversation *after* the turn and writes facts. It adds zero user-visible latency, and it measured **13% higher fact recall** than the usual `save_memory` tool — because a tool competes for the model's attention mid-turn against the thing the user actually asked for. The synchronous version is also worse than it looks: updating or deduping a fact usually needs a read *first*, so one "save" is two round trips inside a user-facing turn.

Separating the extractor buys a second thing: you can scope its inputs. It reads only the user's and the assistant's text, **never tool results** — so a product description, a review, or a policy document can never be promoted into a fact about the user. That is a prompt-injection boundary as much as a quality one.

Reading is tiered:

| Tier | Contents | Cost |
|---|---|---|
| Always in context | Defaults, role, store | Every turn |
| Pre-fetched per turn | Facts relevant to this turn's context | Retrieval, no model turn |
| Behind a lookup tool | Everything else | A tool call when needed |

> Lesson: the "let the agent decide what to remember" pattern is intuitive and measurably worse. Remembering is a background job. It should not be competing with the foreground task for the same attention budget. Compare the tiered scheme in [Agent Memory Architectures](../5.%20AI%20Agents%20%26%20Tool%20Use/Agent%20Memory%20Architectures%20%E2%80%94%20Tiered,%20Vector,%20Temporal-Graph.md).

Governance follows from the typed store: validate fact types on write, expose view/delete to the user, set retention, and make memory a per-deployment switch so a regulated market can turn it off without a code change.

## 6. Cache segmentation by change frequency

Prompt assembly is ordered into three segments, warmest first:

| Segment | Contents | Changes |
|---|---|---|
| Global | System prompt, tool definitions | Never, across all sessions |
| Session | User context, conversation history | Within a session |
| Volatile | Timestamp, current page, live inventory | Every turn |

Volatile content goes **last**. A timestamp near the top of the prompt invalidates everything after it on every single turn — the most common self-inflicted cache miss there is. At scale the blueprint reports **90–99% cache hit rates**, with cached reads at ~10% of fresh-token cost and 1.5–2× faster.

Two implementation corollaries follow from the segmentation, and both are easy to get backwards:

- **Load skills as tool results, not by appending them to the system prompt.** Appending mutates the *global* segment and invalidates it for every other session. As a tool result the skill body lands in the session prefix and is cached along with the conversation.
- **Roll the newest breakpoint to the end of each user turn.** Breakpoints per request are capped, so this is the mechanism that makes each round read the whole accumulated history — including long search results — from cache rather than recomputing it.

> Why it matters: this is a layout rule, not a feature. The ordering costs nothing to get right on day one and is painful to retrofit once prompt assembly is spread across five call sites.

Note the read price is now model-dependent: Fable 5.1 (2026-09-01) cut Claude cache reads a further 75%, to 2.5% of input price rather than the usual 10%. Anthropic attributes ~25% off typical workloads and up to ~45% off highly agentic ones to that single change, which is the tell — **in a tool-heavy loop, cache reads are the dominant cost line, not output tokens.** See [Prompt Caching](../3.%20Prompt%20&%20Context%20Engineering/prompt-caching.md) for the cross-provider mechanics.

## 7. Latency has two budgets, and they are attacked separately

Cost is the easy half of §6. Latency is the half that decides whether a consumer surface is usable, and the blueprint's framing is worth adopting verbatim: **task-completion latency** is the sum over model turns of *time-to-last-token plus tool processing*, which gives three levers that sometimes compete. Minimize the sum, never one term.

| Lever | Techniques |
|---|---|
| **Fewer turns** | Load likely context up front — if the session opened from a product page or a campaign dashboard, that data belongs in the initial context, because answering from context costs no turn. Raise model intelligence. Prompt for parallel independent tool calls, returned as one user message. |
| **Faster tools** | Optimize the tool's own backend; push stitched-together fan-out into a single upstream endpoint (§1). **Dispatch eagerly** — execute each tool as its arguments finish streaming, while the model is still emitting later blocks, and prompt the model to emit its slowest call first. |
| **Faster tokens** | Choose model and effort level by sweeping the eval suite (§9), not by intuition. |

Eager dispatch alone has taken multi-second gaps down to a few hundred milliseconds.

**Perceived latency** is a separate budget, attacked without touching the model at all: stream each presentation-tool parameter to the client and render progressively — a 500–700-token rendered response is otherwise five-plus seconds of spinner — and render a plain-language progress line per step ("finding hotels near the water"), built either from the tool's own arguments or from a dedicated `user_facing_message` parameter. Two harnesses running the same model, prompt, and tools can take the same total time and feel completely different.

> Architectural takeaway: the counterintuitive result is that **a smarter, slower-token configuration frequently wins on p90/p99**, because it plans its tool calls better and needs fewer rounds on exactly the complex requests that produce tail latency. If production shows more than about five turns per task, the faster model is often the smarter one. This inverts the small-model-first instinct in [Small Language Models for Agents](../5.%20AI%20Agents%20%26%20Tool%20Use/Small%20Language%20Models%20for%20Agents%20%E2%80%94%20The%20Heterogeneous%20Architecture.md) for interactive multi-turn work specifically — those economics hold for routine single-step calls, and invert once turn count dominates.

Worth stating plainly, because it is the finding teams most often expect to go the other way: on agentic surfaces, what moved retention, engagement, and cart size was **outcome quality**, not marginal latency. Latency work is about staying inside the user's budget, not about winning on it.

## 8. Evals: snapshots, and a negative for every positive

Two rules do most of the work.

**Grade the endpoint, not the path.** Construct a specific conversation state, append the test message, and grade the *final* output — resulting state plus rendered response. Grading intermediate tool sequences is brittle: a model that reaches the right cart by a different route is a pass, not a regression.

**Negative-case parity.** For every "should serve" case, write the matching "should refuse." Missing negatives is named as the most common gap in real suites — which tracks, because a suite of positives only measures whether the agent is helpful, never whether it is containable. The rule generalizes past safety: for every "should ask a clarifying question," write a "should just do it."

Snapshots are constructible precisely because the model API is stateless — output is a function of system prompt, tools, and messages array, so any reachable state can be built directly. That also names the second-most-common defect: **clean-state bias.** If a behavior only emerges after a busy first turn with several tool calls, or after a contradiction earlier in the session, a case that starts from a clean state passes under every configuration and yields no signal at all. A meaningful share of cases must start from long, messy, or contradictory histories.

Simulated-user evals — a second model plays the customer, a judge grades the transcript — are a poor *measurement* instrument: two non-deterministic systems need larger samples, cost more per trial, and produce failures that are hard to attribute. Use them to **discover** cases, then write each discovery as a snapshot.

One refinement to the coverage table below: split injection into two distinct cases. **User-authored injection**, where the directive is in the customer's own message, and **data-plane injection**, where it is planted in a product name, a review, or a web snippet arriving via a tool result. They fail differently and the fencing rule in §3 only addresses the second.

Coverage areas, roughly in traffic order:

| Area | What it catches |
|---|---|
| Core requests (~90% of traffic) | Everyday regressions |
| Context-dependent queries | Memory retrieval failures |
| Safety / brand | Injection, data leakage, off-policy claims |
| Interface integrity | Malformed or hallucinated presentation calls |
| Cross-capability flows | Skill interaction bugs |

Baseline volume: **50–100 cases per user flow**, sourced from subject-matter experts and mined production incidents rather than invented.

CI shape: high-traffic plus *all* safety cases on every PR; cases touching the changed component and its neighbors; full suite nightly and pre-release.

## 9. Model selection: cost per completed task

Sweep every candidate model and effort level against the eval suite, weighted by the production query mix, and rank on **cost per completed task** — not cost per call. A cheaper model that needs three more turns, or fails one time in eight and gets retried, is not cheaper. When two candidates are close and both fit the latency budget, take the more capable one. See [Model Routing in the Agent Loop](../5.%20AI%20Agents%20%26%20Tool%20Use/Model%20Routing%20in%20the%20Agent%20Loop%20%E2%80%94%20Per-Step%20Model%20Selection.md) for the per-step version of the same question.

A caveat on reading a sweep, since it burns time twice if missed: **a prompt is tuned to a model.** A sweep run with one prompt will underrate models it was not written for — a smaller model needs instructions the incumbent infers on its own, and a larger one follows to the letter what the smaller one was ignoring. Iterate on each candidate's failing cases before ruling it out.

## 10. Ownership and release

| Concern | Rule |
|---|---|
| Skills and tools | One owning team each; changes ship with their test cases |
| Shared system prompt | One platform owner |
| Deployment unit | The whole agent, canaried |
| Kill switch | Per skill, not just per agent |
| Peak periods | Change freeze, same as any other production system |

> Architectural takeaway: a per-skill kill switch is the operational counterpart of the skill/prompt split in §1. If a skill is separable enough to load on demand, it is separable enough to turn off without redeploying the agent. If it is not, it belonged in the system prompt.

The reason process carries this load rather than architecture: unlike a service, **an agent has no module boundary protecting the others.** A change made by the pricing team shares a context window with checkout. The tempting fix is to shard into subagents per business unit, which §1 already rejected on quality grounds — so the isolation has to come from ownership and CI instead.

## 11. What to take, and what is commerce-specific

| Mechanism | Transfers to any write-capable agent? |
|---|---|
| Single loop + skills over subagents | Yes, wherever state is one evolving object |
| Staged writes with server-issued change IDs | Yes — the core one |
| ID provenance enforcement | Yes — the other core one |
| Fenced third-party content | Yes |
| Per-session write serialization | Yes |
| Presentation as typed tool calls | Yes, for any agent with a UI surface |
| Async memory extraction, tiered reads | Yes |
| Cache segmentation by change frequency | Yes |
| Eager tool dispatch and progressive rendering | Yes, for any interactive surface |
| Snapshot evals with negative parity | Yes |
| The >33% prompt/skill threshold | Weakly — a starting point to re-measure per traffic mix, and one that moves each model generation |
| "When two candidates are close, take the more capable one" | Weakly — a claim about the current price/quality frontier, not a law |
| Cart/catalog/promo domain modeling | No — commerce-specific |

The reference implementation ships a shopping agent and a merchant agent across four verticals (retail, travel, telecom, ticketing), on three runtimes: the Messages API loop, the Agent SDK, and Managed Agents calling MCP servers — the same three rungs as [7.1](./7.1.%20Claude%20Platform%20Managed%20Agent.md), [7.2](./7.2.%20Self-Implemented%20Agent%20Harness%20%E2%80%94%20Components.md), and [7.4](./7.4.%20The%20Open%20Harness%20%E2%80%94%20Embedding%20an%20Agent%20Runtime%20Instead%20of%20Building%20One.md). It is published as a reference implementation, explicitly not maintained — read it as an architecture document with a working test suite attached, not as a dependency.
