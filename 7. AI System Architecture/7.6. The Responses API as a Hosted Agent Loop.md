# 7.6. The Responses API as a Hosted Agent Loop

> Companion to [7.1. Claude Platform Managed Agent](./7.1.%20Claude%20Platform%20Managed%20Agent.md)
> and [7.2. Self-Implemented Agent Harness — Components](./7.2.%20Self-Implemented%20Agent%20Harness%20—%20Components.md).
> Those two notes frame the choice as managed-runtime vs build-your-own. OpenAI's
> Responses API is the interesting third position: it looks like an inference
> endpoint and behaves like an agent runtime. The docs say so outright — *"The
> Responses API is an agentic loop, allowing the model to call multiple tools …
> within the span of one API request."* This note reads the whole surface through
> one question: **who owns the loop, and what do you get back for giving it up.**
> The three 2026-09-03 controls that partly answer that question are covered in
> [Breaking the Lockstep Turn](../5.%20AI%20Agents%20&%20Tool%20Use/Breaking%20the%20Lockstep%20Turn%20—%20Async%20Tool%20Calls,%20Mid-Turn%20Steering,%20and%20Configuration%20Updates.md).

---

## 1. The unit of context is an item, not a message

Chat Completions took an array of `messages` and returned a `message`. Responses
takes an `input` array of **items** and returns an `output` array of items. The
docs are explicit about why: *"Unlike a Chat Completions Message, where many
concerns are glued together into one object, Items are distinct from one another
and better represent the basic unit of model context."*

An item is a tagged union. The guides name `message`, `reasoning`,
`function_call`, `function_call_output`; the tool guides add `program`,
`program_output`, `tool_search_call`, `tool_search_output`, `mcp_list_tools`,
`mcp_call`, `mcp_approval_request`, `mcp_approval_response`, `multi_agent_call`,
`multi_agent_call_output`, `agent_message`. No single page enumerates the union —
which is itself the tell that the union is still growing.

Two consequences worth naming:

- **Round-tripping is list concatenation.** `context += response.output`, append the next user item, resend. Tool calls and their results are two separate items joined by `call_id`, not one nested object.
- **`n` is gone.** One generation per request. Parallel candidates now mean parallel requests — the API stopped modelling "several answers" and started modelling "one trajectory."

> **Architectural takeaway:** an item list is a *trace*, not a chat log. Once the
> unit of context is "one thing the agent did," the API has already conceded that
> a turn is a sequence of actions. Everything else in this note follows from that.

---

## 2. One response is a trajectory

The stated benefit list calls it *"Agentic by default."* Concretely, a single
`POST /v1/responses` can contain reasoning, a web search, more reasoning, a code
execution, and a final message — all before you get control back. Hosted tools
run inside the response; the loop only exits to you when it needs a **client**
tool result, an approval, or it is done.

That is the fact that reframes everything people find surprising about the API:

| Observation | Explanation |
|---|---|
| Reasoning models score better here than on Chat Completions (stated: ~3% on SWE-bench, same prompt) | The loop keeps reasoning state across internal steps instead of discarding it per call |
| Cache utilisation improves (stated: 40–80% vs Chat Completions in internal tests) | A stable prefix is reused across many internal steps, not just across your turns |
| From GPT-5.4, Chat Completions **cannot** do tool calling with `reasoning_effort` other than `none` | Tool use and reasoning were coupled to the loop, and the loop only exists here |
| A response can take minutes | It isn't generating; it's *working* |

That last row is why `background`, WebSocket lanes, and steering all exist. They
are not features of an inference endpoint. They are operational concerns of a
runtime.

## 3. The real boundary: hosted vs client execution

This is the line that decides your architecture, and it cuts straight through the
tool list. Everything hosted happens inside one response and you never see it
happen. Everything client-side suspends the loop and hands you control.

| Surface | `type` | Executes | Loop exits to you? |
|---|---|---|---|
| Function / custom tool | `function`, `custom` | Your process | Yes — every call |
| Web search, file search, code interpreter, image gen | built-in | OpenAI | No |
| Hosted shell | `shell` + `environment.container_auto` | OpenAI container | No |
| Local shell | `shell` + `environment.local` | Your machine | Yes |
| MCP / connectors | `mcp` | **OpenAI**, as the MCP client | Only for approvals |
| Tool search (hosted) | `tool_search`, `execution: "server"` | OpenAI | No |
| Tool search (client) | `tool_search`, `execution: "client"` | Your process | Yes |
| Programmatic tool calling | `programmatic_tool_calling` | **Both** — see below | Yes, repeatedly |
| Multi-agent collaboration actions | `multi_agent_call` | OpenAI | No |

Three rows deserve elaboration.

**MCP is hosted, and that is a bigger deal than it reads.** *"When the model
decides to call an MCP tool, the API will make an request to the remote MCP server
to call the tool and put its output into the model's context."* OpenAI originates
the outbound connection — which is why a private server needs Secure MCP Tunnel
rather than a local process. Two knock-on effects: your `authorization` token is
deliberately not stored (*"you must send the `authorization` value in every
Responses API creation request"*), and an egress policy you enforce on your own
network no longer sees the traffic. Compare
[8.4. The Agent Containment Toolchain](../8.%20AI%20Safety%20&%20Ethics/8.4.%20The%20Agent%20Containment%20Toolchain%20—%20Sandbox,%20Runtime,%20and%20Egress%20Proxy.md):
a hosted MCP call is outside every boundary you built.

**Programmatic tool calling is a hybrid, and the docs are more modest than the
folklore.** The model writes JavaScript that runs in *"a fresh, isolated V8
runtime"* with no Node, no packages, no network, no filesystem, no persistent
state — tools reachable only as `tools.<name>(args)`, output only via `text(...)`
or `image(...)`. But the program **pauses** whenever it calls a client-owned
function: you get a `function_call` carrying
`caller: {type: "program", caller_id: "call_prog_…"}`, and you must return the
result with `caller` copied through unchanged so the service resumes the right
program. So the context saving is *not* "intermediate results never enter
context" — client tool calls and outputs remain top-level items you replay. The
saving is whatever the program filters out before `program_output.result`. The
guide declines to quantify it: *"the effect depends on the task and tool
responses. Start with direct tool calling as a baseline."*
See [Code Execution as the Tool-Calling Substrate](../5.%20AI%20Agents%20&%20Tool%20Use/Code%20Execution%20as%20the%20Tool-Calling%20Substrate%20—%20Programmatic%20Tool%20Calling.md).

**Skills run at user privilege.** *"Skill instructions are user prompt input (not
system prompt input), so they're handled with the same priority as other
user-provided instructions."* The docs pair that with unusually direct language —
*"It is very important to inspect any Skill used with the Responses API"*,
*"reviewed as potentially untrusted input until validated"*, and a warning against
letting end users attach arbitrary skills from an open catalog. Consistent with
[8.8. The Skill Supply Chain](../8.%20AI%20Safety%20&%20Ethics/8.8.%20The%20Skill%20Supply%20Chain%20—%20Install-Time%20Scanning%20and%20Why%20It%20Collapses.md).

## 4. Four ways to own state, and a retention asymmetry

| Mechanism | Who holds history | Notable property |
|---|---|---|
| Manual replay (`store: false`) | You | Replay **every** item including encrypted reasoning; the only fully stateless path |
| `previous_response_id` | OpenAI, response-to-response | Supports forking a chain; **does not carry top-level `instructions`** — resend them |
| `conversation` (Conversations API) | OpenAI, as a durable object | Usable *"across sessions, devices, or jobs"* |
| Server-side compaction | OpenAI, lossily | Opaque compaction item replaces older context |

Two things to internalise.

**Chaining does not reduce your bill.** Stated twice across the docs: *"Even when
using `previous_response_id`, all previous input tokens for responses in the chain
are billed as input tokens in the API."* Chaining buys ergonomics and cache hits,
not token savings.

**Choosing `conversation` changes your data-retention posture, not just your
code.** Stored responses carry a 30-day TTL; conversation items do not — *"Conversation
objects and items in them are not subject to the 30 day TTL."* That is a
compliance decision disguised as an API convenience, and it should not be made by
whoever is writing the request builder.

For ZDR, `store: false` is enforced automatically and reasoning survives via
`encrypted_content`, which the current docs describe as returned **by default**
(no `include: [...]` opt-in). Decrypted in memory, used, discarded.

## 5. Context budget: three deferrals and one amputation

The API has landed on progressive disclosure at three separate layers, plus
compaction as the fallback when disclosure isn't enough:

| Mechanism | What it defers | What the model still sees up front |
|---|---|---|
| Tool search (`defer_loading: true`) | The **parameter schema** | Name and description — *"in practice tool search is mostly deferring the parameter schema"* |
| Skills | The `SKILL.md` **body** | `name`, `description`, `path` |
| Programmatic tool calling | Intermediate **tool output** | Nothing — the program's return value is the interface |

None of the three is quantified anywhere in the docs. The only hard numbers are a
model floor (`gpt-5.4`+ for tool search) and a guideline (*"fewer than 10
functions"* per namespace). Treat all three as hypotheses to measure, not
settled wins — the same discipline
[Context Compaction Theory](../3.%20Prompt%20&%20Context%20Engineering/Context%20Compaction%20Theory%20—%20Selection,%20Generation,%20and%20the%20Budget%20Lower%20Bound.md)
applies to compaction claims generally.

Compaction itself comes in two shapes:

```json
{ "context_management": [ { "type": "compaction", "compact_threshold": 200000 } ] }
```

Server-side, it fires mid-response when the rendered token count crosses the
threshold, emits an encrypted compaction item into the same stream, and prunes
before continuing. Or explicitly via `POST /v1/responses/compact`, which is fully
stateless: you send a whole window, you get a compacted window back.

The pruning rules are opposite for the two, and getting them backwards is a live
bug:

- **Server-side, stateless chaining:** you may drop items *before* the most recent compaction item. With `previous_response_id` chaining, *"do not manually prune."*
- **Standalone endpoint:** *"do not prune `/responses/compact` output. The returned window is the canonical next context window."*

The compaction item is *"opaque and not intended to be human-interpretable"* —
which means your conversation history now contains a segment you cannot audit,
diff, or redact. That is a real cost, and it lands squarely on anyone with a
review or retention obligation.

> **Lesson:** compaction is the one mechanism here that destroys information
> rather than deferring it. Deferral is reversible; an opaque summary is not.
> Reach for the three deferrals first.

## 6. When one response is not enough

Three escape hatches, each solving a different failure of the single-response
model.

**Background mode** (`background: true`) for work that outlives an HTTP
connection: poll `GET /v1/responses/{id}` while status is `queued` or
`in_progress`. It is also the **only** place a real cancel exists —
`POST /v1/responses/{id}/cancel`, idempotent, *"subsequent calls simply return the
final `Response` object."* For a synchronous response, *"terminate the
connection"* is the entire cancellation story. Note the retention wrinkle: even
with `store=false`, response data is *"temporarily stored to disk for roughly 10
minutes to enable asynchronous execution and polling."*

**WebSocket mode** for tool-heavy chains. The primitive is `stream_id`: *"A
`stream_id` names an ordered lane on one WebSocket connection."* Same lane is
FIFO and non-overlapping; different lanes run concurrently; a new lane pointed at
an existing `previous_response_id` **forks** the conversation. Claimed payoff:
*"For rollouts with 20+ tool calls, we have seen up to roughly 40% faster
end-to-end execution."* Also `generate: false` to warm request state without
producing output.

The catch is where continuation state lives: a *connection-local in-memory
cache*. That's what makes it ZDR-compatible, and also what makes it fragile —
limits are 16 in-flight responses, 32 named lanes, and **60 minutes per
connection**. When the socket dies, *"its connection-local cache disappears for
every lane,"* and under `store: false` an uncached ID returns
`previous_response_not_found`. There's a documented race worth pinning to the
wall: on a cross-lane fork, *"wait for the fork lane to emit
`response.in_progress` before advancing the source lane,"* or the parent gets
evicted and the fork dies.

**Multi-agent mode** (beta, `multi_agent: {enabled: true, max_concurrent_subagents: 3}`)
for parallel delegation. The design choice worth studying: **there is no
declarative agent list.** You flip a flag and steer composition with
natural-language developer messages; the model spawns the tree at runtime, and
subagents *share the request's model and available tools*. Coordination happens
through six hosted actions — `spawn_agent`, `send_message`, `followup_task`,
`wait_agent`, `interrupt_agent`, `list_agents` — surfaced as `multi_agent_call`
items you must **not** execute. Agents are named by path (`/root`,
`/root/reviewer/tester`), and inter-agent traffic is `agent_message` items whose
content is `encrypted_content`.

Read against
[Multi-Agent Orchestration in Production](../5.%20AI%20Agents%20&%20Tool%20Use/Multi-Agent%20Orchestration%20in%20Production%20—%20Topologies,%20Token%20Economics,%20and%20Coordination%20Failure.md),
two things stand out. The star topology survived here too — subagents talk to
their parent, and `spawn_agent`'s `fork_turns` controls context propagation. But
the token tax is acknowledged only in prose (*"adding subagents can increase token
usage"*) and **usage is reported in aggregate**, with no per-agent breakdown. You
cannot attribute cost to a subagent, which makes the ~15× token tax from that note
unmeasurable on this surface. The restrictions are also telling:
`/responses/compact` unsupported, compaction forced on implicitly per-agent,
`reasoning.summary` unsupported, `max_tool_calls` unsupported. Three observability
and control knobs traded for parallelism.

## 7. Buying back what the hosted loop took

Once the loop is server-side, you have lost the thing a self-implemented harness
gets free: the ability to change your mind between steps. The 2026-09-03 release
sells it back, and the shape of the replacement gives the game away.

| What you lose to the hosted loop | The compensating primitive | What it costs |
|---|---|---|
| Inject input between steps | `response.steer` (WebSocket) | Queued not applied; dies with the connection; cannot cancel |
| Deliver a tool result without ending the response | `response.inject` (WebSocket, multi-agent) | `response_already_completed` is a normal outcome you must handle |
| Change settings between steps | `configuration_update` item | Effort only; no read-back of the effective value |
| Not block on a slow tool | `async: true` + your own `wait_for_tasks` | No cancellation, no TTL, handle collisions are your bug |
| Watch the trajectory for misbehaviour | Misalignment monitoring | Asynchronous, post-hoc, no resume, no rollback |

In a harness you own, every one of those is a line of code in your driver loop and
it always succeeds. Here each is a request to a process you don't control, with an
error taxonomy attached.

> **Architectural takeaway:** this is the honest price of `7.1`-style managed
> execution, stated more precisely than a vendor comparison usually manages. You
> do not lose control outright. You trade *inherent* control for *granted* control
> — and granted control comes with queues, error codes, and a connection that can
> drop. Whether that trade is good depends entirely on whether hosted tools are
> load-bearing for you.

## 8. Choosing a position

| If this is true | Take this position |
|---|---|
| You need hosted web search, code interpreter, hosted shell, or hosted MCP | Responses, hosted loop. There is no other way to get them |
| Every tool is yours, and you need auditable egress and step-level control | Client tools only, or a self-implemented harness (`7.2`) |
| Runs last minutes and must survive disconnects | Responses + `background`, which is also the only cancel |
| 20+ tool calls per rollout and latency matters | Responses + WebSocket lanes, and budget for reconnect logic |
| You need per-agent cost attribution | Not multi-agent mode. Usage is aggregate only |
| You are under ZDR or a retention obligation | `store: false` + encrypted reasoning; avoid `conversation` (no TTL) and know that `background` still touches disk for ~10 minutes |
| The workflow must be auditable end to end | Be wary of compaction's opaque item and hosted MCP's invisible egress |

## 9. Where the documentation is thin

Worth knowing before you build against it, and worth re-checking as the surface
moves:

- **No enumeration of the item-type union.** Types appear scattered across tool guides. Build a permissive parser.
- **`compaction_trigger`** is named in the reasoning guide (*"including a `compaction_trigger` item in a `/responses` request"*) and absent from the compaction guide. Two pages, two models of explicit compaction.
- **No `wss://` URL** published for WebSocket mode; the SDK constructs it.
- **`previous_response_id`** documents only `instructions` as not-carried. Whether `tools` or `text.format` carry is unstated — assume not.
- **`fork_turns`** has one documented value (`"all"`).
- **Cancellation** exists only for background responses. Not for async tool calls, accepted steers, or a synchronous response.
- **`program_output.status: "incomplete"`** is never explained, and program-side error semantics (a thrown exception, a rejected tool call) are undocumented.
- **No skill observability** — no `skill_call` item, no event. You cannot tell from a trace which skill fired.
- Model IDs across the guides are inconsistent (`gpt-6-astra`, `gpt-5.6`, `gpt-5.4`, `gpt-5.2`). Treat page-level model claims as stale by default and check the model page.

The pattern in that list: the **happy path is well specified and the failure path
is not.** For a runtime rather than an endpoint, that is the wrong way round, and
it is where your integration will spend its debugging budget.
