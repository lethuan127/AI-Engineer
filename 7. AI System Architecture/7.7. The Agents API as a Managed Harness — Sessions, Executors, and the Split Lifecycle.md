# 7.7. The Agents API as a Managed Harness — Sessions, Executors, and the Split Lifecycle

> Companion to [7.1. Claude Platform Managed Agent](./7.1.%20Claude%20Platform%20Managed%20Agent.md),
> [7.2. Self-Implemented Agent Harness — Components](./7.2.%20Self-Implemented%20Agent%20Harness%20—%20Components.md),
> [7.4. The Open Harness — Embedding an Agent Runtime Instead of Building One](./7.4.%20The%20Open%20Harness%20—%20Embedding%20an%20Agent%20Runtime%20Instead%20of%20Building%20One.md),
> and [7.6. The Responses API as a Hosted Agent Loop](./7.6.%20The%20Responses%20API%20as%20a%20Hosted%20Agent%20Loop.md).

OpenAI put the **Agents API** into public beta on 2026-09-10. The one-line
description — *"access to the Codex harness through an OpenAI-managed API"* —
reads like a packaging change, and it isn't. `7.6` covered an endpoint that
hosts one *trajectory*; this hosts one *agent*, for as long as you keep it. Two
structural moves are worth the read even if you never call it: the durable
**session** replaces the response as the unit you hold an ID for, and the
**executor inversion** puts the harness in OpenAI's datacenter while the sandbox
stays on your infrastructure — the opposite of every local-agent topology in
`7.2` and `7.4`. The cost lands in a place vendors rarely state so plainly: the
session and the environment have separate lifecycles, and reconciling them is
your job.

---

## 1. Four nouns, and the one that moved

The docs name four concepts: **Agent** (model, instructions, tools, MCP
servers), **Environment** (optional sandbox), **Session** (*"a durable instance
of an agent"*), and **Events and items**.

Only the third is new. Compare what you hold an identifier for across the three
OpenAI runtimes:

| Runtime | The thing you hold an ID for | Lives for |
|---|---|---|
| Chat Completions | Nothing — you replay `messages` | One request |
| Responses (`7.6`) | A `response`, optionally chained or in a `conversation` | One trajectory; 30-day TTL on stored responses |
| Agents API | A `session` | Until you delete it |

A session holds *"configuration, conversation, and saved work over time."* Turns
happen inside it: input to an idle session starts a turn, and — the detail worth
circling — **input to an active session steers the current turn**. Where `7.6`
needed a separate WebSocket `response.steer` verb with its own error taxonomy,
here steering is the same `agent.session.input.message` event you use to start
work; the session's state decides which it means. One channel, two meanings,
resolved server-side.

Cancellation follows the same pattern and closes `7.6`'s worst gap: a real
`agent.session.input.cancel` event exists for the active turn, not only for
background work.

```bash
POST /v1/agents/sessions            # create; OpenAI provisions the environment
POST /v1/agents/sessions/{id}/events # send input, steer, or cancel
GET  /v1/agents/sessions/{id}/items  # saved messages and tool calls
GET  /v1/agents/sessions/{id}/turns  # per-turn usage and subagent_id
```

All of it is beta-gated behind an `OpenAI-Beta: agents=v1` header and a
`client.beta.agents` namespace — treat every shape below as unstable.

> **Architectural takeaway:** once the durable object is the agent rather than
> the request, session ID becomes a foreign key in *your* schema. That is a
> migration, not a config change: you now store, garbage-collect, and
> access-control a remote resource per conversation.

## 2. The executor inversion

`environment.type: "self_hosted"` is the part with no counterpart elsewhere in
the repo. You run `codex exec-server` — the **executor** — inside your own
container, laptop, or VM. It registers with an environment ID and a restricted
key, then opens an **outbound WebSocket** to
`wss://codex-cloud-environments.chatgpt.com` and waits for the hosted harness to
send it commands. Shell, file edits, and *local* MCP servers all run on your
side; the loop that decides what to run does not.

```text
your app  ──create session──▶  Agents API (harness, OpenAI)
                                     │  commands
                                     ▼
your infra:  codex exec-server ◀──outbound WS──┘   (shell, files, local MCP)
```

Read that against the containment architecture in
[8.4. The Agent Containment Toolchain](../8.%20AI%20Safety%20&%20Ethics/8.4.%20The%20Agent%20Containment%20Toolchain%20—%20Sandbox,%20Runtime,%20and%20Egress%20Proxy.md).
Everything egress-shaped inverts. `7.6` flagged hosted MCP as traffic
*originating at OpenAI*, outside every boundary you built; here the network
posture flips back — all connections are outbound from your environment, so no
inbound port and no tunnel. What you give up instead is the decision layer: the
process choosing which command to run is remote, and your sandbox is a pair of
hands executing instructions that arrive over a socket.

Two consequences the docs state and most integrations will miss:

- **The executor key is readable by the agent's own code.** Documented, and scoped down to compensate: it must be a separate key with every permission except environment connection set to **None**, supplied as `CODEX_API_KEY`, kept out of images and logs. Your application key must never enter the environment. This is the same capability-attenuation argument as [11.19. Permission Check Integrity](../11.%20Harness%20Engineering/11.19.%20Permission%20Check%20Integrity%20—%20Aliases,%20Re-Resolution,%20and%20the%20Capability%20Floor.md), applied to a credential rather than a tool call.
- **Agents sharing an environment share everything.** *"Agents that share an environment can access the same files, credentials, and other resources."* Isolate per user or per workload; each session needs its own environment ID and its own executor.

## 3. Three environment shapes

| `environment.type` | Who runs the sandbox | Built-in bash / apply-patch / workspace files | Use when |
|---|---|---|---|
| `none` | Nobody | **Unavailable** | The agent only answers questions, calls remote MCP, or calls your function tools |
| `openai_hosted` | OpenAI | Yes | You want code execution and artifacts without operating compute |
| `self_hosted` | You (or Modal, Cloudflare, Vercel, Daytona, Blaxel, E2B, Runloop, DigitalOcean, OCI) | Yes | Private network, custom software, or compute you need to trust |

`none` is the shape to notice: it makes the Agents API usable as a *pure*
orchestration layer with no compute story at all, at the price of losing the
built-in shell and patch tools. Sessions created with it must carry initial
input.

The nine named sandbox providers are the second thing to notice. Deciding that
the sandbox is a pluggable third-party concern — rather than a product surface
to own — is the same bet `7.4` describes from the other direction, and it is
what makes "bring your own compute" a table row instead of an enterprise
negotiation.

## 4. The split lifecycle

> **Why it matters:** *"An agent session can outlive its environment."* That
> single sentence is the operational content of this whole API, and every
> failure mode below descends from it.

You now run two state machines with no shared owner. The session is durable and
OpenAI's; the compute is ephemeral and yours. The documented seams:

| Seam | What the docs say | What it means for you |
|---|---|---|
| Connection wait | The API waits **up to five minutes** for an input-time connection; expiry fails the submission | Client and proxy timeouts must exceed it; initial input can fail *asynchronously* and leave the session `failed` |
| Shutdown signal | *"An idle event alone is not a safe shutdown signal"* — it can arrive when a connection request clears, before queued input starts its turn | Cancel pending shutdown on connection request or execution start, and recheck state before stopping compute |
| Mid-turn disconnect | Can fail a tool *even if the turn completes*; does not auto-request reconnection or restart a killed command | A completed turn is not evidence the work happened — inspect tool results and the final response |
| Crash recovery | *"The API does not guarantee recovery of pending input after a process crash"*; a late connection does not replay timed-out input | Check outcome before retrying; never resubmit while the original request is waiting |
| Environment reuse | Reusing the environment ID **does not restore files** in replacement compute | Durable state belongs in provider storage or snapshots, not in the sandbox |
| Deletion | Deleting a session neither stops its environment nor emits a deletion webhook | Two cleanup paths, no transaction across them — orphaned compute is the default failure |
| Stream recovery | *"Streams do not replay missed events"* | Events are a live view, not a log; recover by listing saved items |

The startup path has the same shape. The trigger for provisioning compute is
specifically the `agent.session.action_required` webhook carrying
`required_action.type: "environment_connection"` — and the docs call out that
turn creation and `agent.session.in_progress` *"arrive too late to start an
offline executor."* Picking the wrong event to key on produces an integration
that works whenever compute happens to be warm and times out when it isn't.

> **Lesson:** a managed harness does not remove distributed-systems work, it
> relocates it. The loop stopped being yours; the reconciliation between two
> lifecycles became yours, and that is the harder of the two to get right.

## 5. What the harness absorbed

The managed harness runs commands, applies skills, connects MCP, steers,
**compacts context**, delegates to subagents, and resumes. Three of those were
the components a self-built harness spends its time on:

| Capability | Who wrote it before | Now |
|---|---|---|
| Compaction | You, per [3. Context Compaction Theory](../3.%20Prompt%20&%20Context%20Engineering/Context%20Compaction%20Theory%20—%20Selection,%20Generation,%20and%20the%20Budget%20Lower%20Bound.md) | Automatic as the session nears its limit; *"developers do not write their own compaction logic"* |
| Tool-catalog scaling | You, via filtering or search | Tool search, with discovered definitions appended **at the end** of the conversation so the cached prefix survives |
| Subagent orchestration | You, per [Multi-Agent Orchestration in Production](../5.%20AI%20Agents%20&%20Tool%20Use/Multi-Agent%20Orchestration%20in%20Production%20—%20Topologies,%20Token%20Economics,%20and%20Coordination%20Failure.md) | `multi_agent.enabled`; harness supplies create/message/wait/interrupt tools you never declare |

The subagent model is the star topology again, with three constraints worth
pinning up: `max_concurrent_subagents` defaults to **6**; subagents **inherit
MCP tools, credentials, and web-search settings but cannot use function tools**;
and a subagent does **not** get its own environment — the coordinator and every
subagent share one filesystem. The last is a coordination hazard the docs
acknowledge in one line (*"agents that edit the same files must coordinate their
changes"*) and otherwise leave to your prompt.

There is also a versioning claim doing real work: *"versioned access to these
capabilities with each model launch… we maintain and continuously improve the
harness alongside our models."* The pitch is that the harness-rewrite tax every
model release imposes on a self-built loop becomes someone else's. That is the
strongest argument in the announcement, and the least verifiable on day one.

## 6. Per-subagent cost attribution, finally

`7.6` closed its multi-agent section on a specific defect: usage is reported in
aggregate, so the ~15× token tax from the orchestration note is unmeasurable on
that surface. The Agents API fixes it. Turns are public resources; each carries
`usage` and a `subagent_id` that is `null` for root-agent work, so delegated
cost is attributable per agent, and a shell command is attributable to its agent
by retrieving the turn named in its `turn_id`.

Read the caveats before building a chargeback report on it:

- Usage is **best-effort**: *"it can be `null` when unknown, and recorded values may change."* Missing usage does not mean zero.
- **No cache-write count** is exposed, so on models with cache-write pricing these fields cannot reconstruct the charge.
- **Command-output truncation is not reported** — a silently truncated tool result looks identical to a complete one.
- Detailed trace retrieval and external trace exporters are **dashboard-only**, explicitly *"not a supported customer API"* in the beta.

> **Architectural takeaway:** attribution and audit are different properties. You
> can now say which subagent spent the tokens. You still cannot export the trace
> that proves what it did — which is the artifact an incident review actually
> needs, per [6. Evaluation & Observability](../6.%20Evaluation%20&%20Observability/README.md).

## 7. The line that decides it for regulated workloads

Stated flatly in the overview, and easy to miss under a code sample: the Agents
API supports **US data residency only** and **does not support Zero Data
Retention** — and *"choosing a self-hosted sandbox does not make the Agents API
ZDR-eligible."*

That sentence exists because the intuition it corrects is so natural. Running
the sandbox on your own metal feels like it should fix the data question. It
doesn't: the *harness* is what holds conversation, items, and saved work, and
the harness is hosted. Compare `7.6`, where `store: false` plus encrypted
reasoning is a genuine stateless path. Here, durability is the product — you
cannot opt out of the thing you are buying.

## 8. Choosing a position

OpenAI now publishes three runtimes on one axis. Folding in the managed-agent
and open-harness options from the rest of this track:

| If this is true | Take this position |
|---|---|
| Tasks run for hours or days and progress must survive your process restarting | Agents API, durable session |
| You need per-subagent cost attribution | Agents API — the only surface here that exposes it |
| You are under ZDR, or non-US residency | Not the Agents API. `7.6` with `store: false`, or your own harness |
| You want hosted web search or code interpreter inside a single request | Responses API (`7.6`) |
| You need step-level control, custom approval gates, or auditable egress | Self-implemented (`7.2`) or embedded open harness (`7.4`) |
| The sandbox must sit in your VPC but you don't want to own the loop | Agents API, `self_hosted` — and budget for the split lifecycle in §4 |
| You have no compute story and only orchestrate remote tools | Agents API, `environment.type: "none"` |
| Your integration is one model call with tools | None of the above; plain Responses |

Pricing removes cost from this decision in the common case: no fee for the
Agents API itself, only model tokens, tool rates, and container rates for hosted
sandboxes. The trade is the one `7.1` has always described — operational
surface for control — stated at a larger granularity than before.

## 9. Where it is thin

- **Beta everywhere.** `OpenAI-Beta: agents=v1`, `client.beta.*`. The item and event unions will move.
- **No trace export.** Dashboard-only, and the docs say so explicitly. Plan observability around items, turns, and your own event capture.
- **Truncation is invisible.** No signal on truncated command output, in an API whose whole premise is commands you didn't watch run.
- **Usage may change after the fact.** Fine for analysis, wrong for anything that bills a customer in real time.
- **One executor per session.** Environment images, `workspace_directory`, and `capability_directories` are reusable; the environment ID is not. Session-heavy products should cost this out early.
- **Open-source harness, hosted operation.** The [Codex repository](https://github.com/openai/codex) is public, so you can read the loop — but the instance making decisions about your data is the one OpenAI runs, and the two are not pinned to each other by anything you control.

The pattern from `7.6` repeats: the happy path is well documented, and the
failure path — crash recovery, shutdown races, orphaned compute — is documented
as a list of things you must handle rather than things the service handles. That
is honest, and it is also the work.
