# 7.1. Claude Platform Managed Agent

> Source: [Claude Managed Agents — Overview](https://platform.claude.com/docs/en/managed-agents/overview), [Tools](https://platform.claude.com/docs/en/managed-agents/tools), [Sessions](https://platform.claude.com/docs/en/managed-agents/sessions), [Self-hosted sandboxes](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes).

Claude Managed Agents is a **pre-built, configurable agent harness** that runs on Anthropic-managed (or self-hosted) infrastructure. Instead of building your own agent loop, sandbox, and tool runtime, you describe *what* the agent is and *where* it should run, and the platform takes care of the rest.

It is the productionized form of "an LLM in a loop with tools and a filesystem". Studying its API surface is one of the cleanest ways to learn the **architectural primitives every serious AI agent system needs**.

---

## 1. Two Ways to Build with an LLM

| | Messages API | Managed Agents |
|---|---|---|
| Layer | Direct model prompting | Pre-built agent harness + runtime |
| You own | The agent loop, tool exec, sandbox | Just the agent definition + business logic |
| Best for | Fine-grained control, custom loops | Long-running, async, stateful tasks |
| Statefulness | Stateless by default | Stateful sessions (FS + history + outputs) |

**Architectural takeaway** — there is a clean split between **"LLM as a function call"** (Messages) and **"LLM as a long-running process"** (Managed Agents). Production AI systems usually need *both*: a stateless API for short interactions, plus a stateful runtime for tasks that span minutes/hours and many tool calls.

---

## 2. The Four Core Concepts

Managed Agents is built on four concepts that map cleanly to general agent-system architecture:

| Concept | Role | Analogue in classic systems |
|---|---|---|
| **Agent** | Model + system prompt + tools + MCP servers + skills. Versioned, reusable. | Container image / immutable config |
| **Environment** | Where sessions run: Anthropic cloud container, or self-hosted sandbox. | Cluster / runtime target |
| **Session** | A running agent instance in an environment. Has its own filesystem and conversation history. | Pod / process / job |
| **Events** | SSE-streamed messages between client and agent (user turns, tool calls, tool results, status). | Event log / message bus |

This is essentially a **declarative agent platform**: agents and environments are defined once and referenced by ID; sessions are the imperative, stateful instances.

## 3. Lifecycle (How a Task Runs)

```text
┌─────────────────┐   create    ┌────────────────┐
│  Define Agent   │ ──────────► │  Agent (v1..N) │
│ (prompt+tools)  │             └────────────────┘
└─────────────────┘                       │
                                          │ ref by id (+ optional version pin)
┌─────────────────┐   create    ┌────────────────┐
│ Configure Env   │ ──────────► │  Environment   │
│ (cloud / self)  │             └────────────────┘
└─────────────────┘                       │
                                          ▼
                                ┌────────────────┐
                                │    Session     │  ← provisions container
                                └────────────────┘
                                          │
                                  send user event
                                          ▼
                  ┌──────────────────────────────────────────┐
                  │  Agent loop:                              │
                  │   model ↔ tools (bash, fs, web, MCP, …)   │
                  │   stream events back via SSE              │
                  │   write final outputs to /mnt/session/... │
                  └──────────────────────────────────────────┘
                                          │
                                steer / interrupt / fetch history
```

Two-phase lifecycle is important:

1. **Create session** → provisions container, mounts skills, assigns to environment.
2. **Send user event** → starts actual work; model begins tool calls; events stream back.

You can **steer** mid-flight by sending more user events, or **interrupt** to change direction.

## 4. Architectural Patterns You Can Steal

This is the part that generalizes beyond Anthropic.

### 4.1 Control-plane / data-plane split

- **Control plane** (orchestration, conversation state, model calls) lives with Anthropic.
- **Data plane** (tool execution, filesystem, network egress) can live in *your* infrastructure via self-hosted sandboxes.
- The two are connected by a **work queue**: the `self_hosted` environment enqueues sessions; your worker polls/claims them, executes tools locally, and posts results back.

> Why it matters: this is the same pattern as GitHub Actions self-hosted runners, Argo Workflows, or Temporal task queues. For AI: it lets you keep regulated data inside your VPC while still using a managed agent loop.

> **August 2026 update:** the same split now ships for Claude Code's interactive/cloud sessions too, not just the Managed Agents API. [Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments) let an org run `claude self-hosted-runner` processes that claim cloud sessions started from claude.ai, the mobile/desktop apps, or scheduled routines, and execute them inside the org's network — cloning the repo and running the Claude Code process locally — while orchestration, queueing, and model inference stay with Anthropic. Same control-plane/data-plane split, same work-queue pattern (a runner polls and claims, rather than Anthropic pushing in), different product surface. Good confirmation this is a general Anthropic platform primitive, not an artifact of one API.

### 4.2 Versioned, immutable agents

- Agents are **versioned resources**.
- Sessions can either auto-track latest, or **pin to a specific version** (`{type, id, version}`) — enabling staged rollouts and deterministic replays.

> Treat the agent definition like an immutable image. New prompt = new version. This is how you avoid "we changed the prompt and prod broke" incidents.

### 4.3 Stateful sessions with persistent filesystem

Each session has:

- `/workspace` — working directory (skills mounted at `/workspace/skills/...`).
- `/mnt/session/outputs` — durable output artifacts.
- Persistent conversation history server-side, resumable after pauses.

> Filesystem-as-memory is becoming a standard agent pattern. It scales much better than stuffing everything into context: the model `read`s/`write`s files, and only summaries enter the prompt.

### 4.4 Built-in context engineering

The harness ships with:

- **Prompt caching** (reuse of prefix tokens across turns).
- **Compaction** (auto-summarize older turns when context grows).
- **Auto-truncation of large tool outputs** — when a tool returns >100K tokens, the result is *written to a file* and the model only sees a preview + file path.

> This is a critical pattern. **Never let raw tool output gate the context window.** Spill to disk + give the model a handle. This is essentially RAG for tool outputs.

### 4.5 Three layers of tools

| Layer | Examples | Owned by |
|---|---|---|
| Built-in toolset (`agent_toolset_20260401`) | `bash`, `read`, `write`, `edit`, `glob`, `grep`, `web_fetch`, `web_search` | Platform |
| MCP servers | Database, Linear, Slack, internal APIs | Standardized protocol (you or 3rd-party) |
| Custom tools | Any JSON-schema'd function your app implements | You (client-executed) |

> Generalizable design: **standardize a small core toolset, extend through MCP for shared infra, and use custom tools for app-specific operations.** Don't reinvent file/web/shell tools per app.

### 4.6 Steering and interruption as first-class operations

Users can inject events mid-run to redirect the agent. This is the difference between an *autonomous* agent (you submit a task and watch) and a *collaborative* one (you nudge it as it works).

> Architecturally, this requires the agent loop to be pausable/resumable and the input channel to remain open during execution. Most home-grown loops can't do this without rework.

### 4.7 Streaming over SSE + persisted event history

- Live events stream over SSE for low-latency UI updates.
- Full event history is persisted server-side and fetchable on demand.

> Lesson: **stream for UX, persist for replay/debugging.** Your agent system should be able to reconstruct any session from its event log.

### 4.8 Two worker patterns for self-hosted execution

For self-hosted sandboxes:

- **Always-on worker** — long-lived process polls the queue continuously (simple, costs idle compute).
- **Webhook-triggered worker** — wakes on `session.status_run_started`, then polls (cheaper, slightly more latency).

> Same trade-off as queue consumers vs. event-driven Lambda. Pick based on traffic shape and cost sensitivity.

### 4.9 Two independent boundary controls

- **Self-hosted sandbox** controls *where the agent's code executes* (compute boundary).
- **MCP tunnels** control *how Anthropic reaches MCP servers in your network* (network boundary).

> They compose. You can mix-and-match: cloud execution + tunneled MCP, or self-hosted execution + public MCP. Two orthogonal axes of "what stays inside my walls".

### 4.10 Session governance knobs shipped August 2026: budgets, advisors, geo pinning, repo skills

Four primitives landed within days of each other (2026-08-05 to 2026-08-07), all governance-shaped rather than capability-shaped:

| Primitive | What it is | Analogue |
|---|---|---|
| **Session budgets** | Optional hard cap (`budget.max_list_cost`) on a session's spend, priced at public list rates. At the cap, threads pause with `stop_reason: budget_reached` instead of terminating; raising or clearing the budget resumes automatically. | A cloud spend alert that actually throttles instead of just notifying. |
| **Advisor role** | A reserved multiagent roster slot (`type: "advisor"`) naming a model at least as capable as the agent's own. The primary thread consults it mid-turn for planning or review; the advisor doesn't own a delegated task the way a worker agent does. | A second opinion built into the loop, not a peer worker. |
| **`inference_geo` pinning** | Set per-agent (or overridden per-session) to force model requests to a specific data-residency region (`"us"` / `"global"`), validated against the workspace's allowed geos on every turn — not just at creation. | Region pinning for an otherwise-stateless compute function. |
| **GitHub-mounted skills** | Skills auto-discovered from a mounted repo's `.claude/skills/<name>/SKILL.md` at session start — no upload, no entry in the agent's `skills` array. Discovery runs once, at checkout; commits pushed mid-session aren't picked up. | Convention-over-configuration, at the cost of the mounted repo becoming part of the agent's trust boundary. |

> **Architectural takeaway:** budgets and advisors are cost/quality knobs on how a long-running managed session executes; geo pinning and repo-mounted skills are boundary knobs on where inference runs and where instructions come from. All four just add parameters to the same "declarative resource, imperative session" split from §2. The repo-skill knob is the one to actually scrutinize: it collapses the usual "skills are reviewed before use" assumption into "skills are whatever's on the checked-out branch" — anyone who can commit to the repo can add or edit a skill, loaded with no review step, and session tools like `bash` give those instructions real reach.

## 5. When to Use a Managed Agent Harness vs. Roll Your Own

**Use a managed harness (Claude Managed Agents, similar offerings) when:**

- Tasks run for **minutes to hours** with many tool calls.
- You need **stateful sessions** (filesystem + history) without building it yourself.
- You want **prompt caching, compaction, sandboxing, streaming** out of the box.
- You don't want to own the secure container infrastructure.

**Roll your own loop (Messages API + custom code) when:**

- You need **fine-grained control** over the loop (custom planners, multi-agent orchestration, novel control flow).
- Tasks are **short and stateless** — overhead of a session is wasted.
- You have **strict ZDR / HIPAA BAA** requirements that aren't yet supported by the managed product.
- You're optimizing for **latency** at the model-call level and don't want platform overhead.

In practice, mature systems often run both — Messages API for the hot path, Managed Agents for back-office / long-running work.

---

## 6. Compliance and Data Boundaries

Worth flagging because it's an architectural constraint, not just legal fine print:

- Managed Agents is **stateful by design** → currently **not eligible for Zero Data Retention (ZDR) or HIPAA BAA**.
- You retain delete control: sessions and uploaded files can be deleted via API at any time.
- For regulated workloads, the architectural answer is **self-hosted sandboxes + MCP tunnels**, keeping execution and data inside your boundary while the orchestrator stays managed.

## 7. Operational Limits (as of beta)

- Beta header required: `managed-agents-2026-04-01`.
- Rate limits per organization:
  - **Create** endpoints (agents, sessions, environments): **300 req/min**.
  - **Read** endpoints (retrieve, list, stream): **600 req/min**.
- SDK helpers for self-hosted workers require `/bin/bash` at exact path; TS SDK additionally needs `unzip`, `tar`, Node ≥22.

---

## 8. Mental Model — One-Sentence Summary

> A managed agent platform is a **versioned agent definition** running as a **stateful session** on a **pluggable execution environment**, talking to the model + tools through a **streamed, persisted event log**, with **explicit boundaries** between the orchestrator and where code/data live.

If you're designing your own AI system architecture, every one of those bolded primitives is something you'll either build or import. Managed Agents is a useful reference implementation to compare your design against.
