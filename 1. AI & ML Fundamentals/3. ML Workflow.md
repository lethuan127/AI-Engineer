# ML Workflow

Building an ML system follows a repeatable lifecycle. Skipping or rushing any step is the most common cause of failure.

## The Pipeline

```
Problem framing → Data → Features → Model → Train → Evaluate → Deploy → Monitor → (loop back)
```

Each step deserves more time than juniors expect.

## 1. Problem Framing

Before any code:

- **What's the business question?** Reduce churn? Detect fraud? Personalize feed?
- **What's the prediction target?** "User will churn in 30 days" needs a definition of churn AND a 30-day window in your data.
- **What's the cost of being wrong?** False positive vs. false negative trade-off.
- **Is ML the right tool?** Often a rule engine or human review is cheaper.

**Bad framing wastes weeks.** Don't skip this.

## 2. Data Collection

- Where does the data live? (DB, logs, third-party API, manual labeling)
- How much do you have? (More isn't always better; quality wins.)
- Is it representative? (Training on US users, deploying to EU = drift.)
- Is it labeled? (If not, who labels it and how consistently?)

## 3. Feature Engineering

Raw data → numerical features the model can consume.

```python
import pandas as pd
import numpy as np

df["price_per_sqft"] = df["price"] / df["sqft"]      # ratio feature
df["is_weekend"] = df["day_of_week"].isin([5, 6])    # boolean feature
df["log_income"] = np.log1p(df["income"])            # transform skewed values
df = pd.get_dummies(df, columns=["city"])            # one-hot encoding
```

In deep learning and LLMs, **features are learned automatically** from raw inputs (pixels, tokens). In classical ML, **feature engineering is where most of the win comes from**.

## 4. Model Selection & Training

Start simple. Try linear/logistic regression first, then a tree-based model (XGBoost), then a neural net only if needed.

```python
from sklearn.ensemble import GradientBoostingClassifier
model = GradientBoostingClassifier()
model.fit(X_train, y_train)
```

## 5. Evaluation

Compare against:

- A **baseline** (always predict the majority class)
- A **simple model** (logistic regression)
- The **previous version** in production

If your fancy model doesn't beat the baseline, something is wrong.

(See [6. Evaluation Basics](./6.%20Evaluation%20Basics.md) for metrics.)

## 6. Deployment

- **Batch inference**: run the model nightly, store predictions in DB.
- **Online inference**: serve via API, low latency.
- **Edge inference**: on-device (mobile, browser).

Deployment concerns:
- Model versioning (which version is live?)
- A/B testing (does the new model actually win?)
- Latency / cost budget
- Fallback if model fails

## 7. Monitoring

Models **decay** in production:

- **Data drift**: input distribution changes (new user demographic, seasonality)
- **Concept drift**: the relationship between input and output changes (fraud patterns evolve)
- **Performance drift**: accuracy quietly drops

Monitor:
- Input statistics (mean, std, missing rate)
- Output distribution
- Live performance metrics (when ground truth is available)
- Latency and cost

## Common Pitfalls

| Pitfall | Symptom | Fix |
|---|---|---|
| **Optimizing wrong metric** | Model wins offline, fails in business | Align metric with business outcome |
| **Data leakage** | Eval accuracy too good to be true | Strict train/val/test separation; check feature timestamps |
| **Survivorship bias** | Model only sees "successful" examples | Include the negatives (churned users, declined loans) |
| **"Works in notebook, fails in prod"** | Different preprocessing in training vs. serving | Use the same pipeline (feature store, ONNX, etc.) |
| **Ignoring class imbalance** | 99% accuracy by always predicting "no fraud" | Use precision / recall / F1, not accuracy |
| **Correlation ≠ causation** | Features are predictive but cause unintended behavior | Don't deploy without thinking about feedback loops |

## Takeaways

- The workflow is **iterative**: most projects loop back to data multiple times.
- **80% of effort** is data + framing, not model selection.
- **Monitoring isn't optional** — models decay silently.
- For LLM apps, the same lifecycle applies (prompts replace features; eval still rules).
