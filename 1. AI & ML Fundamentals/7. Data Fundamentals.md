# Data Fundamentals

ML is only as good as its data. **80% of ML work is data work.**

## Quality > Quantity (Usually)

Common myth: "more data always wins." Reality:

- 1,000 high-quality, well-labeled examples often beat 100,000 noisy ones.
- Garbage labels poison the model — it learns the noise as signal.
- Diversity (covering edge cases) matters more than raw volume.

## Data Quality Dimensions

| Dimension | Question |
|---|---|
| **Accuracy** | Are labels correct? |
| **Completeness** | Missing values? Missing rows? |
| **Consistency** | Same field defined the same way across sources? |
| **Timeliness** | Is data fresh? Is the schema current? |
| **Representativeness** | Does training data match production data? |
| **Bias** | Are some groups under-represented? |

## Labeling

For supervised learning, you need labels. Options:

- **In-house labeling**: highest quality, expensive, slow.
- **Crowdsourced** (Mechanical Turk, Scale AI, Surge): faster, variable quality.
- **Synthetic labels** (LLMs labeling data): fast, cheap, surprisingly good as of 2024+.
- **Weak supervision**: heuristics + rules → noisy labels at scale (Snorkel framework).
- **Active learning**: model picks the most informative examples to label next.

**Inter-annotator agreement** matters: if two humans disagree on labels, the model can't do better than that ceiling. Cohen's kappa or Krippendorff's alpha measure this.

## Data Drift

Production data **doesn't stay still**:

- **Covariate drift** (input drift): \(P(X)\) changes — new user demographic, seasonal traffic.
- **Concept drift**: \(P(Y \mid X)\) changes — fraud patterns evolve, language shifts.
- **Label drift**: \(P(Y)\) changes — class balance shifts.

Detection:
- Compare training vs. live feature distributions (KS test, PSI, Wasserstein distance).
- Monitor model output distributions.
- Track live performance metrics when ground truth becomes available.

```python
from scipy.stats import ks_2samp
stat, p = ks_2samp(train_feature, live_feature)  # Kolmogorov-Smirnov test
if p < 0.01:
    print("Distribution drift detected")
```

## Bias in Data → Bias in Models

If training data over-represents some groups, the model will:

- Perform worse on under-represented groups.
- Perpetuate or amplify existing societal biases.
- Make harmful recommendations or denials.

**Examples:**
- Hiring model trained on historical (biased) hiring data.
- Facial recognition trained mostly on light-skinned faces.
- Language models reflecting stereotypes from internet text.

**Mitigation** (see also section 8 of the main path — AI Safety & Ethics):
- Audit training data composition.
- Slice eval by demographic group.
- Re-weight under-represented examples.
- Collect more representative data.
- Use de-biasing techniques (cautiously — they have trade-offs).

## Splits Done Right

| Data type | Split strategy |
|---|---|
| **i.i.d. tabular** | Random 70/15/15 |
| **Time series** | Time-based: past → train, future → test |
| **User personalization** | Group-based: same user can't appear in train AND test |
| **Geographic** | Group by region for OOD generalization tests |

```python
from sklearn.model_selection import GroupShuffleSplit
splitter = GroupShuffleSplit(test_size=0.2, n_splits=1, random_state=42)
train_idx, test_idx = next(splitter.split(X, y, groups=df["user_id"]))
```

## Feature Engineering Cheat Sheet

| Type | Technique |
|---|---|
| Numerical (skewed) | Log transform, Box-Cox |
| Numerical (different scales) | StandardScaler, MinMaxScaler |
| Categorical (low cardinality) | One-hot encoding |
| Categorical (high cardinality) | Target encoding, embeddings |
| Datetime | Extract day-of-week, hour, is_weekend, time-since |
| Text | TF-IDF, embeddings |
| Missing values | Imputation (mean/median), or "missingness" indicator |

## Data Versioning

Treat data like code:

- **DVC** (Data Version Control) — Git for datasets.
- **LakeFS**, **Delta Lake** — versioned data lakes.
- **Feature stores** (Feast, Tecton) — centralized, versioned feature definitions.

When a model behaves differently, you need to know **which exact data it was trained on**.

## Data for LLMs / RAG

For AI Engineers, "data" extends to:

- **Pre-training data** — usually inherited from the base model. Affects knowledge & biases.
- **Fine-tuning data** — small, high-quality task-specific examples.
- **RAG corpus** — documents you retrieve at inference time. Quality, freshness, and chunking matter as much as the LLM itself.
- **Eval data** — golden test sets for measuring system quality. **Curate carefully.**

Section 4 of the main path (RAG & Vector Databases) covers RAG-specific data concerns.

## Takeaways

- **Data work dominates.** Plan for it.
- **Quality beats quantity** — clean labels > more noise.
- **Drift is inevitable** — monitor it.
- **Bias in data → bias in models.** Audit by slice.
- **Split strategy depends on data type** — random splits aren't always right.
- **Version your data** like you version your code.
