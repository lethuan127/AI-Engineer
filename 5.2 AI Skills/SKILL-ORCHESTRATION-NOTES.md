## 2. Reliability finding: mandatory response-format elements are also being skipped

Checking the two Bridgeton sessions against `askfullscore`'s own "Self-check before responding" checklist turned up more than the missing feedback flag — **two other items stated as mandatory for every response** were also absent from both final answers:

- The **"How we got this answer" box** (SKILL.md §Response format overlay, item 6) — stated as required after every main answer. Missing in both.
- The **three actionable insights with emoji hierarchy** (item 3) — stated as mandatory for every response. Missing in both.

This matters for how we think about fixing the feedback-flag problem: **it is not uniquely unreliable.** Multiple checklist-driven closing requirements in this skill are being dropped once a response has gone through several rounds of tool-call recovery. A narrow fix aimed only at the ⚠️ flag is unlikely to hold up if the underlying cause — end-of-response checklists losing priority under multi-step tool recovery — isn't addressed.

## 3. Recommendations for skill orchestration going forward

1. ✅ **Implemented — Embed the defect-flag check in each skill's own self-check list**, not only in `report-feedback`'s standalone description. `report-feedback` was never invoked via the Skill tool in any of the three sessions — self-noticing depended on the agent recalling it passively from the skill listing. Adding `- [ ] Hit a broken path / contradicting schema / unfollowable instruction? Append the ⚠️ line.` to the actively-running skill's own checklist puts the reminder where the model is already checking items off. *Applied to `askfullscore/SKILL.md` as new rule 16 ("Self-noticed defects — log and flag, don't just work around") plus a matching self-check line — pending verification against a fourth session.*

2. **Prefer a shared companion skill over per-skill copies.** `askfullscore` already lists `analytics-response-format` as a companion skill used across the whole `ask*` family. Putting the defect-flag requirement there means one edit propagates everywhere and stays consistent as skills evolve, instead of being pasted into N skills that will drift.

3. ✅ **Implemented — Don't rely on end-of-response memory — record the defect the moment it's hit.** The likely failure mode: by the time the final answer is composed, a documented-path failure from several tool-calls back has fallen out of working attention. Instruct the agent to log it as a task (`TaskCreate`) at the moment of detection, then resolve that task by asking the flag question before ending the turn — a tracked task survives across tool calls in a way a "remember to mention this later" intention doesn't. *Applied to `report-feedback/SKILL.md`'s "Self-inferred" trigger section and its self-check list — not yet verified against a freshly-deployed session.*

4. **Consider mechanical enforcement, not just wording, if this keeps failing.** Session transcripts show a `hook_additional_context` mechanism already exists in this framework (it injected extra instructions when a skill was invoked). If a post-tool-use hook is feasible, detecting a Read/Bash failure on a path under a skill's own reference folder and force-injecting a reminder right then would be the only approach that stops depending on the model choosing to comply.

5. **Audit self-check compliance broadly, not just for this one flag.** Given §2's finding, it's worth spot-checking a handful of other `ask*` skills' real sessions against their own mandatory checklists before assuming any single skill's self-check is being honored end-to-end.

## 5. General patterns (beyond `askfullscore`)

Seven patterns generalize from §1-3 to skill design across the whole plugin family:

1. **Documentation-reality drift is the root cause of most content defects.** Every defect in §1 except the self-flag is the same failure mode: a skill asserts something about its own environment — a path, a table, a company scope — that no longer matches reality. A build-time lint verifying every `references/X.md` a SKILL.md mentions exists on disk, and every `sql_table`/model name it cites resolves via `get_semantic_metadata_by_name`, would catch most of these before a user ever hits them.

2. **Copy-paste across operator-scoped skills leaks hardcoded scope.** The Schwazze/inventory-turns file (§1.2) is evidence content gets ported between company-specific plugin variants without being regenericized. Any file copied across operator plugins needs a "did I leave a hardcoded company/table in here" check before it ships.

3. **Single-source rules — don't let two files both claim authority.** Rule 5 and the SKU-availability guide (§1.3) independently assert which table is the OOS source of truth, and disagree. When a rule has both a SKILL.md summary and reference-file detail, the reference file should point back to the rule, not restate it — restating invites drift.

4. **Long tool-chains cause checklist fatigue, not just single-item forgetting.** The real signal from §2 isn't "the feedback flag didn't fire" — three separate mandatory closing items dropped together once a response had gone through several rounds of recovery. End-of-response checklists are structurally unreliable past a certain tool-call depth, independent of which items are on them. Either shorten what's mandatory at the very end, or move checks to trigger immediately after the relevant event instead of deferring to response composition.

5. **Meta-behaviors need to live inside the skill that needs them, not in a separate skill.** `report-feedback`'s self-noticing only works if the agent recalls it passively — it was never invoked (§3.1). Anything that needs to happen *during* another skill's run belongs in that skill's own self-check, with the standalone skill as backup/entry point for explicit user reports.

6. **Externalize anything that must survive multiple tool calls.** `TaskCreate` as a "flag this" marker (§3.3) beats "remember to mention this later" — working memory across a long tool chain is exactly what pattern 4 shows failing. This generalizes past feedback-flagging to any deferred obligation a skill imposes.

7. **Progressive disclosure means the body isn't guaranteed to load — put anything that must fire without explicit invocation into the `description`.** Skills load in two tiers: `name` + frontmatter `description` sit in the always-visible skill listing; the full SKILL.md body only loads once the model actually calls `Skill(<name>)`. `report-feedback` was never invoked in either Bridgeton session — only `askfullscore` was — so an instruction added only to `report-feedback`'s body (as we first did for the `TaskCreate` logging step) would never be read in exactly the self-noticing scenario it's meant to cover. Anything a *passively-recalled* skill needs to guarantee belongs in the description, not the body; the body can hold detail for when the skill *is* invoked (user-reported feedback, or the model explicitly choosing to invoke it), but can't be relied on for behavior that's supposed to trigger while a different skill is running. This sharpens pattern 5: embedding the check in the *active* skill's own self-check (e.g. `askfullscore`'s) is more robust than putting it anywhere in `report-feedback`, active or not — the active skill's body is the one guaranteed to be loaded.
