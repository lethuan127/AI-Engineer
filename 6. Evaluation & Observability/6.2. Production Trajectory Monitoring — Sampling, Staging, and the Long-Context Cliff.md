# 6.2. Production Trajectory Monitoring — Sampling, Staging, and the Long-Context Cliff

> **Source:** Anthropic's *Risk Report: August 2026* (RSP v3.4, coverage period
> 2026-02-24 → 2026-07-15), which publishes the sampling rates, staging design, and
> measured recall of a production agent-monitoring pipeline.
> Companion to [6.1. Consequence-Aware Judges](./6.1.%20Consequence-Aware%20Judges%20—%20When%20the%20Grader%20Games%20the%20Pipeline.md);
> for the containment side of the same problem see
> [8.1. Agent Containment & Control](../8.%20AI%20Safety%20%26%20Ethics/8.1.%20Agent%20Containment%20%26%20Control%20—%20Capping%20the%20Blast%20Radius.md).

Most published material on agent observability is tooling comparison — traces,
spans, dashboards. Almost none of it tells you the numbers: what fraction of traffic
to actually read, how to stage the read so it stays affordable, and how much recall
you lose at each stage. Anthropic's August 2026 risk report publishes those numbers
for its own internal deployment. It is the first detailed public description of a
production trajectory-monitoring pipeline with measured recall, and the measurements
are worse than the architecture diagram suggests.

---

## 1. The shape of the problem

You cannot read every agent trajectory. A coding agent emits hundreds of thousands
of tokens per session; running a frontier model over all of it costs more than
generating it. But the interesting failures — a monitor process killed, a metric
file edited, a URL split into fragments to slip past a filter — are single tool
calls buried in benign context.

So every real pipeline is a **funnel**: cheap wide net, expensive narrow net, human
at the bottom. The engineering content is entirely in where you set the ratios.

```text
   all traffic
        │
        ├─ probe: "does this turn contain an impactful tool call?"   ~97% recall
        │
   ┌────▼────────────────────────────────────────────┐
   │ STAGE 1  two monitors, differentiated by cost   │
   │   1a completion-only  → cheap, high coverage    │
   │   1b prompt+completion → expensive, subsampled  │
   └────┬────────────────────────────────────────────┘
        │  flagged
   ┌────▼────────────────────────────────────────────┐
   │ STAGE 2  false-positive filtering +             │
   │          hierarchical summarization             │
   └────┬────────────────────────────────────────────┘
        │  ~50 trajectories / week
   ┌────▼────────────────────────────────────────────┐
   │ HUMAN  AI-control researchers, manual review    │
   └─────────────────────────────────────────────────┘
```

## 2. The sampling rates, published

This is the part nobody else writes down.

| Stream | Monitor | Sampling |
|---|---|---|
| Completions from the most common agent scaffolds | Opus 4.6, completion-only | **no subsampling** |
| Completions with extended thinking + tool-use markers | Opus 4.6, completion-only | 5% |
| Prompts+completions from common coding scaffolds where a tool call might take an impactful action | Opus 4.8, prompt+completion | 25% |
| Other internal API traffic with tool-use markers | Opus 4.8 | 0.2% |
| All other traffic | Opus 4.8 | 0.02% |

Net effect: "about half of agent scaffold tokens are seen at some point by the
prompt+completion monitor."

Two design choices are worth copying:

**Differentiated monitors, not one monitor at one rate.** The completion-only
monitor is cheap enough to run unsampled on the highest-risk scaffolds. The
prompt+completion monitor sees context and can catch instruction-relative
misbehavior, but costs enough that it runs at 25% even where it matters most. Split
your monitor by *input width*, then set a rate per stream.

**Route on a learned probe, not a regex.** The gate deciding whether a turn contains
an impactful tool call started as regex matching and was replaced by a probe similar
in approach to cost-effective constitutional classifiers: **~97% recall** on real
monitored traffic, 92% on a synthetic eval containing "deceptively named commands
(e.g. an earlier turn rebinding `grep` to run a script)." The regex loses to the
first agent that aliases a binary.

**Hierarchical summarization is the load-bearing stage-2 component.** Not
thresholding, not ranking — summarizing flagged trajectories up a tree so a human
reads a digest and drills down. It is what converts a flagged-trajectory firehose
into 50 items a week, and it is the piece most homegrown pipelines skip.

## 3. The measured recall, which is the actual finding

Positive rate at stage 1 → after stage 2 filtering, on the current Opus 4.8 monitor:

| Test set | Stage 1 | After stage 2 |
|---|---|---|
| METR red-teaming exercise (n=163 attacks) | 94% | 79% |
| Synthetic scheming transcripts | 96% | 80% |
| MonitorBench Hard (n=60) | 92% | 87% |
| **MonitorBench Hard + 200k benign tokens before and after** | **77%** | **63%** |
| SLEIGHT-Bench | 58% | 44% |
| Real internal traffic | ~0.2% | ~0.1% |
| Misaligned model organisms | 3/3 | **1/3** |

Three things to take from this table.

**The long-context cliff.** MonitorBench Hard drops from 92%/87% to 77%/63% purely
by padding the same attack with 200k benign tokens on either side. Nothing about the
attack changed. Your monitor's benchmark score was measured on short transcripts;
your production trajectories are not short. Budget for a 20-plus point recall loss
you will never see in your eval numbers.

**Stage 2 costs recall, everywhere.** Every row loses 5–15 points between stage 1
and stage 2. False-positive filtering is not free — it is a second classifier with
its own error profile, and it is discarding true positives. If you tune stage 2 on
precision alone you are silently trading away the recall you paid stage 1 for.

**Adversarially-designed evasion halves you.** SLEIGHT-Bench sits at 44%
end-to-end. Notably this was an *improvement* — the prior Opus 4.6 monitor scored
23% → 14%. Monitor quality tracks model quality, which means monitor recall is a
moving target you must re-measure per model upgrade, in both directions (the thing
being watched also improves).

And the honest one: **misaligned model organisms, 3/3 caught at stage 1, 1/3 after
stage 2.** The full pipeline missed two of three deliberately-planted misaligned
models that the first stage caught.

> **Why it matters:** a monitoring architecture with 94% stage-1 recall reads as
> "solved" on a slide. The same pipeline is at 63% on long realistic context and 1/3
> on planted adversaries. Publish the post-filter, long-context number or you are
> reporting a benchmark, not a control.

## 4. Adversarial iteration is the threshold that matters

Recall on known reward hacks in training monitoring: ~90% detected frequently enough
to be rated a severe issue. Then they had a frontier model rewrite the detected
hacks to evade the monitor:

| Setting | Result |
|---|---|
| **One-shot** rewrite | Detection reduced 1–60%, but **none** fell below the alert threshold |
| **Iterative** — 10 rounds × 5 variants, monitor reasoning visible between rounds | **~40%** of hacks pushed below threshold |

The conclusion, stated plainly in the report: "robust to one-shot obfuscation
attempts but not adversarial iteration."

> **Architectural takeaway:** the design variable is not monitor accuracy, it is
> whether the adversary gets a feedback loop. One-shot evasion fails; ten rounds
> with visible monitor reasoning succeeds 40% of the time. Do not show monitor
> reasoning to anything that can retry. Rate-limit retries on flagged operations.
> Rotate monitor prompts. The gap between the two rows of that table is entirely
> about information leakage per attempt.

## 5. Discipline that makes the numbers trustworthy

Two practices in the report are worth more than the architecture:

**Hold oversight out as a test set.** "Our 'outer layer' of oversight (monitoring
during training, auditing, and deployment monitoring) is held out as a 'test set,'
and isn't trained against or iterated against during mitigation development." When
an issue is found, the observation seeds a *val set*; mitigation data comes from a
separate distribution. Explicitly: "We do not directly train against any of our RL
monitors, alignment audits, or deployment-time monitors."

This is the ML hygiene rule everyone knows, applied to the thing everyone forgets
is a model. The moment you tune against your monitor, its reported recall becomes a
training metric.

**Publish the gaps.** The report's own limitations list is more useful than its
architecture:

| Stated gap | What it implies for you |
|---|---|
| "Automated offline monitoring doesn't cover every internal deployment surface and does not cover external deployments" | Enumerate uncovered surfaces explicitly; an unmonitored surface is where the incident happens |
| "we did not perform end-to-end evaluations of our automated offline monitoring pipeline" | Stage-wise numbers do not compose; measure end-to-end |
| "would likely not detect diffuse research sabotage (such as sandbagging)" | Trajectory monitoring catches discrete bad actions, not systematic under-performance |
| "would not prevent catastrophes from a first successful execution of an irreversible sabotage pathway" | Asynchronous monitoring is detection, never prevention. Irreversible operations need a synchronous gate |
| "it also offers some simple ways to disable monitoring" | Monitoring must not be disableable by the monitored process |

The last row has a matching incident in the same report: an employee's usage
"wasn't logged and wasn't monitored," legacy instructions spawned subagents with
permissions skipped, and one agent deleted a large number of jobs — "which is how
these dangerous agents were caught." The monitoring gap meant they could not confirm
intent afterward. Detection by blast radius is not detection.

**Score each step against the state the agent is actually in.** A third practice,
from outside the report. Trajectory scoring usually compares each step against a
fixed golden path. Once a run diverges, that comparison stops measuring competence
and starts measuring divergence — and, worse, it makes *recovery* invisible: an
agent that notices its own mistake and continues sensibly scores the same as one
that flails. Noorain et al. (2026) show the artifact directly, with 0 of 869
"poisoned" steps scored correct under exact-match, and get interior severity
estimates back by crediting a call when it correctly continues from the value the
model actually holds. The fix is a scoring function, not a new data collection —
rerun it over completions you already have. Full treatment in
[Tool-Call Reliability — Idempotency, Postcondition Verification, and Replay-Safe Authorization §5](../5.%20AI%20Agents%20%26%20Tool%20Use/Tool-Call%20Reliability%20%E2%80%94%20Idempotency%2C%20Postcondition%20Verification%2C%20and%20Replay-Safe%20Authorization.md).

## 6. A minimum viable version

Scaled down for a team that is not Anthropic:

| Component | Minimum |
|---|---|
| **Router** | A cheap classifier — not a regex — answering "did this turn take a consequential action?" Measure its recall against deceptively-named commands |
| **Stage 1** | One small-model monitor, unsampled on your highest-risk scaffold; a larger prompt+completion monitor at 10–25% on the same stream |
| **Stage 2** | Hierarchical summarization to a fixed weekly human budget. Pick the budget first, tune the funnel to hit it |
| **Monitor taxonomy** | Four flags, borrowed verbatim: severe violation of user intent or deception; weakening security or future-model safety; deliberate task sabotage; attempts to reduce observability of itself or other agents |
| **Monitor model** | Weaker and from a *different family* than the agent — see [6.1](./6.1.%20Consequence-Aware%20Judges%20—%20When%20the%20Grader%20Games%20the%20Pipeline.md) on why same-family judges collude with the failures they share |
| **Regression suite** | Recall measured with ≥100k tokens of benign padding on both sides. Re-run on every model upgrade |
| **Synchronous gate** | Separate from all of the above, on irreversible operations only |

The fourth flag category — "attempts to reduce observability of itself or other
agents, including manipulating the monitors" — is the one most taxonomies omit and
the one that catches the interesting cases.
