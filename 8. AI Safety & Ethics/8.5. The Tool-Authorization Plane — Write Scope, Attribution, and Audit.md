# 8.5. The Tool-Authorization Plane — Write Scope, Attribution, and Audit

> Companion to [8.4. The Agent Containment Toolchain — Sandbox, Runtime, and Egress Proxy](./8.4.%20The%20Agent%20Containment%20Toolchain%20—%20Sandbox,%20Runtime,%20and%20Egress%20Proxy.md). 8.4 closes with a question the three containment planes cannot answer: *what is irreversible?* This note covers the fourth plane that answers it, and the reference implementation that shipped in August 2026.

The infrastructure, runtime, and network planes all reason about the agent's *process*. None of them can tell a `get_merge_request` from a `merge_mr` — both are HTTPS POSTs to the same host, with the same credential, from the same container. The distinction that matters operationally is not where the call originates but **what it changes and whether that change can be undone**. That distinction lives at the tool boundary, and until recently nobody enforced it there.

Cloudflare's WriteGuard, announced 5 August 2026 and now in private beta, is the first widely documented implementation. It is worth reading not as a product but as an argument about where agent authorization belongs.

---

## 1. The failure mode: attribution collapse

The motivating incident in Cloudflare's writeup is deliberately unglamorous. An engineer's background agent, running a cleanup task with an over-broad prompt, closes thousands of tickets over an afternoon. The engineer was also closing tickets by hand that afternoon. The ticketing system recorded every change under his name, and the network logs did not distinguish one agent session from another.

> Why it matters: the incident is not primarily an *authorization* failure. The agent had permission to close tickets — it was using its owner's credentials, and its owner could close tickets. It is an **attribution** failure. Nothing in the system could separate "Joe did this" from "one of Joe's three concurrent agent sessions did this," which is why finding the culprit took half an hour and repairing state was guesswork.

This generalizes. Every design that gives an agent the operator's OAuth token inherits the same property: the downstream system sees a human, and the audit trail is unusable at exactly the moment you need it.

## 2. Why the harness-side approval prompt is not a control

The obvious response is the permission prompt — the approval dialog every coding agent already ships. Cloudflare rejects it in one sentence, and it is the sharpest architectural claim in the piece:

> "We could not count on client-side controls such as skills or elicitation prompts. Their behavior varies by harness, and users can disable them."

Both halves matter. **Behavior varies by harness**: the same MCP server reached from Claude Code, an IDE agent, and a long-running background service gets three different approval UXes, and a headless service gets none. **Users can disable them**: an approval a user can turn off is a default, not a boundary.

| Control location | What it actually is | Holds under a headless agent? |
|---|---|---|
| Harness permission prompt | Interaction design | No — no human in the loop to prompt |
| MCP elicitation | Protocol-level UX affordance | No — client decides whether to honor it |
| Server-side tool policy | Enforcement | Yes — runs regardless of caller |

> Architectural takeaway: this is the same lesson as [8.4 §5](./8.4.%20The%20Agent%20Containment%20Toolchain%20—%20Sandbox,%20Runtime,%20and%20Egress%20Proxy.md) — a constraint that lives on the client side of a trust boundary is advice. Enforcement belongs on the side that owns the consequence.

## 3. Keep the person, add the agent

The design decision that makes the rest coherent: WriteGuard **does not** give agents their own identities. The agent runs as its operator, inheriting that person's permissions exactly — if Joe cannot close an issue, Joe's agent cannot either. Cloudflare's stated reason for rejecting agent service accounts is that they "would create a second set of permissions to manage and make the connection to the person responsible for the agent less clear."

Attribution is then solved as a *separate* layer rather than by splitting identity:

```text
identity  =  human (from OAuth / SSO)
attribution =  human  +  MCP client  +  session
              └─ who is accountable ─┘  └─ which agent run ─┘
```

That triple is what the audit log records, and — where the downstream tool has a free-text field — what gets injected into the payload so the label appears in the ticket, comment, or email a human later reads.

> Architectural takeaway: **authorization and attribution are separable concerns, and conflating them is what pushes teams toward agent service accounts.** Keeping authZ coarse (agent = its operator) and paying for observability with a dedicated attribution layer is the cheaper trade: one permission model to maintain, and a named human on every action.

## 4. The mechanism

Policy is declared per tool, alongside the tool, without modifying the MCP server:

```ts
const sendEmailTool = {
  tool: EmailMCP.sendEmailTool,
  writeGuard: {
    riskLevel: RiskLevel.CONTAINED_WRITE,
    enabled: true,
    labeling: {
      field: "body",
      supportedFormats: [
        LabelFormat.PLAIN_TEXT,
        LabelFormat.HTML,
      ],
    },
  },
};
```

Three fields, three jobs:

| Field | Job |
|---|---|
| `riskLevel` | Classification. Drives whether the call is logged, and makes the audit log queryable by risk. |
| `enabled` | Enforcement. The boolean that actually blocks. |
| `labeling.field` | Names a key in the tool's own input schema — the injection point for the attribution string. `supportedFormats` declares what the downstream app can render. |

Three paths through the wrapper, all resolved **before the tool handler runs**:

```text
read tool          ──►  pass through unchanged
allowed write      ──►  inject attribution into `field`  ──►  call handler  ──►  async audit event
disabled write     ──►  block  ──►  record the attempt
```

Audit delivery is asynchronous to an internal Worker, "so it adds no latency to the response the agent is waiting for." The event is key-scrubbed and carries server, tool, risk tier, outcome (successful / failed / blocked), user, client, and duration.

> Lesson: `labeling.field` is the quietly clever part. Because the attribution goes into the tool's *existing* payload schema, no downstream system needs to know WriteGuard exists — the label shows up as text in the GitLab note or the email body, legible to humans and to the next agent that reads the same thread.

## 5. The risk tiers, and what they actually decide

| Tier | Examples given |
|---|---|
| `READ_ONLY` | Search issues; read a merge request; view pipeline status |
| `MINIMAL_IMPACT` | Add a reaction; mark a notification read; subscribe to an issue |
| `CONTAINED_WRITE` | Add a comment; create an MR; update an issue field |
| `CRITICAL` | Merge an MR; trigger a production deployment; bulk-delete records |

Read that table for what it is: a taxonomy defined **ostensively**, by example, with no published predicate. There is no stated rule for what makes something `CONTAINED_WRITE` rather than `MINIMAL_IMPACT`. And the tier is not the enforcement mechanism — `merge_mr` is blocked because `enabled: false`, not because it is `CRITICAL`. The tier is metadata: a reason recorded alongside the decision, and a query dimension on the log.

Classification is also entirely manual. Tools are tagged by hand in TypeScript. Notably, the taxonomy does not build on MCP's own `readOnlyHint` / `destructiveHint` / `idempotentHint` annotations — it is a parallel vocabulary. Cloudflare names "how the risk model maps to customer tools" as the first thing the beta exists to validate.

> Architectural takeaway: everything mechanical here is straightforward wrapper plumbing you could build in an afternoon. **The hard, unsolved, unautomated part is deciding which tier each tool belongs to** — and that is a judgment about your systems, not something a vendor ships you.

## 6. What this plane still does not stop

Worth stating plainly, because the tier names oversell the guarantees:

| Gap | Consequence |
|---|---|
| **No approval path** — enforcement is binary allow/deny | `CRITICAL` + human-in-the-loop is implemented as *deny*. The human loop happens entirely outside the system. |
| **No rate or velocity control** | The opening anecdote is fundamentally a *rate* problem. Had `close_ticket` been `CONTAINED_WRITE` and enabled, WriteGuard would have labeled and logged all thousand closures — turning a 30-minute investigation into a 30-second one, but not preventing it. |
| **Policy granularity stops at the tool** | No argument-level rules — no "allow `update_issue`, but not on production projects." |
| **Best-effort audit** | Async fire-and-forget means the trail is not transactional with the write. Cloudflare lists "what audit delivery guarantees customers require" as an open question. |
| **Labeling needs a rendering surface** | Tools with no free-text field in their schema get no visible attribution — only the out-of-band audit event. |

> Lesson: read the limits before the tier names. "Critical" here means "we turned it off," not "we gated it." A design that assumes a `CRITICAL` tool is gated rather than absent has misread the mechanism.

## 7. The four planes, revised

| Plane | Question | Reference implementation |
|---|---|---|
| Infrastructure | If the process is hijacked, what can it touch on the host? | NemoClaw / microVM sandboxes |
| Runtime | What software is running inside the loop, and how exploitable is it? | NanoClaw + Echo |
| Network | What is allowed to leave the boundary? | CrabTrap |
| **Tool authorization** | **Which actions are available, who is accountable, and what did they do?** | **WriteGuard** |

The fourth plane is the only one that reasons about *semantics* rather than *mechanism*, which is exactly why it cannot be handed to you pre-configured. The first three ship with sensible defaults. This one requires you to enumerate your own tools and decide which ones you would not want to discover after the fact.

Design checklist, extending [8.4 §6](./8.4.%20The%20Agent%20Containment%20Toolchain%20—%20Sandbox,%20Runtime,%20and%20Egress%20Proxy.md):

1. **Enumerate every write tool** your agents can reach. Not every tool — every *write* tool.
2. **For each, ask whether an accidental thousand-fold execution is survivable.** If not, it needs enforcement, not classification.
3. **Confirm the enforcement point is server-side.** If your answer is "the agent asks first," you have a default, not a control.
4. **Verify attribution reaches the downstream system**, not just your logs. The person investigating at 4 p.m. is reading the ticket, not your observability stack.
