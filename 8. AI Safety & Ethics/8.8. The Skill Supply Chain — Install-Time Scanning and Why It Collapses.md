# 8.8. The Skill Supply Chain — Install-Time Scanning and Why It Collapses

> Sixth plane, and the only one that runs *before* the agent does. [8.4. The Agent Containment Toolchain](./8.4.%20The%20Agent%20Containment%20Toolchain%20—%20Sandbox,%20Runtime,%20and%20Egress%20Proxy.md) and [8.5. The Tool-Authorization Plane](./8.5.%20The%20Tool-Authorization%20Plane%20—%20Write%20Scope,%20Attribution,%20and%20Audit.md) constrain an agent at execution time. This note is about the admission gate on the artifacts that *become* the agent's instructions.
>
> Companion to [11.4. Skills](../11.%20Harness%20Engineering/11.4.%20Skills.md) and [Agent Plugins — Packaging Skills and MCP Servers for Cross-Client Portability](../5.%20AI%20Agents%20%26%20Tool%20Use/Agent%20Plugins%20—%20Packaging%20Skills%20and%20MCP%20Servers%20for%20Cross-Client%20Portability.md), which cover the format and the packaging. This one covers what happens when the format becomes a registry.

A skill is a markdown file with a YAML header that an agent reads and obeys. That is the entire artifact. It ships with the agent's full authority — shell, filesystem, credentials, network, persistent memory — and until 2026 most registries required nothing more than a `SKILL.md` and a GitHub account to publish. The ecosystem reproduced npm's first decade in about six months, and then discovered that the obvious fix, scanning at install time, does not survive contact with an adversary who can rewrite text without changing behavior.

The claim of this note: **install-time scanning is a real plane and you should run it, but it is a filter on *unmodified* malware, not a trust boundary. Every published evaluation shows behavior-preserving transformation collapsing static scanners from near-perfect to near-useless, and every proposed fix trades the boundary for a probabilistic execution simulation with a stated blind spot.**

## 1. Why skills are a worse supply chain than packages

The parallels to npm and PyPI are exact enough to be useful, and the divergences are where the design work is.

| Property | Language package ecosystems | Agent skills |
|---|---|---|
| Typosquatting | Observed | Observed |
| Malicious maintainer | Observed | Observed |
| Post-install execution | `postinstall` scripts | Skill "prerequisite" / "setup" instructions |
| Privilege at run time | Process privileges of the build or app | Full privileges of the agent that loaded it |
| Attack medium | Code | Code **and** natural language |
| Persistence | Reinstall required | Agent memory files survive the session |
| Review gate at publish | Registry policy, signing, provenance | Historically none |

Three of those rows have no analog on the left. A skill does not need an exploit; it needs a persuasive paragraph. Unit 42 names this **semantic instruction hijacking** and draws the consequence plainly: because nothing isolates skill logic from agent authority, installation is equivalent to handing over the agent's identity.

The natural-language medium also breaks the detection model. Snyk's February 2026 audit of 3,984 skills across ClawHub and skills.sh found 1,467 (36.82%) carrying at least one security flaw and 534 (13.4%) at critical severity, with 76 human-confirmed malicious payloads. The load-bearing number in that study is not the prevalence, it is the convergence: **100% of confirmed malicious skills contained malicious code and 91% simultaneously carried prompt injection.** The injection exists to make the agent accept the code. Neither a code scanner nor a model's own safety training sees the pair.

> Why it matters: a code scanner asks "does this file do something dangerous." A skill asks the agent to do the dangerous thing on its behalf, in prose, and supplies a jailbreak first so the agent does not object. The two halves are individually below threshold.

## 2. What the registries actually shipped

Scanning arrived as an admission gate at three different points in the chain, with different failure modes.

| Gate | Where it runs | Verdicts | Notable limits |
|---|---|---|---|
| **NVIDIA SkillSpector** (open source, Aug 2026) | Author's machine or registry CI | Risk score 0–100; `>50` = do not install | 64 patterns; static AST + taint + YARA + OSV dependency query; optional LLM triage at ~87% claimed precision |
| **Snyk `mcp-scan --skills`** (open source) | Developer machine, pre-deployment | 8 policy classes, 3 severities | 90–100% recall on *confirmed* malicious samples, 0% FP on curated top-100 |
| **Anthropic skill and plugin scanning** (beta, Enterprise) | Upload/edit time, server side | pass / warn / fail | Off by default; new uploads only; excludes MCP servers, hooks, Skills API, and CMEK/ZDR/HIPAA orgs |

Three design decisions in the Anthropic gate are worth copying regardless of vendor, because each answers a question the others leave open:

1. **Three verdicts, not two.** `warn` exists because "I could not verify this" is a different state from "this is malicious," and collapsing them either blocks half the ecosystem or waves it through. `warn` stays usable behind an acknowledged banner; `fail` is hard-blocked.
2. **A blocked skill cannot be overridden — by the uploader *or* the admin.** This is the unusual choice. It removes the approval-fatigue path that [8.1](./8.1.%20Agent%20Containment%20%26%20Control%20—%20Capping%20the%20Blast%20Radius.md) documents killing every other human-in-the-loop gate, at the cost of having no escape hatch for false positives.
3. **Scanning happens in an isolated environment, and the copy is deleted.** The scanner reads attacker-authored text with a model. That is itself an injection surface, and it must not share a session with the user's agent.

The exclusions are the more instructive half. Scanning covers *new uploads only* — existing skills keep working, so turning the gate on does not retroactively secure the installed base. It does not cover MCP servers or hooks, which carry comparable authority. And it is off by default, which means the population it protects is the subset of Enterprise orgs that went looking for it.

> Architectural takeaway: an install-time gate that exempts what is already installed is a gate on *growth rate*, not on inventory. Pair it with a one-time audit of the existing set (`uvx mcp-scan@latest --skills` or equivalent) or the gate's coverage is whatever fraction of your skills postdate the day you enabled it.

## 3. The evasion results

Two independent 2026 papers, different teams, different attack primitives, same conclusion.

**SkillCloak** (HKUST) preserves behavior and changes only appearance, two ways: rewriting command tokens, credential paths and URLs into equivalent forms the agent reassembles at run time; and packing the payload into a directory the scanner skips, behind a clean cover. Evaluated on 1,613 genuine malicious skills pulled from a marketplace archive — every one already flagged by some detector.

| Technique | Result |
|---|---|
| Packing | Evaded **every** scanner >90% of the time |
| Token rewriting | Cleared >80% of static scanners; 96% against one hybrid rules+LLM tool |
| Best static scanner, before → after rewriting | **~99% → ~10%** detection |

**SkillCamo** (NTU/UCAS/BUAA) attacks the modality boundary instead. It hides operational instructions inside images bundled with the skill and rewrites `SKILL.md` so the documentation references those images as a normal part of the workflow. The malice exists only in the *joint* text+image reading; neither artifact is incriminating alone. Against six deployed scanners, the full-image variant achieved 100 / 87 / 92 / 78 / 87 / 100 attack success. The text-only baseline it is compared against scored 90 and 100 on two scanners and **0** on the other four — meaning SkillCamo is precisely what breaks the scanners that had already solved text-only injection.

> Lesson: both results are the same result. Scanners match on the *surface form* of a payload, and surface form is the one property an attacker can change for free while holding behavior fixed. This is the reason AV moved from signatures to behavior twenty years ago, rediscovered.

Unit 42's field data confirms it outside the lab. Of five malicious skills they found unblocked on ClawHub between February and May 2026, all five had passed the detection tools in place at the time. One (`omnicogg`) simply prepended a base64 `curl | bash` dropper to `README.md` and followed it with **22 MB of padding** — over the size ceiling content-analysis pipelines enforce before they decline to process a file. VirusTotal returned clean. The evasion was a file-length check.

## 4. Execution-grounded defenses, and their shared blind spot

Both papers propose the same class of fix — stop reading the artifact, run it and watch.

- **SkillDetonate** (paired with SkillCloak) is a sandbox observing OS-boundary behavior, with two mechanisms that matter: *on-demand closure lift*, feeding instructions the skill writes for itself mid-run back into the same session so multi-stage payloads actually fire; and *marker-based taint analysis*, labelling every sensitive read and following it across files, processes, network calls, and the agent's own language context. Reported 97% detection at ~2% false positives on synthetic payloads, 87% on real-world malicious skills, holding under SkillCloak. Cost: ~2.5 minutes per skill.
- **ExecScan** (paired with SkillCamo) simulates execution across contexts rather than detonating, analyzing documentation, code, referenced resources and visual content jointly, and flags when *any* plausible context yields high-risk behavior. Against SkillCamo's full variant it holds attack success to 8% where the six deployed scanners sat between 78 and 100.
- **SkillProbe** goes one level up and audits for *inter-skill* risk: individually benign skills that combine into malicious behavior. Auditing 2,500 real ClawHub skills, only 9.9% came through fully clean, over 90% of high-popularity skills failed, and — the structurally interesting finding — high-risk skills form a **single giant connected component** in the risk-link graph. Cascaded risk is systemic, so per-skill atomic auditing is the wrong unit of analysis.

The blind spot is stated by the SkillDetonate authors and applies to all three: **a detonation sandbox only sees the behavior the agent chooses to run.** A payload sitting behind an instruction the agent skips never fires. Worse, an attacker can use prompt injection to steer the agent *away* from the malicious path during analysis. The scanner is an agent, so the scanner is injectable.

> Architectural takeaway: execution-grounded scanning converts a pattern-matching problem into an agent-reliability problem. That is progress — the detection rates are real and large — but it does not produce a boundary. It produces a better probabilistic filter whose failure mode is now correlated with the failure mode of the agent it protects.

## 5. Where this leaves the plane

The honest position is that the install-time gate belongs in the stack and belongs low in it. Ranked by what actually holds:

| Layer | Holds against | Fails against |
|---|---|---|
| Registry provenance (signing, content hash, pinned version) | Silent post-approval mutation, republish-under-new-ID | A signed malicious skill |
| Install-time scan (static) | Unmodified, previously-seen malware | Any behavior-preserving rewrite |
| Install-time scan (execution-grounded) | Obfuscation, packing, multimodal hiding | Paths the agent declines to take; injection of the scanner |
| Runtime egress + filesystem policy ([8.4](./8.4.%20The%20Agent%20Containment%20Toolchain%20—%20Sandbox,%20Runtime,%20and%20Egress%20Proxy.md)) | Exfiltration regardless of intent | Exfiltration through an allowlisted destination |
| Tool authorization ([8.5](./8.5.%20The%20Tool-Authorization%20Plane%20—%20Write%20Scope,%20Attribution,%20and%20Audit.md)) | Write actions outside granted scope | Damage inside granted scope |

The order matters: everything above the runtime line is probabilistic, and the deterministic planes are what get hit when the probabilistic ones miss. This is the same conclusion [8.1](./8.1.%20Agent%20Containment%20%26%20Control%20—%20Capping%20the%20Blast%20Radius.md) reaches from the incident side, arriving here from the supply-chain side.

OWASP's Agentic Skills Top 10 — an Incubator project, v1.0 dated March 2026, so an emerging taxonomy rather than a settled standard — is worth reading for the vocabulary and for one specific proposal. Its **Universal Skill Format** sketch is the missing provenance layer: `signature` plus `content_hash` for Merkle-root registry verification, `network.allow` as a *domain allowlist* rather than a boolean, and `scan_status` / `risk_tier` carried in the artifact itself. That format does not exist yet. Its absence is why every control in this note is downstream of an unauthenticated markdown file.

Its own AST08 entry — "Poor Scanning," rated Medium — is the one rating the evidence contradicts. Two papers and one field study say scanner failure is the load-bearing assumption behind the other nine.

## 6. Checklist

For a team running agents that load third-party skills or plugins:

1. **Turn the gate on, then audit the backlog separately.** New-uploads-only coverage means the installed base is untouched. Scan it once with an offline tool.
2. **Treat `warn` as `fail` for anything with shell or credential access.** The three-verdict model is only useful if the middle verdict routes somewhere.
3. **Scan the artifacts the gate excludes.** MCP servers and hooks carry the same authority and are outside every vendor gate surveyed here.
4. **Never scan in the user's session.** The scanned artifact is attacker-authored text going into a model.
5. **Pin and hash.** Provenance is the only layer in §5 that does not degrade under adversarial rewriting. A skill that fetches its instructions at run time (`curl … | source`) is unpinnable by construction — 2.9% of ClawHub skills do this, and 21% of confirmed malicious ones.
6. **Audit combinations, not just skills.** SkillProbe's connected-component finding means the risk of your skill set is not the max of its members.
7. **Assume the gate is bypassed and check that the runtime planes still bound the damage.** If the answer depends on the scan having worked, you have one plane, not six.
