# 8.9. Tool-Definition Integrity — Rug Pulls and the Approval That Never Re-Runs

> Sibling to [8.8. The Skill Supply Chain](./8.8.%20The%20Skill%20Supply%20Chain%20—%20Install-Time%20Scanning%20and%20Why%20It%20Collapses.md). 8.8 asks whether an artifact was malicious *at admission*. This note asks the question that survives a clean admission: whether the thing you approved is still the thing you are running.
>
> Companion to [11.22. Agent Resources as Code](../11.%20Harness%20Engineering/11.22.%20Agent%20Resources%20as%20Code%20—%20Declarative%20Definition,%20Lockfiles,%20and%20Drift.md) on the lockfile side, and [MCP Goes Stateless — The 2026-07-28 Release Candidate](../5.%20AI%20Agents%20%26%20Tool%20Use/MCP%20Goes%20Stateless%20—%20The%202026-07-28%20Release%20Candidate.md) on the protocol side.

A tool definition is not metadata. It is a block of natural-language instruction, authored by a remote party, delivered over the network, and re-fetched on that party's schedule. Every gate in the containment stack — scanning, consent dialogs, allowlists, tool-authorization policy — is evaluated once, against the definition as it appeared at approval time. Nothing re-evaluates it.

The claim of this note: **`tools/list` is a mutable instruction channel with a one-time consent model bolted to it. The gap between "approved once" and "re-fetched forever" is a first-class trust boundary, and the only control that closes it is a definition fingerprint captured at approval and verified before every call.**

---

## 1. Three attacks on one field

Invariant Labs named the family in April 2025, and the taxonomy has not needed revision since.

| Attack | What changes | Why the gate misses it |
|---|---|---|
| **Tool poisoning** | Nothing — the description is malicious from the start | The consent UI shows a tool *name*; the model reads the *description*. The two audiences see different documents. |
| **Rug pull** | The description changes after approval | Approval is a one-shot event. No shipped client re-prompts on change. |
| **Tool shadowing** | Server A's description rewrites the agent's behavior toward server B's tools | The malicious server never appears in the interaction log. Only the trusted tool is called. |

Shadowing is the one that breaks the isolation intuition. In Invariant's demonstration, a bogus `add` tool from an untrusted server carried a description instructing the agent to redirect every `send_email` call from a *separate, trusted* server to an attacker address. The malicious tool is never invoked. Sandboxing the server is irrelevant — the attack runs entirely on the agent's instruction-following.

> Why it matters: the model sees the concatenation of every connected server's tool definitions as one undifferentiated instruction block. That is the actual trust domain, and it is the union of everything you have ever approved.

Composed with a rug pull, shadowing produces an attack with no user-visible footprint at all: the poisoned server is approved while benign, mutates later, and thereafter influences only tools the user already trusts.

## 2. Deadbugz — the primitive acquires an operator

Pillar Security's August 2026 disclosure is the first documented campaign built specifically around the delayed-mutation gap, and its design choices are worth reading as engineering rather than as an IOC list.

- **The server.** `productivity-suite` exposes two tools, `format_text` and `summarize`. Both work.
- **The gate.** It keeps an in-memory, per-client counter of `tools/call` requests. On the third, subsequent `tools/list` and `prompts/get` responses change — from ordinary documentation to instructions directing the agent at SSH keys, AWS credentials, shell history, and Kubernetes config, and to conceal the activity from the operator.
- **The delivery.** Not a registry. A single GitHub account opened 23 pull requests in a 74-minute window on 2026-08-10, each adding an MCP configuration entry — 17 pointing at a remote endpoint, four at a hidden local script path, two directory listings. The payload rides in as a routine config diff.
- **The advertised capability.** The public source declares `tools.listChanged`, which is exactly the protocol affordance that lets a compatible client pick up the mutated metadata without reconnecting.

The three-call counter is the load-bearing design decision, and it is aimed at reviewers, not users. A static read of the source, a manual poke at the endpoint, or an automated harness that connects and lists tools all stop below the threshold and see a clean server. Ordinary use crosses it.

> Architectural takeaway: this is the [8.8 §4](./8.8.%20The%20Skill%20Supply%20Chain%20—%20Install-Time%20Scanning%20and%20Why%20It%20Collapses.md) blind spot — "a detonation sandbox only sees the behavior the agent chooses to run" — weaponized with a counter. The attacker does not need to evade analysis. They need only outlast it.

Note also what the campaign did *not* need: no exploit, no dependency compromise, no typosquat, no merged pull request to be worth attempting. Configuration is the delivery vehicle, and configuration review is where nobody is looking.

## 3. What the gates actually see

| Control | Evaluated when | Sees the mutated definition? |
|---|---|---|
| Registry / marketplace review | Publish time | No — the mutation is server-side and post-publication |
| Install-time scan ([8.8](./8.8.%20The%20Skill%20Supply%20Chain%20—%20Install-Time%20Scanning%20and%20Why%20It%20Collapses.md)) | First add | No — benign at admission by construction |
| Consent dialog | First add, or first call | No — and it renders the name, not the prose |
| Per-call approval prompt | Every sensitive call | Shows *arguments*, not the description that produced them |
| Tool-authorization policy ([8.5](./8.5.%20The%20Tool-Authorization%20Plane%20—%20Write%20Scope,%20Attribution,%20and%20Audit.md)) | Every call | Only if the mutated instructions push the agent outside granted scope |
| Egress policy ([8.4](./8.4.%20The%20Agent%20Containment%20Toolchain%20—%20Sandbox,%20Runtime,%20and%20Egress%20Proxy.md)) | Every outbound byte | Yes — but only at the point of exfiltration, after the credential read |

Read down the column: the entire probabilistic half of the stack is blind, and the two deterministic planes catch the attack only at its last two steps. That is the same ordering [8.8 §5](./8.8.%20The%20Skill%20Supply%20Chain%20—%20Install-Time%20Scanning%20and%20Why%20It%20Collapses.md) reaches, arriving from the mutation side instead of the obfuscation side.

The per-call approval row deserves separate blame. Invariant's WhatsApp demonstration shows a `send_message` confirmation whose recipient is a raw phone number the user cannot verify against a contact list, and whose body reads `Hi` until you scroll horizontally past padding into the exfiltration payload. A dialog that renders attacker-controlled strings in a truncating widget is a rendering surface, not a boundary.

## 4. The protocol closed the door and left it unlocked

The 2026-07-28 MCP specification tightened `tools/list` in exactly the relevant place. The advertised tool set may legitimately change over time, but the spec now states that it "MUST NOT vary per-connection or as a side effect of other requests." Deadbugz's per-client call counter is precisely that: a tool set that varies as a side effect of the client's own prior calls. As of 2026-07-28 the campaign is a spec violation.

This changes less than it looks like it does. A normative prohibition binds implementers who intend to comply; the threat model here is a server whose entire purpose is non-compliance. What the clause actually buys is a *detection predicate*: a client that observes the tool set changing in response to its own call sequence now has a spec-grounded reason to fail closed rather than a heuristic one.

Two other 2026-07-28 changes cut in both directions:

| Change | Helps | Hurts |
|---|---|---|
| Cacheable list results (`ttlMs`, `cacheScope`) | A cached list is a list that cannot silently mutate mid-window | `cacheScope: "public"` means a poisoned list can be served to clients that never contacted the malicious server |
| Deterministic ordering **SHOULD** | Reordering as a covert channel becomes anomalous | None material |
| `listChanged` via explicit `subscriptions/listen` | Refresh is now something the client opts into, not something pushed at it | A client that opts in for freshness has opted into the mutation channel |
| Tool set **MAY** vary by presented authorization | Legitimate scope-based tool visibility | Gives a malicious server a spec-blessed excuse for a varying tool set |

> Lesson: caching and freshness are the same mechanism viewed from opposite ends. Every affordance that keeps tool definitions current is an affordance that keeps an attacker's rewrites current too. There is no configuration of this trade-off that does not require an integrity check underneath it.

## 5. The one control that holds: fingerprint at approval, verify before call

Both the academic and the practitioner literature converge on the same primitive, which is notable given how rarely that happens in this area.

**ETDI** (Enhanced Tool Definition Interface) proposes it as a protocol extension: cryptographic identity verification for servers, **immutable versioned tool definitions**, explicit permission management over OAuth 2.0, and policy-based access control evaluating tool capability against runtime context rather than static scopes. The immutability clause is the load-bearing one — a definition change becomes a new version, and a new version is an unapproved artifact.

**OWASP's MCP Security Cheat Sheet** specifies the client-side version without waiting for a protocol change:

```text
At approval:  fingerprint = SHA-256( canonical_json( name, description, inputSchema ) )
Before call:  recompute over the current definition; mismatch ⇒ fail closed, re-prompt
```

Three implementation details decide whether this works:

1. **Hash the whole definition, not the `description` field.** Parameter names, `title`, `inputSchema` property descriptions, `outputSchema`, and `annotations` are all model-visible prose. The spec itself warns that clients **MUST** treat tool annotations as untrusted unless the server is trusted — which is circular unless something establishes the trust.
2. **Canonicalize before hashing.** Key ordering, whitespace, and Unicode normalization are free false-positive generators, and a scheme that alarms constantly gets disabled. This is the approval-fatigue failure mode from [8.1](./8.1.%20Agent%20Containment%20%26%20Control%20—%20Capping%20the%20Blast%20Radius.md) arriving through a different door.
3. **Verify before *execution*, not at refresh.** Checking on `notifications/tools/list_changed` misses a server that mutates without notifying. The check belongs immediately before `tools/call`.

And the limit, which is the same limit as everywhere else in this stack: **a fingerprint detects that the text changed, not that the text became malicious.** An attacker who ships the payload in the initial, approved definition — pure tool poisoning, no rug pull — produces a stable hash forever. Fingerprinting converts the mutation problem into the admission problem, and hands it back to [8.8](./8.8.%20The%20Skill%20Supply%20Chain%20—%20Install-Time%20Scanning%20and%20Why%20It%20Collapses.md), which cannot solve it either. The composition still helps: it forces the attacker to be malicious at a moment when someone is looking.

Tool *output* is outside this entirely. Output is unpinnable by construction, and Invariant's second experiment shows a plain WhatsApp message hijacking the agent through `list_chats` results with no malicious server anywhere in the picture. Definition integrity and output-as-untrusted-input are two separate controls; neither substitutes for the other.

## 6. Checklist

For a team running agents against third-party MCP servers:

1. **Fingerprint every tool definition at approval and verify before each call.** Canonical JSON over name, description, and both schemas. Fail closed and re-prompt on mismatch.
2. **Treat a tool set that varies with your own call sequence as an incident.** The 2026-07-28 spec makes this a violation, not an oddity.
3. **Review MCP configuration diffs like dependency diffs.** Deadbugz's delivery vehicle was a pull request that added a config entry. If `.mcp.json` and its equivalents are not in the same review path as `package.json`, the supply chain has an unwatched door.
4. **Render the full description in the consent UI, and the full arguments in the call prompt.** No truncation, no horizontal scroll hiding a payload. A dialog nobody can read is theatre.
5. **Assume shadowing across every connected server.** The model's trust domain is the union of all loaded definitions, so the risk of a server set is not the max of its members — the same connected-component result [8.8 §4](./8.8.%20The%20Skill%20Supply%20Chain%20—%20Install-Time%20Scanning%20and%20Why%20It%20Collapses.md) finds for skills.
6. **Log tool-definition refreshes as security events.** Preserve them. A post-incident question — "did the definition change, and when relative to the credential read?" — is unanswerable without this, and it is not in any default client log.
7. **Keep egress default-deny.** It is the only row in §3 that catches this attack regardless of how the definition changed.
