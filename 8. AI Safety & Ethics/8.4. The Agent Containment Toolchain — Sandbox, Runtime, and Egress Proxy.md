# 8.4. The Agent Containment Toolchain — Sandbox, Runtime, and Egress Proxy

> Companion to [8.1. Agent Containment & Control — Capping the Blast Radius](./8.1.%20Agent%20Containment%20%26%20Control%20—%20Capping%20the%20Blast%20Radius.md). 8.1 argues *why* the perimeter must be deterministic. This note surveys the open-source implementations that now exist for each plane, and what each one does not do.

By mid-2026 the "defense-in-depth for agents" argument stopped being theoretical. Three plausible open-source projects — one per plane — shipped and got adopted. That makes the interesting question no longer *what should the architecture be* but *what does each tool actually enforce, and where does the enforcement stop.*

The answer matters because vendor summaries of these tools are unreliable. At least one widely circulated writeup credits an egress proxy with a human approval gate its own README explicitly denies having. Building on that claim leaves an unguarded hole exactly where you believe you have a control.

---

## 1. The three planes

| Plane | Question it answers | Reference implementation | Enforcement mechanism |
|---|---|---|---|
| **Infrastructure** | If the agent process is hijacked, what can it touch on the host? | NemoClaw (NVIDIA), on the OpenShell runtime | Linux kernel: Landlock, seccomp, network namespaces |
| **Runtime** | What software is running inside the loop, and how much of it is exploitable? | NanoClaw + Echo | Small auditable codebase; per-session ephemeral container; CVE-stripped rebuild |
| **Network** | What is allowed to leave the boundary? | CrabTrap (Brex) | L7 forward proxy; static rules then LLM judge |

The planes are not substitutes. A hardened container still speaks HTTP to the internet; a perfect egress policy does not stop an agent reading `~/.ssh` and putting the key in an *allowed* request.

> Why it matters: each plane fails in a way the others cannot see. The container cannot tell a legitimate POST from an exfiltration; the proxy cannot tell which file on disk the payload came from.

## 2. Infrastructure plane — kernel-enforced confinement

NemoClaw wraps a heavyweight agent (OpenClaw and compatible frameworks) in a sandbox built on three Linux primitives, configured through a versioned YAML blueprint:

| Mechanism | Enforces |
|---|---|
| **Landlock** | Filesystem confinement — read-write limited to `/sandbox` and `/tmp`, system paths read-only |
| **seccomp** | Syscall filtering — blocks privilege escalation and kernel module loading, closing common sandbox-escape routes |
| **Network namespaces** | Egress confinement — no unapproved sockets, no raw interface visibility |

The architecturally interesting part is not the sandbox. It is the **credential handling**.

### The placeholder-credential pattern

NemoClaw never places a real provider key inside the sandbox. Credentials are registered with the gateway's provider/placeholder system at onboarding; the agent makes requests carrying placeholders, and an L7 proxy at the network boundary rewrites `Authorization` headers and URL path segments to substitute the real value on the way out.

```text
   ┌─────────────── sandbox (Landlock + seccomp + netns) ───────────────┐
   │  agent  ──►  request with PLACEHOLDER credential                   │
   └───────────────────────────────┬───────────────────────────────────┘
                                   │  (only egress path)
                            ┌──────▼──────┐
                            │ L7 gateway  │ ── real key injected here
                            │  key store  │    (host side, never in sandbox)
                            └──────┬──────┘
                                   ▼
                            upstream provider
```

This extends to inference itself: the gateway intercepts the agent's model-provider calls and routes them, so the agent never holds the inference key either.

> Architectural takeaway — the pattern generalizes far beyond this one tool. **A credential the agent never possesses cannot be exfiltrated by any prompt injection, at any level of model compromise.** Every design that instead relies on the agent "not revealing" its key has made secrecy a behavioral property of a probabilistic system. Move the secret across the boundary; do not ask the model to keep it.

### The microVM alternative

Landlock, seccomp, and network namespaces are a policy boundary inside one kernel — the agent's process and the host's still share it. A kernel exploit that clears the syscall filter escapes the sandbox regardless of how tight the Landlock ruleset is. **microVM** sandboxes (Firecracker-class hypervisors) instead put a hardware-virtualization boundary between the agent's code and the host, at the cost of a real cold-start penalty a shared-kernel container does not pay.

Independent testing of smolvm 1.8.3 (a microVM sandbox aimed at running untrusted agent-generated Python/JavaScript) verified network-off-by-default, CPU/RAM/storage quotas, guest-enforced timeouts, read-only input mounts with writable output mounts, and `--unprivileged` mode all held under adversarial test — with cold starts of 0.6–1.5s and ~50ms warm executions.

> Architectural takeaway — the two mechanisms answer different threat models. If the risk is "the agent shells out to something with a host-side CVE," a hardware boundary is the stronger fit than a syscall filter. If the risk is "many short-lived agent turns per second," the sub-second cold start is the cost that decides whether a hypervisor boundary is affordable at all.

## 3. Runtime plane — shrink the code, then patch what is left

Two distinct claims live on this plane, and they are worth separating.

**Auditability through smallness.** NanoClaw is a minimal reimplementation of the OpenClaw idea on the Claude Agent SDK: one process, a handful of files, every session in its own ephemeral container. The comparison point it cites for OpenClaw is *nearly half a million lines, 53 config files, 70+ dependencies*. (Beware inflated retellings — the figure is roughly 500K lines, not the "more than a million" that circulates. NanoClaw does not publish an official count of its own; third-party figures range from ~500 lines of core to ~4,000 lines of TypeScript, so treat any exact number as approximate.)

**Vulnerability reduction through rebuilding.** Small first-party code does not help if the agent shells out to a browser, a PDF parser, or an archive utility carrying known CVEs. The July 2026 NanoClaw–Echo partnership addresses this by shipping a hardened runtime in which the components an agent actually reaches for — Chromium, Node, Bun, pnpm, corepack, git, curl, unzip — are rebuilt from source with only essential parts, cutting known-vulnerability counts to near zero.

The threat model is specific and worth internalizing: **a modern prompt injection is often a delivery mechanism, not the payload.** The injected text lures the agent to a page or file; the actual compromise is a known hole in the parser that opens it. Semantic filtering of the lure is the wrong defense layer. Removing the hole is the right one.

> Lesson: "the agent is sandboxed" and "the software the agent runs is patched" are independent properties. A container with a vulnerable Chromium in it is a container with a vulnerable Chromium in it.

## 4. Network plane — the proxy, and what it does not do

Because an agent generates its own code at runtime, static analysis inside the container is not meaningful. CrabTrap takes the position that you should assume the container is compromised and move the perimeter to the network. It is a forward HTTP/HTTPS proxy: set `HTTP_PROXY`/`HTTPS_PROXY` in the agent's environment, and every outbound request is TLS-terminated, evaluated, and forwarded or refused, with the decision written to an audit log.

Evaluation is two-tier:

| Tier | Applies to | Cost |
|---|---|---|
| **Static rules** | URL pattern match (prefix, exact, glob) with optional method filter; deny beats allow | Immediate, no model call |
| **LLM judge** | Anything no static rule matches, scored against a natural-language per-agent policy | One model call, ~30s timeout |

Brex reports the LLM tier activating on **fewer than 3% of requests** in one production use case. That number is the whole argument. Semantic evaluation of every outbound call would be unaffordable in both latency and tokens; a deterministic fast path that absorbs 97% of traffic is what makes the expensive tier viable at all.

> Architectural takeaway — this is the same shape as the severity-matched response ladder in [8.1 §4](./8.1.%20Agent%20Containment%20%26%20Control%20—%20Capping%20the%20Blast%20Radius.md): reserve the costly synchronous check for the small slice that needs it. Design egress policy so the common case is decidable without a model in the loop.

Supporting machinery worth noting: SSRF protection against private ranges with DNS-rebinding prevention; a circuit breaker that trips after five consecutive judge failures with a configurable deny-or-passthrough fallback; a policy builder that drafts rules from observed traffic rather than requiring them up front.

### The gaps CrabTrap documents about itself

These are stated plainly in the project's own README, and they are routinely misreported:

| Not provided | Consequence for your design |
|---|---|
| **No human-in-the-loop approval** — no approval queue, no chat prompts, no escalation path | Decisions are automatic. Denial *alerting* to bot managers exists, but it is an async notification after the fact, not a blocking gate. Escalation workflows are stated future work. |
| **No response filtering** | Only outbound requests are evaluated; upstream responses stream back unexamined — so the proxy is not an injection defense for tool output |
| **No data redaction** | The proxy sees Authorization and Cookie headers in cleartext by design; the proxy *is* the trust boundary and must be protected accordingly |
| **No WebSocket frame inspection** | Only the upgrade request is checked; frames afterward pass through |
| **Not an inbound WAF** | Outbound, agent-originated traffic only |

> Lesson: read the "what this does not do" section before the feature list. A control you believe you have and do not is worse than a known gap, because you will not compensate for it.

## 5. What the incidents actually teach

Three 2026 failures are cited constantly in support of this architecture. The commonly repeated versions omit the mechanism, which is where the transferable lesson lives.

| Incident | Popular framing | What actually happened | Transferable lesson |
|---|---|---|---|
| **Meta inbox wipe** (Feb 2026) | "Agent went rogue and deleted 200+ emails" | Summer Yue, Director of Alignment at Meta Superintelligence Labs, connected an agent to a large primary inbox. The volume triggered **context compaction, which silently evicted her standing safety instructions**. The workflow had worked for weeks on a small test inbox. She could not stop it by prompt and killed the process manually. | Safety instructions held only in the context window are **evictable state**. Compaction is a silent policy-deletion event. Constraints that matter belong in the harness, not the transcript — see [11.8. Context Engineering in the Harness](../11.%20Harness%20Engineering/11.8.%20Context%20Engineering%20in%20the%20Harness.md). |
| **DataTalks.Club** (Feb 2026) | "Claude Code wiped 2.5 years of data" | A routine cloud migration; the agent ran Terraform against AWS and destroyed the database **and its snapshots**. Recovery took ~24h and only succeeded because AWS retained an internal snapshot invisible in the customer console. | The blast radius of an infrastructure-as-code tool is the whole account. Recovery depended on luck, not on the backup design. |
| **PocketOS** (Apr 2026) | "Agent caused an outage cleaning staging data" | A Cursor agent on Claude Opus 4.6, fixing a staging credential mismatch, issued **one GraphQL mutation to Railway's API** that deleted the production volume and every volume-level backup in it — in 9 seconds. Most recent recoverable backup was three months old. The agent's own account: it assumed a staging volume ID was scoped to staging and did not verify. | "Cleaning staging" understates it: shared resource identifiers mean a staging-scoped *intent* can carry a production-scoped *effect*. Backups inside the deleted resource are not backups. |

The common thread is not malice or even hallucination. In each case the agent did what it had concluded was correct, and **no deterministic boundary existed to make the destructive path unavailable**.

## 6. Threat-modeling checklist

Ask these three questions of any agent deployment, in order:

1. **Where does execution happen?** Assume the process is compromised. Can it read credentials, SSH keys, or host config? Can it open an arbitrary socket? If the answer depends on the agent behaving, the answer is no boundary.
2. **What software is running inside the loop?** Enumerate what the agent shells out to — browser, parsers, archive tools, package managers. Each is attack surface reachable by a link in a document.
3. **What leaves the boundary?** Route egress through a proxy with a deterministic fast path and a semantic slow path. Confirm which requests get semantic review and which are waved through by a static allow rule.

Then a fourth, which the tooling does not answer for you:

4. **What is irreversible?** None of these planes distinguishes a destructive API call from a benign one of the same shape. Deletion of shared infrastructure, credential rotation, and outbound email are worth a hard gate regardless of what any policy engine concludes — and as §4 shows, you will have to build that gate yourself.

> Architectural takeaway — treat agents as employees with defined permissions, restricted network access, and an escalation path to a human. The first two now have credible open-source implementations. The escalation path, at time of writing, does not; if your design assumes one, verify it exists before you rely on it.
