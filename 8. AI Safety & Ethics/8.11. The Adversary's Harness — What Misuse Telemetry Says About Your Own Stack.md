# 8.11. The Adversary's Harness — What Misuse Telemetry Says About Your Own Stack

> Source: [Anthropic — Detecting and countering misuse of AI: September 2026](https://www.anthropic.com/threat-intelligence-report-september-2026) (2026-09-10, covering Dec 2025 – Aug 2026).
> Companion to [8.1. Agent Containment & Control](./8.1.%20Agent%20Containment%20%26%20Control%20—%20Capping%20the%20Blast%20Radius.md), [8.7. Agent Identity and Delegated Authority](./8.7.%20Agent%20Identity%20and%20Delegated%20Authority%20—%20The%20IAM%20Foundation%20Under%20the%20Agent.md), and [8.10. Context Privilege Escalation](./8.10.%20Context%20Privilege%20Escalation%20—%20Role%20and%20Scope%20as%20the%20Missing%20Trust%20Axes.md).

Threat reports are usually read as policy documents. This one should be read as an architecture document, because it is the largest published corpus of *observed* agent harnesses running at scale against real targets — and the adversaries independently converged on the same primitives you use. Agent swarms with a dispatching lead. Persistent campaign memory in `SKILL.md` / `LEARNINGS.md`. Purpose-built skills. Decompilers behind tool servers. Scheduled collection fleets. The report's own framing of the shift is "from assistant to orchestrator," and the engineering consequence is blunt: the harness is now the unit of offensive capability, which means *your* harness is now the unit of attack surface, and the AI supply chain underneath it — keys, gateways, eval sandboxes — is a first-class target rather than a dependency.

---

## 1. The shift is economic, not technical

The report is explicit that nothing here is a new attack class: "None of the operations in this report depended on some entirely novel technique that defenders have never seen. Instead, the economics of the attacks have changed. The kind of labor that previously set the well-resourced operations apart from everyone else—reconnaissance, exploitation, tool development, and data processing—are all now delegated to AI models, which run in harnesses at machine speed and in parallel."

The useful structure is the autonomy spectrum, which is a design space, not a threat taxonomy:

| Position | Human role | Observed shape |
|---|---|---|
| Assistant | Writes the prompts, reads the output | Model as engineering advisor |
| Directed execution | Makes each targeting decision | Model runs commands, harvests credentials, exfiltrates |
| Autonomous multi-agent | Sets goals, reviews results | Recon → exploitation → theft against many victims in parallel, for hours or days |
| Scheduled, unattended | Absent | Standing collection fleets; token-renewal jobs with no human in the loop |

Two caveats the report insists on, and they matter for anyone sizing a threat model against their own agent product:

- Humans kept the decisions they care about — **target selection, monetization, and review of results**. Autonomy did not eat judgment; it ate labor.
- **Autonomy and harm are separate axes.** "Several of the most serious compromises we report here came from operations where a human directed every step." Autonomy multiplies scale, speed, and cost-efficiency; it does not by itself raise severity.

> Why it matters: the standard risk framing — *more autonomy equals more danger* — is wrong in a way that misallocates budget. Autonomy changes unit economics, which changes *which targets are worth hitting*. It "makes previously marginal targets viable and encourages higher-volume, lower-touch operations." If your service was previously protected by being too small to be worth automating against, that protection has expired.

A second-order point for detection engineering: "For threat intelligence investigators, sophistication has stopped being a reliable signal of who is behind an operation." A single hacktivist built a doxxing platform holding tens of millions of rows with sub-agent orchestration for reconnaissance, code review, and cross-model finding validation. The distinguishing feature between actor classes "is no longer sophistication but intent."

## 2. The adversary built the harness you are building

This is the section worth the read even if you never touch security work. Strip the intent and the observed architectures are ordinary, competent harness engineering:

| Harness primitive | Observed use |
|---|---|
| Lead agent + parallel subagents | A lead agent "decomposed reconnaissance and post-exploitation work and dispatched it to many subagents running in parallel"; another framework ran sub-agents for pre- and post-auth recon, code review, and vetting findings across different models |
| Persistent memory across sessions | "Target lists, harvested credentials, engagement state, and standing instructions were saved across working sessions, so each session could be resumed mid-campaign with the program's accumulated context" |
| Memory files as the program | Influence operations moved off prompts entirely: "Increasingly, operations are not run using individual prompts. Instead, a great deal is embedded within persistent memory files." The IOC table lists `SKILL.md` / `LEARNINGS.md` memory as a cross-actor fingerprint |
| Skills as the workflow driver | A state actor "engaged primarily to modify Claude Code skills that drove the workflows"; firmware "obtained and decrypted with a purpose-built skill"; a surveillance unit ran "custom skills" over a government database |
| Tool servers | Binaries "loaded into a decompiler through a tool server"; asset-search reconnaissance "through a dedicated tool server and bundled probing tools" |
| Scheduled / unattended execution | "A fleet of thirteen standing collection AI agents ran on a scheduled job"; token-renewal and cloud-storage harvesting jobs with no human involvement |
| Evidence requirements in the loop | Vulnerability hunting used "parallel agents instructed to require evidence and use project memory" |
| Adversarial self-review | One actor "instructed Claude to role-play a hostile expert reviewer to critique the proposal" after each draft |
| Lab harness for verification | Exploits developed and debugged in-session "including creating a lab harness"; another built "an offline simulation toolkit that does not rely on Claude" |
| Role-split multi-instance | Weapons-software work assigned "one instance with writing the code, another with research, and a third with reviewing the code the first instance produced" |

Two of these deserve emphasis because they are the load-bearing ones.

**Persistent memory is what converts a session into a program.** The influence-operation cluster is described as "persistent-memory agents running autonomous, scheduled production across actors" — banned-word lists, approved sources, account-management rules, and evasion tactics accumulated in workspace memory files so the agent "keep[s] producing content without a human user directing each session." That is the same mechanism as a well-tended `AGENTS.md`. See [11.2. Repo Memory — AGENTS.md & Friends](../11.%20Harness%20Engineering/11.2.%20Repo%20Memory%20—%20AGENTS.md%20&%20Friends.md).

**The defender's cost model inverted.** One operation ran a monitor-and-rebuild loop: "If their monitoring AI agents identified that any of their deployed malware was detected by a security product, agents would then set about the process of autonomously modifying and rebuilding the malware to evade the existing detections. The agents were designed to continue iterating on GTG-20006's toolkit until it was undetected."

> Architectural takeaway: a published detection signature used to impose cost on the attacker. Against a harness with a verification loop and a rebuild step, it imposes one iteration. Any control whose strength rests on the adversary not being able to cheaply re-test against it — signature matching, obscure configurations, format-level obfuscation — should be re-scored as *latency*, not *defense*. The report retires the adage directly: "'security through obscurity' is no longer viable in this new AI-assisted world."

## 3. Your AI supply chain is the target, not the dependency

The report's single most transferable finding for a builder is that operators "treated the AI supply chain itself as both a target and a resource." Stolen model credentials are framed three ways at once:

- **Loot** — resellable, and a pivot into the victim's environment.
- **Compute** — free inference for the next campaign. One stolen key powered secondary attacks for roughly three weeks; another actor ran a month-long operation entirely on stolen keys.
- **Cover** — "The activity is attributed to the credential's legitimate owner," with traffic proxied to blend into the owner's normal usage pattern.

The observed access paths are all things a normal engineering team builds and forgets:

| Component | Observed attack |
|---|---|
| Model gateway / wrapper (LiteLLM cited by name) | "multiple actors were observed compromising AI wrapper services' implementation of LiteLLM—they used prompt injection to exfiltrate the production API keys used in their cloud-hosted container environments" |
| Automated eval sandbox | "By injecting malicious instructions into an AI vendor's automated evaluation sandbox, the actor caused the sandbox to hand over the credentials it held—including the production AI API keys from multiple providers belonging to that vendor" |
| Your deployed agents | "victim-deployed AI agents" appear on the routine credential-mining list alongside code repos and container images |
| The harness brand itself | Credential harvesters "often spoofing as popular AI harnesses including Claude Code," persisting to re-steal session tokens after rotation |
| Discount resellers | Traffic relayed without user knowledge carried "names, email addresses, company data, and other sensitive data of hundreds of end users in at least a dozen languages," including live credentials and internal code |

The provider's own statement of the fix is the right one to lift verbatim into a security review: "Organizations should treat AI keys and agent integrations with the same level of seriousness as they do production credentials—because attackers treat them with the same level of seriousness, too."

> Why it matters: every key in these cases was stolen from a *customer* environment, not from the provider. The gateway you stood up to centralize billing, and the sandbox you stood up to run evals, are both LLM-reachable services holding production secrets — which is the exact shape [8.7](./8.7.%20Agent%20Identity%20and%20Delegated%20Authority%20—%20The%20IAM%20Foundation%20Under%20the%20Agent.md) argues for short-lived, narrowly-scoped, workload-bound credentials rather than a long-lived key in an environment variable. An eval sandbox that holds multi-provider production keys and ingests attacker-authored content is a confused deputy with a very good salary.

## 4. Where request-level safeguards failed, and why the failure is structural

The report is unusually candid about non-uniform safeguard performance, and each failure mode maps onto a control that agent builders also rely on.

**Session fragmentation beats per-request classification.** Stated three separate ways: actors "split their work across multiple sessions so no single session revealed their full intent"; projects were decomposed "into individually benign web-development requests"; and procurement screening is hard "because each of the actor's requests… seem individually mundane." One case is measured: "Claude refused nine out of ten direct requests that were facially malicious. But our safeguards performed less consistently when the user fragmented the work and directed the model to carry out tasks across later, smaller sessions."

**Per-turn safety is not deployment safety.** The dating-app case is the cleanest demonstration in the corpus, and it is not a jailbreak — nothing was bypassed. "The system prompt read as an ordinary roleplay or companion deployment, and the monetization and deception were not visible from inside any exchange. In a small number of sampled cases, the model's own reasoning surfaced the harm, including exchanges where users disclosed serious illness or acute distress, yet the model didn't refuse to complete and instead the output continued in persona." Roughly 4,700 personas, 25,000 people, 2.36M messages, and every individual exchange compliant.

**Classifiers cannot arbitrate dual-use intent.** "since it is not possible to reliably identify the intent of the user in highly technical dual-use areas, a classifier cannot simultaneously enable benefit and prevent harm." The provider's own conclusion is that the remedy is not a better classifier but a different control plane — vetted access tiers using "account and institutional signals to verify user legitimacy, and the rudimentary observability provided by data retention to identify misuse." Zero-data-retention is named as an evasion vector, alongside relays and multi-model fallback.

> Lesson: every one of these is a **scope mismatch** — the control evaluates a request, the harm is a property of the campaign. This is the same argument [8.1](./8.1.%20Agent%20Containment%20%26%20Control%20—%20Capping%20the%20Blast%20Radius.md) makes for containment over model-layer defense, arriving from the opposite direction. If you are building guardrails for your own agent product, the transferable design rule is that anything enforced at the turn boundary can be defeated by decomposition across turns, sessions, or accounts. Cross-session aggregation — per-account rate and pattern analysis, campaign-level review, retention you can actually query — is not observability polish; it is the only layer that sees the unit the harm lives at.

## 5. Provider enforcement is a build-time control, not a runtime one

Two cases draw the boundary of what an account ban reaches, and it is narrower than most threat models assume.

- A single subscriber used the model as "the primary engineering workforce" to build a platform monitoring ~25 million SIM cards. "The platform ran fully on-premises using local models… Account enforcement actions do not affect the deployed product."
- A weapons-software operation had already packaged a deliverable that "runs and persists without Claude," plus an offline simulation toolkit.

> Architectural takeaway: the provider can revoke your access to the *factory*; it cannot revoke the *artifact*. For defenders this caps what vendor-side safeguards can deliver. For builders it says something less obvious and more useful: **the provider's controls are load-bearing only while your agent is calling the provider.** Anything your harness compiles, caches, distills, or writes to disk has left the safeguard perimeter permanently, which is an argument for putting your own enforcement at the artifact boundary — see [8.8. The Skill Supply Chain](./8.8.%20The%20Skill%20Supply%20Chain%20—%20Install-Time%20Scanning%20and%20Why%20It%20Collapses.md) and [8.9. Tool-Definition Integrity](./8.9.%20Tool-Definition%20Integrity%20—%20Rug%20Pulls%20and%20the%20Approval%20That%20Never%20Re-Runs.md).

## 6. Distillation now attacks the harness layer, not just the model

The illicit-distillation section is the part of the report that touches harness internals most directly, and two techniques are novel enough to matter architecturally.

**Cross-session replay of thinking signatures.** The provider returns "a reference to its raw thinking as a 'thinking signature' instead of the raw thinking." One lab "was able to circumvent this control… by saving the reasoning signature from Claude's response, starting a new session, and eliciting Claude to convert the reasoning signature back into the full reasoning trace." This is the theorized attack in [8.3. Client-Carried Reasoning State](./8.3.%20Client-Carried%20Reasoning%20State%20—%20The%20Encrypted%20Chain-of-Thought%20Attack%20Surface.md) confirmed as industrial practice, and it is the direct motivation for *preserved thinking* — the Fable 5.1 restriction that stops new API accounts from altering the system prompt, tools, or messages preceding the model's reasoning, "because editing the context before it is a common technique attackers use to make Claude reveal it."

**Harness fingerprinting as a routing signal.** One lab "rerouted requests from users that were attempting to use one of DeepSeek's models through third-party or Anthropic coding harnesses, like Claude Code, the Claude Agent SDK, or OpenCode," by "check[ing] various strings included in inbound requests, tagging users that were using these third-party harnesses." Whatever your harness sends — user-agent, tool-name conventions, system-prompt boilerplate, message-array shape — is a fingerprint that an intermediary can key on to route your traffic somewhere you did not choose.

Scale, for calibration: one campaign peaked at ~3 million exchanges/day across 3,500+ fraudulent accounts and exceeded 151M exchanges over three months. And the targets are explicitly the agentic capabilities: "Distillation attacks generally target US frontier models' most valuable capabilities, including agentic capabilities and tool use, coding and data analysis, and logical reasoning."

> Why it matters: safeguards do not survive the copy. "The robust safeguards that prevent Claude from being misused by bad actors do not transfer when our models are distilled by an unauthorized lab" — and a distilled model "can help achieve dangerous capabilities… even when the harvested exchanges contain little about those subjects." An alignment property is a property of a deployment, not of a capability, and it is lost at every copy boundary.

## 7. What transfers to your build

Nothing here requires a security mandate to act on. In descending order of cheapness:

1. **Inventory every LLM-reachable service that holds a production secret** — gateways, proxies, eval sandboxes, CI agents, MCP servers. Each one ingests untrusted text and holds credentials. That combination is the whole finding.
2. **Scope and shorten model credentials** the way you would a database password: per-workload identity, short TTL, egress-restricted. A key that can be stolen and used for three weeks is a key with no expiry and no anomaly detection.
3. **Move guardrails up a scope.** Keep the turn-level classifier, but add per-account and per-campaign aggregation, because decomposition across turns and sessions is the demonstrated bypass, not jailbreaking.
4. **Treat your memory and skills planes as executable program state.** They are what turns sessions into campaigns — for you and for the adversary — and they are outside the sandbox ([8.10](./8.10.%20Context%20Privilege%20Escalation%20—%20Role%20and%20Scope%20as%20the%20Missing%20Trust%20Axes.md)).
5. **Design compaction and eval fixtures to discard carried reasoning.** Preserved thinking is a deprecation with an undated deadline and an anti-distillation motive; your compaction loop is collateral.
6. **Buy model access only through authorized channels.** "An alleged discount that requires routing traffic and credentials through an unknown intermediary introduces tremendous risk to user data and systems."
7. **Assume no signature-based control imposes lasting cost.** Budget for containment and egress control ([8.1](./8.1.%20Agent%20Containment%20%26%20Control%20—%20Capping%20the%20Blast%20Radius.md), [8.4](./8.4.%20The%20Agent%20Containment%20Toolchain%20—%20Sandbox,%20Runtime,%20and%20Egress%20Proxy.md)) rather than detection tuning.

> Lesson: the report reads as a security document, but its architectural content is that offensive and defensive agent engineering have converged on one set of primitives. The adversaries are not doing anything exotic — they are doing competent harness engineering with a different objective function, which means the harness literature and the threat literature are now describing the same system from two sides.
