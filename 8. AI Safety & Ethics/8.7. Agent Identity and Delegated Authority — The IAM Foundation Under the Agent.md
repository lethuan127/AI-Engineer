# 8.7. Agent Identity and Delegated Authority — The IAM Foundation Under the Agent

> Companion to [8.5. The Tool-Authorization Plane — Write Scope, Attribution, and Audit](./8.5.%20The%20Tool-Authorization%20Plane%20—%20Write%20Scope,%20Attribution,%20and%20Audit.md). 8.5 asks *what does this call change, and can it be undone*. It assumes the call already carries a usable identity. This note is about the layer underneath, where that assumption usually fails.
>
> The MCP-side view of the same problem — what identity looks like once the transport is stateless — is [The Post-Stateless MCP Roadmap — Agent Identity, Progressive Discovery, and One Transport](../5.%20AI%20Agents%20%26%20Tool%20Use/The%20Post-Stateless%20MCP%20Roadmap%20—%20Agent%20Identity,%20Progressive%20Discovery,%20and%20One%20Transport.md).

On 2026-08-27 NIST's NCCoE published a post arguing that agentic identity is not a new discipline in need of new primitives. It is four practices that identity and access management spent two decades eliminating, reintroduced at speed because they are the fastest way to make an agent work — plus a fifth failure that the industry's favorite mitigation *creates*. The post draws on public comments to the NCCoE's February 2026 concept paper on software and AI agent identity and authorization.

The claim worth carrying out of it is narrow: **an agent that runs on a human's credentials is not an authorization problem you can fix at the tool boundary, because by the time the call reaches the tool there is no longer a principal to attenuate.** Every control in 8.4 and 8.5 is downstream of whether the identity was ever distinct in the first place.

---

## 1. The four regressions

Each row is a pattern that IAM abandoned deliberately, and that agentic deployments have re-adopted because it ships on a Friday afternoon.

| Regression | Why IAM abandoned it | What agents do to it |
|---|---|---|
| **Credential sharing** — handing the agent the user's personal or enterprise credential | Destroys accountability: the system cannot verify *who* attempted a transaction, only that a valid secret was presented. Fatal wherever non-repudiation is a requirement (payments, health records). | The agent becomes the user. Downstream systems and audit logs see a human. This is the attribution collapse of [8.5 §1](./8.5.%20The%20Tool-Authorization%20Plane%20—%20Write%20Scope,%20Attribution,%20and%20Audit.md), reached one layer earlier. |
| **Static and long-lived credentials** — API keys, long-lived bearer tokens | Bearer tokens prove *possession*, not identity. API keys carry no scoping at all. Both leak into config files, markdown, and logs, and both have been the root cause of large breaches for years. | Agents carry the credential across networks, tools, and sub-agents, so leak surface grows with every hop. And the mismatch is structural: agents are frequently ephemeral, their credentials are not. |
| **Broadly scoped access** — coarse role entitlements instead of least privilege | Entitlement creep and legacy role models already defeat least privilege for humans, who are slow and few. | Agents are fast, numerous, and driven by high-level goals through probabilistic reasoning. Given latitude they will "seek, probe, and execute multiple paths," reaching tools and data nobody modeled. Even tightly scoped, an agent will opportunistically use an orphaned credential it finds. |
| **Local user accounts** — running the agent on the developer's own machine under the developer's own login | Local accounts are unmanaged: no central registry, no lifecycle, secrets in dotfiles. | Combines the first and third regressions and adds a governance one — there is no agentic identity repository to query, so "which agents can reach production?" has no answer. |

> Why it matters: three of the four are *identity* failures, not authorization failures. The agent in each case is doing something it is permitted to do. What is missing is any record of the fact that an agent, rather than its owner, did it.

## 2. The ephemerality mismatch

The point most teams miss sits inside the second regression. Short-lived agents are already normal — a container per task, a session per request. The credentials those agents carry are not short-lived, because credential lifetime is set by whatever was convenient at integration time.

```text
agent lifetime      |--task--|                        (minutes)
credential lifetime |=================================...=====>  (until rotated, if ever)
```

The gap between the two lines is the window in which a leaked secret is still worth stealing. Closing it is not a research problem; it is a configuration decision that nobody owns because the agent's author and the credential's issuer are different people.

## 3. The fifth failure: human-in-the-loop decays

Binding an agent identity to a human, attenuating delegated rights, and scoping authorizations narrowly all reduce the blast radius. Human-in-the-loop approval is usually offered as the backstop when those fail. NIST's argument is that HITL is not a stable control, and the failure mode has a precedent with a name.

MFA bombing works because an attacker sends push notifications until the victim approves one reflexively. A chatty agent produces the same conditioning without an attacker: enough approval prompts and the user clicks *allow* to keep the workflow moving. At that point HITL is not providing the non-repudiation it was installed to provide — it is manufacturing a signed record of a decision nobody made.

There is a second, sharper version. MCP's elicitation mechanism lets a server request additional input from the user mid-task. It is a good primitive for keeping an agent aligned with intent, and it is also a channel for requesting credentials or other sensitive data through a UI the user has been trained to trust. The MCP specification warns against using elicitation for sensitive information, but that is a normative statement in a spec, not an enforced boundary.

> Architectural takeaway: an approval prompt is a control that degrades with use. Budget approvals like a scarce resource and spend them on the actions in the top risk tier only — the same argument 8.5 §2 makes about harness-side prompts, arrived at from the human side rather than the trust-boundary side.

The mitigation direction is to move approval *earlier and coarser*: approve a bounded plan once, rather than each step inside it. Anthropic's auto mode uses this "flight plan" shape, and its harness-design writeup on long-running applications is the reference for hardening the local case.

## 4. What already exists

The post's practical contribution is that almost nothing here needs inventing. The gap is adoption, not specification.

| Standard | Status | What it gives an agentic system |
|---|---|---|
| OAuth 2.0 (RFC 6749) | Established | Delegated access without credential sharing — the baseline pattern agents skipped. |
| SPIFFE / SVID | Established | Cryptographic workload identity issued at deploy time, so a container has a name that is not a copied secret. |
| DPoP (RFC 9449) | Established | Sender-constrained tokens. Proof of possession removes most token-theft-and-replay scenarios. |
| Rich Authorization Requests (RFC 9396) | Established | Dynamic, fine-grained authorization details instead of a static coarse `scope` string. |
| AuthZEN Authorization API 1.0 | Final specification (Jan 2026) | A standard interface between policy enforcement and policy decision points, so granular authorization scales past hand-rolled checks. |
| WIMSE | Active IETF working group | Workload identity across multi-system environments — the multi-hop case OAuth alone does not cover. |
| Transaction Tokens | IETF draft | Carries authorization *context* along a call chain so that authority attenuates as it is delegated, agent to agent. |
| Identity Assertion JWT Authorization Grant | IETF draft | Cross-app access: exchanging an identity assertion for a scoped grant at the next service, without re-prompting. |
| FIDO agent authenticators | Early | The consumer case — an agent authenticator bound to a user identity, so a relying party can tell agent from human. |

Two of these are the interesting ones for agent builders. **Transaction Tokens** address delegation depth: in a chain of sub-agents, each hop should be able to *narrow* authority and never widen it. **Identity Assertion JWT Authorization Grant** addresses breadth: reaching the next SaaS system without falling back to a stored API key.

The consumer story is materially worse than the enterprise one. An enterprise controls both the agent and the resource server. A consumer-facing service controls neither, cannot reliably distinguish an agent from the human whose credentials it is presenting, and has no leverage to demand otherwise. NIST's framing is that until the secure path is also the easy path, credential sharing and impersonation will keep spreading.

## 5. Where this lands in the harness

For a locally deployed agent — the dominant case for coding work — the identity plane and the containment planes converge:

1. **Give the agent its own identifier**, bound to the human or system that operates it, not a copy of that principal's credential. "Alice's agent acted on Alice's authority" is a different log line from "Alice did this," and only the first is actionable.
2. **Issue credentials whose lifetime matches the agent's**, audience-restricted and sender-constrained. This is available today with DPoP and short-lived JWTs.
3. **Scope authorization to the task, not the role.** RAR exists precisely because a static scope string cannot express "this run, these repos, read-only."
4. **Run it inside a hardened harness and a sandbox** so the constraint holds even when the model reasons its way toward an unmodeled path. That is [8.4](./8.4.%20The%20Agent%20Containment%20Toolchain%20—%20Sandbox,%20Runtime,%20and%20Egress%20Proxy.md).
5. **Separate human and agent activity in logs** at write time. Reconstructing the split afterwards is the half-hour of guesswork from 8.5 §1.

> Lesson: the credential is where the harness's security posture is actually decided. A perfect permission model in the harness config is decorative if the process underneath it is holding the operator's personal access token.

## 6. What the identity plane still does not answer

Authorization is granted at a point in time; execution does not stay where it started. An agent switches tools, delegates to a sub-agent, reaches a different data source, or finds another route to the same goal. Every identity in that sequence can be valid and every individual grant correctly scoped, and the system can still lose track of whether execution is operating under the intent originally authorized. This was raised in the post's own comment thread and it is the honest open problem — and it cannot be closed by asking the human again at each shift, for the reason in §3.

That gap is where the planes stack up:

| Plane | Question it answers | Note |
|---|---|---|
| Infrastructure / runtime / network | What can this process reach? | [8.4](./8.4.%20The%20Agent%20Containment%20Toolchain%20—%20Sandbox,%20Runtime,%20and%20Egress%20Proxy.md) |
| Tool authorization | What does this call change, and is it reversible? | [8.5](./8.5.%20The%20Tool-Authorization%20Plane%20—%20Write%20Scope,%20Attribution,%20and%20Audit.md) |
| Peer isolation | Can two runs reach each other? | [8.6](./8.6.%20Covert%20Coordination%20Channels%20—%20Isolation%20Between%20Agents,%20Not%20Just%20Around%20Them.md) |
| Identity and delegated authority | Who is acting, on whose authority, and how far does it attenuate? | this note |
| *Unnamed* | Is the execution *still* within the authority originally granted? | open |

The NCCoE project is the venue where the first four get standardized. The fifth row does not have one yet.
